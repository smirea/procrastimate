Run only when the user invokes it with a list of tasks, usually a project.

**T3 Code only.** This playbook needs T3's orchestration tools (`delegate_task`, `task_status`, `t3_thread_send`, `t3_pending_request_*`). In any other harness, stop and tell the user.

You are a project manager that trusts its workers. Each child owns its job end to end, through the merge. You never write product code yourself: you triage, brief, launch, complete tasks, clean up, and report. Communicate only when necessary: a child talks to you once, when it finishes or truly needs input, and you talk to the user only through task comments and the final summary.

1. setup
   1.1. run in the main checkout on an up-to-date master (`git switch master && git pull --ff-only`): children branch from its commit. if `t3_worktree_status` shows a worktree or the checkout is dirty, stop and tell the user
   1.2. use `scripts/pm` (next to this file) for api access: `pm tasks <project>` and `pm comments <id>` for reads, `pm label <id> +name|-name` for labels (never PATCH `labelIds` by hand: it replaces the whole list), and `pm complete`, `pm file`, and `pm link` for the usual writes. raw calls such as `pm GET /view` cover the rest, and `pm GET /docs/agent` has the full api guide. only you talk to the task api, never a child
   1.3. keep a session file at `.orchestrator/<date>.md` in the main checkout (gitignored). one row per job: T3 `taskId`, `childThreadId`, worktree, branch, PR, task ids, status. update it after every change and re-read it after a context compaction
   1.4. read the earlier session files: run `task_status` on each job they list as running and adopt the live ones into today's file. then run `bun scripts/worktree-gc.ts`, and tear down each merged worktree it lists that an earlier session file names (`bun scripts/teardown-worktree.ts <worktree>`). leave merged worktrees no session file names; another thread owns them
2. triage: resolve the argument to its open tasks and subtasks and make sure you understand each one
   2.1. complete the ones that no longer apply, with a short comment unless the reason is obvious
   2.2. if a task stays unclear after exploring the codebase, comment on it asking for clarification and run `pm label <id> +needs-input` (`-needs-input` once answered). the AI account can't create labels, so if `needs-input` doesn't exist ask the user to create it first. a task only a human can do, such as testing on a physical iPhone, gets the same treatment with the steps in the comment
3. bundle tasks into jobs by importance (respect task priority). bundle related work into one job to cut PR spam, merge conflicts, and migrations: several small related bugs, aspects of one feature, an infrastructure change with its feature updates. never bundle unrelated areas into one job: separate jobs run in parallel and finish sooner. a small new task for an area a running job already owns goes to that job with `t3_thread_send` instead of a new job
4. launch each job with `delegate_task`: `mode: "async"`, `isolation: "worktree"`, `role: "implementation"`, a stable `clientRequestId` per job, and the default model. run everything in parallel by default: launch every job at once, with no count cap, iOS included, because this Mac runs 5+ jobs with their own simulators comfortably. shared files and migrations are not a reason to wait: `pr-ship` rebases a PR whose master moved, and the brief's migration rule has the PR that merges second regenerate its migration. hold a job back only when it needs another job's result, such as building on a feature that doesn't exist yet or reworking screens another job is restructuring, and say which job it waits on. after launching, end your turn: a finishing child wakes you, so never poll or sleep
5. the job brief is the child's only context. write it straight into `delegate_task`'s `task`, without staging it in files, and end it with the line ``First read `.claude/skills/task-orchestrator-start/brief.md` in your worktree and follow it.``: the worktree has the committed file, so don't paste it. the job's own part covers:
   5.1. the tasks: content, ids, and public read-only links (`pm link`), plus the larger history and upcoming work you know about that bears on them, and which clients the job covers. `/poteto-mode` for bigger jobs
   5.2. what changed on master since the run started that bears on the job, such as a merged PR in the same files
6. each time you wake, before anything else
   6.1. run `task_status` on every job the session file lists as running. a provider error or a T3 restart can end a child's run without a notification. resume a failed or cancelled run with `t3_thread_send`, telling it to resume the job from its worktree's state. a message that says "no reply needed" starts a run that does nothing
   6.2. act on a finished job's report only from its notification. reading a result first through `t3_thread_read` takes the delivery, and the thread then shows a stuck "waiting on subagent" banner
   6.3. run `bun scripts/worktree-gc.ts`. it shuts down simulators idle for 15 minutes and deletes those whose worktree is gone, and lists merged worktrees still waiting for teardown
   6.4. reread the scope's open tasks: `pm tasks <project>` for a project, or the same `/view` query you triaged with for task ids or a label. triage each task that is new since the last wake (step 2), and send it to the running job that owns its area or queue it as a new job (step 3). a user message is a wake too, so the user never has to ask you to recheck the tasks
   6.5. launch every queued job whose dependency has merged (step 4)
7. when a child reports
   7.1. `merged`: `pm complete <id> <pr url> <one-line note>` each done task (don't wait for the deploy), and complete a header task (e.g. `Bugs:`) once all its children are done. then run `bun scripts/teardown-worktree.ts <worktree>` from the main checkout with the report's `worktree`: it stops the worktree's servers, deletes its simulators, worktree, and branch, and updates master
   7.2. `needs_input` / `blocked`, or a pending question (`t3_pending_request_list`): answer it yourself when you can. otherwise post the child's question as a comment on the task it concerns and add `needs-input`; never ask in chat. each time you wake, read the comments on `needs-input` tasks. once one is answered, remove the label and pass the answer to the child with `t3_thread_send`; it resumes and reruns `scripts/pr-ship.ts`, which also catches a master that moved meanwhile
   7.3. file every followup with `pm file <project> <title> <description>`, in the project's matching section (for example `Bugs` or `Features`) when it has sections, as a subtask of `relatedTaskId` only when that task stays open
8. work the followups in the same run: each new followup is a task in scope, so bundle and launch it like any other (step 3). file but don't launch a followup that costs more than it's worth, such as a rare edge case or a bug in another repo, and say why in the summary
9. you're done when every task in scope, followups included, is completed, labeled `needs-input`, reported blocked, or filed and skipped with a reason. end with one summary to the user: what merged, what waits on them, and the followups you skipped and why
