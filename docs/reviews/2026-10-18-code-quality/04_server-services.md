## Verdict

This slice is in decent shape. Config is parsed once at the boundary, the Worker code uses no Bun or Node APIs, push scheduling across time zones is correct and tested, and the PowerSync proxy and token design hold up: a stolen sync token is read-only for 5 minutes, and a forged install id only reaches the caller's own push rows. The two problems that matter most are both confirmed. First, Ramble's per-user daily cap can be doubled, because each session caches the stored seconds when it opens and never sees sessions that closed after that. Second, `readSession` turns any database failure into "not signed in", and the web and iOS clients sign the user out on that 401. The Ramble session code has no tests at all (they were deleted in 4d5e059), and that is how F1 went unnoticed.

## Findings (most important first)

### F1. Concurrent Ramble sessions can stream twice the daily cap [bug] [CONFIRMED] [effort: M]

`session()` in `server/src/ramble.ts:256` copies `storedToday` into a per-session `stored` and re-reads it only when the day rolls (`roll`, :395). `shutdown` (:277-278) removes the session's tally from `ramble.live` and adds its seconds to the `ramble_usage` row. Any session that was already open still holds its old `stored`, so from its point of view those seconds are gone: `dailyLeft = RAMBLE_DAILY_SECONDS - stored - liveSeconds(live, day)` (:364) gets larger by exactly what the closed session used. Scratch test `/tmp/procrastimate-thermo/s04/ramble-cap.test.ts` drives the real `rambleRoute` on PGlite with a fake upstream. It opens 12 idle sessions, then runs 12 sessions of 5 minutes back to back until the table holds 3,600 s and a new upgrade is refused. The 12 idle sessions can then still stream 300 s each. Output: `daily cap 3600 streamed 7200`. A leaked token, which is the case the docs say the caps exist for ("bound what a leaked token costs"), gets 2x the per-user cap. That alone is enough to use up the whole 2-hour global ElevenLabs budget and lock Stefan out for the UTC day. A related problem: on the Bun dev server, `dev-server.ts:50` builds one `ramble(...)` for every user, so `live` mixes the open sessions of all users there. Parallel e2e users count each other's seconds. The docs and the `ramble.ts` header say `live` holds "the user's open sessions".

Remedy: keep one authoritative counter per (user, day) on the host instead of a per-session copy. On the Worker the user's Durable Object is the only writer of that user's `ramble_usage` row, so after the first load the in-memory value is the truth. On Bun, keying by user also fixes the shared `live`:

```ts
type Day = { stored: number; live: Set<Tally> };
// Ramble.days: Map<`${userId}:${day}`, Promise<Day>>, loaded once from ramble_usage
// per frame:      dailyLeft = RAMBLE_DAILY_SECONDS - day.stored - sum(day.live)
// shutdown/roll:  day.live.delete(tally); day.stored += tally.seconds; usage.add(...)
```

This removes the `storedToday` option, the per-session `stored` variable, and the async re-read race inside `roll`. User-visible behavior does not change, except that the cap holds. Port the scratch test as a regression test. It also restores some of the session coverage that was deleted.

### F2. A database failure while reading the session answers 401, and both clients sign out on 401 [bug] [CONFIRMED] [effort: S]

`readSession` in `server/src/better-auth.ts:208` does `auth.api.getSession(...).catch(() => null)`. When the database fails, Better Auth's `getSession` throws `APIError INTERNAL_SERVER_ERROR` (better-auth `api/routes/session.mjs`, the final catch), and that becomes "no session". `requireHuman` then throws `UNAUTHORIZED`. `/tmp/procrastimate-thermo/s04/session-blip.test.ts` signs up, makes the db's `select` throw, and calls `GET /api/sync/token` with the real bearer token. The answer is `401 {"code":"UNAUTHORIZED","message":"Not signed in"}`. On that 401 the web `fetchCredentials` (`app-web/src/lib/powersync.svelte.ts:57`) and `uploadData` (:99) call `session.clear()`, which sets the state to `out`. iOS `SyncConnector.fetchCredentials` and `uploadData` call `signedOut()`. iOS sends a bearer and has no cookie cache, so every iOS request reads the session row. One Hyperdrive or Supabase blip therefore signs Stefan out on that device. The comment above the catch ("a failed read is no session either way") is the faulty premise. Remedy: catch only Better Auth's `APIError` with status 401, and rethrow everything else so the request answers 5xx. Clients already treat 5xx as retryable. The failure is still reported, through the Better Auth logger hook.

### F3. The daily backup is not one consistent snapshot [bug] [CONFIRMED] [effort: S]

`dumpJson` in `server/src/db/backup.ts:30` claims "one read transaction, so the dump is one consistent snapshot". `db.transaction(fn)` with no config compiles to postgres.js `begin` with no isolation level (drizzle `postgres-js/session.js:116-128`). That means READ COMMITTED, where each `SELECT` takes its own snapshot. The dump reads about 20 tables one after another, and uploads run without transactions. A write that lands during the 09:00 UTC dump can therefore appear in `tasks` but not in `log`, or point at a project created after `projects` was read. Remedy, one line: `db.transaction(fn, { isolationLevel: 'repeatable read', accessMode: 'read only' })`. Related and already documented: the dump is one string in 128 MB, and image bytes grow it fastest, not `log`. Each image is up to 1.7 MB (full plus thumb), and the bytes are held as driver rows, then as the latin1 binary string, then as base64, then inside the JSON string. That puts the ceiling at very roughly 30 to 40 MB of stored images. Images are immutable and keyed by id, so writing each one to R2 once as its own object, and leaving them out of the JSON, removes both the memory ceiling and the daily re-upload of every image.

### F4. Malformed VAPID and PowerSync keys pass `parseConfig` and fail only at first use [robustness] [CONFIRMED] [effort: S]

`parseConfig` (`server/src/config.ts:72-76`) checks that the VAPID values are present and that the PowerSync JWK has the right shape, but never checks that they decode to keys. `/tmp/procrastimate-thermo/s04/vapid.test.ts` passes `VAPID_PRIVATE_KEY='nope'` and a JWK with `x:'x', d:'d'`. Config parses. Then `signSyncToken` and `sendPush` both reject with `Invalid keyData`. A broken key never fails boot. A broken VAPID secret is worse: `push.ts:83-91` catches the error, classifies it `retry`, retries for 10 minutes, and drops every notification. Those notifications are lost and the only trace is Sentry. This breaks the user's rule "throw on startup". Remedy: check the lengths synchronously in `parseConfig`. The VAPID public key decodes to 65 bytes starting with `0x04`, the VAPID private key and Ed25519 `x` and `d` to 32 bytes each. Optionally `index.ts` can also await one `signSyncToken` and one VAPID `importKey` before `serveDev`.

### F5. Every Ramble open loads the whole space, just to build 50 keyterms, before the cap check [efficiency] [CONFIRMED] [effort: S]

`rambleRoute` (`ramble.ts:466`) calls `loadTree`, which reads every column of every task (completed ones included, with notes, images JSON, and clients), every section, project, and label, then sorts and resolves dangling references. `rambleKeyterms` reads only `projectId`, `labelIds`, and `createdAt` of tasks, plus project and label names. The daily-limit refusal path (:469-470) runs after this load too. At a few thousand tasks this means hundreds of KB to MBs over Hyperdrive into the Durable Object per open. Remedy: check the cap first, then run one narrow query, either a `select({ projectId, labelIds, createdAt })` or SQL `max(created_at)` grouped per project and per label, plus the two name lists. `rambleKeyterms` keeps its signature over a `Pick`. The keyterm order stays the same.

### F6. The Ramble wiring has three shapes for one thing, and a laziness that buys nothing [simplification] [CONFIRMED] [effort: S]

Every host spells `rambleRoute(db, ramble(stream, rambleConfig(settings, () => db, upstream)))` (`dev-server.ts:48-54`, `ramble-object.ts:33-39`, `test-app.ts:57`). `RambleConfig` (`{connect, budget?}`) gets copied into `Ramble` (`{stream, connect, live, budget|null}`) by a one-line factory. The `db: () => Db` thunk exists so that `ramble-object.ts` can open the connection lazily, but the first argument `this.open().db` already opens it eagerly on the same line. The `connection` field and `open()` therefore have no purpose. Collapse to one `rambleRoute(db, stream, settings, upstream)` that builds `live` and the budget inside. In the object, write `this.route ??= rambleRoute(connect(config(this.env).database).db, workerStream(), ...)`. This removes `ramble()`, the `Ramble` and `RambleConfig` split (test-app passes `{ connect: null }` today, and no test passes anything else), the thunk, and `open()`: about 30 lines. Behavior is unchanged. Two smaller items: `rambleForward` in `worker.ts:33` types the actor as `object` and casts it back to `{id}`. Typing it as `RambleRoute` removes both casts. The module-level `fail` (:439, which returns a Response) and the session's inner `fail` (:298, which ends a socket) share a name in one file. Renaming the outer one to `refuse` would help readers.

### F7. Three base64 encoders and three hand-rolled JWT signers [simplification] [CONFIRMED] [effort: S]

`toBase64` (`ramble.ts:202`) and `base64` (`db/backup.ts:17`) are the same 32 KB-slice loop. `base64urlEncode` (`web-push.ts:18`) is a third, byte-at-a-time version. Bun 1.4 has `Uint8Array.prototype.toBase64({ alphabet: 'base64url', omitPadding: true })` and `Uint8Array.fromBase64` (checked with `bun -e`). workerd at compatibility date 2026-10 ships a V8 that has them too (PLAUSIBLE, so check under `wrangler dev`). If it does, all three helpers and `base64urlDecode` go away, along with the stack-overflow workaround comment. Separately, `signSyncToken` (`sync.ts:28`), `vapidAuthorization` (`web-push.ts:91`), and `appleClientSecret` (`better-auth.ts:81`) each base64url-encode a JSON header and claims, then sign and join with dots. A shared `signJwt(header, claims, key, algorithm)` cuts about 20 lines and leaves one place that builds JWTs.

### F8. The global ElevenLabs budget leaks on eviction, and idle sessions hold reservations [robustness] [PLAUSIBLE] [effort: S]

A session reserves `min(300, remaining)` s of the shared 2 h when it opens, and returns what it did not stream only in `shutdown` (`ramble.ts:281`). When a deploy or eviction kills the Durable Object while a session is open, `shutdown` never runs, and up to 300 s of that UTC day's budget is gone for good. Idle sessions also hold their reservation until the 60 s idle timeout. That means 24 sockets opened at once, sending one byte every 59 s, hold the entire global budget without being charged for it. Sign-up is open (`emailAndPassword: { enabled: true }`), so any stranger's account can do this. Remedy: reserve per chunk as audio actually streams (for example 30 s at a time) instead of the whole session up front. This keeps the "never call ElevenLabs without a recorded budget" rule and limits both the leak and the hoarding to one chunk. Product question for Stefan: should the ElevenLabs path be limited to an allow-listed account? With open sign-up, any account can spend from the shared 2 h.

## Smaller notes

- `deleteUser` (`better-auth.ts:242-247`) calls `deleteUserSessions` and `deleteAccounts` after `deleteUser`. Both tables have `onDelete: 'cascade'` on `userId` (`db/auth-schema.ts`), and the only caller deletes AI accounts, which never have sessions or credentials. One call is enough.
- `auth.ts` holds three unrelated things: the `Access` type (which belongs with `space.ts` and `accessIn`), `sha256`, and `deviceIdFrom`. Next to `better-auth.ts` and `actor.ts`, the name sends readers to the wrong file.
- `push-receiver.ts` lives in `src/` but only `web-push.test.ts` imports it, and `web-push.ts` exports `concat`, `utf8`, `deriveContentKey`, `ecdhSecret`, and `importEcdhPublic` only for it. In `push-schedule.ts`, `splitDue(...).pending` is read only by its test. `push.ts:190` needs just `notifications.filter(p => p.at <= now)`.
- Doc drift: `docs/decisions/ramble.md` says "The Bun dev server also uses cassettes when it has no key". With neither `ELEVENLABS_API_KEY` nor `RAMBLE_UPSTREAM`, `config.ramble` is `null` and `index.ts` logs "nothing (off)". One of the two is wrong.
- `isAllowedEndpoint` (`push.ts:78`) accepts any https URL, so `POST /api/push/test` lets any signed-up user make the Worker POST to a host of their choice and read back the status (blind SSRF with a status oracle). It also accepts loopback http in production, which exists only for the e2e fake push service. Gate loopback on a non-production config, or restrict endpoints to known push-service hosts.
- `better-auth.ts:42-46` trusts any loopback `Origin` in production, and `ALLOWED_HOSTS` keeps `localhost:*` and `procrastimate.test` with `trustedProxyHeaders: true`. SameSite cookies limit the harm, but the dev and test entries could come from config instead of being on in production.
- `deliverDue` (`push.ts:184`) processes owners one at a time in a loop. A throw for one owner, for example the settle transaction, skips every later owner for that minute.
- `images.ts:126` reads the whole body before the size check when there is no `Content-Length`. Fine on the Worker, which buffers anyway, but a streamed read with a cap would make the limit real.
- `sweepImages` deletes from a list read earlier. A task restored in the milliseconds between the read and the `DELETE` loses its image. Adding `orphaned_at <= cutoff` to the delete's `WHERE` makes that a no-op.
- Worker cold starts run `migrate` (an advisory lock plus 4 statements) before the first request of every isolate. Correct, but it is first-request latency that a CI migrate step before `wrangler deploy` would remove.
