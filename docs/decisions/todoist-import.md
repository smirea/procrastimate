# Todoist import

- **Client-side only.** `Import from Todoist` opens a file picker for the `.zip` that Todoist's Settings > Backups produces. The browser unzips and reads it and writes the result to the local store in one command and one write. Nothing is uploaded. A summary then shows how many projects and tasks were added and how many tasks were skipped as already imported, any labels added, and a warning for everything that did not carry over. A file that is not a zip, or a zip with no project CSVs, shows an error and changes nothing.
- **Format.** One CSV per active project, named `<Project Name> [<todoist id>].csv`, UTF-8 with a byte order mark, with the columns `TYPE`, `CONTENT`, `DESCRIPTION`, `PRIORITY`, `INDENT`, `DATE`, `DATE_LANG`, `TIMEZONE`, `DURATION`, `DURATION_UNIT`, `DEADLINE`, the reminder columns, and others. Columns are read by name, so older exports with fewer columns work. Completed tasks and archived projects are not in a backup, so they are not imported.
- **Projects.** The project name is the file name without ` [id].csv`. Todoist's `Inbox` maps to our Inbox. Another project reuses a project with the same name, ignoring case, or else is created.
- **Rows.** `task` rows become tasks in file order. `note` rows are Todoist comments and join the task's notes after its description. `reminder` rows attach to the task above them: `relative` becomes a reminder that many minutes before the due time, and `absolute` becomes a reminder at its date and time. `meta` and blank rows are ignored, and any other type is skipped with a warning.
- **Priority.** Todoist's CSV uses the app's scale, so `1` is p1 and `4` is p4, the reverse of its API, where `4` is urgent. Todoist's CSV help page says so, and real exports agree: packing lists and chore lists are all `4`, and a course export marks exams `1` and homework `3`. A blank or unknown value is p4.
- **Dates.** `DATE` is a Todoist phrase in `DATE_LANG`, read by the quick add parser, which must account for all of it. A date without a year is the next one, counting today, as in quick add. So an overdue task from earlier this year comes back next year, which is the cost of Todoist leaving out the year. ISO dates such as `2027-05-20T09:00:00` also work. A date the parser cannot read, such as `every! 3 days`, or one in a language other than English keeps the task undated, with `Todoist date: <text>` in its notes and a warning. `TIMEZONE` is ignored, since there is one user in one place.
- **Labels.** Todoist writes a task's labels into its content as `@name`, so those become our labels, matched by name ignoring case or else created, and leave the title. This is the one token read from content. `#Project`, markdown links, and everything else in the content stay as written.
- **Sections are not imported.** A section name such as `Later` or `Planning` only means something inside its project, so as a label it would merge unrelated groups across projects. Tasks keep their order, and a warning lists each project's sections. They can map to sections once those exist.
- **Indent is nesting.** A task's parent is the nearest task above it with a smaller `INDENT`, so `INDENT` 2 under 1 is a subtask and 3 under 2 is a subtask of that, at any depth. A subtask joins its parent's subtasks last, in its parent's project, which is what `addTask` with a parent does, so Todoist's order carries over without a reorder. The merge uses the same sibling-order rule as `addTask` instead of calling it per row, so a backup still lands in one command and one write. A new subtask under a task from an earlier import joins that task's subtasks last.
- **Duration and deadline.** Tasks have no such fields, so they go into notes as `Duration: 90 minutes` and `Deadline: 2027-06-01`. `AUTHOR` and `RESPONSIBLE` are ignored.
- **Re-running is safe.** Every imported task and project stores a source key. A project's key is its Todoist id. A task's key is its project's id plus its content and its parents' content, with an occurrence number when the same content repeats under the same parent. A task whose key is already stored is skipped, so importing the same backup twice adds nothing. Todoist's CSV has no task ids, so a task whose content changed in Todoist imports again as a new task, and a task deleted here comes back on the next import. An existing task is never updated by an import.
- **Libraries.** `fflate` unzips (MIT, no dependencies, maintained). Its unzip adds 5.6 KB minified, 2.8 KB gzipped, measured with `bun build --minify`. The CSV reader is a 30-line RFC 4180 state machine in `shared/csv.ts`, because the format is small and fixed, and the alternatives are much larger (Papa Parse) or need Node streams (`csv-parse`).
- **Fixtures.** The repo is public, so tests never use a real backup. `shared/fixtures/todoist-backup.mts` builds a synthetic backup with Todoist's file names, header, byte order mark, and CRLF line endings. Unit tests read its CSVs, and the e2e tests zip it in memory.
