# Sharing

Sharing lets the owner of a space give other people, AI accounts, or anyone with a link access to some or all of it. The shapes are in `shared/sharing.ts`, the tables in `shared/db/schema.ts`, and the routes in `shared/api/contract.ts`.

## Concepts

- **Space.** One user's tasks, projects, sections, labels, and comments: every row with that user's `user_id`. Every entity stays in the space it was created in. A new task takes its parent's space, else its project's, else its label's when it is added from a label view, else the creator's own. Projects and labels a guest creates are always the guest's own. Nothing moves between spaces.
- **Actor.** Who makes a request: `{ id, name, kind, ownerId }`, resolved by the Worker from the session or an API token (see [Auth](auth.md)). A space serves the actor when the actor owns the space, holds a live share in it, or reads it through a public link. Anything else gets `FORBIDDEN`.
- **Share.** A row in the owner's space (`shares`). It targets the whole space, a project, a label, or a task, and grants `view` or `edit`. A share with no grantee is a public link, always `view`, whose id is the secret in the token `<ownerId>.<id>`. Revoking deletes the row. Only AI accounts get whole-space shares; the server refuses one to anyone else.
- **Access.** The server's projection of the shares for PowerSync and for admitting a guest's writes: one `access` row per entity a grantee may see, with its role (`edit` on a task they may edit, and on a project, section, or label a new task of theirs may land in, which takes an edit share on it or on the whole space). It is recomputed after every share change, and after an upload only when a write moved what a guest may see (a task created, deleted, or moved between parents, projects, sections, or labels, a section created, moved, or deleted, or a project or label created or deleted, since a share reaches only live ones) in a space shared with anyone but managers; a title edit or a completion touches it not at all. A guest's device syncs exactly the rows its `access` rows name, and loses them when a share goes. A share change (`createShare`, `deleteShare`) recomputes only its grantee's rows; the recompute after an upload rewrites every grantee's. Both run under the space's advisory lock and read the space's shares there, then the space's links (`loadLinks`: ids, parents, projects, sections, and labels, no other column) only when a grantee needs rows, so neither reads shares the other is changing. A person and an AI account get rows the same way; only a manager of the whole space needs none, since it sees everything, and an AI account's rows sit unread by PowerSync, since it never syncs. Every grantee's reads and writes check the same rows, so a narrowed AI account can edit what an edit share gives it, which it could not while it had no rows. A link moves no `access` row, so deleting one takes no lock. See [Sync tokens and access](sync-auth.md).
- **People.** Better Auth's users. Activity, share lists, comments, and the people route name people from the `user` table, joined through shares and AI ownership (`server/src/people.ts`); there is no people table. Clients keep a device-local people cache so names show offline.
- **AI account.** A Better Auth user with `kind: 'ai'` and an `ownerId`. It has no credential, so it never signs in and never syncs. It acts through API tokens `pm.<ownerId>.<secret>`, whose SHA-256 the owner's space stores in `api_tokens`. Creating one also shares the owner's whole space with it, to edit. A token may call the agent API and read images; `POST /api/upload` and `PUT /api/images` answer it `403`, since an AI account has no PowerSync queue and no image to attach.
- **Manager.** Whoever holds a whole-space edit share (`managesSpace` in `shared/scope.ts`). Only AI accounts can: `shares.create` refuses the whole space to a person or as a link with `BAD_REQUEST`. A manager does what the owner does with the space's contents: it sees every project and label, empty ones included, writes projects, sections, and labels, and makes and revokes public links. It still never touches person shares, tokens, AI accounts, settings, or read markers.

## Data

- **The log names who wrote each row.** `log.actor` is the user id that sent the write (`server` only in rows imported from the old engine's repairs), `log.client` the app it came from, and `log.at` the server's time. Clients never read the log.
- **Tasks know who made and finished them.** `createdBy` and `completedBy` are stamped by the server, which overwrites whatever a client sends. `lastCompletedAt` is written by `completeTask` on every completion, a recurring roll included, so a roll reads differently from a postpone. Undo restores it.
- **Shared rows live next to the user's own.** A device's database holds its own rows and the rows other spaces share with it, each with its owner's `user_id`, and the client groups them by owner. The `access` rows it syncs say which it may only read.

## Server

- **One write path, two doors.** A guest's upload goes through `applyWrites`, which learns that a write is a guest's when the actor's own space has no such row and looks the row up in the space it names, so a put of a stored row is checked as an edit, and an agent command goes through `applyAs` with the standing `accessIn` decided from the caller's own grants: the owner, an AI manager with the owner's rights, or a human guest (see [Sync](sync.md)). Both check a guest's writes with `guestRefusal` and write with the same single statements. A guest's writes to one space run in one transaction that holds the space's advisory lock shared, then reads its `access` rows there (`asGuest`), checks the batch in its order with a task the batch adds counting as editable for the writes after it, and gives each write a savepoint, so a refused write is still rejected alone, a revoke or downgrade (which holds the lock exclusive) waits for writes it would forbid, and writes after it see the new rows; a plain read, or an `EXISTS` inside each statement, would still let a write land on rows a committing downgrade was replacing. The lock is on the space rather than `FOR SHARE` on the rows, which deadlocked against a recompute deleting and upserting them in another order.
- **Scope and admission are pure.** `shared/scope.ts` is server only: `scopeOf` turns the owner's snapshot and the guest's shares into the visible and editable task ids plus the projects, sections, and labels they reference, which the server stores as `access` rows; `filterTree` projects the tree for public links and the agent view; and `guestRefusal` reads a guest's write against the guest's `access` rows in that space, with no load of the space: a task the space holds needs an `edit` row whatever the op and keeps its project and parent (clearing either would move the owner's task to the owner's Inbox, out of the share; the server passes the stored place to the rule), a new task an `edit` row for its parent, project, or label, every parent, project, section, and label the write names must be among the rows (the parent with `edit`), a new comment needs an editable task, an existing comment is only its author's and stays on an editable task, and projects, sections, labels, read markers, and settings are never a guest's to write (see [Comments](comments.md)). `shared/scope.test.ts` has a test per rule. A guest's `sourceKey` is dropped before the write rather than refused, so a guest's undo of a deleted import restores the task without its key and a re-put keeps the stored one. A refused write is listed in `rejected`, and the device reverts it at its next checkpoint. When a batch's statements fail partway, the log rows and derived work still run for what landed, then the failure is rethrown.
- **Authorship is stamped in the statement.** Every task write drops the client's `createdBy` and `completedBy`: the insert sets `createdBy` to the actor, and `completedBy` is a `CASE` on the stored row that sets the actor when `completedAt` moves to a value or `lastCompletedAt` moves, null when `completedAt` clears, and otherwise keeps it. A comment's insert sets `authorId` to the actor, and a comment's edit or delete matches only the author's row, the owner included.
- **Tasks know which app made and last changed them, for bots only.** The web and iOS send `x-procrastimate-client` (`Client` in `shared/values.ts`: `kind` `web` or `ios`, app version, device model or browser, OS, and time zone) on every request. A request without it is an `api` client whose `device` is its `User-Agent`, and a header that does not parse is refused with `400`. Every `log` row carries it, and the agent API reads a task's first and latest log rows in one select, two lateral reads per task that each take one row off `log_entity` (`user_id, kind, id, seq`) however long the task's history, so every returned task is an `AgentTask` with `clients: { created, edited }`, each the row's client plus its `at`. A task whose rows carry no client, imported from the old engine, reads `null` for both. The stamps the server kept in `task_clients` before the log carried them were copied onto each task's first and latest log rows when that table went (migration `0003_task_clients_to_log`). A write that changed no row is not logged, so a patch to a deleted task stamps nothing, and a retried batch's writes count once.
- **Activity is read off the log, folded into changes.** `GET /api/activity?space=&id=` replays the task's log rows into its state and reports only what really changed: a `put` of a new task is `created` (or `restored` when the task had been deleted), a `delete` is `deleted`, a set `completedAt` or a moved `lastCompletedAt` is `completed`, a cleared `completedAt` is `reopened`, and anything else is `edited`. A row that rewrites a value the task already had shows nothing, and the log's unique `(user_id, op_id)` keeps a retried write to one row. A comment's first appearance on the task is `commented`, quoting it. Bookkeeping fields (`order`, `createdAt`, `sourceKey`, the stamps) never show, nor do the old engine's imported repairs or iOS refreshing an already linked event's times.

- **Activity names only what the reader sees.** An entry names a project, section, label, or parent task only when the caller's sight (`sightOf`) includes it, read in the same select as the name, and words the rest generically: `moved it to another project`, `put it in a section`, `added a label` or `added labels home and another label`, `made it a subtask`. A deleted one reads the same way to everyone. A section cleared by a move to another project is not said twice.
- **Five-minute runs.** Consecutive edits by one actor less than five minutes apart (`COALESCE_WINDOW`) are one entry, timed at the last edit and naming each field's net change, so a field changed and changed back drops out. A completion or delete that the same actor undoes within the window shows neither. Another actor's entry in between ends the run.
- **The server writes the words.** Each entry carries a `summary` that follows the actor's name, such as `changed due to Oct 20 and edited notes`, `moved it to Home`, or `added label Urgent`, naming projects, labels, and parent tasks from the space's current data. Web and iOS print it as is, grouped by day (`Today`, `Yesterday`, `Mon, Oct 12`) newest first, with the time of day on each row.
- **The command API is the store's rules on the server.** `server/src/commands.ts` loads the tree, the time zone, and the one comment a comment command names (no command changes read markers or settings, so neither is loaded), runs the task, project, section, and label rules from `shared/store.ts` on that snapshot, turns the before and after into row writes with `rowWrites`, applies them with `applyAs`, and refuses with `FORBIDDEN` when `guestRefusal` refuses any of them, writing nothing of the command in that case. It then reads the task back, since the statement stamped it. There is no lock around the rule and the write, so two agents adding one name at the same moment can both add it. The project, section, label, and link commands refuse anyone but the owner and a manager before they look anything up, so a name clash never tells a guest what it cannot see. `text` goes through the quick add parser in the space's time zone with the visible projects and labels, so `#Home` and `@urgent` resolve like in the app; explicit fields win over parsed ones. A task outside the caller's scope is `NOT_FOUND`. Names are unique ignoring case, in the space for projects and labels and in the project for sections, because quick add resolves `#name`, `/name`, and `@name` to one. Adding one whose name is taken returns the existing one, so an agent's retry never duplicates it; renaming onto a taken name is `BAD_REQUEST`.
- **Agents publish links as share rows.** `/api/links` lists, makes, and revokes the space's link shares, the same rows the share sheet shows, for the owner and a manager. A link targets a task, project, or label, never the whole space, so an agent cannot publish everything at once.
- **Links and tokens are random secrets.** A link share's id is 24 random bytes, base64url, and its URL is `<request origin>/s/<ownerId>.<id>`. An API token is `pm.<ownerId>.<secret>` with the same kind of secret, stored as its SHA-256 in `api_tokens`; `server/src/actor.ts` resolves a `pm.` bearer against the owner's rows and reads the AI user from Better Auth.
- **Agent docs come from the contract.** `GET /api/docs` is public Markdown: what ProcrastiMate is, that the owner makes the token in Settings, and the bearer header. `/llms.txt`, a static asset, points to it. `GET /api/docs/agent` (Markdown) and `GET /api/docs/openapi` (OpenAPI 3.1 with the caller's origin as its server) need any signed-in actor, an AI token included, and cover exactly `agentContract`. `bun run generate` writes that subset to `shared/api/generated/agent-openapi.json`; `server/src/docs.ts` builds the route table from it and the curl examples from data the docs test runs one by one with a real AI token, and the test fails when a route has no example. Route `summary` and `description` in the contract are the agent's text, so they stay plain and true.
- **A new token comes with a prompt.** `POST /api/ai-tokens` also answers `prompt`: the token, the bearer header, and the guide's URL at the request's origin, built on the server so both clients copy the same words.
- **Universal Links.** `app-web/static/.well-known/apple-app-site-association` is a static asset and `app-web/static/_headers` gives it `Content-Type: application/json`.
- **Reads are sized to the route.** No route loads a whole space. The owner's standing costs nothing and a guest's is one select of its own grants (`accessIn`). Routes that ask about one task (activity, comments, images) check it with one select through `sightOf`, which says what of every kind the caller sees: everything for the owner and a manager, and the `access` rows for every other grantee, person or AI account. A whole-space view grant counts as narrower, since it sees only the projects and labels its tasks use. Views and store rules load the tree (tasks, projects, sections, and labels with dangling references resolved), since a guest's view filters the resolved tree. Activity names projects, sections, labels, and parents by id once the log says which, only those the caller sees. `server/src/read-cost.test.ts` pins each route's statements.
- **Tests.** `server/src/sharing.test.ts` runs guests, `access`, links, AI accounts, and task clients through the routes on PGlite; `server/src/activity.test.ts` the fold; `server/src/docs.test.ts` every agent example with a real token.

## Clients

Web and iOS build the same behavior. The client agents document their PowerSync stores; what follows is the behavior they share.

- **Spaces, by owner.** The user's own rows are their data. Rows with another `user_id` are that owner's shared space. Lookups, details, children, and the shared project and label screens read the merged view of own data and every space. Each command finds the space that holds its target and runs the store rule on that space's data only. A new task takes its parent's space, then its project's, then a shared label's, then the user's own, and drops a project or label from another space. Personal views (Inbox, Today, No date, places, events, search, reminders, and on iOS Spotlight and the App Intents) read own data only, so shared tasks never show there.
- **Sections follow their project.** A guest sees every section of each project in its view and writes none of them; a guest's task may only name a section it can see. See [Sections](sections.md).
- **Read only is the server's call.** A task whose `access` row says `view` loses the checkbox, swipes, editable title and notes (their links still open), the floating Complete and Delete buttons, and subtask add. Copy as Markdown stays. Adding follows the shares themselves: a project's or label's `access` row says `edit` only under an edit share on it or on the whole space, because the server admits a new task only there, and a shared project or label offers an add row and quick add defaults only then (`canAddTo` in `shared/screens.ts`, ported to Core's `Screens`). Another space's projects and labels are never renamed or deleted, and the pickers on a shared task list only that space's projects and labels, with no create.
- **Shared with me** lists each target the owner shared with this user, from the `access` rows and the people cache, with the owner's name. A whole-space share lists its projects. Both clients list it with `sharedEntries` in `shared/space-routing.ts`: the spaces by their owner's name, and in each its projects in their order, its labels by name, then each top-level task that no project or label of the space leads to.
- **Commands pick their space in one shared module.** Web and iOS must pick the same space for every command, or a task lands in different places depending on the device; when each client had its own copy, they had drifted (#184). `shared/space-routing.ts`, ported to Swift as `SpaceRouting` and held to it by recorded vectors, decides where each command runs: a new task goes to its parent's space, else its project's, else its first shared label's, else the user's own (`creationHome`), and keeps only that space's project, section, and labels (`fitToSpace`). An edit that would move a task into another space's project or section leaves it where it is, and another space's labels drop (`fitPatch`), so the server never has to refuse it. Deleting a comment offers undo only for the user's own comment, the only kind the rule deletes.
- **Authorship offline, history online.** Task details show `Created by` and `Completed by` from the task's fields and the people cache. The Activity list comes from `GET /api/activity` and shows only when someone other than the user touched the task, so a solo task looks as it did. An AI account carries an `AI` badge wherever a person shows.
- **Sharing needs the target on the server.** The share sheet uploads pending writes before it creates a share, so a project made a moment ago can be shared at once.
- **Optimistic share sheet.** Adding a person and stopping a share change the list at once and roll back with a toast (see [UX principles](ux-principles.md)). A new link's row shows at once with a pending URL. The web writes the clipboard in the tap with a promised `ClipboardItem`, because Safari refuses a clipboard write after the request returns. People search first matches the people cache on a name prefix (`namePrefixed` in `shared/sharing.ts`, the server's rule too), then adds the server's exact email matches when they arrive.
- **Public links.** The web `/s/[token]` route renders outside the sign-in gate from `GET /api/shared`. iOS opens `https://procrastimate.stf.lol/s/<token>` through Universal Links (`applinks:procrastimate.stf.lol`) in a read-only screen, also when signed out, and sends a member of that space to the space's own screen.
- **AI accounts in Settings.** Create by name, generate a token shown once with Copy and `Copy prompt for your AI`, delete. Tokens are never listed again. Create and delete are optimistic.
