# Sharing

Sharing lets the owner of a space give other people, AI accounts, or anyone with a link access to some or all of it. The shapes are in `shared/sharing.ts`, the tables in `shared/db/schema.ts`, and the routes in `shared/api/contract.ts`.

## Concepts

- **Space.** One user's tasks, projects, and labels, served by the `Account` object named by that user's id. Every entity stays in the space it was created in. A new task takes its parent's space, else its project's, else its label's when it is added from a label view, else the creator's own. Projects and labels a guest creates are always the guest's own. Nothing moves between spaces.
- **Actor.** Who makes a request: `{ id, name, kind, ownerId }` in the `x-procrastimate-actor` header, which only the Worker sets. A space's object serves the actor when the actor owns the space, holds a live share in it, or reads it through a public link. Anything else gets `FORBIDDEN`.
- **Share.** A row in the owner's space. It targets the whole space, a project, a label, or a task, and grants `view` or `edit`. A share with no grantee is a public link, always `view`, whose id is the secret in the token `<ownerId>.<id>`. Revoking deletes the row. Only AI accounts get whole-space shares; the server refuses one to anyone else.
- **Membership.** A row in the guest's space naming a space shared with them. The owner's object writes it. It is a cache: the owner's shares are the truth, and a `403` on a shared space's sync drops the membership.
- **People.** A per-space cache of everyone the space has met, so activity and share lists can name them offline.
- **AI account.** A Better Auth user with `kind: 'ai'` and an `ownerId`. It has no credential, so it never signs in. It acts through API tokens `pm.<ownerId>.<secret>`, whose SHA-256 the owner's space stores. Creating one also shares the owner's whole space with it, to edit.
- **Manager.** Whoever holds a whole-space edit share (`managesSpace` in `shared/scope.ts`). Only AI accounts can: `shares.create` refuses the whole space to a person or as a link with `BAD_REQUEST`. A manager does what the owner does with the space's contents: it sees every project and label, empty ones included, writes projects, sections, and labels, and makes and revokes public links. It still never touches person shares, tokens, AI accounts, settings, or read markers.

## Data

- **The log names who wrote each row.** `log.actor` is the user id that sent the op, or `server` for a fixup, and `log.at` is the server's time. The server stamps both and keeps them off the wire. Rows from before sharing read as `server` at `0`.
- **Tasks know who made and finished them.** `createdBy` and `completedBy` are stamped by the server, which overwrites whatever a client sends. `lastCompletedAt` is written by `completeTask` on every completion, a recurring roll included, so a roll reads differently from a postpone. Undo restores it.
- **Shared spaces live apart in the stored document.** `spaces` maps each owner id to a section with its own cursor, outbox, epoch, scope hash, read-only task ids, and data. The document's one sync clock serves every space. A section that fails validation is dropped on its own and refills on its next sync, so a bad shared space never wipes the user's own tasks. Switching users drops every section.

## Server

- **The object is the space, the header is the actor.** `Account` is named by its owner's id and serves three kinds of caller: the owner, a guest the owner has a live share with, and the Worker's internal calls, which act as the owner. Anyone else gets `FORBIDDEN`. The Worker's `forward` resolves the actor once (`server/src/actor.ts`), picks the object from `?space=` (default: the actor's own space, or an AI's owner's), and puts the actor on the request as JSON. In Turso mode the rows loaded are the space owner's. Every non-internal request upserts its actor into the space's `people`, the owner included, so activity and share lists can name them.
- **Better Auth stays in the Worker.** The object never looks a user up. Routes that need one are Worker routes that call the owner's object through the internal contract: `shares.create` resolves the grantee and calls `internal.share`; `ai.create` makes the user and calls `internal.share` with a whole-space edit share; `ai.delete` deletes the user and calls `internal.revokeAi`; `people.search` merges an exact email match and the caller's AIs with the space's `people` cache from `internal.people`; `shared.view` parses the owner id from the token and calls `internal.sharedView`. The internal routes are never forwarded, so nothing outside the Worker can reach them.
- **One policy table.** `agentContract` in `shared/api/contract.ts` holds what a guest of a space, or an AI account anywhere, may call: sync, view, the task, project, section, label, and link commands, comments, and activity. The project, section, label, and link routes answer `FORBIDDEN` to anyone but the owner and a manager. `SHARED_ROUTES` in `server/src/actor.ts` is its route keys. The Worker refuses an AI outside it and the object refuses a guest outside it, both with `FORBIDDEN`. Everything else is the human owner's, on a registered device as before. A guest or an AI registers no device.
- **Scope and admission are pure.** `shared/scope.ts` is server only: `scopeOf` turns the owner's snapshot and the guest's shares into the visible and editable task ids plus the projects and labels they reference, `filterSnapshot` projects the snapshot, `scopeHash` hashes it stably (cyrb53 over sorted-key JSON), and `admit` walks a guest's ops in order against a working copy, letting through task ops whose task is editable before and after the op (a new task after, a delete before), comment ops on an editable task that are new or the actor's own (see [Comments](comments.md)), and a manager's project, section, and label ops that set no `sourceKey`, and refusing everything else. Refused ops are acked and logged with empty fields, so a retry dedupes and the owner's data never changes.
- **Guest sync never pages.** `guestSync` writes the admitted ops as the guest, runs the usual fixups over the owner's whole data, and answers with no changes when the filtered snapshot still hashes to the guest's `scope`, else the whole filtered snapshot with `readOnly`. A guest's `reset` is ignored, and the owner's push schedule is replanned after a guest's write like after the owner's.
- **Authorship is stamped on the server.** `push` strips `createdBy` and `completedBy` from every task op and sets `createdBy` when the task first appears, `completedBy` when the op sets `completedAt` or moves `lastCompletedAt`, and `null` when it clears `completedAt`. The stamps carry the op's own clock, so they win and lose with the fields they describe.
- **Activity is read off the log, folded into changes.** `GET /api/activity?space=&id=` replays the task's log rows into its state and reports only what really changed. The log has a row per op, and one notes edit can be hundreds of rows: logs written before the outbox coalesced per field hold one per keystroke, and typing that syncs while it happens still adds a few; a row that rewrites a value the task already had, such as a second device uploading its snapshot, shows nothing, and a repeated `opId` counts once. A tombstone is `deleted`, an appearance is `created` (or `restored` after a tombstone), a set `completedAt` or a moved `lastCompletedAt` is `completed`, a cleared `completedAt` is `reopened`, and anything else is `edited`. A comment's first appearance on the task is `commented`, quoting it. The server's own repairs and bookkeeping fields (`order`, `createdAt`, `sourceKey`, the stamps) never show, nor does iOS refreshing an already linked event's times.
- **Five-minute runs.** Consecutive edits by one actor less than five minutes apart (`COALESCE_WINDOW`) are one entry, timed at the last edit and naming each field's net change, so a field changed and changed back drops out. A completion or delete that the same actor undoes within the window shows neither. Another actor's entry in between ends the run. Grouping happens at read time, so existing logs read the same way with no migration.
- **The server writes the words.** Each entry carries a `summary` that follows the actor's name, such as `changed due to Oct 20 and edited notes`, `moved it to Home`, or `added label Urgent`, naming projects, labels, and parent tasks from the space's current data. Web and iOS print it as is, grouped by day (`Today`, `Yesterday`, `Mon, Oct 12`) newest first, with the time of day on each row.
- **Cross-object calls wait for the queue.** Membership writes and nudges to guests' objects run through `context.defer`, which the host runs after the request leaves the object's serial queue (`ctx.waitUntil` on the Worker). The `nudge` internal route is answered before the queue and without the store, since it only touches sockets. So two spaces shared with each other cannot wait on one another; `server/src/account/sharing.test.ts` holds both queues busy at once to prove it. The Bun dev server and the `memoryAccount` test binding run the same queue per space.
- **The command API is the store's rules on the server.** `server/src/account/commands.ts` runs the task, project, section, and label rules from `shared/store.ts` on the space's snapshot, diffs, stamps, and pushes through the same merge, and refuses with `FORBIDDEN` when `admit` would refuse any resulting op. The project, section, label, and link commands refuse anyone but the owner and a manager before they look anything up, so a name clash never tells a guest what it cannot see. `text` goes through the quick add parser in the space's time zone with the visible projects and labels, so `#Home` and `@urgent` resolve like in the app; explicit fields win over parsed ones. A task outside the caller's scope is `NOT_FOUND`. Names are unique ignoring case, in the space for projects and labels and in the project for sections, because the fixups merge projects by name and quick add resolves `/name` and `@name` to one. Adding one whose name is taken returns the existing one, so an agent's retry never duplicates it; renaming onto a taken name is `BAD_REQUEST`.
- **Agents publish links as share rows.** `/api/links` lists, makes, and revokes the space's link shares, the same rows the share sheet shows, for the owner and a manager. A link targets a task, project, or label, never the whole space, so an agent cannot publish everything at once.
- **Links and tokens are random secrets.** A link share's id is 24 random bytes, base64url, and its URL is `<request origin>/s/<ownerId>.<id>`. An API token is `pm.<ownerId>.<secret>` with the same kind of secret, stored as its SHA-256 in the owner's space; the Worker resolves a `pm.` bearer through `internal.resolveToken`, which touches `lastUsedAt`, then reads the AI user's name from Better Auth.
- **Agent docs come from the contract.** `GET /api/docs` is public Markdown: what ProcrastiMate is, that the owner makes the token in Settings, and the bearer header. `/llms.txt`, a static asset, points to it. `GET /api/docs/agent` (Markdown) and `GET /api/docs/openapi` (OpenAPI 3.1 with the caller's origin as its server) need any signed-in actor, an AI token included, and cover exactly `agentContract`. `bun run generate` writes that subset to `shared/api/generated/agent-openapi.json`; `server/src/docs.ts` builds the route table from it and the curl examples from data the docs test runs one by one with a real AI token, and the test fails when a route has no example. Route `summary` and `description` in the contract are the agent's text, so they stay plain and true. The docs answer `text/markdown` as an oRPC `File`, so a bot reads Markdown, not a JSON string.
- **A new token comes with a prompt.** `POST /api/ai-tokens` also answers `prompt`: the token, the bearer header, and the guide's URL at the request's origin, built on the server so both clients copy the same words.
- **Universal Links.** `app-web/static/.well-known/apple-app-site-association` is a static asset and `app-web/static/_headers` gives it `Content-Type: application/json`, the same mechanism that already sets cache headers.

## Sync

- **Same protocol, one space per request.** `POST /api/sync?space=<ownerId>` syncs a shared space; no `space` is the caller's own. The Worker routes on the query alone and never reads bodies. A guest sends `scope`, the hash of what it last saw, and gets either no changes or a fresh filtered snapshot with `readOnly`.
- **A nudge names its space.** A socket nudge with `space` tells the client to sync that section. The owner's object sends it to each human grantee's object after a request moved its log, with the owner's new head as `cursor`. A new membership is followed by one too, so a client that hears an unknown space lists its spaces again.

## Clients

Web and iOS build the same behavior.

- **Sections, routed by id.** The user's own data stays where it was. Each shared space is a section with its own outbox. Lookups, details, children, and the shared project and label screens read the merged view of own data and every section. Each command finds the space that holds its target and runs the store rule on that space's data only. A new task takes its parent's space, then its project's, then a shared label's, then the user's own, and drops a project or label from another space. Personal views (Inbox, Today, No date, places, events, search, reminders, and on iOS Spotlight and the App Intents) read own data only, so shared tasks never show there.
- **Sections follow their project.** A guest sees every section of each project in its view and writes none of them; a guest's task may only name a section it can see. See [Sections](sections.md).
- **Read only is the server's call.** A section's `readOnly` ids lose the checkbox, swipes, editable title and notes (their links still open), the floating Complete and Delete buttons, and subtask add. Copy as Markdown stays. Another space's projects and labels are never renamed or deleted, and the pickers on a shared task list only that space's projects and labels, with no create.
- **The sync loop.** Own sync runs first, unchanged. Then `GET /api/spaces` adds or drops sections, at launch, every five minutes, and when a nudge names an unknown space. Then each section syncs with `POST /api/sync?space=`. A `403` drops the section and its unsent edits. A section with unsent edits sends an empty `scope`, so an edit the server refused comes back overwritten instead of lingering.
- **Shared with me** lists each target the owner shared with this user that is still in the section, with the owner's name. A whole-space share lists its projects.
- **Authorship offline, history online.** Task details show `Created by` and `Completed by` from the task's fields and the people cache. The Activity list comes from `GET /api/activity` and shows only when someone other than the user touched the task, so a solo task looks as it did. An AI account carries an `AI` badge wherever a person shows.
- **Sharing needs the target on the server.** The share sheet uploads unsent edits before it creates a share, so a project made a moment ago can be shared at once. The upload is part of the optimistic request, so the person or link row shows before it finishes.
- **Optimistic share sheet.** Adding a person and stopping a share change the list at once and roll back with a toast (see [UX principles](ux-principles.md)). A new link's row shows at once with a pending URL. The web writes the clipboard in the tap with a promised `ClipboardItem`, because Safari refuses a clipboard write after the request returns. People search first matches the space's `people` cache on a name prefix (`namePrefixed` in `shared/sharing.ts`, the server's rule too), then adds the server's exact email matches when they arrive.
- **Public links.** The web `/s/[token]` route renders outside the sign-in gate with the list rows over a read-only lookup. iOS opens `https://procrastimate.stf.lol/s/<token>` through Universal Links (`applinks:procrastimate.stf.lol`) in a read-only screen, also when signed out, and sends a member of that space to the space's own screen.
- **AI accounts in Settings.** Create by name, generate a token shown once with Copy and `Copy prompt for your AI`, delete. Tokens are never listed again. Create and delete are optimistic. The token's panel opens at once with a pending secret.
