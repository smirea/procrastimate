# Sharing

Sharing lets the owner of a space give other people, AI accounts, or anyone with a link access to some or all of it. The shapes are in `shared/sharing.ts`, the tables in `shared/db/schema.ts`, and the routes in `shared/api/contract.ts`.

## Concepts

- **Space.** One user's tasks, projects, sections, labels, and comments: every row with that user's `user_id`. Every entity stays in the space it was created in. A new task takes its parent's space, else its project's, else its label's when it is added from a label view, else the creator's own. Projects and labels a guest creates are always the guest's own. Nothing moves between spaces.
- **Actor.** Who makes a request: `{ id, name, kind, ownerId }`, resolved by the Worker from the session or an API token (see [Auth](auth.md)). A space serves the actor when the actor owns the space, holds a live share in it, or reads it through a public link. Anything else gets `FORBIDDEN`.
- **Share.** A row in the owner's space (`shares`). It targets the whole space, a project, a label, or a task, and grants `view` or `edit`. A share with no grantee is a public link, always `view`, whose id is the secret in the token `<ownerId>.<id>`. Revoking deletes the row. Only AI accounts get whole-space shares; the server refuses one to anyone else.
- **Access.** The server's projection of the shares for PowerSync: one `access` row per entity a human grantee may see, with its role, recomputed after every write to a shared space and every share change. It replaces the old memberships and scope hashes: a guest's device syncs exactly the rows its `access` rows name, and loses them when a share goes. See [Sync tokens and access](sync-auth.md).
- **People.** A per-space cache of everyone the space has met (`people`), so activity and share lists can name them. Every write to a space upserts its actor there.
- **AI account.** A Better Auth user with `kind: 'ai'` and an `ownerId`. It has no credential, so it never signs in and never syncs. It acts through API tokens `pm.<ownerId>.<secret>`, whose SHA-256 the owner's space stores in `api_tokens`. Creating one also shares the owner's whole space with it, to edit.
- **Manager.** Whoever holds a whole-space edit share (`managesSpace` in `shared/scope.ts`). Only AI accounts can: `shares.create` refuses the whole space to a person or as a link with `BAD_REQUEST`. A manager does what the owner does with the space's contents: it sees every project and label, empty ones included, writes projects, sections, and labels, and makes and revokes public links. It still never touches person shares, tokens, AI accounts, settings, or read markers.

## Data

- **The log names who wrote each row.** `log.actor` is the user id that sent the write, or `server` for a repair, and `log.at` is the server's time. Clients never read the log.
- **Tasks know who made and finished them.** `createdBy` and `completedBy` are stamped by the server, which overwrites whatever a client sends. `lastCompletedAt` is written by `completeTask` on every completion, a recurring roll included, so a roll reads differently from a postpone. Undo restores it.
- **Shared rows live next to the user's own.** A device's database holds its own rows and the rows other spaces share with it, each with its owner's `user_id`, and the client groups them by owner. The `access` rows it syncs say which it may only read.

## Server

- **One code path for every write.** A guest's upload and an AI account's command both end in `applyWrites` (see [Sync](sync.md)), which loads the space, asks `accessOf` who the actor is to it, and runs a guest's writes through `admit`.
- **Scope and admission are pure.** `shared/scope.ts` is server only: `scopeOf` turns the owner's snapshot and the guest's shares into the visible and editable task ids plus the projects, sections, and labels they reference, `filterSnapshot` projects the snapshot for public links and the agent view, and `admit` walks a guest's row writes in order against a working copy, letting through task writes whose task is editable before and after the write (a new task after, a delete before), comment writes on an editable task that are new or the actor's own (see [Comments](comments.md)), and a manager's project, section, and label writes that set no `sourceKey`, and refusing everything else. A refused write is listed in `rejected`, and the device reverts it at its next checkpoint.
- **Authorship is stamped on the server.** `applyWrites` strips `createdBy` and `completedBy` from every task write and sets `createdBy` when the task first appears, `completedBy` when the write sets `completedAt` or moves `lastCompletedAt`, and `null` when it clears `completedAt`. A comment's `authorId` is whoever sent it, and only the author edits or deletes it, the owner included.
- **Tasks know which app made and last changed them, for bots only.** The web and iOS send `x-procrastimate-client` (`Client` in `shared/values.ts`: `kind` `web` or `ios`, app version, device model or browser, OS, and time zone) on every request. A request without it is an `api` client whose `device` is its `User-Agent`, and a header that does not parse is refused with `400`. The server keeps it in `task_clients`, one row per task id, written in one upsert that sets `created` only when the row is new and `edited` on every write, so a task's creator app is never overwritten. Repairs stamp nothing. The agent API reads the rows, so every returned task is an `AgentTask` with `clients: { created, edited }`, and a task with no row reads `null` for both.
- **Activity is read off the log, folded into changes.** `GET /api/activity?space=&id=` replays the task's log rows into its state and reports only what really changed: a `put` of a new task is `created` (or `restored` when the task had been deleted), a `delete` is `deleted`, a set `completedAt` or a moved `lastCompletedAt` is `completed`, a cleared `completedAt` is `reopened`, and anything else is `edited`. A row that rewrites a value the task already had shows nothing, and a repeated `op_id` counts once. A comment's first appearance on the task is `commented`, quoting it. The server's own repairs and bookkeeping fields (`order`, `createdAt`, `sourceKey`, the stamps) never show, nor does iOS refreshing an already linked event's times.
- **Five-minute runs.** Consecutive edits by one actor less than five minutes apart (`COALESCE_WINDOW`) are one entry, timed at the last edit and naming each field's net change, so a field changed and changed back drops out. A completion or delete that the same actor undoes within the window shows neither. Another actor's entry in between ends the run.
- **The server writes the words.** Each entry carries a `summary` that follows the actor's name, such as `changed due to Oct 20 and edited notes`, `moved it to Home`, or `added label Urgent`, naming projects, labels, and parent tasks from the space's current data. Web and iOS print it as is, grouped by day (`Today`, `Yesterday`, `Mon, Oct 12`) newest first, with the time of day on each row.
- **The command API is the store's rules on the server.** `server/src/commands.ts` runs the task, project, section, and label rules from `shared/store.ts` on the space's snapshot inside `transact`, turns the before and after into row writes with `rowWrites`, and refuses with `FORBIDDEN` when `admit` refuses any of them. The project, section, label, and link commands refuse anyone but the owner and a manager before they look anything up, so a name clash never tells a guest what it cannot see. `text` goes through the quick add parser in the space's time zone with the visible projects and labels, so `#Home` and `@urgent` resolve like in the app; explicit fields win over parsed ones. A task outside the caller's scope is `NOT_FOUND`. Names are unique ignoring case, in the space for projects and labels and in the project for sections, because the fixups merge projects by name and quick add resolves `/name` and `@name` to one. Adding one whose name is taken returns the existing one, so an agent's retry never duplicates it; renaming onto a taken name is `BAD_REQUEST`.
- **Agents publish links as share rows.** `/api/links` lists, makes, and revokes the space's link shares, the same rows the share sheet shows, for the owner and a manager. A link targets a task, project, or label, never the whole space, so an agent cannot publish everything at once.
- **Links and tokens are random secrets.** A link share's id is 24 random bytes, base64url, and its URL is `<request origin>/s/<ownerId>.<id>`. An API token is `pm.<ownerId>.<secret>` with the same kind of secret, stored as its SHA-256 in `api_tokens`; `server/src/actor.ts` resolves a `pm.` bearer against the owner's rows and reads the AI user from Better Auth.
- **Agent docs come from the contract.** `GET /api/docs` is public Markdown: what ProcrastiMate is, that the owner makes the token in Settings, and the bearer header. `/llms.txt`, a static asset, points to it. `GET /api/docs/agent` (Markdown) and `GET /api/docs/openapi` (OpenAPI 3.1 with the caller's origin as its server) need any signed-in actor, an AI token included, and cover exactly `agentContract`. `bun run generate` writes that subset to `shared/api/generated/agent-openapi.json`; `server/src/docs.ts` builds the route table from it and the curl examples from data the docs test runs one by one with a real AI token, and the test fails when a route has no example. Route `summary` and `description` in the contract are the agent's text, so they stay plain and true.
- **A new token comes with a prompt.** `POST /api/ai-tokens` also answers `prompt`: the token, the bearer header, and the guide's URL at the request's origin, built on the server so both clients copy the same words.
- **Universal Links.** `app-web/static/.well-known/apple-app-site-association` is a static asset and `app-web/static/_headers` gives it `Content-Type: application/json`.
- **Tests.** `server/src/sharing.test.ts` runs guests, `access`, links, AI accounts, and task clients through the routes on PGlite; `server/src/activity.test.ts` the fold; `server/src/docs.test.ts` every agent example with a real token.

## Clients

Web and iOS build the same behavior. The client agents document their PowerSync stores; what follows is the behavior they share.

- **Spaces, by owner.** The user's own rows are their data. Rows with another `user_id` are that owner's shared space. Lookups, details, children, and the shared project and label screens read the merged view of own data and every space. Each command finds the space that holds its target and runs the store rule on that space's data only. A new task takes its parent's space, then its project's, then a shared label's, then the user's own, and drops a project or label from another space. Personal views (Inbox, Today, No date, places, events, search, reminders, and on iOS Spotlight and the App Intents) read own data only, so shared tasks never show there.
- **Sections follow their project.** A guest sees every section of each project in its view and writes none of them; a guest's task may only name a section it can see. See [Sections](sections.md).
- **Read only is the server's call.** A task whose `access` row says `view` loses the checkbox, swipes, editable title and notes (their links still open), the floating Complete and Delete buttons, and subtask add. Copy as Markdown stays. Another space's projects and labels are never renamed or deleted, and the pickers on a shared task list only that space's projects and labels, with no create.
- **Shared with me** lists each target the owner shared with this user, from the `access` rows and the people cache, with the owner's name. A whole-space share lists its projects.
- **Authorship offline, history online.** Task details show `Created by` and `Completed by` from the task's fields and the people cache. The Activity list comes from `GET /api/activity` and shows only when someone other than the user touched the task, so a solo task looks as it did. An AI account carries an `AI` badge wherever a person shows.
- **Sharing needs the target on the server.** The share sheet uploads pending writes before it creates a share, so a project made a moment ago can be shared at once.
- **Optimistic share sheet.** Adding a person and stopping a share change the list at once and roll back with a toast (see [UX principles](ux-principles.md)). A new link's row shows at once with a pending URL. The web writes the clipboard in the tap with a promised `ClipboardItem`, because Safari refuses a clipboard write after the request returns. People search first matches the people cache on a name prefix (`namePrefixed` in `shared/sharing.ts`, the server's rule too), then adds the server's exact email matches when they arrive.
- **Public links.** The web `/s/[token]` route renders outside the sign-in gate from `GET /api/shared`. iOS opens `https://procrastimate.stf.lol/s/<token>` through Universal Links (`applinks:procrastimate.stf.lol`) in a read-only screen, also when signed out, and sends a member of that space to the space's own screen.
- **AI accounts in Settings.** Create by name, generate a token shown once with Copy and `Copy prompt for your AI`, delete. Tokens are never listed again. Create and delete are optimistic.
