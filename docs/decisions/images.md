# Task attachments

Tasks can hold images and any other file. Web attaches them from a file picker, a paste, or a drop onto task details or quick add. iOS attaches them from the photo library, the camera, or the pasteboard, in details and in quick add, and from a paste into the title field of either. Details show thumbnails, the row shows a count, a tap opens the image full screen, and an image can be deleted with undo. Any other file, up to 2 GB, shows as a tile with an icon for its kind, its name, and its size, and opens or downloads on a tap.

## Files

- **One upload for everything.** The picker, paste, and drop take any file. An image a canvas (or `ImageEncoder` on iOS) can decode becomes an image, with its two encoded sizes; anything else, an SVG, or an image that fails to decode, is kept as the bytes it was picked as. There is no separate image upload and file upload.
- **A file ref says what the icon needs.** `FileRef` is `{ id, name, type, bytes }`. `type` is the MIME type the client reported, often empty. `fileKind` in `shared/images.ts` picks one of eleven kinds from the extension first, then the type, and `FILE_KIND_COLORS` tints each from the label palette so it has light and dark values on both clients. iOS mirrors the table in `Core/FileKinds.swift`, checked by the recorded vectors.
- **An untagged union.** A task's `attachments` holds `ImageRef | FileRef`, told apart by shape (`isImage` checks for `width`), because image refs synced before files existed carry no tag. Swift gets `enum Attachment { case image, file }` through `x-case-names`.
- **One object per file, of any size up to 2 GB.** A file is one object in the bucket (`size=file`). A file of at most 16 MiB (`FILE_PART_BYTES`) goes up in one `PUT`. A longer one is an R2 multipart upload the client drives: it begins the upload, sends parts of 16 MiB, three at a time, and completes it with the parts' etags. 16 MiB is over R2's 5 MiB minimum for a part and far under the 100 MB a Worker request carries, and losing one to a dropped connection costs little. The client records the upload id and each part's etag as it goes, so an upload cut short resumes with the parts still missing. `FILE_MAX_BYTES` is a product choice, not a storage limit.
- **Never read into memory whole.** The web keeps a file over 64 MB in IndexedDB as a `Blob`, which the browser holds on disk, and slices each part from it. iOS copies a picked file into its temporary folder and reads one part at a time; whoever holds the copy discards it when done (attached, turned into an image, or dropped from a draft), and launch clears what a crash left. Downloads go straight to disk on both: the browser's own download or tab, and a `URLSession` download on iOS.
- **Served as itself only when that is safe.** A file's upload declares its name and type, and the server decides once, from those, what it is served as (`previewType` in `shared/images.ts`): a PDF, plain text, audio, video, or a raster image keeps a type a browser shows in a tab, `inline`; everything else, HTML and SVG included, is `application/octet-stream` with `Content-Disposition: attachment`. Every answer carries `nosniff`, so bytes that are not what they claim never run in the app's origin. The web opens a shown kind in a new tab at the file's own URL and downloads the rest under its name; iOS shows files in Quick Look.
- **Names stay storage-era.** The task's TypeScript and Swift field is `attachments`, but its SQL column and the route keep `images`; renaming them would have needed a data migration the additive schema does not have.

## Quick add

- **Images wait in the draft.** Quick add holds picked, pasted, or dropped images as the source bytes and shows them as small thumbnails under the title, each with a remove button. They attach only after the task is saved, through the same attach path details uses, so the bytes still go into the upload queue before the edit that lists them, and a task added offline uploads its images later. Encoding waits for the save, so an image removed from the draft costs nothing. The task's space is known only once it is saved, and the upload queue is keyed by space.
- **Camera in quick add's `+` menu.** The `+` menu at the end of the chip row lists `Camera` beside the attribute actions, on iOS only where `UIImagePickerController` reports a camera, and on the web only on touch screens, where its file input asks for `capture="environment"` so the phone opens the camera instead of a picker. The shot lands in the draft like any other image. It is a menu action, not a quick add button, so it has no chip to pin; `Images` still offers the camera among its sources. A long press on the tab bar's `+` was tried first and dropped: the camera belongs inside quick add, next to the other things a draft can carry.
- **A photo is enough to save.** On both clients, a draft holding images and no title saves as `Photo` (or `<n> photos`), a lone file as its name, and a mix as `<n> attachments` (`attachmentsTitle` in `shared/format.ts`), so snap and `Add task` is the whole capture; the title can be renamed later. Expanding into details keeps an untitled draft untitled, as before.
- **An `Attachments` button.** It is a quick add button like the others (`images` in `QUICK_ADD_BUTTONS`, the id kept so pinned rows survive), so it can be pinned and is always in the `+` menu. Its picker takes any file, and a drafted file shows as its icon and name. It is not in the default row. It shows on its own once the draft holds an image.

## Data

- **A task lists its attachments.** `tasks.attachments` (SQL column `images`) is a list of `ImageRef` `{ id, width, height }` and `FileRef` (`shared/values.ts`), one last-writer-wins field like `labelIds`. Two devices that add images to the same task offline keep one device's list, which [Sync](sync.md) already accepts for arrays. The id is a client-made UUID, so creating offline never collides. `width` and `height` let a client lay the image out before its bytes arrive.
- **Visibility is the task's.** Because the list is a task field, a guest syncs only the attachments of tasks its `access` rows name, and `admit` lets a guest change the list only on a task it may edit. There is no attachment kind to sync or scope. A task in a section follows its project's share, and its subtasks follow it, the same scope comments use.
- **Bytes never sync, and never enter the database.** They live in a private R2 bucket. No client database and no server table holds them.

## Storage in a private bucket

- **R2, reached only through the Worker.** The bytes are objects in `procrastimate-attachments`, keyed `<owner id>/<attachment id>/<full|thumb|file>`. The bucket has no public address and no S3 credentials exist for it: the Worker's binding is the only way in. They were blobs in the `App` object's SQLite until they outgrew it: a row holds 2 MB, so a file was 1.5 MB parts capped at 25 MB in all, every byte passed through the one object every request waits on, and the daily dump carried them all as base64 in one string.
- **The Worker streams, the object only answers who may.** `server/src/image-bytes.ts` runs in the Worker. For each request it asks the `App` object for a grant (`authorizeImages` in `server/src/images.ts`, over `/internal/images`, with the request's headers and query but never its body) and then streams between the client and the bucket itself. The object's part is one or two reads, however long the transfer runs. Presigned URLs were weighed and dropped: they need an S3 key, bucket CORS, and a second request per attachment or signed URLs synced and rotated as rows, and a URL someone holds keeps working after a share is revoked. Through the Worker the URL is the same forever, access is checked on every request, and the whole path runs locally.
- **Image sizes.** Clients scale the full image to 2048 px on its long side and the thumbnail to 320 px, then step the quality down until they fit 1.5 MB and 200 KB (`IMAGE_LIMITS` in `shared/images.ts`).
- **Format.** WebP where the browser can write it, else JPEG. Safari's canvas answers a WebP request with a PNG, and iOS has no WebP encoder, so both send JPEG. Re-encoding drops EXIF, location included, and applies its orientation first. The Worker checks an image's declared type against its first bytes and refuses anything else with `415`, and anything past the cap with `413`.
- **Outside Cloudflare the bucket is a folder.** The Bun server and the unit tests use `localBucket` (`server/src/local-bucket.ts`), which answers the part of R2's binding the routes and the sweep use from a directory (beside the dev database, or a temporary one in tests), streaming to and from disk, with the rules a client can trip over: a put that only creates, ranges, multipart parts of one size. Wrangler's own emulation through `getPlatformProxy` was tried first and dropped: it runs a `workerd` process that outlives the server and ignores SIGTERM, so every restart and test run leaked one, and a stream cannot cross to it from Bun. The end to end suite's Worker mode runs on `wrangler dev`, so the real binding is tested there; it caught three things the folder did not (a `HEAD` grant with no body, a range's undefined fields, and gzip on text files).

## Routes

- **One path, four methods.** `GET /api/images?id=&size=&space=` answers an object, `size` being `full`, `thumb`, or `file`, with `Range`, `If-None-Match`, and `HEAD`, so audio and video seek and a client can ask whether a file has arrived. `download=1` answers it as a download whatever its type. `PUT` stores an image size or a whole file (with the file's `name` and `type`), or with `upload` and `part` one part of a multipart upload. `POST` begins a multipart upload, answering its id, or with `upload` completes it from the parts' etags.
- **Reading is in the agent contract; uploading is not.** `GET` is `agentContract.images.get`, so AI accounts read attachments and the agent docs show an example. The uploads take raw bytes, which the JSON contract does not describe, so they stay outside it, like the WebSocket.
- **Who may.** The owner of the space reads and writes with no database read past the session. A guest or an AI account reads its grants, then one select checks that a task it may see lists the id: a human guest's `access` rows say which tasks those are, and a manager sees them all (`sightOf` in `server/src/space.ts`). A guest uploads with any edit share, since an upload reaches the server before the write that lists it, often for a task the server has not seen; the write itself still goes through `guestRefusal`. Only humans upload. A guest's upload is refused when a task it cannot edit lists the id: a file is listed before its bytes arrive, so everyone who sees the task knows the id while the upload runs, and without this a guest with an edit share elsewhere could store its own bytes there first.
- **Bytes are cached for good, and never transformed.** An id's bytes never change, so `GET` answers `Cache-Control: private, max-age=31536000, immutable, no-transform` and `Content-Encoding: identity`. Without those Cloudflare gzips a text file on the way out, which breaks a ranged read: the range counts the stored bytes.
- **Bytes are written once.** A `PUT` of an id the bucket already holds keeps the stored bytes (`If-None-Match: *`), and beginning a multipart upload for one answers that it is already stored. Completing a multipart upload for an id that is stored by then drops the upload; that is a check, not a lock, since R2 has no create-only completion. So a retry is harmless, and together with the rule on who may write, a guest cannot swap the bytes behind an id it can only see.
- **Public links show the row count, not the images.** A link viewer has no session, and the image routes need one.

## Pasting on iOS

- **A paste into a title field attaches the image.** SwiftUI's `TextEditor` takes an image paste but keeps only an attachment character (U+FFFC) and drops the image. `ImagePaste` is the paste delegate of every SwiftUI text view: the focused `SmartInput` claims it, and it takes the image items of the user's own paste before they reach the text, then hands them to the field's owner: quick add's draft or the task in details. The title never changes. Reading the image back from `UIPasteboard` afterwards showed the "Allow Paste" prompt, since only the paste's own items come without asking. `pasteDestination` never fires while the text view is first responder. Other smart inputs drop the character.
- **The image menu pastes through the system paste control.** The `Paste` item in details' and quick add's image menus is SwiftUI's `PasteButton` for image types, which works as a menu item. The user's tap on it grants access, so it shows no "Allow Paste" prompt and hands over the paste's item providers; a plain button reading `UIPasteboard` asked every time. It greys itself out while the pasteboard holds no image.
- **Nothing heavy on the main actor.** Pasted images are read as the bytes they were copied as, through the pasteboard's item providers, not through `UIPasteboard.images` and `jpegData`. Decoding and re-encoding a full-size photo on the main actor froze the app for 3 to 4 seconds (Sentry `PROCRASTIMATE-IOS-7`). `ImageEncoder` runs off it, and so do the camera's JPEG encode and quick add's thumbnails.

## Viewer

- **iOS zooms out of the thumbnail and swipes down to close.** The viewer is a full-screen cover with the zoom navigation transition from the tapped thumbnail, which also gives the system's interactive swipe-down dismiss, as in Photos.
- **Standard image affordances, from system parts.** iOS zooms in a `UIScrollView`: pinch, pan with bounce, double-tap to zoom in on the tapped point and back. At full size the image fits and the scroll view cannot scroll, so its pan gives way to the page swipe and the swipe down. A long press lifts the image with `Copy` and `Share…` (`UIContextMenuInteraction`), and the bar's share button is a `ShareLink`. Both hand over the full-size image, never the thumbnail, as JPEG bytes or a `UIImage`, so the sheet offers Save Image and Copy; web-attached images are stored as WebP, which other apps take less well, so the stored bytes are not passed on. Save Image needs `NSPhotoLibraryAddUsageDescription`. The web viewer has `Download image` (a link to the loaded bytes, named for the task) and, where the browser can share files, `Share image`; zoom and copy are the browser's own (pinch zoom, the image's context menu).

## Order and offline

- **An attachment shows before the task lists it.** Attaching shows a tile at once, from the bytes the file was picked as: an image as itself (a quick downscaled preview on iOS), a file as its icon, name, and size. Behind it the image is encoded, the bytes are written to the device's upload queue, and only then is the task edit recorded, at which point the same tile becomes the task's. Listing the attachment before its bytes were safe on the device was the alternative and was dropped: a tab closed in that half second would leave a task naming bytes no device has.
- **Image sizes go before the edit that lists them.** The engine's `beforePush` uploads every queued image size, each to its own space, before a sync that carries writes (in the web's database worker, `app-web/src/lib/attachments/upload.ts`, and in iOS's `SyncClient`), and a failed upload fails that sync, so the writes wait for the retry. So another device never shows an image it cannot load, and an image added offline uploads on the first sync back online. An upload the server refuses for good (`400`, `403`, `413`, `415`) is dropped so it cannot block sync.
- **Files upload in the background.** A file can take minutes, so no sync waits on it: the task lists the file as soon as its bytes are queued, and the upload runs on its own (`uploadQueuedFiles` in the web's database worker, under a Web Lock so one tab uploads at a time; `FileUploads` on iOS), when a file is queued, when the network or the app comes back, and on a growing delay after a failure. A file past one part shows how far it is on its tile. Another device shows the tile at once and, until the bytes arrive, answers a tap with `<name> has not finished uploading`.
- **Where the clients keep them.** The web keeps a `bytes` cache and an `uploads` queue in IndexedDB, next to the database, each image as an `ArrayBuffer` with its type, because WebKit refuses a `Blob` in IndexedDB in a private window; the database worker reads the queue from there. iOS keeps the queue in Application Support and the cache in Caches, which the system may purge since everything in it can be fetched again. A fetched image is cached, so it shows offline afterwards. A file leaves the web's store once it has uploaded, since keeping every file ever attached would fill the device; iOS keeps a hard link to it in Caches, which costs nothing while the queue holds the bytes and lets the system reclaim them later.
- **A missing image waits.** When another device has not uploaded an image yet, the tile shows a placeholder and asks again every 30 seconds while it is on screen.
- **One gap is accepted.** An upload leaves the queue once the server has it. If the edit that lists it then fails to sync for longer than the two-day grace period, the sweep deletes the bytes, and the image stays a placeholder.
- **Switching users clears both.** Nothing of the previous user's stays on the device or uploads.

## Deleting

- **Deleting removes the id from the task.** There is no delete route. Bytes are garbage once no live task lists their id.
- **A sweep collects them after a grace period.** The daily cron (`0 9 * * *`, after the backup) runs `sweepImages` over every user: it lists the bucket, reads the tasks that list attachments, marks the attachments no live task lists in the `orphans` table, and clears the mark of ones listed again. An attachment marked two days ago or more is deleted from the bucket. Nothing on the upload path writes to the database, so the bucket's own listing is what exists. The grace period covers undo, an offline device restoring a task, and an upload whose edit has not synced yet. A deleted task's row is gone, so its attachments go too. R2 aborts a multipart upload nobody completed after a week.
