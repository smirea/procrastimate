# Observability

- **Sentry for errors and traces, one project per runtime.** Org `self-uo7` holds `procrastimate-web`, `procrastimate-worker`, and `procrastimate-ios`. Separate projects keep source maps, dSYMs, and alert rules per platform, and a trace still crosses all three.
- **DSNs are committed constants.** A DSN is public, so it is not a secret and not an env-manager value. The web and Worker DSNs live in `shared/sentry.ts`, the iOS one in the app. This matches how Release iOS pins the production API URL, and it lets CI, which has no AWS access, build the production client.
- **Only production reports.** A runtime reports only when it is given `SENTRY_ENVIRONMENT` (`production` or `development`) and `SENTRY_RELEASE` together. The `master` deploy sets both: the web build gets them as env, and the Worker gets them as `wrangler deploy --var`s. Local dev, pull request CI, and end-to-end runs set neither, so tests never send events. Release iOS builds report as `production`, and Debug builds never do. Set both locally to try Sentry in development.
- **Misconfiguration fails early.** An environment without a release, an unknown environment, or an environment for a project whose DSN is empty fails the web build and every Worker request. The deploy job fails when the `SENTRY_AUTH_TOKEN` secret is missing, and the iOS archive fails without a DSN, instead of shipping without readable stack traces.
- **The browser reaches Sentry through the Worker.** The browser SDK posts envelopes to `/api/sentry`, a route outside the contract like Better Auth's. The Worker accepts only envelopes whose DSN is the web project's and forwards them. This keeps the single-origin rule, and ad blockers cannot drop the events. Without Sentry config the route answers `204` and drops the envelope.
- **One trace per user action, end to end.** The browser and iOS send `sentry-trace` and `baggage` on API requests. The Worker continues the trace, the `Account` object's request nests under the Worker's, and Turso's HTTP calls are `http.client` spans. The Worker drops the incoming trace headers before forwarding to the `Account` stub, so the SDK's own headers make the object a child of the Worker's span instead of a sibling. Every transaction is kept (`tracesSampleRate: 1`), since there is one user. Tunnel requests are not traced.
- **Spans sit at boundaries.** `server/src/sentry.ts` is the Worker's only Sentry module, and feature code calls its `span` and `identify`. These do nothing where Sentry is off. Custom spans wrap the `AccountStore` interface, the Turso session load and flush, and the sync merge. The store's per-row methods (`entity`, `putEntity`, `appendLog`, `hasOp`, `hasDevice`) get no span, because about 10 µs per span on a large sync would eat the free plan's 10 ms CPU budget. Transactions are static (`traceLifecycle: 'static'`), because streamed spans are named only by HTTP method.
- **The user is an id, and no request data leaves.** Each runtime tags events with the signed-in user's id, and never an email. The JavaScript SDKs collect request bodies, headers, cookies, query values, and database query values by default; `dataCollection` turns all of them off on the Worker and in the browser. Sync bodies carry task text, sign-in carries the email, and reading every POST body costs Worker CPU.
- **iOS reports its own errors once.** `Sources/App/Support/Telemetry.swift` captures every `ErrorReport` in one place and skips offline failures. The SDK's failed-request capture is off, because it duplicated each report, and its user-interaction tracing is off, because tap transactions saw only UIKit internals. A sync cycle is a transaction bound to the scope, so its API calls become its `http.client` spans. Store load and save are their own transactions, and the tab roots trace their screen loads. Release gets `SENTRY_ENVIRONMENT = production` from `Config/Base.xcconfig`, and Debug gets none.
- **No session replay or profiling.** Both add bundle weight or battery cost against the snappy bar, and nobody needs them yet.
- **Releases and readable stack traces come from CI.** The `master` deploy bundles the Worker with `--dry-run --outdir`, injects debug ids into the web and Worker bundles with `sentry-cli`, uploads the maps, and deletes the web `.map` files so they are never served. It then deploys that same bundle with `--no-bundle`, and marks the release deployed. The release is the commit SHA. TestFlight uploads the archive's dSYMs to `procrastimate-ios`. `SENTRY_AUTH_TOKEN` lives in env-manager `prod` under the `scripts` target and reaches GitHub through `bun run secrets:github`.
