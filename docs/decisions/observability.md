# Observability

- **Sentry for errors and traces, one project per runtime.** Org `self-uo7` holds `procrastimate-web`, `procrastimate-worker`, and `procrastimate-ios`. Separate projects keep source maps, dSYMs, and alert rules per platform, and a trace still crosses all three.
- **DSNs are committed constants.** A DSN is public, so it is not a secret and not an env-manager value. The web and Worker DSNs live in `shared/sentry.ts`, the iOS one in the app. This matches how Release iOS pins the production API URL, and it lets CI, which has no AWS access, build the production client.
- **Production and development report; tests never do.** `SENTRY_ENVIRONMENT` is `production` in env-manager `prod` and `development` in `dev`, and it reaches the web build, the Bun dev server, and Debug iOS (through `bun run env:ios`). The `master` deploy sets `production` and the commit SHA as `SENTRY_RELEASE`: the web build gets them as env, and the Worker gets them as `wrangler deploy --var`s. Locally, a missing `SENTRY_RELEASE` becomes `git rev-parse HEAD` (`scripts/sentry-release.mts`, used by `vite.config.ts` and `server/src/index.ts`). Playwright starts its Vite and Bun servers with both set empty, which wins over `--env-file`, and the shared e2e fixture fails any test whose browser context sends `sentry-trace` or posts to `/api/sentry`. `bun test` never initializes a client, and pull request CI sets nothing. iOS UI test and demo launches (any `LaunchOptions` key or `PROCRASTIMATE_DEMO`) skip `Telemetry.start`. Release iOS is pinned to `production` in `Config/Base.xcconfig`.
- **Misconfiguration fails early.** An unknown environment, an environment for a project whose DSN is empty, or a Worker given an environment without a release fails the web build, the Bun dev server's start, and every Worker request. The deploy job fails when the `SENTRY_AUTH_TOKEN` secret is missing, and the iOS archive fails without a DSN, instead of shipping without readable stack traces.
- **The browser reaches Sentry through the Worker.** The browser SDK posts envelopes to `/api/sentry`, a route outside the contract like Better Auth's. The Worker accepts only envelopes whose DSN is the web project's and forwards them. This keeps the single-origin rule, and ad blockers cannot drop the events. Without Sentry config the route answers `204` and drops the envelope.
- **One trace per user action, end to end.** The browser and iOS send `sentry-trace` and `baggage` on API requests. The Worker continues the trace, the `Account` object's request nests under the Worker's, and Turso's HTTP calls are `http.client` spans. The Worker drops the incoming trace headers before forwarding to the `Account` stub, so the SDK's own headers make the object a child of the Worker's span instead of a sibling. Every transaction is kept (`tracesSampleRate: 1`), since there is one user. Tunnel requests are not traced.
- **Spans sit at boundaries.** `server/src/sentry.ts` is the server's only Sentry module. `worker.ts` wraps the Worker and the `Account` object with its `sentryOptions`, and `index.ts` starts `@sentry/bun` with its `serverOptions` before `serveDev`, so the dev server continues the browser's traces as `http.server` transactions. Feature code calls `span`, `identify`, and `reportError`, which go through `@sentry/core`'s one global client and so work under either SDK, and do nothing where no client is set up. Custom spans wrap the `AccountStore` interface, the Turso session load and flush, and the sync merge. The store's per-row methods (`entity`, `putEntity`, `appendLog`, `hasOp`, `hasDevice`) get no span, because about 10 µs per span on a large sync would eat the free plan's 10 ms CPU budget. Transactions are static (`traceLifecycle: 'static'`), because streamed spans are named only by HTTP method.
- **No failure is swallowed silently.** Both oRPC `OpenAPIHandler`s turn a thrown error into a response, so `withSentry` never saw it; their `onError` interceptor, `reportRpcError`, reports anything that is not an `ORPCError`, and any 5xx `ORPCError` by its `cause`, and reports a request that fails the contract as a warning with the validation issues. Better Auth answers its own failures, so its logger reports each `error` line. Deferred cross-space tasks, push delivery, the Ramble ledger, budget, and upstream, and rejected sync ops go through `reportError` too. In the browser, `httpClientIntegration` turns every 5xx from `/api/*` into an event in the same trace as the server's, and handled failures (an unreadable sync response, a failed push subscription or image attach) are captured where they are caught.
- **Full data, and the user by email.** Debugging ease beats redaction for a one-user app. The JavaScript SDKs keep their defaults, which collect request headers, cookies, query values, bodies, and database query values; the SDK still filters cookie and header values it recognizes as secrets, such as the session token. The Worker and the Bun server read whole request bodies up to 1 MB (`maxRequestBodySize: 'always'`), except the tunnel's own envelopes. Every runtime names the user with id, email, and name: the Worker in `readActor`, which also puts the email on the actor header so the `Account` object names the same user; the browser after the session loads; iOS after sign-in and at launch from the id, email, and name it keeps beside the session. With Sentry on, a 500-op sync (104 KB) under `wrangler dev` took a median 74 ms against 64 ms with Sentry off; reading the body was within noise (73.4 to 75.1 ms with body capture off), so the cost is the spans, not the body.
- **iOS reports its own errors once, in full.** `Sources/App/Support/Telemetry.swift` captures every `ErrorReport` in one place and skips offline failures. The event carries the error itself, and the report's `message` and `detail` as the `report` context, grouped by message. `sendDefaultPii` is on. The SDK's failed-request capture is off, because it duplicated each report, and its user-interaction tracing is off, because tap transactions saw only UIKit internals. A sync cycle is a transaction bound to the scope, so its API calls become its `http.client` spans. Store load and save are their own transactions, and the tab roots trace their screen loads.
- **No session replay or profiling.** Both add bundle weight or battery cost against the snappy bar, and nobody needs them yet.
- **Releases and readable stack traces come from CI.** The `master` deploy bundles the Worker with `--dry-run --outdir`, injects debug ids into the web and Worker bundles with `sentry-cli`, uploads the maps, and deletes the web `.map` files so they are never served. It then deploys that same bundle with `--no-bundle`, and marks the release deployed. The release is the commit SHA. TestFlight uploads the archive's dSYMs to `procrastimate-ios`. `SENTRY_AUTH_TOKEN` lives in env-manager `prod` under the `scripts` target and reaches GitHub through `bun run secrets:github`.
- **Development stack traces resolve locally.** The Vite dev server serves transformed modules, which moves their lines, and Sentry cannot fetch source maps from a local origin, so `app-web/src/lib/sentry-dev-frames.ts` maps a development event's frames through each module's inline map before it is sent. Bun reports original paths and lines as is. Debug iOS keeps its DWARF in object files, which Sentry cannot read, so `scripts/sentry-ios-smoke.ts` builds with a dSYM and uploads it before launching.
- **Smoke triggers prove each path.** `POST /api/debug/error` (any signed-in caller, the Worker) and `POST /api/debug/account-error` (the `Account` object) throw from named functions. The web's `?sentry-smoke` calls both once the session loads, then throws its own; iOS does the same at launch with `PROCRASTIMATE_SENTRY_SMOKE=1`, in Release too. `bun scripts/sentry-check.ts --environment <env> --since <window> --expect web,worker,account,ios` reads the latest smoke events back and fails unless each names its user by id and email, shares its trace with another project, and has top in-app frames whose file and line are the smoke's `throw` in this checkout.
