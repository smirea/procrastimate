# Sync

Web and iOS share one set of tasks, projects, sections, labels, and comments through [sync-engine](https://github.com/smirea/sync-engine), the SQLite sync engine a-better-me runs on too. Each client keeps a full local copy in a SQLite database, works fully offline, and catches up when it is online. Conflicts resolve on their own, so there is never a conflict screen. The engine's protocol, its laws, and its clients are documented in its own repository; this file records how ProcrastiMate uses it. sync-engine replaced Postgres and PowerSync, which needed a managed database, a replication slot, and a sync service per environment, plus Docker locally; the plan of that move is in [sync-engine migration](../sync-engine-migration.md).

## What syncs

- **Synced tables.** `projects`, `sections`, `labels`, `tasks`, `comments`, `reads`, `settings`, and `access`, as `shared/db/schema.ts` defines them and `shared/db/sync.ts` hands them to the engine (`syncSchema`), in that snapshot order, with the Zod shapes of `shared/db/json.ts` as column validators. Every row keeps `user_id`, the owner of the space it lives in. `settings` has one row per user, which the server makes at sign-up through the engine so it syncs; a client only ever patches the changed fields, a `put` fills the row in when it is missing and otherwise changes nothing, and a `delete` is refused. `timeZone` (IANA name) is what the server needs to compute notification times, and `dictation` is `native` or `elevenlabs`. `reads` are per reader and live in the reader's own space even for a task in a space shared with them. `access` is the server's and read only on clients (see [Sharing](sharing.md)).
- **Row ids are unique across users.** Every user's rows share one database, so the two per-user kinds keep their owner in the row id: a user's settings row is the user's id, and a read is `<reader>:<task>`. The domain keeps `SETTINGS_ID` and keys a read by its task; `rowIdOf` and `entityIdOf` in `shared/rows.ts`, and `Rows.rowID` and `Rows.entityID` in Swift, convert where rows are written and read.
- **Names never collide with SQL.** The engine writes table and column names unquoted on every client, so it refuses an SQLite keyword; the domain's `order` is stored in a column named `position`.
- **Device-local.** The theme, `remindersCheckedAt`, the push subscription, the install id, the people cache, and the session. See [Auth](auth.md).
- **Entities keep their shape.** `Task`, `Project`, `Section`, `Label`, and `Comment` in `shared/model.ts` are a row's columns without `user_id`. Ids are client-made UUIDs, so creating offline never collides.

## Server

- **One space holds every user.** The server is one engine space in the SQLite of one Durable Object, `App`, beside the server-only tables and Better Auth's ([Production hosting](production-hosting.md)). One space per user was rejected: sharing makes a guest's write, the `access` recompute, the push plan, and the purge read and write more than one user's rows, which one database does in one transaction and separate objects would turn into calls between them, and every client would sync several spaces.
- **Sync is one round trip.** `POST /api/sync` (a signed-in human; AI accounts write through the agent API) carries a client's outbox and cursor and answers the rows changed since; `GET /api/live` is a WebSocket that hears every new head, so a client pulls when it hears one above its cursor. Both take the session token as a bearer, and the browser's socket sends it as the `bearer.<token>` subprotocol (`withBearer` in the engine). `GET /api/sync/token` answers the session's raw token and the user, and both clients use it as their launch session check. A refused write comes back in `rejected`, is reported to Sentry as a warning, and the server's row comes back with it so the client reverts.
- **The server's rules are engine hooks.** `server/src/writes.ts` gives the space three hooks, run inside the engine's transaction with the request's actor (`syncContext`). `admit` decides each write: the space it lands in (a `put` names it, a `patch` or `delete` finds it on the stored row), a `put` of a row stored in another space is refused with `Belongs to another space`, a write to another user's space is a guest's and is checked with `guestRefusal` against the guest's `access` rows there, a guest's `sourceKey` is dropped, read markers and settings are only ever the actor's own, and the stamps are the server's: `createdBy` on a new task, `completedBy` when `completedAt` moves to a value or `lastCompletedAt` moves (null when `completedAt` clears), and a comment's `authorId`, whose edit or delete only its author may make. `landed` runs once with the writes that counted: one `log` row each, then the push plan when a write moved when a notification is due, the `access` rows when a write moved what a guest may see, and the purge when the owner's own delete emptied the space. `view` filters each pull to its reader (below). The Durable Object runs one request at a time and its SQLite is synchronous, so none of this locks.
- **The agent API writes through the same hooks.** A command runs the store's rules on the loaded space, turns the before and after into row writes with `rowWrites`, and applies them with `space.write`, atomically: one refused write rejects the command and nothing of it lands. Share changes and the settings row at sign-up write their rows through `space.change`, which counts and syncs them without the hooks. Every one of them publishes the new head to the sync sockets.
- **Pulls are filtered per reader.** A reader pulls their own rows, their `access` rows, and the rows those name in other spaces, a task's comments through the task. A delta that adds one of their `access` rows also brings the row it opens and that task's comments; one that removes it tombstones them. Tombstones of rows they never had reach them too, which costs a no-op delete and names nothing but an id. A refused write's row they cannot see comes back as a tombstone, so their local copy goes.
- **Exactly once, in order.** The engine applies a client's writes once each, by the client's sequence numbers, so a retried request writes nothing twice; a `log` row's `op_id` is `<client>:<seq>`. A delete beats a later patch, a patch of a missing row is a no-op, and a delete of a missing row still counts, so the tombstone reaches devices that hold it.
- **The log.** `log(seq, user_id, op_id, kind, id, op, fields, actor, client, at)` has a row per write that counted: `op` is `put`, `patch`, or `delete`, `fields` the domain fields as applied, `actor` the user, `client` the request's app (`Client` in `shared/values.ts`, null for rows imported from the old engine), and `id` the row id. Clients never read it; activity and the agent API's `clients` do ([Sharing](sharing.md)), and memo tasks read it for source keys the space once held ([Integrations](integrations.md)). Two partial expression indexes serve those reads: `log_source_key` on a task row's `fields ->> '$.sourceKey'` and `log_comment_task` on a comment put's `fields ->> '$.taskId'`. The engine keeps its own `_log` for 30 days; the app's `log` is never pruned on a schedule.
- **Emptying a space forgets its history.** Delete all data uploads one delete per row, and the log would keep every deleted row's fields and apps for good. In the transaction of the owner's own delete that leaves their space with no task, project, section, or label, `purgeIfEmptied` in `server/src/purge.ts` deletes every comment in the space whose task is gone, whoever wrote it, through the engine so every device drops it, and then the space's log rows for every row that is gone, settings and live rows kept. A comment outlives its task so undo can bring it back, but an empty space has no task for any comment, and a guest's comment on the owner's task would otherwise stay and keep syncing. Delete all deletes no comment someone else wrote, on web and iOS: the server would refuse it as not the author's, and the purge removes it anyway. Only the owner's own writes trigger it, so a guest's or AI account's delete never purges a space, and it touches only that owner's log rows. Undoing a delete after the purge brings the row back as newly created and without its comments, and a Notouroboros memo re-sent afterwards creates its tasks again. The daily backups taken before the purge keep those rows until they age out of the newest 30.

## Conflicts

A write carries only the columns it changed, so edits to different fields of one task both survive. Two edits to the same field keep whichever reached the server last. The server repairs nothing: a row is stored as its client sent it, and every reader resolves a reference to a row that is gone the same way (`resolveDangling` below), so clients converge on exactly what the server holds without a second round of writes.

- **Delete vs edit: delete wins.** A delete removes the row. A patch for a row that no longer exists changes nothing and is not an error, so an edit made offline to a task deleted elsewhere is dropped. Undoing a delete puts the row again, which recreates it with its fields and stamps it created by the actor.
- **Complete vs edit.** `completedAt`, `due`, and `reminders` are separate columns from `title`, `notes`, and the rest, so both changes survive.
- **Recurring task completed on two devices.** Completing sends the resulting `due` and `reminders`, not "advance by one". Two devices that complete the same occurrence send the same next date, so the task advances once.
- **Reorder.** `order` is a fractional position. Moving writes only that row's `order`: the midpoint of its new neighbors, or one more or less than the last or first. Siblings sort by `order`, then `createdAt`, then `id`. When a gap gets below `1e-9`, the move renumbers its siblings instead (`shared/order.ts`).
- **Dangling references resolve on read.** `resolveDangling` in `shared/dangling.ts`, applied in memory when the web groups its rows, when the server loads a space, and on iOS when it loads its rows (`Spaces`), and never written back: a subtask whose parent is gone, or whose parents loop, reads as top level; a task in a deleted project reads as in Inbox, and a subtask's project is its root's; a section of a deleted project is dropped, and a task keeps its section only while it is top level and the section is a live one of its project; a deleted label leaves every `labelIds`. Undoing the delete brings the reference back to life on every device. It is recorded as test vectors (`shared/vectors/dangling.json`) so the Swift port matches.
- **No merges.** Two devices that create a project or label with one name offline keep both, as do two imports of one Todoist backup, and an open subtask under a parent completed elsewhere leaves the parent completed. The client rules still refuse a duplicate name and reopen a parent when the subtask reopens on that device.
- **Arrays are single fields.** `labelIds` and `reminders` are last-writer-wins as a whole.
- **Deterministic order everywhere.** Clients keep tasks sorted by `createdAt` then `id`, and `loadTree` sorts the server's tree the same way, so the store rules see the same order on every replica.

## Unsynced tasks

- **The outbox says what has not reached the server.** A task with a row in the engine's `_outbox` shows a small cloud with an up arrow at the end of its row, and its details show `Not saved yet. Will sync when online.` floating above the title, in the field's top inset, so the title never moves when it comes or goes. Nothing guesses: the signal is the outbox itself, and the cloud leaves once the server acknowledges the write. A write to a task's comment, read marker, or project does not mark the task.
- **A grace online, at once offline.** Online, a write leaves within the engine's 100 ms throttle and lands a moment later, so a task shows only once its oldest queued write has waited 3 seconds. The grace restarts whenever that write leaves the outbox, so notes typed online never show it. A task once shown stays until its oldest write leaves, so coming back online never hides it for a moment. One timer per read of the outbox ripens every task that read found newly waiting, so an import of 1,000 tasks updates the rows once. Offline (`navigator.onLine` on the web, `NWPathMonitor` on iOS while the app runs) it shows at once. The grace runs on timers, not clock readings, since the specs pin the clock.
- **Web.** `app-web/src/lib/unsynced.svelte.ts` reads the outbox after every local write and every sync (`onChange` and `onStatus`), and runs while sync does. Rows read it through `useLookup().unsynced`; a public link's rows never show it.
- **iOS.** `UnsyncedTasks` in `Sources/App/Sync` observes the same query with GRDB, off the main thread, once per transaction. `SyncClient.isUnsynced` hides it for rows written without a session (owner `local`), which never sync, except under the DEBUG `PROCRASTIMATE_OFFLINE` launch, which stands in for a session without a network.
- **No background upload on iOS.** Uploading soon after the network returns while the app is suspended was investigated and not built. `NWPathMonitor` and the engine's socket stop when the app is suspended. A `BGAppRefreshTask` runs when iOS chooses from usage patterns, with no network trigger, and a `BGProcessingTask` with `requiresNetworkConnectivity` usually waits for the phone to charge and idle, hours later. A silent push needs APNs, which the app does not use, and the server cannot know a device holds unsent writes. A background `URLSession` upload would be a second path beside the engine's outbox, and a batch handed to it could land after newer edits and undo them. Writes still sync the next time the app is open; the cloud says which ones are waiting.

## Clients

Each client keeps its in-memory store and every store command stays a synchronous function from one snapshot to the next. After a command, `rowWrites(before, after)` in `shared/rows.ts` turns the two snapshots into the rows to write, in dependency order (projects, sections, and labels before the tasks that point at them, tasks before their comments), and the client writes them to its local database through its ORM. The engine's triggers capture every write into its outbox, which stores no values: the push reads the current row, so a column edited five times offline goes up once. When the local database changes, from a sync or another writer, the client reads what changed back into memory. Rows are grouped by `user_id`: the signed-in user's rows are their own data and each other owner is a shared space, with `readOnly` the tasks whose `access` row says `view`. `rowWrites` is recorded as test vectors (`shared/vectors/rows.json`) and ported to Swift. The web client and the iOS client are documented by their own sections and areas: [Web client](#web-client) below and [iOS app](ios.md).

- **A change reads only the rows it changed.** Triggers on the synced tables write the table and id of every row that changes to `procrastimate_changes`, a local table outside the engine's schema, so it never syncs (`changeLogStatements` in `shared/local-database.ts`, generated into Swift too). Every writer goes through them: a command, another tab, a sync, and a reset. A read is one transaction: the ids logged after the store's cursor and the rows that still have them. The first read after opening, a read whose cursor the log no longer reaches, and the read after a write the database refused take every table whole. `LocalRows` in `shared/local-rows.ts` keeps the stored rows grouped by `user_id`, and a read builds again, with `resolveDangling`, only the spaces whose rows it changed. iOS runs its Swift port (`Core/LocalRows.swift`), held to it by the `local-rows` vectors. The log is trimmed to its newest 1,000 entries once it passes 10,000.
- **Image bytes go before the writes that list them.** Each client's sync runs the engine's `beforePush` before a sync that carries writes, and both upload the image bytes queued since ([Task images](images.md)); a failed upload fails that sync, which retries, and the writes wait. A pull uploads nothing.

## Web client

- **One database per browser profile.** `app-web/src/lib/database.ts` starts sync-engine's browser client on first use: a module worker per tab (`app-web/src/lib/sync/worker.ts`) that runs SQLite in WebAssembly on OPFS (`opfs-sahpool`, no COOP or COEP), one tab's worker holding the database as host and the others forwarding to it over a `BroadcastChannel`. Drizzle runs on it through the engine's proxy over the tables of `shared/db/schema.ts`, and a command's rows go in one `batch` transaction. A worker the browser refuses fails that first use, which the store reports as a database it could not open. The page passes its client header in the worker's query, since a worker cannot read the page; the token arrives later through `setToken`. The database belongs to the account its local `procrastimate_owner` table names ([Auth](auth.md) says why the name lives in the database): signing in as someone else stops sync, `reset()`s the engine's database for every tab (every synced table, the outbox, and a new client id), empties the change log, and clears the local images first, and signing out keeps it. The owner changes only once that clear worked, and a failed clear is tried again, so a reload or a crash mid-switch finds the database still named after the previous account and clears it again before any read.
- **The store stays synchronous.** `store.svelte.ts` keeps its public API and its in-memory snapshot. A command replaces memory at once, then queues `rowWrites(before, after)` for the space it ran in, with that space's owner as `user_id`, on one promise chain that writes each command's rows in one transaction. A put upserts, so a put of a row already there updates it, and the triggers record only the columns that changed.
- **Settings are only ever patched.** The server makes every user's settings row and never lets a client's put overwrite it, so the web never puts one. A settings change patches only the fields it changed, once the local database holds the row. Until the first sync brings the row, the change shows at once, waits in memory, and is written as a patch when the row arrives, so a new browser can never write defaults over the choices made on another device.
- **A command survives a reload.** The database writes in a worker, so a reload a moment after an edit would lose it. Each command's row writes also go synchronously into `procrastimate-unwritten` in the tab's `sessionStorage`, with the signed-in user's id, and leave it once their transaction commits; a write that fails keeps its copy. The reloaded tab writes what is left before its first read, and only when the copy names the user now signed in. Each write converges, so replaying one that did land is harmless. The copy is per tab on purpose, so two tabs never overwrite or replay each other's.
- **Reloads never undo a command.** A read waits while writes are queued and is thrown away, its cursor with it, when a command ran during it; the queue's end starts the next one. Entities equal to memory keep their objects, so a read of what memory already shows re-renders nothing.
- **The first frame waits for the local read, never the network.** The signed-in app renders once the first read finishes (`store.loaded`); reminders and a push's `?task=` wait for it too. When that read fails, the app says it could not open the tasks and offers a reload (`store.unreadable`), instead of showing an empty list whose edits would never be written.
- **The web opens offline.** The service worker (`app-web/src/service-worker/index.ts`) caches the app shell at install: the one HTML, the built scripts, the database worker with its chunks and `sqlite3.wasm`, and the static files, in a `shell-<version>` cache a new deploy replaces at once with `skipWaiting` and `claim`. Nothing the database needs is cached on first use: such a file was lost with the old shell at every deploy. `$app/manifest` names the worker's entry but not its chunks or wasm, so the `database-worker-files` plugin in `app-web/vite.config.ts` lists them from the client build for the service worker's own build, and fails the build when the wasm is missing. An immutable file matches the cache ignoring its query, since the worker's carries the client header. A navigation answers from the network when it does within 1.5 s and from the cached HTML otherwise. API calls never go through it. `e2e/offline-shell.e2e.ts` empties the HTTP cache, reloads offline, and sees the Inbox.
- **The browser is asked to keep the data.** Once signed in the web calls `navigator.storage.persist()` (`keepStorage` in `device.ts`), unless the origin is already persisted, because the local database holds writes that are not on the server yet.
- **The connector.** `sync.svelte.ts` hands the worker the session's token once the store opened, from the token the session check fetched at launch or from `GET /api/sync/token`, retrying from 2 s while it cannot be reached; a `401` signs out. From then on the engine syncs on its own: 100 ms after a local write, on every head the live socket hears, on reconnects and its timers, and with backoff after a failure, which the worker caps at 3 s as PowerSync's 2 s retry was. A 401 stops the loop until a new token, and the connector then checks the session again. After every sync each tab hears the host's status (`onStatus`): the one the user is looking at names the writes the server refused with `rejectionNotice`, and every refusal is reported. Locally a change reaches a second device within the throttle plus a round trip.
- **What the specs read.** `window.procrastimate` exposes `pending()` (writes not on the server yet, settings changes still waiting for the settings row included), `reads()` (the reloads so far, the rows they read, and their milliseconds), `taskId(title)`, and `entity(kind, id)` for the end-to-end specs, which cannot read the database.

## Testing

- **Unit tests** run the server on `bun:sqlite` in memory (`server/src/test-app.ts`): `sync.test.ts` for the route and its hooks (own writes, stamps, refusals by the engine and by the rules, a resent batch applied once, settings and reads, a put naming another space's row, the three-device races, and what a guest's device pulls and loses on revoke), `purge.test.ts` for the log and comment purge when a space empties, `sharing.test.ts` for guests and `access`, `actor.test.ts` for the bearer session cache, and the rest per area. `shared/rows.test.ts` covers `rowWrites` and `coalesce`, `shared/scope.test.ts` has a test per guest rule, and `shared/dangling.test.ts` records the read-time resolution as vectors. The engine's own suite, its Bend proofs, and its conformance vectors cover the protocol.
- **End to end.** The Playwright suite runs the web app against its own server and an in-memory database (see [Testing](testing.md)).
