# Sync

Web and iOS share one set of tasks, projects, sections, labels, and comments through Postgres. Each client keeps a full local copy in a SQLite database that PowerSync keeps in step with the server, works fully offline, and catches up when it is online. Conflicts resolve on their own, so there is never a conflict screen. The requirements and the history of the move off Turso and the old sync engine are in [Postgres and PowerSync](../postgres-powersync.md).

## What syncs

- **Synced tables.** `tasks`, `projects`, `sections`, `labels`, `comments`, `reads`, `settings`, and `access`, as `shared/db/schema.ts` defines them (`SYNCED_TABLES`). Every row keeps `user_id`, the owner of the space it lives in. `settings` has one row per user with the id `settings`, which exists without a create and cannot be deleted; `timeZone` (IANA name) is what the server needs to compute notification times, and `dictation` is `native` or `elevenlabs`. `reads` are per reader, keyed by task id, and live in the reader's own space even for a task in a space shared with them. `access` is the server's and read only on clients (see [Sharing](sharing.md)).
- **Device-local.** The theme, `remindersCheckedAt`, the push subscription, the install id, the people cache, and the session. See [Auth](auth.md).
- **Entities keep their shape.** `Task`, `Project`, `Section`, `Label`, and `Comment` in `shared/model.ts` are a row's columns without `user_id`. Ids are client-made UUIDs, so creating offline never collides.

## Server

- **Postgres holds the truth.** One database on Supabase in production, one per worktree in Docker locally, PGlite in unit tests. The Worker reaches it through Hyperdrive and Drizzle on postgres.js, a client per request; the Bun dev server connects with `DATABASE_URL`. There is no sync engine of ours: no clocks, no outbox, no log cursor, no epoch, no tombstones. A delete removes the row. See [Persistence](persistence.md) and [Production hosting](production-hosting.md).
- **PowerSync streams rows down.** PowerSync reads Postgres through logical replication of the `powersync` publication, which a migration creates for exactly the synced tables, and streams each user their rows. `powersync/sync-config.yaml` holds the two Sync Streams, shared by local Docker, dev, and prod: `own` is every synced table `WHERE user_id = auth.user_id()` plus the user's `access` rows, and `shared` joins `tasks`, `projects`, `sections`, `labels`, and `comments` through `access` on the entity id for the grantee. Each shared row is its own bucket, so revoking a share drops buckets rather than sending removals.
- **Clients reach PowerSync through the Worker.** `/api/powersync/*` on the Worker forwards to the PowerSync service, the streaming response included, so the browser talks to one origin ([Dev hosting](dev-hosting.md)). The proxy asks for an identity encoding and drops `content-encoding` and `content-length`, because the runtime decompresses the stream but keeps the headers and a browser then closes every stream. It drops the cookie; PowerSync reads only its token.
- **Tokens.** `GET /api/sync/token` (a signed-in human) answers `{ token, endpoint }`: an EdDSA JWT the Worker signs with WebCrypto from `POWERSYNC_JWT_PRIVATE_KEY` (an Ed25519 JWK with a `kid`), `sub` the user id, `aud: 'powersync'`, five minutes long. Each PowerSync config lists the matching public key inline, so PowerSync never calls back into the Worker. Local Docker and CI trust the committed `powersync/local/INSECURE-dev-jwt-key.json`, which is named so nobody mistakes it for a secret. See [Sync tokens and access](sync-auth.md).
- **Writes go up through one route.** Each client's PowerSync upload queue sends its pending changes to `POST /api/upload` as `{ writes: [{ op, table, id, values, opId }] }`, one write per changed row with `values` as PowerSync reports them (snake_case columns, JSON as text). `server/src/upload.ts` is the boundary: it maps each write to a `RowWrite` with camelCase keys through the Drizzle columns and parses the values with the generated row schemas. One bad write is rejected alone, listed in `rejected` as `{ table, id, reason }`, and the rest still apply; the route never answers a 4xx for the batch, because PowerSync stops uploading on one, and `401` only for no session. Rejections are reported to Sentry as warnings.
- **One function applies writes.** `applyWrites` in `server/src/writes.ts` is the only way rows change; the agent API ends there too through `transact`. In one transaction, per space it names: take an advisory lock on the space, load the snapshot and the shares (eight parallel selects), admit a guest's writes with `admit` ([Sharing](sharing.md)), stamp authorship, apply the writes to the snapshot in memory, run `fixups` and turn the repairs into the server's own writes with `rowWrites`, then write the rows (one upsert per table for puts, one delete per table, a patch per row), a `log` row per applied write, the task's `task_clients` stamp, the actor's `people` row, the owner's `access` rows, and the push plan ([Push notifications](push-notifications.md)). The lock serializes uploads to one space, so each sees the repairs the other made.
- **Stamps.** The server overwrites whatever a client sends for `tasks.created_by` (set when the task first appears, kept after), `tasks.completed_by` (the actor when `completed_at` is set or `last_completed_at` moves, null when `completed_at` clears), and `comments.author_id` (whoever sent the comment). Only a comment's author edits or deletes it.
- **The log.** `log(seq, user_id, op_id, kind, id, op, fields, actor, at)` has a row per applied write: `op` is `put`, `patch`, or `delete`, `fields` the values written, `actor` the user or `server` for a repair, and `op_id` the client's id for the write when it sent one. Clients never read it; activity does ([Sharing](sharing.md)), and memo tasks read it for source keys the space once held ([Integrations](integrations.md)).

## Conflicts

A write carries only the columns it changed, so edits to different fields of one task both survive. Two edits to the same field keep whichever reached the server last. After applying a batch the server runs `fixups`, whose repairs are written like any other change, so clients converge on exactly what the server holds.

- **Delete vs edit: delete wins.** A delete removes the row. A patch or delete for a row that no longer exists changes nothing and is not an error, so an edit made offline to a task deleted elsewhere is dropped. Undoing a delete puts the row again, which recreates it with its fields and stamps it created by the actor.
- **Complete vs edit.** `completedAt`, `due`, and `reminders` are separate columns from `title`, `notes`, and the rest, so both changes survive.
- **Recurring task completed on two devices.** Completing sends the resulting `due` and `reminders`, not "advance by one". Two devices that complete the same occurrence send the same next date, so the task advances once.
- **Reorder.** `order` is a fractional position. Moving writes only that row's `order`: the midpoint of its new neighbors, or one more or less than the last or first. Siblings sort by `order`, then `createdAt`, then `id`. When a gap gets below `1e-9`, the move renumbers its siblings instead (`shared/order.ts`).
- **Repairs.** `fixups` in `shared/fixups.ts`: a subtask whose parent is gone becomes top level; an open subtask under a completed parent reopens the parent; a subtask takes its root's project; a task in a deleted project lands in Inbox; a section of a deleted project goes, and a task in a deleted section or a section of another project lands in no section; a deleted label leaves every `labelIds`; labels and projects whose names match ignoring case merge into the oldest, as do sections in one project and imported rows with one `sourceKey`.
- **Arrays are single fields.** `labelIds` and `reminders` are last-writer-wins as a whole.
- **Deterministic order everywhere.** Clients keep tasks sorted by `createdAt` then `id`, and `loadSpace` sorts the server's snapshot the same way, so the store rules see the same order on every replica.

## Clients

Each client keeps its in-memory store and every store command stays a synchronous function from one snapshot to the next. After a command, `rowWrites(before, after)` in `shared/rows.ts` turns the two snapshots into the rows to write, in dependency order (projects, sections, and labels before the tasks that point at them, tasks before their comments), and the client writes them to its local database through its ORM, which PowerSync queues for upload. When PowerSync applies changes from the server, the client reloads the snapshot from the local database. Rows are grouped by `user_id`: the signed-in user's rows are their own data and each other owner is a shared space, with `readOnly` the tasks whose `access` row says `view`. `rowWrites` is recorded as test vectors (`shared/vectors/rows.json`) and ported to Swift. The web client (`@powersync/web` with `@powersync/drizzle-driver` over the generated `sqlite-core` tables) and the iOS client (`PowerSync` with `PowerSyncGRDB` over the generated records) are documented by their own areas: [iOS app](ios.md) and [Web client](#web-client) below.

## Web client

- **One database per browser profile.** `app-web/src/lib/database.ts` opens `procrastimate.db` with `@powersync/web` and the generated `AppSchema`, and Drizzle over the generated `sqlite-core` tables (`app-web/src/lib/generated/tables.ts`). Vite builds workers as ES modules and keeps `@powersync/web` and `@journeyapps/wa-sqlite` out of its prebundler. Tabs of one profile share the database, so a change in one shows in the others at once. It belongs to `procrastimate-owner`: signing in as someone else runs `disconnectAndClear()` and clears the local images first, and signing out keeps it ([Auth](auth.md)).
- **The store stays synchronous.** `store.svelte.ts` keeps its public API and its in-memory snapshot. A command replaces memory at once, then queues `rowWrites(before, after)` for the space it ran in, with that space's owner as `user_id`, on one promise chain that writes each command's rows in one Drizzle transaction. A put of a row already there updates it, because PowerSync's tables are views that refuse an upsert. The first settings change puts the whole row; later ones patch.
- **A command survives the tab closing.** The database writes in a worker, so a reload or a closed phone tab a moment after an edit would lose it; under load in WebKit that window passed 270 ms. Each command's row writes also go synchronously into `procrastimate-unwritten` in `localStorage` and leave it once their transaction commits. The next launch writes what is left before its first read. Each write converges (a put of a row that exists updates it, a patch or delete of what is already so changes nothing), so replaying one that did land is harmless. Two tabs share the key, so one tab's save can drop the other's copy; that tab's edit then has only its own write to rely on.
- **Reloads never undo a command.** PowerSync's `onChange` over the synced tables reloads the whole snapshot: one read-only transaction over every table, rows parsed with the generated schemas (a row that does not parse is left out), grouped by `user_id` in `spaces.ts`. A reload waits while writes are queued and is thrown away when a command ran during its read; the queue's end starts the next one. Entities equal to memory keep their objects, so a reload of what memory already shows re-renders nothing.
- **The first frame waits for the local read, never the network.** The signed-in app renders once the first read finishes (`store.loaded`); reminders and a push's `?task=` wait for it too, so they see the user's tasks.
- **The connector.** `powersync.svelte.ts` connects while the session is confirmed, with a 100 ms upload throttle. `fetchCredentials` calls `GET /api/sync/token` and uses the endpoint's path on the page's own origin, since behind the proxy the server can only name its own; a `401` signs out, and any other failure throws so PowerSync retries. `uploadData` reads a batch, uploads every queued image ([Images](images.md)), folds the batch to one write per row with `coalesce`, fills a put's null columns (PowerSync leaves them out, and the server reads a put as the whole row), posts it, shows `rejectionNotice` for what came back `rejected`, and completes the batch. Locally a change reaches a second device in about 70 to 190 ms in Chromium and 120 to 170 ms in WebKit.
- **Nothing else triggers sync.** No focus, online, or visibility triggers, no timer, no socket, no outbox, no `localStorage` document. The old `procrastimate` document is deleted on launch. Device-local state has its own `localStorage` keys in `app-web/src/lib/device.ts`: `procrastimate-owner`, `procrastimate-install` (the install id for push and Ramble), `procrastimate-people`, `procrastimate-reminders-checked-at`, and `procrastimate-unwritten`; the theme keeps `procrastimate-theme`.
- **What the specs read.** `window.procrastimate` exposes `pending()` (writes not on the server yet), `taskId(title)`, and `entity(kind, id)` for the end-to-end specs, which cannot read the database.

## Testing

- **Unit tests** run the server on PGlite through the real migrations (`server/src/test-app.ts`): `upload.test.ts` for the route (own writes, stamps, rejections, coalesced batches, delete beats a late patch, undo re-put, fixups, the log, task clients, settings and reads), `sharing.test.ts` for guests and `access`, and the rest per area. `shared/rows.test.ts` covers `rowWrites`, `coalesce`, and `applyWrite`, and `shared/fixups.test.ts` the repairs.
- **The sync smoke.** `bun scripts/sync-smoke.ts` runs against a live server and PowerSync: it signs up two users, gets a token, opens the sync stream through the proxy, uploads a put, a patch, and a delete and waits for each to stream back, sends bad writes and sees them refused alone, shares a task, edits it as the guest, adds a subtask as the guest, reads the agent view and activity, and revokes the share. It is the proof a worktree's stack works end to end.
- **End to end.** The Playwright suite runs the web app against its own API server, database, and PowerSync (see [Testing](testing.md)).
