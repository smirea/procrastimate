# Sync

Web and iOS share one set of tasks, projects, sections, labels, and comments through Postgres. Each client keeps a full local copy in a SQLite database that PowerSync keeps in step with the server, works fully offline, and catches up when it is online. Conflicts resolve on their own, so there is never a conflict screen. PowerSync replaced a sync engine of our own: its clocks, outbox, merge, paging, realtime nudge, and their Swift ports were about 2,000 lines plus 1,600 lines of tests, and their bugs kept coming (8 `fix(sync)` commits in 10 days). The requirements and the history of the move off Turso and the old engine are in [Postgres and PowerSync](../postgres-powersync.md).

## What syncs

- **Synced tables.** `tasks`, `projects`, `sections`, `labels`, `comments`, `reads`, `settings`, and `access`, as `shared/db/schema.ts` defines them (`SYNCED_TABLES`). Every row keeps `user_id`, the owner of the space it lives in. `settings` has one row per user with the id `settings`: Better Auth's `user.create` hook inserts it with the defaults at sign-up, so no client ever builds one, a client only ever patches the changed fields, a `put` fills the row in when it is missing and otherwise changes nothing, and a `delete` is refused. `timeZone` (IANA name) is what the server needs to compute notification times, and `dictation` is `native` or `elevenlabs`. `reads` are per reader, keyed by task id, and live in the reader's own space even for a task in a space shared with them. `access` is the server's and read only on clients (see [Sharing](sharing.md)).
- **Device-local.** The theme, `remindersCheckedAt`, the push subscription, the install id, the people cache, and the session. See [Auth](auth.md).
- **Entities keep their shape.** `Task`, `Project`, `Section`, `Label`, and `Comment` in `shared/model.ts` are a row's columns without `user_id`. Ids are client-made UUIDs, so creating offline never collides.

## Server

- **Postgres holds the truth.** One database on Supabase in production, one per worktree in Docker locally, PGlite in unit tests. The Worker reaches it through Hyperdrive and Drizzle on postgres.js, a client per request; the Bun dev server connects with `DATABASE_URL`. There is no sync engine of ours: no clocks, no outbox, no log cursor, no epoch, no tombstones. A delete removes the row. See [Persistence](persistence.md) and [Production hosting](production-hosting.md).
- **PowerSync streams rows down.** PowerSync reads Postgres through logical replication of the `powersync` publication, which a migration creates for exactly the synced tables, and streams each user their rows. `powersync/sync-config.yaml` holds the two Sync Streams, shared by local Docker, dev, and prod: `own` is every synced table `WHERE user_id = auth.user_id()` plus the user's `access` rows, and `shared` joins `tasks`, `projects`, `sections`, `labels`, and `comments` through `access` on the entity id and on `access.owner = user_id` for the grantee, so an `access` row only ever opens rows of the space whose owner wrote it. Each shared row is its own bucket, so revoking a share drops buckets rather than sending removals.
- **Clients reach PowerSync through the Worker.** `/api/powersync/*` on the Worker forwards to the PowerSync service, the streaming response included, so the browser talks to one origin ([Dev hosting](dev-hosting.md)). The path is appended to the configured `POWERSYNC_URL`, never resolved against it, so `/api/powersync//evil.example/x` reaches PowerSync and not another host. The proxy asks for an identity encoding and drops `content-encoding` and `content-length`, because the runtime decompresses the stream but keeps the headers and a browser then closes every stream. It drops the cookie; PowerSync reads only its token.
- **Tokens.** `GET /api/sync/token` (a signed-in human) answers `{ token, endpoint }`: an EdDSA JWT the Worker signs with WebCrypto from `POWERSYNC_JWT_PRIVATE_KEY` (an Ed25519 JWK with a `kid`), `sub` the user id, `aud: 'powersync'`, five minutes long. Each PowerSync config lists the matching public key inline, so PowerSync never calls back into the Worker. Local Docker and CI trust the committed `powersync/local/INSECURE-dev-jwt-key.json`, which is named so nobody mistakes it for a secret. See [Sync tokens and access](sync-auth.md).
- **Writes go up through one route.** Each client's PowerSync upload queue sends its pending changes to `POST /api/upload` (a signed-in human; AI accounts write through the agent API) as `{ writes: [{ op, table, id, values, opId }] }`, one write per changed row with `values` as PowerSync reports them (snake_case columns, JSON as text). `server/src/upload.ts` is the boundary: it maps each write to a `RowWrite` with camelCase keys through the Drizzle columns, parses the values with the generated row schemas, and refuses text with U+0000, which Postgres would refuse later with an error. One bad write is rejected alone, listed in `rejected` as `{ table, id, reason }`, and the rest still apply; the route never answers a 4xx for the batch, because PowerSync stops uploading on one, and `401` only for no session. Rejections are reported to Sentry as warnings.
- **One statement per write.** `applyWrites` in `server/src/writes.ts` is the only way rows change from an upload, and the agent API ends in `applyAs` next to it. Every write is one single-row statement with the ownership check inside it: a `put` is `INSERT … ON CONFLICT (id) DO UPDATE … WHERE <table>.user_id = excluded.user_id`, a `patch` is `UPDATE … WHERE id = $id AND user_id = $owner`, a `delete` the same `DELETE`. There is no transaction, lock, savepoint, or read of the space, except for a guest's writes (below), which hold the space's lock shared so a share revoke cannot race them: a rename once ran 21 statements to change one row, and now runs the write and its log row. Postgres makes the row atomic, and every write converges when replayed (a put upserts, a patch sets values, a delete removes), so PowerSync resending a batch is harmless. A batch's statements run without waiting on each other. A write to the actor's own space runs at once; its puts of one kind with the same columns go in one multi-row upsert (`upsertMany`), so an import or a long offline stretch lands in a few statements, and a group the database refuses is retried one row at a time to name the row at fault. A `put` that then changed nothing names a row stored in another space and is refused with `Belongs to another space`, because the entity tables are keyed by `id` alone. A `patch` or `delete` that changed nothing is looked up, one select per table: gone, which is how a delete beats an edit that arrives after it, or stored in another space, which makes it a guest's write to that space, checked with `guestRefusal` against the guest's `access` rows there, one query per space ([Sharing](sharing.md)). `reads` and `settings` are always the actor's own: a settings `put` inserts only when the row is missing (`ON CONFLICT DO NOTHING`), and a settings `delete` is refused at the boundary. A data or integrity error from Postgres (SQLSTATE 22xxx or 23xxx) rejects that write alone with `The database refused the write` and the rest of the batch still lands with a 200. Any other error fails the request and PowerSync retries. An owner's title edit is two statements, the update and the log row (`server/src/write-cost.test.ts` holds the counts).
- **Derived work only when its inputs change.** After the log insert, and only for the spaces a write changed: the `access` rows are recomputed when a write created, deleted, or moved a task (`parent_id`, `project_id`, `section_id`, `label_ids`) or created, moved, or deleted a section, or created or deleted a project or label, in a space shared with anyone but managers, under the space's advisory lock the share routes also take ([Sync tokens and access](sync-auth.md)); the push plan when a write created or deleted a task, changed its `due`, `reminders`, `recurrence`, `completed_at`, `event`, or `location`, or changed the time zone, and only when the owner has a push subscription ([Push notifications](push-notifications.md)). When both run they run in that order, the push plan first, because a retried guest delete finds its space through the `access` row the recompute drops. The image sweep runs in the daily cron, not on the write path ([Images](images.md)).
- **Stamps are in the statement.** The server drops whatever a client sends for `tasks.created_by`, `tasks.completed_by`, and `comments.author_id`. A task's insert sets `created_by` to the actor and the conflict update never touches it. `completed_by` is a `CASE` against the stored row: the actor when `completed_at` moves to a value or `last_completed_at` moves, null when `completed_at` clears, else kept. A comment's insert sets `author_id` to the actor, and a comment's edit or delete matches only `WHERE author_id = $actor`, so a write that changed nothing on an existing comment is refused as not the author's, the owner's included.
- **The log.** `log(seq, user_id, op_id, kind, id, op, fields, actor, client, at)` has a row per write that changed a row, inserted as one statement per batch: `op` is `put`, `patch`, or `delete`, `fields` the values the client sent, `actor` the user, `client` the request's app (`Client` in `shared/values.ts`, null for rows imported from the old engine), and `op_id` the client's id for the write. A unique index on `(user_id, op_id)` and `ON CONFLICT DO NOTHING` keep a retried batch to one row per write; the web names a write `<database id>:<queue id>`, and the server mints an id for its own writes and for a write that came without one. Clients never read it; activity and the agent API's `clients` do ([Sharing](sharing.md)), and memo tasks read it for source keys the space once held ([Integrations](integrations.md)). Two partial expression indexes serve those reads: `log_source_key` on a task row's `fields->>'sourceKey'` and `log_comment_task` on a comment put's `fields->>'taskId'`.

## Conflicts

A write carries only the columns it changed, so edits to different fields of one task both survive. Two edits to the same field keep whichever reached the server last. The old engine kept a clock per field to merge concurrent edits; for one user editing on two devices, the last write per column gives the same result without any clocks. The server repairs nothing: a row is stored as its client sent it, and every reader resolves a reference to a row that is gone the same way (`resolveDangling` below), so clients converge on exactly what the server holds without a second round of writes.

- **Delete vs edit: delete wins.** A delete removes the row. A patch or delete for a row that no longer exists changes nothing and is not an error, so an edit made offline to a task deleted elsewhere is dropped. A delete that finds its row gone still counts as landed, because it may be the retry of one that removed the row and then failed before its log row and derived work: it is logged under its op id, which a first attempt that got that far already holds, and its derived work reruns, in the space where the actor last wrote the row (the log's `(kind, id, seq)` index finds it, even after the first attempt's recompute dropped the guest's `access` row), else the space of a guest's `edit` row for the task, else the actor's own. Undoing a delete puts the row again, which recreates it with its fields and stamps it created by the actor.
- **Complete vs edit.** `completedAt`, `due`, and `reminders` are separate columns from `title`, `notes`, and the rest, so both changes survive.
- **Recurring task completed on two devices.** Completing sends the resulting `due` and `reminders`, not "advance by one". Two devices that complete the same occurrence send the same next date, so the task advances once.
- **Reorder.** `order` is a fractional position. Moving writes only that row's `order`: the midpoint of its new neighbors, or one more or less than the last or first. Siblings sort by `order`, then `createdAt`, then `id`. When a gap gets below `1e-9`, the move renumbers its siblings instead (`shared/order.ts`).
- **Dangling references resolve on read.** `resolveDangling` in `shared/dangling.ts`, applied in memory when the web groups its rows, when the server loads a space, and on iOS when it loads its rows (`Spaces`), and never written back: a subtask whose parent is gone, or whose parents loop, reads as top level; a task in a deleted project reads as in Inbox, and a subtask's project is its root's; a section of a deleted project is dropped, and a task keeps its section only while it is top level and the section is a live one of its project; a deleted label leaves every `labelIds`. Undoing the delete brings the reference back to life on every device. It is recorded as test vectors (`shared/vectors/dangling.json`) so the Swift port matches.
- **No merges.** Two devices that create a project or label with one name offline keep both, as do two imports of one Todoist backup, and an open subtask under a parent completed elsewhere leaves the parent completed. The client rules still refuse a duplicate name and reopen a parent when the subtask reopens on that device.
- **Arrays are single fields.** `labelIds` and `reminders` are last-writer-wins as a whole.
- **Deterministic order everywhere.** Clients keep tasks sorted by `createdAt` then `id`, and `loadTree` sorts the server's tree the same way, so the store rules see the same order on every replica.

## Clients

Each client keeps its in-memory store and every store command stays a synchronous function from one snapshot to the next. After a command, `rowWrites(before, after)` in `shared/rows.ts` turns the two snapshots into the rows to write, in dependency order (projects, sections, and labels before the tasks that point at them, tasks before their comments), and the client writes them to its local database through its ORM, which PowerSync queues for upload. When the local database changes, from a sync or another writer, the client reads what changed back into memory. Rows are grouped by `user_id`: the signed-in user's rows are their own data and each other owner is a shared space, with `readOnly` the tasks whose `access` row says `view`. `rowWrites` is recorded as test vectors (`shared/vectors/rows.json`) and ported to Swift. The web client (`@powersync/web` with `@powersync/drizzle-driver` over the generated `sqlite-core` tables) and the iOS client (`PowerSync` with `PowerSyncGRDB` over the generated records) are documented by their own areas: [iOS app](ios.md) and [Web client](#web-client) below.

## Web client

- **One database per browser profile.** `app-web/src/lib/database.ts` opens `procrastimate.db` with `@powersync/web` and the generated `AppSchema`, and Drizzle over the generated `sqlite-core` tables (`app-web/src/lib/generated/tables.ts`). Vite builds workers as ES modules and keeps `@powersync/web` and `@journeyapps/wa-sqlite` out of its prebundler. Tabs of one profile share the database, so a change in one shows in the others at once. It belongs to the account its local `procrastimate_owner` table names ([Auth](auth.md) says why the name lives in the database): signing in as someone else runs `disconnectAndClear()` and clears the local images first, and signing out keeps it ([Auth](auth.md)). The owner changes only once that clear worked, and a failed clear is tried again, so a reload or a crash mid-switch finds the database still named after the previous account and clears it again before any read. The session opens the cached user's database as the page loads, so a stale owner is cleared without waiting for the network.
- **The store stays synchronous.** `store.svelte.ts` keeps its public API and its in-memory snapshot. A command replaces memory at once, then queues `rowWrites(before, after)` for the space it ran in, with that space's owner as `user_id`, on one promise chain that writes each command's rows in one Drizzle transaction. A put of a row already there updates it, because PowerSync's tables are views that refuse an upsert.
- **Settings are only ever patched.** The server makes every user's settings row and never lets a client's put overwrite it, so the web never puts one. A settings change patches only the fields it changed, once the local database holds the row. Until the first sync brings the row, the change shows at once, waits in memory, and is written as a patch when the row arrives, so a new browser can never write defaults over the choices made on another device.
- **A command survives a reload.** The database writes in a worker, so a reload a moment after an edit would lose it; under load in WebKit that window passed 270 ms. Each command's row writes also go synchronously into `procrastimate-unwritten` in the tab's `sessionStorage`, with the signed-in user's id, and leave it once their transaction commits; a write that fails keeps its copy. The reloaded tab writes what is left before its first read, and only when the copy names the user now signed in. Each write converges (a put of a row that exists updates it, a patch or delete of what is already so changes nothing), so replaying one that did land is harmless. The copy is per tab on purpose, so two tabs never overwrite or replay each other's: it does not survive closing the tab, so an edit made in the moment before a tab or a phone's home screen app closes can be lost.
- **A change reads only the rows it changed.** Triggers on the tables under PowerSync's views write the table and id of every row that changes to `procrastimate_changes`, a table of the local database outside PowerSync's schema, so it never syncs. Every writer goes through them: a command in this tab, another tab, a sync, and `disconnectAndClear`, which deletes rows. They and the table are created on the first read with `IF NOT EXISTS`, so every tab and launch may. The web watches only that log through PowerSync's `onChange`, and iOS through a GRDB `ValueObservation` of its newest `seq`. A read is one read-only transaction: the ids logged after the store's cursor and the rows that still have them, parsed with the generated schemas (a row that does not parse is left out). The first read after opening, a read whose cursor the log no longer reaches, and the read after a write the database refused take every table whole. `LocalRows` in `shared/local-rows.ts` keeps the stored rows grouped by `user_id`, and a read builds again, with `resolveDangling`, only the spaces whose rows it changed. iOS runs its Swift port (`Core/LocalRows.swift`), held to it by the `local-rows` vectors. It keeps rows rather than what the store shows, so a reference that dangles comes back when its row does. The log is trimmed to its newest 1,000 entries once it passes 10,000, and a tab further behind reads everything once. On 1,000 tasks a rename used to read every row twice (2,072 rows, about 46 ms) on its own device and once (1,036 rows, 22 ms) on the other. It now reads 2 rows (its write, then the server's copy of it), about 5 ms, and 1 row, about 2 ms (`an edit reads back only the row it changed` in `e2e/sync.e2e.ts` pins the rows).
- **Reloads never undo a command.** On the web a read waits while writes are queued and is thrown away, its cursor with it, when a command ran during it; the queue's end starts the next one. On iOS reads run one at a time and always apply to `LocalRows`, which mirrors the database, and the store holds back what they show until the writer catches up ([iOS app](ios.md)). Entities equal to memory keep their objects, so a read of what memory already shows re-renders nothing.
- **The first frame waits for the local read, never the network.** The signed-in app renders once the first read finishes (`store.loaded`); reminders and a push's `?task=` wait for it too, so they see the user's tasks. When that read fails, the app says it could not open the tasks and offers a reload (`store.unreadable`), instead of showing an empty list whose edits would never be written.
- **The web opens offline.** The service worker (`app-web/src/service-worker/index.ts`) caches the app shell at install: the one HTML, the built scripts without the wasm variants (cached on first use), and the static files, in a `shell-<version>` cache a new deploy replaces at once with `skipWaiting` and `claim`. A navigation tries the network and falls back to the cached HTML; an immutable asset comes from the cache. API calls never go through it. `e2e/offline-shell.e2e.ts` reloads offline and sees the Inbox.
- **The connector.** `powersync.svelte.ts` connects while the session is confirmed, with a 100 ms upload throttle and a 2 s retry, the same as iOS. `fetchCredentials` calls `GET /api/sync/token` and uses the endpoint's path on the page's own origin, since behind the proxy the server can only name its own; a `401` signs out, and any other failure throws so PowerSync retries. `uploadData` reads a batch of up to 1,000 writes, so one command's writes, which the store writes in one transaction, almost never split across requests; names each write `<database id>:<queue id>` as its `opId`, so a retried batch logs nothing twice; then it uploads every queued image ([Images](images.md)), folds the batch to one write per row with `coalesce`, fills a put's null columns (PowerSync leaves them out, and the server reads a put as the whole row), posts it, reports and shows `rejectionNotice` for what came back `rejected`, and completes the batch. A queued write to a table only the server writes is reported and dropped, since throwing would stall every upload behind it, as on iOS. Locally a change reaches a second device in about 70 to 190 ms in Chromium and 120 to 170 ms in WebKit.
- **Nothing else triggers sync.** No focus, online, or visibility triggers, no timer, no socket, no outbox, no `localStorage` document. The old `procrastimate` document is deleted on launch. Device-local state has its own `localStorage` keys, all named in `app-web/src/lib/device.ts` (`DEVICE_KEYS` lists the ones other modules read: the cached user, the theme, the push rekey marker, and the Completed and No date view choices): `procrastimate-owner` (only a signal for other tabs to reload when the account changes; the database's owner is its own `procrastimate_owner` table, see [Auth](auth.md)), `procrastimate-install` (the install id for push and Ramble), `procrastimate-database` (the name of this local database in upload op ids, minted again when the database is cleared, since PowerSync's queue ids restart then), `procrastimate-people`, and `procrastimate-reminders-checked-at`, plus the tab's `procrastimate-unwritten` in `sessionStorage`; the theme keeps `procrastimate-theme`.
- **What the specs read.** `window.procrastimate` exposes `pending()` (writes not on the server yet, settings changes still waiting for the settings row included), `reads()` (the reloads so far, the rows they read, and their milliseconds), `taskId(title)`, and `entity(kind, id)` for the end-to-end specs, which cannot read the database.

## Testing

- **Unit tests** run the server on PGlite through the real migrations (`server/src/test-app.ts`): `upload.test.ts` for the route (own writes, stamps, rejections, coalesced batches, delete beats a late patch, undo re-put, no repairs, the log with its client, a retried batch, settings and reads, a put naming another space's row, U+0000, a write the database refuses, and the three-device races the old engine's interleaving enumeration once found, run as uploads in the order the devices' changes reached the server: a task put into a section another device deleted, a place put back on a task after its delete, and an undo that lands after another device's edit), `write-cost.test.ts` for the literal statement count of each kind of upload, `sharing.test.ts` for guests and `access`, `actor.test.ts` for the bearer session cache, and the rest per area. `shared/rows.test.ts` covers `rowWrites` and `coalesce`, `shared/scope.test.ts` has a test per guest rule, and `shared/dangling.test.ts` records the read-time resolution as vectors. `sharing-lock.test.ts` needs two connections, so it runs only with `DATABASE_URL` pointing at the local Docker Postgres and is skipped on PGlite: it holds a space's lock and shows a share revoke waiting for it.
- **The sync smoke.** `bun scripts/sync-smoke.ts` runs against a live server and PowerSync: it signs up two users, gets a token, opens the sync stream through the proxy, uploads a put, a patch, and a delete and waits for each to stream back, sends bad writes and sees them refused alone, shares a task, edits it as the guest, adds a subtask as the guest, reads the agent view and activity, forges an `access` row in Postgres naming a third user's task and sees the row reach the guest with no task behind it, and revokes the share. It is the proof a worktree's stack works end to end, and the way to validate a `sync-config.yaml` change: restart the worktree's PowerSync container to load it, then run the smoke.
- **End to end.** The Playwright suite runs the web app against its own API server, database, and PowerSync (see [Testing](testing.md)).
