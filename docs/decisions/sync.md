# Sync

Web and iOS share one set of tasks, projects, and labels through the Worker. The server holds the truth. Each client keeps a full local copy, works fully offline, and catches up when it syncs. Conflicts resolve on their own, so there is never a conflict screen.

## What syncs

- **Synced:** tasks, projects, sections, labels, and one `settings` record with the id `settings`, which exists without a create and cannot be deleted. `timeZone` (IANA name) is what the server needs to compute notification times. A device writes it only when its own zone changes from the last one it saw, such as after travel, never because the synced value differs. So two devices in different zones do not overwrite each other, and the device that moved last wins. `dictation` is `native` or `elevenlabs`, `native` until changed. It is last-writer-wins like any other field: the device that changed it last wins, and the other device adopts that choice on the next sync.
- **Device-local:** the theme (see [Theming](theming.md)), `remindersCheckedAt` (each open app toasts its own reminders), the push subscription, the sync section, and the session. The session never sits in the snapshot document. See [Auth](auth.md).
- **Entities keep their shape.** `Task`, `Project`, and `Label` stay as they are in `shared/task.ts`. Ids are client-made UUIDs, so creating offline never collides. The one model change is ordering (see Conflicts).

## Server

- **Task data lives in Turso.** When `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` are both set, the Worker loads the account into memory for the request and writes it back, so the merge stays synchronous. The client is `@libsql/client/web`. `TURSO_API_TOKEN` is a prod-only env-manager value and is not a Worker secret. Without those two secrets the Worker keeps the Durable Object's SQLite and the Bun dev server keeps memory, so CI and Playwright still sync. The Durable Object stays for the push alarm and the realtime and Ramble sockets.
- **Tables.** Drizzle defines them in `shared/db/schema.ts`, every one scoped by `user_id` (see [API and database types](api.md)).
  - `tasks`, `projects`, `sections`, `labels`, and `settings`: the current value of every entity, a column per field, with one hybrid logical clock per field in `clocks`, which also says which fields the row holds. A deleted entity stays as a tombstone (`deleted: true`), so a late edit cannot bring it back by accident.
  - `log(seq, op_id, kind, id, fields, actor, at)`: append-only, with `seq` as the monotonic server sequence. Each row holds only the fields that won, so clients can apply the log in order without clocks. Every applied op gets a row, with empty `fields` when it won nothing, so the log alone answers whether an op was applied. When an entity turns live (a create or an undelete), its row carries all its fields, so a client that never had it can build it. A delete or undelete that loses gets a row restating the server's answer: all the fields of an entity that stays live, or `deleted: true`. A client skips a partial row for an entity it does not have. `actor` and `at` say who wrote the row and when, for activity; they never go to clients (see [Sharing](sharing.md)).
  - `devices(id, name, token_hash, created_at, last_seen_at, revoked_at)` for installs. There is no pairing table. A `meta` row holds the wipe `epoch`.
- **No compaction yet.** The log grows by one row per change. A client whose cursor is `0` gets a full snapshot instead of the log. If the log ever needs trimming, clients behind the trimmed point get the snapshot too.
- **The merge is shared code.** `shared/sync/` holds the pure rules: `applyPush` (`applyOps`, then `applyFixups`, which runs `fixups` and writes its repairs as server ops) and `serverSnapshot` on the server, and the HLC, `diff`, `commit`, `startSync`, and `applyResponse` (`applyChanges` plus outbox replay) on clients. The Durable Object only reads rows, calls them, and writes rows. The Bun dev server runs the same handler on an in-memory store, so local dev and Playwright can sync without `wrangler`.

## Protocol

- **Ops.** One op per changed entity per command: `{ opId, hlc, kind, id, fields }`. `fields` carries the new values of the fields that changed, and `deleted: true` or `false` for delete and undelete. Clients never send intent like "complete" or "advance", only resulting values.
- **Ops come from diffs.** The store's commands stay as they are. Each command's commit compares the snapshot before and after, entity by entity and field by field, and queues one op per changed entity in the outbox. A missing entity becomes a tombstone, and one that comes back (undo of delete) is sent with `deleted: false` and all its fields. Undo of a completion writes only the fields it restores, as it does now.
- **The outbox holds one value per entity field.** Title and notes fields commit on every keystroke, so the store and the screen update at once, and `enqueue` in `shared/sync/apply.ts` (ported as `SyncEngine.enqueue`) keeps the outbox to the latest value of each field. A sync therefore carries one op for a typed title, not one per character, and the server's log grows by one row. Each field keeps the clock it was written at, so coalescing never changes who wins a conflict:
  - An op carrying `deleted` (a delete, or a create or undelete with every field) replaces every queued op for its entity, since each of their fields would lose to it.
  - An edit to an entity whose create or undelete is still queued folds into that op, which takes the edit's op id and clock, because the server builds an entity only from an op that carries every field. For a create no other device has the entity yet, so the later clock on its other fields matters only for an undelete, where it can beat a concurrent edit to the same task. That is accepted.
  - Any other edit takes its fields out of the older ops for its entity, and an op left with no fields is dropped.
  - Ops already sent may still change, since the outbox has no in-flight marker. A stripped op keeps its id, so the server applies either the original or what is left. A folded op gets a new id, so it applies even when the original already did.
- **Hybrid logical clock.** `<wall ms>:<counter>:<deviceId>`, compared as a tuple. A client never issues a clock lower than the highest one it has seen from the server. The server replaces a clock whose wall time is more than a minute ahead of its own with its own next clock, keeping the device id as the tie-break, so a device with a wrong clock cannot win every conflict. A wall time or counter past `Number.MAX_SAFE_INTEGER` fails validation.
- **One round trip.** `POST /api/sync { cursor, ops, epoch, reset? }` applies the ops in order, skipping any `opId` already in the log, so a retry never applies twice. It then runs `fixups` and returns `{ acked, rejected, changes, cursor, hlc, epoch }`. With `cursor: 0`, a cursor past the log, `reset`, an `epoch` behind the server's, or a rejected op, it returns `{ acked, rejected, snapshot, cursor, hlc, epoch }` instead. `reset` wipes tasks, projects, labels, and the log (but not `task_clients`, see [Sharing](sharing.md)), then bumps `epoch`, then applies the ops that came with it. A client whose epoch is behind and did not send `reset` has its ops discarded and its outbox dropped, so a device that missed a delete-all cannot recreate what was deleted.
- **One bad op never wedges a device.** The request schema checks only the envelope (`cursor`, `epoch`, `reset`, `scope`, and that `ops` is a list), and `parseOps` in `server/src/account/sync.ts` parses each op on its own. An op that fails is listed in `rejected` as `{ opId, reason }` and is neither applied, logged, nor acked; the valid ops around it apply and are acked as usual. Before, one invalid op (such as the year-12784 due date quick add once parsed) failed the whole push with a `400`, the client retried the same outbox forever, and the device never uploaded again.
  - **The answer is the snapshot.** A rejected op's entity may already show the refused value on the device, and the log alone may never carry the server's value again, so a push with any rejection answers with the snapshot, as cursor `0` does. The client drops the rejected ops with the acked ones (`settle` in `shared/sync/apply.ts`, ported as `SyncEngine.settle`), takes the snapshot, and replays what is left, so the entity shows what the server holds.
  - **A subtle notice.** Each client shows one toast, `rejectionNotice`: "Couldn’t save a change to “Title”" for one task, project, section, or label, "Couldn’t save a change" for other kinds, and "Couldn’t save changes to N items" for several. The name is what the device showed before the snapshot replaced it. The server logs each rejection with its reason.
  - **Malformed ops.** No op can fail the request, however malformed: it is rejected alone, by its `opId`. An entry without a string `opId` cannot be named, so the server skips it; neither client can store one. Only a broken envelope is still a `400`, which only a client bug can build. On the web, a stored op that no longer validates would fail the whole `procrastimate` document on load and wipe it, so `dropInvalidOps` in `app-web/src/lib/persistence.ts` drops that op and sets the cursor to `0`, and the next sync's snapshot puts its entity back. iOS keeps such an op (`SyncOp` holds fields as JSON values), sends it, and the server rejects it like any other. Its request no longer runs each op through the contract's validating decoder, which used to throw and stop the sync before it was sent.
- **The handler.** `server/src/account/router.ts` authenticates the device, then `server/src/account/sync.ts` in one storage transaction loads every entity, runs `applyPush` with the log answering whether an op was applied, writes the entities that changed, and appends every returned log entry, empty ones included. The server's clock is not stored: it only has to stay ahead of every field clock, so each request rebuilds it from them, and `tick` keeps it ahead of the wall time.
- **Paging.** A response carries at most 1,000 changes, and its `cursor` is the last one it carries. A client that gets a full page syncs again right away. Before the last page, `acked` lists only the ops whose rows the page carries, so the client never drops an op from its outbox while applying older rows without it. Its retry dedupes, and the last page acks everything. A cursor past the end of the log, as after the in-memory dev server restarts, gets the snapshot like cursor `0`, so the client starts over instead of waiting for rows that will never come.
- **Local state.** The client stores its snapshot plus a `sync` section with its device id, cursor, and outbox: in the `procrastimate` `localStorage` document on the web, and in the same JSON document on iOS. After a response, the client drops the acked ops, applies `changes` in order, then reapplies what is still in the outbox, so edits made while the request was in flight stay visible. The server reports what actually won on the next sync.
- **When to sync.** Sync is always on. On launch, on focus or foreground, when the network returns, one second after a commit, and every minute while visible. On iOS also from the `BGAppRefreshTask` that refills notifications. A failed sync keeps the outbox and retries on the next trigger. While visible, the client also syncs when the realtime socket reports a cursor past its own (see Realtime nudge). Nothing about sync is shown except the notice for a rejected op.
- **Deterministic order everywhere.** Top-level task lists use the store's array order today, and sync must not depend on arrival order. Clients keep tasks sorted by `createdAt` then `id`, which matches the current insertion order because a new task's `createdAt` is always past the newest task's (see [Persistence](persistence.md)).

## Realtime nudge

- **The socket only says "sync now".** `GET /api/sync/socket` upgrades to a WebSocket on the `Account` object. After any request that moved the log, the object sends `{ cursor }`, the new head, to every open socket, the sender's included. It never carries changes, so the protocol, paging, and outbox stay in `POST /api/sync`, and a lost nudge only delays a sync until the next trigger. Contracts are in `shared/sync/protocol.ts`; `server/src/account/realtime.ts` holds the route and the nudge and revoke logic.
- **Hibernation keeps it free.** On the Worker the object accepts sockets through the hibernation API, tagged with the device id, so it can be evicted while they stay open and idle sockets cost no duration. The runtime answers the client's `ping` with `pong` itself (`setWebSocketAutoResponse`) without waking the object. Only nudges and new connections count as Durable Object requests, which is far below the free plan's daily limit for one user.
- **Authenticated by the session.** The web upgrade sends the cookie and `device.<id>` as a subprotocol next to `procrastimate.sync`, which the server echoes. iOS sends `Authorization: Bearer` and `x-procrastimate-device`. A query string would put the credential in logs.
- **A rejected token registers again.** A `401` drops the token and registers a new one, with no notice. There is no device list and no revoke screen.
- **One handler, two hosts.** The nudge hook sits in `accountHandler`, which compares the log head before and after each route. A `SocketHost` accepts upgrades and lists sockets: the hibernation API on the Worker, and Bun's WebSocket server in `server/src/dev-server.ts` for local dev and Playwright. Vite proxies `/api` with `ws: true`.
- **The web client.** `sync.svelte.ts` opens the socket while visible, closes it when hidden, and opens it again on focus and `online`. On a nudge it waits for any sync already in flight, then syncs only when the cursor is past its own. It pings every 30 seconds and drops a socket that answered nothing since the last ping. A dropped socket reconnects after 1 second, doubling to a minute. Every open syncs once, since a nudge sent before the handshake is lost.

## Conflicts

Every field is last-writer-wins by HLC. Different fields from different devices merge, so renaming on one device while completing on the other keeps both. After applying a push, the server runs `fixups`, which writes any repair as server ops into the log like any other change. Clients therefore converge on exactly what the server holds.

- **Delete vs edit: delete wins.** `deleted` is a field of its own. Editing other fields never clears it, so an edit made offline to a task deleted elsewhere is dropped. While an entity is deleted, only `deleted` can change, so dropped edits are not stored either. Undo of delete writes `deleted: false` with a newer clock and restores the task.
- **A delete that loses comes back.** Every device must converge on the server, including the one whose op lost. A delete or undelete is the one op whose device shows the opposite of what can win: a device that deleted an entity no longer has it, so the only rows that could fix it are full ones. When device A deletes a project offline, device B deletes it and undoes, and device C renames it after B's undo, B's undelete wins `deleted` but not `name`. Its row was partial, since the project never stopped being live on the server, and A's own delete won nothing, so its row was empty. A skipped the partial row and kept the project gone for good. Now the losing delete's row carries every field, and a losing undelete's row carries `deleted: true`. Such a row changes nothing on the server, so it records no editing app. The fuzz found this only when an unrelated change shifted its random sequence.
- **Complete vs edit.** `completedAt`, `due`, and `reminders` are separate fields from `title`, `notes`, and the rest, so both changes survive.
- **Recurring task completed on two devices.** Completing sends the resulting `due` and `reminders`, not "advance by one". Two devices that complete the same occurrence send the same next date, so the task advances once. If one device completed it twice offline, the later write wins, so it never advances more than one device did.
- **Reorder.** `order` becomes a fractional position. Moving a subtask writes only that task's `order`: the midpoint of its new neighbors, or one more or less than the last or first. Siblings sort by `order`, then `createdAt`, then `id`, so a tie from two concurrent moves still settles the same way everywhere. When a gap gets below `1e-9`, the move renumbers its siblings instead, which is rare. Sections and projects move the same way (`moveOrders` in `shared/sync/order.ts`).
- **A field added to existing rows starts at its default, with no clock.** A row exposes only the fields its clocks name, so a migration that wrote real values into old rows would never reach a client's cached copy, and the server and clients would disagree. Projects gained `order` this way: every old project sits at 0, so ties fall back to `createdAt` and the list keeps its creation order. The first move renumbers the projects it lands between. Old documents, server rows, and patches from older builds without the field load it at 0 on both clients.
- **Subtask whose parent was deleted.** A subtask added offline under a task deleted elsewhere was never seen by the deleter, so `fixups` keeps it and makes it top level, the same rule as `detachOrphans`. Subtasks the deleter did know about are tombstoned by its own diff.
- **Open subtask under a completed parent.** A subtask added or reopened offline under a parent completed elsewhere reopens the parent and its completed ancestors, like `addTask` and `reopenTask` do locally.
- **Subtask project.** A subtask always takes its root's project. If a move and a parent change race, `fixups` rewrites the subtask's `projectId` to the root's.
- **Project deleted while tasks moved into it.** Deleting a project tombstones it and every task its device saw in it. A task moved into it or added to it on another device lands in Inbox (`projectId: null`). A task that device moved out of it is still deleted, because the deleter saw it there; that loss is accepted.
- **Sections.** A section of a deleted project is deleted, a task in a deleted section or a section of another project lands in no section of its own project, and sections with the same source key or the same name in one project merge into the oldest. See [Sections](sections.md).
- **Label deleted while being added or renamed.** Delete wins over the rename. `fixups` removes a deleted label's id from every task's `labelIds`.
- **Arrays are single fields.** `labelIds` and `reminders` are last-writer-wins as a whole. Two devices adding different labels to the same task offline keep one device's set. Per-item merging is not worth the complexity for one user.
- **Duplicate names.** Two live labels whose names match ignoring case merge into the one with the lowest `createdAt`, then `id`. Tasks get the survivor's id and the other is tombstoned. Projects merge the same way, moving their tasks. This also covers a rename on one device that collides with a create on another. A project or label screen whose record merges away follows its last-seen name to the survivor, replacing the route on iOS and the URL on the web, and leaves for Inbox when nothing matches, so nobody lands on a dead screen.
- **Todoist imported on two devices.** Live tasks or projects with the same `sourceKey` merge into the lowest `createdAt`, then `id`. Subtasks of the dropped copy get the survivor as their parent. The import still runs locally, and its tasks sync as ordinary creates.

## First sync

- **Every install syncs.** The local document always has a `sync` section. A new section starts with `seed: true` and an outbox holding only the device's zone. The first sync sends `cursor: 0` without the local tasks, projects, or labels, and gets the server's snapshot. `seedPatches` then queues only what the local data adds to it: entities the server lacks and fields it holds differently. Nothing the server has is removed, and its settings stay, so a new install never resets another device's dictation choice. A first snapshot with a newer `epoch` means the account was wiped after this copy was made, so the device seeds nothing and keeps the server's state. Otherwise the client syncs again at once to upload what it queued. A device whose tasks the server already has therefore pushes no task ops, and the log does not record them as created again. Ids are UUIDs, so two devices that each have local data simply add up. `fixups` then merges what they share: Todoist imports by source key, and labels and projects by name. Two hand-typed tasks with the same title on two devices stay two tasks.
- **The local store is the UI.** The web keeps the `procrastimate` document in `localStorage`, because reads and writes stay synchronous and the screen already renders from it. iOS keeps the same JSON file. Neither client waits on the server to show a change.
- **Delete all data.** Settings wipes tasks, projects, and labels locally, clears the outbox, and sends `reset` so the server wipes them too and bumps `epoch`. Edits made after the wipe and before that sync travel with `reset` and apply after it. Other devices drop their outbox when the epoch changes.

## The web client

- **One loop, one module.** `app-web/src/lib/sync.svelte.ts` owns the triggers. Only one sync runs at a time, and a trigger during one queues one more right after it. A response with a full page of changes syncs again at once. A `401` clears the session and shows sign-in. A network failure keeps the outbox for the next trigger. There is no sync status in the UI.
- **The store records, the loop sends.** Every store command diffs its before and after into the outbox and tells the loop, which syncs one second later. The loop sends the whole outbox and hands the response back to the store, which runs `applyResponse`.
- **The device's own zone.** The client's settings record holds the zone this device last wrote, kept in its `sync` section, so ordinary diffs never touch `timeZone`. The first sync writes the device's zone, and a later sync that finds the zone changed writes the new one first. `dictation` lives in that same section. Changing it writes one settings op, and a sync applies the server's choice back onto it.
- **The clock persists.** The `sync` section keeps the last clock the device issued or saw, so a reload never issues a clock below one it has seen. It also keeps `epoch` and `reset`.

## Auth

Sign-in, sessions, and per-user data are in [Auth](auth.md). `server/src/auth.ts` turns a checked session plus a device id into the device row.

## Notifications

- **The server computes the Web Push schedule.** The account knows every task, so after each push it recomputes pending notifications from `notificationTimes` in the account's `timeZone` and arms one alarm for the earliest. It sends to every subscribed web device. Subscriptions register for the signed-in device.
- **iOS keeps local notifications.** They are recomputed from the synced state after every pull, so iOS needs no APNs.
- **Time zones.** The server cannot use the process zone, so `shared/zoned-time.ts` turns a `DateKey` and `TimeOfDay` into epoch milliseconds in a named zone with `Intl`, and `notificationTimes` and `upcomingNotifications` take an optional zone. Clients pass none and keep the device zone. The details are in [Push notifications](push-notifications.md).

## Testing

- **Unit tests** cover each rule in `shared/sync/` with the cases above. `server/src/account/realtime.test.ts` runs the dev server with real sockets for auth, the nudge, and revoke, and checks the Durable Object host against a stand-in for the hibernation API.
- **Convergence fuzz.** `shared/sync/converge.test.ts` simulates two or three clients and the server with a seeded random generator. Clients apply random commands (add, edit, complete, reopen, move, delete, undo, rename, label, import), go offline, and sync in random interleavings. After a final sync of everyone, every replica must equal the server, and the invariants must hold: no orphans, no open task under a completed one, subtasks in their root's project, unique label and project names, and unique source keys. Undo comes both as the generic restore of the last command before a sync and as the app's `undelete` of the last delete, which survives syncs like the toast does. Each client must also equal the server right after each of its syncs, so a divergence fails at the step that caused it rather than only at the end, where a later delete could hide it. CI runs a fixed set of seeds. `SYNC_SEEDS=<n>` runs more locally, and a failing seed prints a replayable log.
- **Seeds find races only by luck.** A race that needs three devices in one order hides from random seeds. The losing-delete race above showed up in 1 of 1,000 seeds, and adding a command moved it between seeds. So the same file also runs every interleaving of short scripts on three devices, each ending in a sync. The world is a project with a section, a saved place, an unused label, and one task in the section at the place. The scripts delete the project, the section, or the place, and undo before or after a sync, as the toast does. The other scripts rename each of them, edit the task, label or unlabel it, or move it out of its section. Interleavings that reach the same world, with clocks compared only by order, run their rest once. `SYNC_INTERLEAVINGS=all` checks all 816 casts of three scripts, about 1.1 million interleavings, in about 16 seconds. Add a script there when a new op can race on one entity. [Testing](testing.md) says which casts `bun test` runs.
- **Swift vectors.** iOS only runs the client half: the HLC, `diff`, `applyChanges`, the outbox's `enqueue`, `seedPatches`, and `settle` and `rejectionNotice` for rejected ops. `shared/sync/outbox.test.ts` records `enqueue`, `seedPatches`, `settle`, and `rejectionNotice` into `shared/vectors/sync.json` through `recorded('sync', …)`, the same as the other modules (see [iOS app](ios.md)), so the Swift port must produce identical ops and patches. The merge and `fixups` run only on the server, so Swift never ports them.
- **End to end.** `app-web/e2e/sync.e2e.ts` opens two browser contexts as two devices and covers propagate, realtime, offline, reconnect, a rejected op, conflict, and delete-all from the [feature map](../../.cursor/skills/verify-procrastimate/features/offline-sync.md). The Playwright config starts the Bun API next to Vite, or `wrangler dev` with `E2E_WORKER=1`, so it runs against the real `POST /api/sync`. Going offline blocks only that device's `/api/sync` requests. Each test has its own account (see [Testing](testing.md)), and the two contexts in one test share it.
