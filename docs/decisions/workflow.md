# Workflow

- **One PR per thread, never stacked.** Each thread ships one PR off `master`.
- **Doc-only changes go straight to `master`.** A change that touches only docs (`docs/`, `AGENTS.md` files, the verify skill's feature map) is committed and pushed to `master` with no PR. Anything that touches code, config, or scripts still ships as a PR.
- **Fold small follow-ups in.** Before starting a new thread for new work, consider folding it into an existing open PR or thread when it touches the same area or files or is a small follow-up. Start a new thread only when the work is genuinely independent.
- **Rebase only on a real conflict.** Rebase a PR only when GitHub reports a conflict. PR CI already tests the merge with `master`, so do not rebase every open PR after each merge.
- **Decisions live one file per area.** Each area of `docs/decisions/` is its own file, so parallel PRs don't conflict. Record a decision in the matching area file, and add a new file when no area fits.
- **Workers build features themselves.** Never hand the whole build to a helper sub-agent that can't receive messages.
- **Run only the relevant tests locally.** Run the unit and e2e specs that cover the change. The full suite runs in CI.
- **iOS CI runs only where the app can change.** The macOS `core` (`swift test`) and `app` (API URL and build checks) jobs in `.github/workflows/ios.yml` run on a pull request whose diff touches `app-ios/`, `shared/`, the Swift generator, or the other inputs its `changes` job lists, and on a manual `workflow_dispatch`. They skip `master`, since TestFlight archives every such merge. The Linux `core-linux` job runs `swift test` on every pull request and push. A job skipped by `if` reports success, so a required check of that name does not block the merge.
- **Screenshots only for UI changes.** Attach 2 to 4.

## Clients

- **Every feature is built for all clients at once.** Web and iOS today. A feature request is planned and built for every client where it makes sense, not for one client with the others catching up later.
- **Each feature plan names its clients.** It lists the target clients and says why any are excluded. Some clients get a subset; a future Apple Watch app, for example, gets only what suits a watch.
- **Web and iOS slices are planned together.** Shared logic lands once in `shared/` with its Swift port through the test vectors. Each UI slice has a twin on the other client. Automated UI pairs are not part of the suite; parsers, vectors, and the auth and sync smoke are ([Testing](testing.md)). The twins may run as parallel PRs.

## Parallel agents

- **Every agent worktree is sandboxed by script.** `scripts/setup-worktree.ts [branch]` renames the worktree's branch to its final name and gives it its own ports (a git-ignored `.env.override` that env-manager applies to every target), its own SQLite database file in `.data/` (see [Dev hosting](dev-hosting.md)), and a git-ignored `./sim` bound to its own simulator. `scripts/teardown-worktree.ts <worktree>` removes all of it from the main checkout once the PR is merged, and `scripts/worktree-gc.ts` reclaims what a vanished worktree left behind. The simulator is named after the stable worktree directory, and a rerun keeps the name recorded in `./sim`, and the database after the worktree directory, because T3 Code renames a thread's branch seconds after its setup starts. T3 runs the script as the project's blocking setup script (`async: false`), so an agent starts in a ready worktree. A permission alert raised before the launcher granted permissions survives later grants and relaunches, so `./sim` reboots its own simulator once if it is booted without the marker file in its data directory. Every launch after that is already granted. Rules that a script can enforce live in the script, not in prompts.
- **Agent simulators boot lazily, run headless, and are reclaimed by script.** Every booted simulator slows every parallel job, so an agent proves a change with `app-ios/scripts/test` and `./sim build` (which compiles for its simulator without booting it) and boots one only through `./sim test` or `./sim` to look at the app. `./sim` boots its simulator without opening Device Hub unless given `--show`. Every `./sim` command writes the worktree's path into the simulator's data directory, and that file's mtime is the simulator's last use. `scripts/worktree-gc.ts` shuts down a claimed simulator unused for 15 minutes that no running process names, deletes one whose worktree is gone, and deletes DerivedData of removed checkouts. A custom simctl device set would keep agent simulators out of Device Hub entirely, but `xcodebuild` can't see devices in one, so UI tests couldn't run there.
- **Throwaway iOS UI tests run through `./sim test`.** The repo keeps no XCUITest target ([Testing](testing.md)). `./sim test <file.swift>` builds and installs the app, generates a host app and UI test bundle under the worktree's git-ignored `app-ios/DerivedData/uitest`, runs the given files against the installed app under a time limit, and stops the simulator. AXe taps and CGEvent clicks don't reach the simulator on the agent Mac; XCUITest does.
- **PRs wait on one script.** `scripts/pr-ship.ts [--merge]` waits for CI and for Codex's first review, lists failing checks and unresolved review threads, reports a conflict with master, and merges when green. It exits before the 600-second tool limit with a code that names the next step, printed as its last line so a pipe that swallows the status still shows it, so an agent reruns it instead of writing `sleep` loops a hook blocks. Codex reviews only when a PR opens, and its summary's unresolved-findings flag never clears, so findings come from the review threads.
- **CI installs Playwright's apt packages from a cache.** The e2e job keeps every deb apt downloads in `~/.cache/apt-archives`, restored before `playwright install-deps` and saved right after it, keyed on the runner image and the Playwright version, so a warm run installs from disk. An install that times out still saves what it fetched under a per-run key that the restore prefix matches, so a rerun on a slow mirror resumes instead of starting over. The install and browser steps each have a 5-minute limit. The Ubuntu mirror sometimes took minutes per package, and one run spent the job's whole 25 minutes there before any test ran.
- **CI runs no env-manager.** The CI workflow sets the few schema defaults the env readers require (`API_URL`, `API_PORT`, `CLIENT_PORT`) as plain workflow env, and the deploy's credentials are repository secrets that `bun run secrets:github` writes. A global `bun add -g` of env-manager resolved its AWS SDK dependencies with no lockfile on every run, so an AWS release npm had not finished serving failed the install of unrelated PRs.
- **Git hooks are never skipped.** A Claude Code hook in `.claude/settings.json` blocks `--no-verify` and lefthook overrides. A failing hook gets its cause fixed; a flaky test is a bad test.

## Worktree storage

- T3 generates a descriptive branch name concurrently with setup. Never pass a branch name to setup in a T3-owned worktree or rename its branch from a setup/teardown hook. Resource identity follows the worktree directory, not the branch name.
- On this Mac, T3 runs `worktree-cache-clean` from the shared scripts repository when a thread settles. It removes only wholly ignored Xcode `DerivedData` directories in linked worktrees, independently of whole-worktree retention. It preserves source, uncommitted files, env files, and databases, and skips worktrees with running T3 turns or open build files. Main checkouts are never cleaned. The next build regenerates the output.
- Native launchers reuse `DerivedData/SourcePackages` within each checkout; device and simulator compilation outputs remain separate. Do not create ad hoc `check`/`test` package caches: pass `-clonedSourcePackagesDirPath app-ios/DerivedData/SourcePackages` when running `xcodebuild` from the repository root. Each worktree keeps its own package directory so parallel tasks do not mutate another checkout's dependencies.
- Branch metadata mismatches can still block T3's whole-worktree cleanup. Repair ownership through T3 rather than force-removing a potentially live checkout; build-cache cleanup does not depend on the saved branch name.
