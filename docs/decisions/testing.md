# Testing

- **What the suite is for.** Tests cover parsing (quick add and the Ramble grammar), the shared functions recorded as TS-to-Swift vectors, the generated API and Swift types, a few real regressions, and a short end-to-end smoke. A test that only checks wiring, a mock, a framework, or a library, or that repeats a case already in a parser table or a vector, does not stay.
- **What earns an end-to-end test.** A browser test costs a sign-up, a boot, and often a second device, and each one has failed CI for timing reasons a unit test never meets. So a step gets one only when a browser is the only place it can break: the sync loop across devices, the offline shell, a gesture, focus, or a paint, or a real regression that lived in the page. Logic behind a screen, such as which options a menu offers, a grace period, or a backoff, moves into a plain module with a unit test, and the component calls it. A step that shares a setup with an existing test joins that test instead of signing up again, so one test may walk several steps of a feature, and its title names them.
- **Parsers.** Quick add cases live in `shared/quick-add.test.ts` as tables. Ramble's grammar is the corpus in `shared/fixtures/ramble-corpus.ts`, run from `shared/ramble.test.ts`. The one ICU-versus-JavaScript difference that vectors cannot record is `QuickAddTests` in `app-ios`.
- **Vectors and generated types.** `bun run vectors` records every call to a `recorded` function into `shared/vectors/*.json`. The iOS `VectorTests` replay them. `APITests` checks the generated Swift types: a one-character highlight decodes, and an optional field refuses `null` as zod does. Generated files are git-ignored and rebuilt before every run, so none can be stale.
- **Server tests run on PGlite.** `server/src/test-app.ts` boots Postgres compiled to WebAssembly in the test process, runs the real migrations, and serves the same `handle` the Worker does, so a test signs up through Better Auth and calls routes the way clients do. Each `testApp()` is a fresh database loaded from one migrated snapshot, and a file shares one across its tests. A fresh `new PGlite()` runs initdb, which took 3 to 7 s with ten agent worktrees loading the Mac (load average about 800), past the 5 s hook limit, while the migrations themselves took 0.2 s. So `scripts/pglite-snapshot.ts`, preloaded by `bun test`, migrates one database and saves its data directory to `server/src/db/generated/pglite-<hash>.tar.gz`, the hash covering the migrations and the PGlite version, and `testApp()` loads it in 0.2 to 1.4 s on the same machine. The same run saves the database as initdb left it, before any migration, as `pglite-empty-<hash>.tar.gz`, which the tests of `migrate` itself load. A test that shares its file's database seeds what it reads, its own person, task, share, or subscription, so it passes run alone with `-t` as well as after the tests above it; seven once read what an earlier test left behind. `scripts/test-guard.ts` refuses to start `bun test` when `DATABASE_URL` points anywhere but the local Docker Postgres, and `scripts/test-guard.test.ts` locks that rule; the tests themselves never read it. Ramble's socket tests wait for the message they expect, such as `started` or `ended`, never a sleep: a 20 ms sleep for `ended` can miss it under load, and the daily cap test then loops past the cap until it times out. A session sends `ended` only after its seconds are stored, so a test reads the usage table right after it.
- **Unit tests.** `bun test`, colocated as `*.test.ts`. The natural-language parser and the Todoist import are tested with a fixed clock. `scripts/test-timezone.ts`, preloaded first, runs every test in `America/New_York`, the zone `bun run vectors` records in, since a shell in UTC never crosses a daylight-saving change and the DST cases then prove nothing. Theme contrast is tested against the real tokens in `index.css`.
- **End to end.** Playwright runs every `app-web/e2e/*.e2e.ts` spec in the `desktop` project (Chromium, 1280×800). The `mobile` project runs again, in WebKit at 393×852, only the tests tagged `{ tag: '@webkit' }`, since the local database is SQLite in WebAssembly on IndexedDB, which WebKit runs its own way. The tag goes on a test whose outcome the engine decides: the sync loop, the commit window before a reload, an account switch's clear, image storage, and the origin of sync requests. Everything else, sharing's UI and every server-side rule included, runs in Chromium only, since Linux WebKit on one worker costs several times as much per test. Each test signs up a new account, its email suffixed per worker process, since the database outlives the run. By default it builds the client and starts the Bun API on port 6131 next to `vite preview` on 6130, against the worktree's database and PowerSync container, the same ones `bun run start` uses (`DATABASE_URL` and `POWERSYNC_URL` in `.env.override`, provisioned by `scripts/setup-worktree.ts`, and by `scripts/ci-stack.ts` in CI), so the sync tests run the real PowerSync loop. Better Auth's rate limit is off for those servers (`AUTH_RATE_LIMIT=off`). With `E2E_WORKER=1` the suite runs against `wrangler dev` through `bun scripts/wrangler-dev.ts`, which points the Hyperdrive binding at the same database; CI runs both projects that way, with Chromium and WebKit installed: desktop on two workers, then WebKit on one, because Linux WebKit on CI's two cores rendered so slowly beside a second worker that the longest specs crossed their limits in 3 of 3 runs, a different spec each time; on one worker it went green twice in a row. Hooks never run these tests.
- **Slow setup runs before the clock starts.** A test, hook, or web server's time limit covers only the work it exists to check. Setup that grows with machine load, such as initdb or a client build, runs where no limit applies: a `bun test` preload or a step of the `test:e2e` script. A limit that still fails under load is fixed by making the step cheaper or moving it out, never by retrying or sleeping. Measure a change against the old path in the same conditions, interleaving the two runs, since the load on this Mac swings by hundreds within a minute.
- **End to end runs a build, never the Vite dev server.** The dev server serves the app as about 600 separate modules and transforms each one on first request. Every test opens a fresh browser context with an empty cache, so each test's first page load fetched all of them. Eight workers starting at once on a Mac shared with other agents' Xcode builds took 5 s to render the sign-in screen, which is exactly the assertion timeout, and specs failed with element-not-found on their first heading. At the time, a `30_000` timeout on the `app` fixture's first heading hid that delay. CI never saw it, because it tests the Worker bundle (`E2E_WORKER=1`). `bun run test:e2e` now runs `vite build` (about 2 s, more under load) through `app-web/scripts/e2e-build.ts` before Playwright starts, so the build never counts against the 60 s web server limit it once missed, and the local servers serve it with `vite preview`, which applies the same `/api` proxy. The first render takes about 140 ms in 41 requests, and the full suite passes at 8 workers at a load average above 500. The boot after it is still slow in WebKit, as the next point records. The dev server's Svelte dev-mode checks are lost, but CI never ran them either.
- **A page boot is setup with its own limit.** A page shows its first heading only once it has opened its local database. A fresh WebKit context builds SQLite on IndexedDB from nothing: 0.3 to 0.5 s with one worker, but 2 to 15 s with eight WebKit workers at once on the shared Mac, while Chromium takes 1.6 s. With the default 5 s wait, the images, sync, and single-origin specs failed in the `mobile` project at 8 workers on their first heading. So every load and reload goes through `boot` in `e2e/fixtures.ts`: the `app` fixture, `devices.open()`, and `App.reload()`. It waits up to `BOOT_TIMEOUT` (30 s) for the first heading, then adds the time the boot took to the test's limit, so a slow boot never eats the test's budget. A spec reloads with `app.reload()`, never `page.reload()` followed by a default wait. The exceptions are a spec that times the reload itself (`offline-shell`), and a page without the app's heading (a public link).
- **End-to-end determinism.** A spec waits for its condition, never a sleep or a retry. Before any test starts, `e2e/global-setup.ts` signs up one account and waits, up to 120 s, until PowerSync streams that account's `settings` row through the app's origin. PowerSync exits whenever the shared Postgres restarts, and a restarted one answers its probes and completes a first checkpoint before its replication reaches the newest writes. The app holds its first settings write until that row arrives, so on a first run every spec that seeds through `App.pushFromOtherDevice` timed out at its 15 s wait for `pending()` to reach 0. The `context` fixture fails a test on any uncaught error in its pages, so a crash in a handler cannot hide behind a passing assertion. The pinned clock catches an error thrown in a timer and logs it with `console.error(error)`, so `watchPageErrors` also counts a console error whose first argument is an Error; the app never logs one itself. `e2e/page-errors.e2e.ts` proves both paths. The `app` fixture waits for `document.fonts.ready`, since Linux CI's fallback font wraps text wider until Google Sans Flex arrives. A title that must be unique comes from `unique()` in `e2e/fixtures.ts`, whose suffix starts with a letter so quick add cannot parse it as a token. A spec clicks only what is fully in view when the scroll position matters, since Playwright scrolls a clipped target into view first. `App.row()` skips a row that is animating out, which `leaving` marks `aria-hidden`, so a row that moves between day sections resolves to one element mid-animation and a spec asserts on it directly. `App.settle()` waits for running animations. A spec switches views with `App.go()`, which waits for the new heading, before it opens `App.listMenu()`: the menu's name matches every view, and a click right after `nav().click()` opened the old view's `No date actions` while the place view was still loading, so `Save place` never appeared. A field the web cannot set, such as an iOS place, is seeded with `App.pushFromOtherDevice`, which waits for the page's writes to reach the server, patches the row through `/api/upload` as another device of the same account, and waits until PowerSync streams it back. Specs read the page's sync state through `window.procrastimate` (`pending()`, `taskId`, `entity`). Offline is `goOffline` in `e2e/fixtures.ts`: `context.setOffline(true)` plus refusing the sync routes, since Playwright never sees the stream Chromium runs in a shared worker. Extra contexts come from the `devices` fixture (`devices.open()` for another browser of the account, `{ person }` for another account), which copies the project's device, signs in, opens a view, and closes them with the test. Every context blocks service workers (`serviceWorkers: 'block'` in the config), because WebKit sends a page's requests through the worker where `context.route` does not see them; the one spec of the offline shell allows them. A spec that needs many rows seeds them through `App.seed`, whole rows posted as another device's upload, rather than typing each. A phone flow runs in the same project under `test.use({ viewport: { width: 393, height: 852 }, hasTouch: true, isMobile: true })`; below 768 px `App.openQuickAdd()` uses the floating `Quick add` button, and `App.openNavigation()` opens the drawer. `App.addCreating()` creates each unknown `#project` and `@label` from its chip before saving, and `App.closeDetails()` uses `Close`, since Escape in a details field leaves the sheet open. A spec that finds a real app bug keeps its assertion in a `test.fixme` named for the behavior, and the feature map says the step is skipped until the fix lands.
- **Hooks.** Lefthook's pre-commit and pre-push run `scripts/test-changed.ts` on the changed files: the colocated `*.test.ts` and any unit test that imports the changed module. `swift test` runs only when `app-ios` changed, and is skipped when `swift` is not installed. Web end-to-end stays in CI. The hooks start the script with `bun --no-env-file`: `bun test` never loads `.env.local`, but a plain `bun` script does and its child `bun test` inherits it, which pointed Better Auth at the dev database (Turso at the time) and its shared sign-up rate limit.
- **iOS.** `swift test` in `app-ios/` runs the `Core` unit tests, including `VectorTests`, on macOS and on the Linux `core-linux` job. There is no XCUITest target. Agents verify iOS UI with throwaway XCUITests through `./sim test` ([Workflow](workflow.md)), which never enter the repo. The macOS `core` and `app` jobs run on pull requests that can change the app and on a manual dispatch. `app` checks the Debug and Release API URLs and the privacy manifest. See [iOS app](ios.md).
- **Linux Swift builds with the native build system.** `core-linux` runs `swift test --build-system native` in the pinned `swift:6.4.1` image. SwiftPM 6.4 made Swift Build the default backend, and on Linux its planner segfaults (exit 139) in about one run in 60: three of roughly 190 `core-linux` jobs from October 14 to 16, 2026. Every crash had the same crashing thread, libdispatch's manager thread in `_dispatch_event_loop_drain`, inside `swift-package` at `Planning` or `Pre-planning`, before any of our code compiled. The `SpecRegistry`, `LazyCache`, and `completeTaskWithClosure` frames are on other planner threads that were mid-work. This is [swiftlang/swift-build#1786](https://github.com/swiftlang/swift-build/issues/1786), a libdispatch use-after-free that Swift Build reaches by reading subprocess output with `DispatchIO`. It also hits 6.4.0 and the Ubuntu 24.04 image, so changing the patch or the base image does not avoid it. Our code is not involved: the crash comes before it compiles, and five Thread Sanitizer runs of the `Core` tests report nothing. 300 clean builds in arm64 Docker did not reproduce the crash. The native backend uses the same compiler and runs the same tests, and `swift:6.2` used it with no crash. The tag is pinned so the image cannot change under the job unnoticed. On October 26, 2026, a CI probe of clean `swift build --build-tests` runs on the default backend crashed 13 times in 1,700 on `swift:6.4.1`, every time on a `DispatchWorker` thread in `_dispatch_event_loop_drain`, and 0 times in 1,150 on the `nightly-main-noble` 6.5-dev snapshot. Swift Build's `main` reads subprocess output through swift-subprocess, which polls with its own epoll instead of `DispatchIO`, while `release/6.4.x` still uses `DispatchIO`. So the fix should ship with 6.5, but no release has it, and a nightly compiler is too unstable and slow to pin. The weekly `Swift Build crash watch` workflow (`.github/workflows/swift-build-1786.yml`) watches for the fix. It fails when #1786 closes, or when a Swift release newer than the pinned tag finishes 500 clean default-backend builds without a crash. Run it by hand with `force` to stress the pinned release. When it fails, bump the tag, drop the flag, and delete the watch. SwiftPM has deprecated `native`; when a release removes it, the job fails loudly. The job never retries, since a retry would also hide a real crash. Local `swift test` keeps the default backend, so a rare crash there needs a rerun.
- **Feature map.** `.cursor/skills/verify-procrastimate/features/` describes each user-facing feature and how to drive it by hand. Keep it in sync with every change. A step may cite the test that proves it, and `scripts/feature-map-citations.test.ts`, part of `bun test`, fails when a cited spec file, test title, Swift test, Playwright project, or saved screenshot does not exist. Its message lists each stale line; point it at the real test, write the test, or drop the citation and keep the step manual. Agents trust these citations, so a stale one sends them to a test that proves nothing.
