# Push notifications

- **Real Web Push.** Due times and reminders reach Stefan as system notifications while the app is closed, through a service worker and the browser's push service. On iPhone this needs the app added to the Home Screen (iOS 16.4 or later), because Safari only gives Push to Home Screen web apps.
- **The server computes the schedule from the synced tasks.** After every write to a space, a guest's included, `replan` in `server/src/push.ts` recomputes each subscribed install's pending notifications from the space's tasks with the shared `upcomingNotifications`, so due times, reminders, and event moments notify the same way on every client, and stores the earliest as the row's `next_at`. Place triggers are not scheduled here; only iOS can see arriving and leaving (see [Places and events](places-and-events.md)). Completing, editing, deleting, and restoring a task need no special cancel path: the next replan drops the old times. A recurring task schedules its next occurrence once completing moves its due date. A change made on iOS or on another browser reaches every subscribed browser without that browser being open.
- **Times are in the synced time zone.** The server cannot use its process zone, so `shared/zoned-time.ts` turns a `DateKey` and `TimeOfDay` into epoch milliseconds in the account's `timeZone` with `Intl`, and names the day a moment falls on for bodies such as `Due Tomorrow at 5:00 PM`. A time skipped by a daylight saving jump lands after it and a repeated one takes the first, like `Date` does locally. An unknown or missing zone falls back to UTC. Clients keep the device zone.
- **Web Push is per install.** `PUT /api/push/subscription` registers the subscription for the install named by `x-procrastimate-device`, a client-made id kept on the device and sent only on the push routes and Ramble. One endpoint belongs to one install, so a browser that registers again as a new install replaces its old entry and keeps its pending notifications when the endpoint is unchanged. A new subscription is planned at once from the account's tasks, since the cron only reads subscriptions with a next notification. `DELETE` removes it, `GET /api/push/schedule` shows what the server will deliver, and `POST /api/push/test` sends one notification to a subscription the caller provides. All need a signed-in human; the public key route stays open.
- **A cron every minute, not an alarm.** The `push` table holds each install's subscription, pending notifications, when the cron last delivered to it, and `next_at`, indexed. The Worker's `* * * * *` Cron Trigger runs `deliverDue`: it selects the users with a `next_at` at or before now, sends each install what is due, then settles in a transaction under the space's advisory lock against the rows stored now, so an upload's replan landing meanwhile is not lost, and replans from the space's current tasks. The `Account` object and its single alarm are gone with the sync engine (see [Sync](sync.md)); a minute's granularity is what the alarm gave too, since it fired on the next whole minute.
- **Dedup.** A future moment is pending until the cron delivers it, and never again after. A past moment stays pending only while it already was, as a retry or for a cron tick that has not run yet, so making a task due a minute ago never notifies. Notifications more than ten minutes stale are dropped. Each notification's tag is the task and moment, so the OS replaces instead of stacking a repeat. While push is on, the open app shows only the toast and leaves the system notification to the push.
- **Failures are per install.** A 404 or 410 from the push service drops that install's subscription. A 429, a 5xx, or no answer keeps that install's notification and retries a minute later, for up to ten minutes, without resending to installs that got it. Completing the task during a retry stops it. A send is given up after ten seconds (`PUSH_TIMEOUT_MS`) and counts as no answer, so a hanging push service cannot hold one run past the next minute's, which would read the same unsettled notifications and send them again.
- **VAPID keys live in env-manager.** `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (base64url P-256) are kept in env-manager `prod` and pushed to the Worker with `bun run secrets:push`, like every other secret (see [Production hosting](production-hosting.md)). `secrets:push` refuses half a pair. The browser reads the public key from `GET /api/push/key`. To rotate, put a new pair from `generateVapidKeys()` in env-manager and push it. On its next launch each device sees its subscription was made for another key and, with permission already granted, subscribes again with the new key and registers it, with no prompt. Local `wrangler dev` reads an ignored `.dev.vars`, written from env-manager `dev` or with a generated pair, and the Bun dev server generates a pair per start when `dev` has none, so both register subscriptions and compute the schedule; only the Worker has the cron that delivers.
- **Web Push without a library.** `server/src/web-push.ts` implements payload encryption (RFC 8291, `aes128gcm`) and VAPID (RFC 8292) with WebCrypto, because the `web-push` package depends on Node crypto and the code is short.
- **Asking for permission.** The app asks on first launch (iOS) and first load (web), with no explanation of its own. If the browser will not prompt without a gesture, the next click or keypress asks, still with no copy. Settings then shows one line: `Notifications: On`, `Notifications: Off`, or `Notifications need permission` when the system has blocked them. That last line asks again on the web and opens system Settings on iOS. Reminder toasts while the app is open stay. There is no Turn on prompt, no test notification, and no Add to Home Screen instructions.
- **Installable.** A web app manifest, icons, and an Apple touch icon make the app installable. Chromium browsers also get an `Install app` button.
- **Tests.** `server/src/push.test.ts` runs the routes and the cron on PGlite: subscribe, replan after an upload, delivery, a retry, a gone subscription, and an install that paired again. `server/src/push-schedule.test.ts` and `shared/zoned-time.test.ts` cover the pure rules and daylight saving edges.
