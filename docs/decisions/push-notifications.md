# Push notifications

- **Real Web Push.** Due times and reminders reach Stefan as system notifications while the app is closed, through a service worker and the browser's push service. On iPhone this needs the app added to the Home Screen (iOS 16.4 or later), because Safari only gives Push to Home Screen web apps.
- **The server computes the schedule from the synced tasks.** After a write that can move a notification, a guest's included (a task created or deleted, or its `due`, `reminders`, `recurrence`, `completed_at`, `event`, `location`, or `project_id` changed, the last because a group opens the project its tasks share, or the time zone changed), and only when the owner has a push subscription, `replan` in `server/src/push.ts` reads the owner's open tasks and time zone, recomputes each subscribed install's pending notifications with the shared `upcomingNotifications`, so due times, reminders, and event moments notify the same way on every client, and stores the earliest as the row's `next_at`. A title edit reads nothing. Place triggers are not scheduled here; only iOS can see arriving and leaving (see [Places and events](places-and-events.md)). Completing, editing, deleting, and restoring a task need no special cancel path: the next replan drops the old times. A recurring task schedules its next occurrence once completing moves its due date. A change made on iOS or on another browser reaches every subscribed browser without that browser being open.
- **Times are in the synced time zone.** The server cannot use its process zone, so `shared/zoned-time.ts` turns a `DateKey` and `TimeOfDay` into epoch milliseconds in the account's `timeZone` with `Intl`, and names the day a moment falls on for bodies such as `Tomorrow 5:00 PM`. A time skipped by a daylight saving jump lands after it and a repeated one takes the first, like `Date` does locally. An unknown or missing zone falls back to UTC. Clients keep the device zone.
- **Only the browsers' push services.** A subscription's endpoint must be https on Chrome's, Apple's, Firefox's, or Windows' push host (`PUSH_HOSTS` in `server/src/push.ts`), or the test suite's `push.example`. `POST /api/push/test` returns the push service's status to the caller, so any other host would let a signed-in account use the Worker as a proxy that reads a response status.
- **Web Push is per install.** `PUT /api/push/subscription` registers the subscription for the install named by `x-procrastimate-device`, a client-made id kept on the device and sent only on the push routes and Ramble. One endpoint belongs to one install, so a browser that registers again as a new install replaces its old entry and keeps its pending notifications when the endpoint is unchanged. A new subscription is planned at once from the account's tasks, since the cron only reads subscriptions with a next notification. `DELETE` removes it, `GET /api/push/schedule` shows what the server will deliver, and `POST /api/push/test` sends one notification to a subscription the caller provides. All need a signed-in human; the public key route stays open. The install id is also kept in Cache Storage (`app-web/src/lib/install-cache.ts`), which the worker can read: on `pushsubscriptionchange`, a subscription the browser rotated while the app was closed, the worker subscribes again and registers the new one with that id, so notifications continue without a launch.
- **A cron every minute, not an alarm.** The `push` table holds each install's subscription, pending notifications, when the cron last delivered to it, and `next_at`, indexed. The Worker's `* * * * *` Cron Trigger runs `deliverDue`: it selects the users with a `next_at` at or before now, sends each install what is due, then settles in a transaction under the space's advisory lock against the rows stored now, so an upload's replan that landed while sends were in flight is kept, and replans from the space's current tasks, one update per install that settles and plans together. An upload's replan takes no lock, so one that read the row before the settle and wrote after it can bring a sent notification back for one more send, which the OS replaces by its tag. The `Account` object and its single alarm are gone with the sync engine (see [Sync](sync.md)); a minute's granularity is what the alarm gave too, since it fired on the next whole minute.
- **Dedup.** A future moment is pending until the cron delivers it, and never again after. A past moment stays pending only while it already was, as a retry or for a cron tick that has not run yet, so making a task due a minute ago never notifies. Notifications more than ten minutes stale are dropped. Each notification's tag is its moment (`at:<epoch ms>`), so the OS replaces instead of stacking a repeat. While push is on, the open app shows nothing of its own and leaves the system notification to the push.
- **Failures are per install.** A 404 or 410 from the push service drops that install's subscription, unless the install registered that endpoint less than two minutes ago (`subscribed_at`, `FRESH_SUBSCRIPTION_MS`): then it is FCM's early 410 for a new token, and the push retries a minute later like a 5xx. Dropping it would leave the device without push until a reload, since the open app does not register an endpoint it already registered. A 429, a 5xx, or no answer keeps that install's notification and retries a minute later, for up to ten minutes, without resending to installs that got it. Completing the task during a retry stops it. A send is given up after ten seconds (`PUSH_TIMEOUT_MS`) and counts as no answer, so a hanging push service cannot hold one run past the next minute's, which would read the same unsettled notifications and send them again.
- **VAPID keys live in env-manager.** `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (base64url P-256) are kept in env-manager `prod` and pushed to the Worker with `bun run secrets:push`, like every other secret (see [Production hosting](production-hosting.md)). `secrets:push` refuses half a pair. The browser reads the public key from `GET /api/push/key`. To rotate, put a new pair from `generateVapidKeys()` in env-manager and push it. On its next launch each device sees its subscription was made for another key and, with permission already granted, subscribes again with the new key and registers it, with no prompt. Local `wrangler dev` reads an ignored `.dev.vars`, written from env-manager `dev` or with a generated pair, and the Bun dev server generates a pair per start when `dev` has none, so both register subscriptions and compute the schedule; only the Worker has the cron that delivers.
- **Web Push without a library.** `server/src/web-push.ts` implements payload encryption (RFC 8291, `aes128gcm`) and VAPID (RFC 8292) with WebCrypto, because the `web-push` package depends on Node crypto and the code is short.
- **Asking for permission.** The app asks on first launch (iOS) and first load (web), with no explanation of its own. If the browser will not prompt without a gesture, the next click or keypress asks, still with no copy. Settings then shows one line: `Notifications: On`, `Notifications: Off`, or `Notifications need permission` when the system has blocked them. That last line asks again on the web and opens system Settings on iOS. There is no Turn on prompt, no test notification, and no Add to Home Screen instructions.
- **One notification per moment.** Tasks that notify at the same moment, such as several due at 9:00 AM or all of an event's tasks at its start, share one notification. `upcomingNotifications` groups them, so the server's schedule and iOS's local schedule each hold one entry per moment, the web's offline fallback folds everything since its last check into one (`caughtUpNotification`), since a closed tab's catch up can span days, and a place crossing on iOS notifies once for every task it reaches. A lone task reads as before. A group is titled with its count and what its tasks share, `4 tasks at Austin`, `2 tasks for Night out`, or `3 tasks`, and its body lists the first three titles, `Gun courses, Yoga maybe, Setup arcade, and 1 more`. Stacking one banner per task buried the lock screen.
- **A tap opens the relevant screen.** Each notification carries `opens`, a `NotificationTarget`: a lone task opens its details, and a group opens the list all its tasks share, their event, else their place, else their project, else Inbox. A saved place's screen is its label's, which both clients already redirect to. The web maps it to a path with `notificationHref`.
- **Text like Todoist's.** The title is the task, and the body is its due day and time, such as `Today 3:00 PM`, `Tomorrow 9:00 AM`, or `Tue Oct 20 9:00 AM`, named relative to the moment it shows, for a reminder as for the due time. A date with no time reads only the day, a task with no due date `Reminder`, and an event task its event. `notificationBody` and `taskNotificationBody` in `shared/notifications.ts` build it for the server, the web, and iOS. Web Push has no interruption level; iOS marks its local notifications time-sensitive (see [iOS](ios.md)).
- **No in-app reminders.** The open app shows no toast or banner of its own for a reminder, since it duplicated the system notification. The web checks reminders every minute only for the case no push can cover: while push is off, or the browser is offline. Then it shows the system notification itself, with the same text and under the push's tag (`pushTag`), so a push delivered on reconnect replaces it instead of showing twice, and clicking it opens the task.
- **A refused subscribe waits a day.** Chrome answers `AbortError: Registration failed - push service error` when its push service (FCM) will not register the browser, which nothing the page does fixes. The web then stores when it was refused (`procrastimate-push-refused-at`), reads `Notifications: Off`, and skips subscribing on launches and tab switches for a day, instead of failing and reporting to Sentry on each one. A later success clears it.
- **A new FCM token is not sendable at once.** For up to about 10 s after Chrome subscribes, FCM answers 410 Gone for the new endpoint, or it accepts pushes and never delivers them, for up to about 25 s. Chrome's registration has already succeeded and the subscription never changes, so the client has no signal for when the token goes live. Anything that pushes right after subscribing, such as `verify-push.ts`'s test push, waits out that window instead of treating the first 410 as a dead subscription, and the cron retries a 410 within two minutes of subscribing. A silent 200 in that window is still lost.
- **Installable.** A web app manifest, icons, and an Apple touch icon make the app installable. Chromium browsers also get an `Install app` button.
- **Tests.** `server/src/push.test.ts` runs the routes and the cron on PGlite: subscribe, replan after an upload, delivery, a retry, a gone subscription, a fresh subscription's early 410, and an install that paired again. `server/src/push-schedule.test.ts` and `shared/zoned-time.test.ts` cover the pure rules and daylight saving edges. `shared/notifications.test.ts` covers grouping and targets, and its vectors keep the Swift port in step.
