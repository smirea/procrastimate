# Push notifications

- **Real Web Push.** Due times and reminders reach Stefan as system notifications while the app is closed, through a service worker and the browser's push service. On iPhone this needs the app added to the Home Screen (iOS 16.4 or later), because Safari only gives Push to Home Screen web apps.
- **The server computes the schedule from synced tasks.** After every push to `POST /api/sync`, the `Account` object replans each subscribed device's pending notifications from the synced tasks with the shared `upcomingNotifications`, so due times, reminders, and event moments notify the same way on every client. Place triggers are not scheduled here; only iOS can see arriving and leaving (see [Places and events](places-and-events.md)). Completing, editing, deleting, and restoring a task need no special cancel path: the next replan drops the old times. A recurring task schedules its next occurrence once completing moves its due date. A change made on iOS or on another browser reaches every subscribed browser without that browser being open. See [Sync](sync.md#notifications).
- **Times are in the synced time zone.** The server cannot use its process zone, so `shared/zoned-time.ts` turns a `DateKey` and `TimeOfDay` into epoch milliseconds in the account's `timeZone` with `Intl`, and names the day a moment falls on for bodies such as `Due Tomorrow at 5:00 PM`. A time skipped by a daylight saving jump lands after it and a repeated one takes the first, like `Date` does locally. An unknown or missing zone falls back to UTC. Clients keep the device zone. A device writes `timeZone` only when its own zone changes (see [Sync](sync.md#what-syncs)).
- **Web Push uses the install's token.** A subscription registers with `PUT /api/push/subscription` for the signed-in device. One endpoint belongs to one device, so a browser that registers again moves its subscription to the new device. There is no Notifications panel. `POST /api/push/test` sends one notification to a subscription the caller provides, and it requires the same signed-in session. The public key route stays open.
- **One alarm on the account.** The `Account` object stores each device's subscription, pending notifications, and the time its last alarm ran, and arms its single alarm for the earliest pending one. The alarm sends what is due to every device, then replans and re-arms. This fires on the minute with no polling and fits the free plan, which includes SQLite-backed Durable Objects. Cron Triggers plus KV would poll every minute and exceed KV's 1,000 free writes a day to record what was sent. D1 would also need a polling cron.
- **Dedup.** A future moment is pending until the alarm delivers it, and never again after. A past moment stays pending only while it already was, as a retry or for an alarm that has not fired yet, so making a task due a minute ago never notifies. A sync landing just after a due time fires the alarm at once instead of waiting a minute. Notifications more than ten minutes stale are dropped. Each notification's tag is the task and moment, so the OS replaces instead of stacking a repeat. While push is on, the open app shows only the toast and leaves the system notification to the push.
- **Failures are per device.** A 404 or 410 from the push service drops that device's subscription. A 429, a 5xx, or no answer keeps that device's notification and retries a minute later, for up to ten minutes, without resending to devices that got it. Completing the task during a retry stops it.
- **VAPID keys live in env-manager.** `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (base64url P-256) are kept in env-manager `prod` and pushed to the Worker with `bun run secrets:push`, like every other secret (see [Production hosting](production-hosting.md)). CI never generates or uploads them. `secrets:push` refuses half a pair. The browser reads the public key from `GET /api/push/key`. To rotate, put a new pair from `generateVapidKeys()` in env-manager and push it. On its next launch each device sees its subscription was made for another key and, with permission already granted, subscribes again with the new key and registers it, with no prompt. A rekey that fails after dropping the old subscription is remembered in `localStorage` and retried when the device comes back online or visible, or on the next launch. Until a device opens the app, pushes to it fail. Local `wrangler dev` reads an ignored `.dev.vars`, written from env-manager `dev` or with a generated pair. The Bun dev server has no VAPID keys or alarms, so push is unavailable there and the UI says so, though its in-memory account still registers subscriptions and computes the schedule.
- **Web Push without a library.** `server/src/web-push.ts` implements payload encryption (RFC 8291, `aes128gcm`) and VAPID (RFC 8292) with WebCrypto, because the `web-push` package depends on Node crypto and the code is short.
- **The old per-subscription objects are gone.** The `PushSchedule` class is removed with a `deleted_classes` migration (`v3` in `wrangler.jsonc`), which deletes its stored schedules on deploy. Its alarms die with it.
- **Asking for permission.** The app asks on first launch (iOS) and first load (web), with no explanation of its own. If the browser will not prompt without a gesture, the next click or keypress asks, still with no copy. Settings then shows one line: `Notifications: On`, `Notifications: Off`, or `Notifications need permission` when the system has blocked them. That last line asks again on the web and opens system Settings on iOS. Reminder toasts while the app is open stay. There is no Turn on prompt, no test notification, and no Add to Home Screen instructions.
- **Installable.** A web app manifest, icons, and an Apple touch icon make the app installable. Chromium browsers also get an `Install app` button.
