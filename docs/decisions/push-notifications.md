# Push notifications

- **Real Web Push.** Due times and reminders reach Stefan as system notifications while the app is closed, through a service worker and the browser's push service. On iPhone this needs the app added to the Home Screen (iOS 16.4 or later), because Safari only gives Push to Home Screen web apps.
- **The client owns the schedule, until sync.** With sync, the server computes it from synced state instead (see [Sync](sync.md#notifications)). Tasks live in `localStorage`, so the server cannot compute times. After every change, the client computes each future notification moment (epoch milliseconds, with the title and a short body) from `notificationTimes` and replaces the device's whole schedule with one `PUT /api/push/schedule`. Completing, editing, deleting, and restoring a task need no special cancel path. The next sync drops the old times. A recurring task schedules its next occurrence once completing moves its due date. The client syncs on start, after a change (debounced, `keepalive` so a sync survives closing the app), and after a failed sync when the network or the app comes back.
- **One Durable Object per subscription, woken by an alarm.** `PushSchedule` stores that device's subscription and pending notifications and sets its alarm to the earliest one. The alarm sends what is due, then re-arms for the next. This fires on the minute with no polling, keeps each device's schedule apart (each device has its own `localStorage` until sync exists), and fits the free plan, which includes SQLite-backed Durable Objects. Cron Triggers plus KV would poll every minute and exceed KV's 1,000 free writes a day to record what was sent. D1 would also need a polling cron.
- **Dedup.** The client sends each moment of a task once. The object remembers the time it last delivered through and never re-accepts a notification at or before it, so a sync racing an alarm cannot send twice. It also drops notifications more than ten minutes stale. Each notification's tag is the task and moment, so the OS replaces instead of stacking a repeat. While push is on, the open app shows only the toast and leaves the system notification to the push.
- **Dead subscriptions clean themselves up.** A 404 or 410 from the push service wipes that object's state. A 429 or 5xx keeps the notification and retries a minute later, for up to ten minutes.
- **VAPID keys are Worker secrets.** `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (base64url P-256) live only as secrets. After every deploy, CI runs `bun server/scripts/vapid.ts ensure`, which creates and uploads a pair only when the Worker lacks one, so the first deploy provisions them with no human step. The browser reads the public key from `GET /api/push/key`. To rotate, delete both secrets and redeploy. Clients notice the new key and subscribe again. Local `wrangler dev` reads a generated, ignored `.dev.vars`. The Bun dev server has no Durable Objects, so push is unavailable there and the UI says so.
- **Web Push without a library.** `server/src/web-push.ts` implements payload encryption (RFC 8291, `aes128gcm`) and VAPID (RFC 8292) with WebCrypto, because the `web-push` package depends on Node crypto and the code is short.
- **No accounts.** The push API is open, like the rest of `/api`. A subscription endpoint is an unguessable URL, so only the device that holds it can read or replace its schedule.
- **Asking for permission.** The app never prompts on its own. The Notifications panel in the sidebar explains what will notify and asks only when Stefan taps `Turn on notifications`, which iOS requires. Saving the first timed task while push is off shows a one-time toast that opens the panel. In a Safari tab on iPhone, the panel shows how to add the app to the Home Screen instead. A denied permission shows how to re-enable it in Settings or the browser.
- **Installable.** A web app manifest, icons, and an Apple touch icon make the app installable. Chromium browsers also get an `Install app` button.
