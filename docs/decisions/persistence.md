# Persistence

- **Source keys.** A task or project brought in by an import stores where it came from, such as `todoist:task:…`, so the import can skip what it already brought in. Other tasks have none.
- **Local databases are sync-engine's.** Each client keeps its rows in a SQLite database the engine syncs: on the web sync-engine's browser client on OPFS with Drizzle, on iOS the engine's Swift client over a GRDB `DatabasePool` (`Application Support/procrastimate/sync.sqlite`). The in-memory store the screens render from is loaded from it and written back through `rowWrites` after every command (see [Sync](sync.md)). The client areas document their databases: [iOS app](ios.md) and the web client in [Sync](sync.md#web-client).
- **Task order.** Tasks are stored sorted by `createdAt`, then `id`. A new task's `createdAt` is at least one millisecond past the newest task's, so tasks added within one millisecond keep the order they were added in instead of falling back to their random ids.

## The server database

- **One SQLite database in one Durable Object.** The `App` object's SQLite storage holds every user's synced rows, the engine's bookkeeping (`_changes`, `_clients`, `_log`, `_meta`), the server-only tables, and Better Auth's. The Bun dev server opens the same schema on a `bun:sqlite` file, and unit tests on `:memory:`. Durable Object storage keeps 30 days of point-in-time recovery on its own.
- **Every query goes through Drizzle.** `shared/db/schema.ts` is the `sqlite-core` schema, `server/src/db/auth-schema.ts` Better Auth's. The server runs Drizzle on `drizzle-orm/durable-sqlite` in the object and `drizzle-orm/bun-sqlite` elsewhere (`Db` in `server/src/db/sqlite.ts`), and the engine runs on its own driver over the same connection, so the engine's transaction covers what its hooks write through Drizzle (`openStore` in `server/src/db/store.ts`). Both are synchronous: an object runs one request at a time and a statement runs to completion, so nothing locks. The only SQL outside Drizzle is the migrator's DDL and the engine's.
- **Migrations are additive and computed from the live database.** As the engine does for the synced tables, `server/src/db/migrate.ts` compares the live tables with the schema on every start of the object or the Bun server and creates what is missing: a table, a column, an index (the synced tables' server-side indexes included, which the engine's DDL leaves out). Nothing is dropped or retyped, there is no history to agree with, and a removed column stays in place, ignored; a column whose type must change gets a new name, and a `NOT NULL` column added later needs a default. There is no migration folder and no `db:generate` step.
- **The Durable Object's SQLite has limits `bun:sqlite` lacks.** At most 100 bound parameters per statement: the Bun store's Drizzle logger and engine driver throw past 100, so the limit fails locally too, inserts go one row per statement, and `IN` lists over ids run in parts of 90 (`server/src/db/chunks.ts`). A compound `SELECT` of many terms is refused there and not in Bun, which only the Worker build catches; the end to end suite runs against `wrangler dev` in CI for that.
- **Daily JSON backups, and the same format restores.** The Worker's `0 9 * * *` cron asks the object to dump every server table through Drizzle into R2 as `sqlite/<YYYY-MM-DD>.json` and keeps the newest 30 (`server/src/db/backup.ts`). `restoreDump` loads such a dump into a database that holds no user yet, one row per statement in one transaction, and moves the engine's head and horizon past any cursor a device could hold, so every device takes a fresh snapshot. The object restores `restore/pending.json` from the backups bucket on its first start while it holds no user, then deletes it, and the Bun server takes a dump through `PROCRASTIMATE_RESTORE`. Production's Postgres arrived that way: `scripts/sync-engine-migration/import-postgres.ts` read it, read-only, into a dump. See [Production hosting](production-hosting.md).
