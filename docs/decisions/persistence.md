# Persistence

- **Source keys.** A task or project brought in by an import stores where it came from, such as `todoist:task:…`, so the import can skip what it already brought in. Other tasks have none.
- **Web persistence.** The whole store is one JSON document in `localStorage`, validated on load and written synchronously on every change. Invalid stored data is discarded, since there is no backwards compatibility. A task that fails validation is dropped on its own, so one bad task never wipes the rest of the store. A newly added optional field gets a default during validation instead, so adding it does not wipe the tasks already stored in production.
- **Tabs share one document.** Every tab of the web app saves the whole document, and a hidden tab neither syncs nor stops saving (the reminder check writes every 15 seconds). So each tab adopts the document whenever another tab writes it, through the `storage` event. Otherwise a background tab or the installed app saves its stale copy, cursor included, over what the visible tab synced, and every launch opens on that old state until its first sync catches up. iOS has one process and does not need this.
- **One schema.** `shared/snapshot.ts` defines the document and its loading rules for both clients, including the device-local `sync` section (device id, cursor, outbox, the last clock, the zone it last wrote, the dictation choice last applied, `epoch`, and `reset`). A document stored before dictation loads as `native`. The first launch always writes that section, so an existing list uploads. The iOS `Snapshot` decodes the same rules, proven by the snapshot vectors.
- **Task order.** Tasks are stored sorted by `createdAt`, then `id`. A new task's `createdAt` is at least one millisecond past the newest task's, so tasks added within one millisecond, or under a frozen test clock, keep the order they were added in instead of falling back to their random ids.
- **iOS persistence.** The native app stores the same snapshot shape as one JSON file on the device. See [iOS app](ios.md).
- **Sync.** Both clients sync through the Worker, which holds the truth. Each commit diffs the snapshot into an outbox of ops. See [Sync](sync.md).

## Server databases

- **A foreign migration history fails, it never wipes.** Turso holds Stefan's real data, in `dev` and `prod`. `server/src/db/migrate.ts` applies only the migrations a database is missing. When its history is not a prefix of `server/drizzle` (a database from before Drizzle, one a branch with a newer migration ran against, or a rebased or hand-merged journal), it throws `MigrationHistoryError` with the expected and found history, before it runs a single statement. Every caller says which mode it wants: `strict` for Turso and a Durable Object's own SQLite, `rebuild` (drop every table, then migrate) only for in-memory and test databases. The mode is never inferred from the environment, because one wrong guess wipes production.
- **A failed migration stops serving.** The Bun dev server migrates Turso before it listens, so a mismatch exits it. The Worker has no startup hook, so every request that needs the database fails with the error until the history is fixed; the migrator retries on the next request and still drops nothing. An `Account` object migrates its own SQLite only when Turso is not configured, since that storage is otherwise never read.
- **Migrations are append only.** CI runs `server/scripts/migration-history.ts`, which fails unless the branch's `server/drizzle` journal keeps every entry of master's unchanged and in order, with its SQL untouched, and only appends later ones. When another PR's migration lands first, delete yours, rebase, and run `bun run db:generate` again. Squashing migrations is no longer free: it would fail every database.
