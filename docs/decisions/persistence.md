# Persistence

- **Source keys.** A task or project brought in by an import stores where it came from, such as `todoist:task:…`, so the import can skip what it already brought in. Other tasks have none.
- **Local databases are PowerSync's.** Each client keeps its rows in a SQLite database PowerSync manages: on the web `@powersync/web` with Drizzle over the generated `sqlite-core` tables, on iOS `PowerSync` with GRDB records. The in-memory store the screens render from is loaded from it and written back through `rowWrites` after every command (see [Sync](sync.md)). The client areas document their databases: [iOS app](ios.md) and the web client in [Sync](sync.md#web-client).
- **Task order.** Tasks are stored sorted by `createdAt`, then `id`. A new task's `createdAt` is at least one millisecond past the newest task's, so tasks added within one millisecond keep the order they were added in instead of falling back to their random ids.

## The server database

- **Postgres everywhere.** Supabase in production and dev, plain Postgres with row level security on every table and no policies, so the Data API serves nothing and the server connects as the owner. Locally, one Docker Postgres 17 (`docker/compose.yaml`, `wal_level=logical`) serves every worktree, each with a database named after its branch and a second one for its PowerSync (see [Dev hosting](dev-hosting.md)). Unit tests run PGlite, Postgres compiled to WebAssembly, in the test process.
- **Every query goes through Drizzle.** `shared/db/schema.ts` is the `pg-core` schema, `server/src/db/auth-schema.ts` Better Auth's. The server opens Drizzle on postgres.js (`server/src/db/postgres.ts`), over the Hyperdrive binding's connection string on the Worker and `DATABASE_URL` elsewhere, and tests on `drizzle-orm/pglite`. The only SQL is in the migrations and `scripts/local-stack.ts`'s database setup.
- **Migrations are drizzle-kit's, bundled.** `bun run db:generate` writes a migration to `server/drizzle/` and nobody edits the SQL. `scripts/generate` bundles them into `server/src/db/generated/migrations.ts`, because the Worker cannot read files. `server/src/db/migrate.ts` applies the missing ones under a transaction-level advisory lock, so Worker isolates and dev servers starting together apply each once, and records them in drizzle-kit's own `drizzle.__drizzle_migrations`, so `drizzle-kit migrate` agrees. A custom migration creates the `powersync` publication for exactly the synced tables; a new synced table needs its own `ALTER PUBLICATION powersync ADD TABLE`.
- **A foreign migration history fails, it never wipes.** When a database's history is not a prefix of `server/drizzle` (a database a branch with a newer migration ran against, or a rebased journal), the migrator throws `MigrationHistoryError` with the expected and found history before it runs a statement. There is no rebuild mode: tests start from an empty PGlite, and a worktree database recovers with `bun scripts/setup-worktree.ts --reset-db`. The Bun dev server migrates before it listens, so a mismatch exits it; the Worker migrates once per isolate on its first request, and every request fails with the error until the history is fixed.
- **Migrations are append only.** CI runs `server/scripts/migration-history.ts`, which fails unless the branch's journal keeps every entry of master's unchanged and in order, with its SQL untouched, and only appends later ones. When another PR's migration lands first, delete yours, rebase, and run `bun run db:generate` again.
- **Daily JSON backups.** The Worker's `0 9 * * *` cron dumps every table through Drizzle into R2 as `postgres/<YYYY-MM-DD>.json` and keeps the newest 30. See [Production hosting](production-hosting.md).
