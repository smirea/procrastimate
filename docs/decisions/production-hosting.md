# Production hosting

- **One Cloudflare Worker on the free plan.** It serves the built client as static assets and runs `server/src/api.ts` for `/api/*` through `server/src/worker.ts`, the entry that wraps it and the `Account` object in Sentry, so the browser talks to one origin in production too. `wrangler.jsonc` at the repo root configures it.
- **Production URL is `https://procrastimate.stf.lol`.** It is a Workers Custom Domain on Stefan's `stf.lol` zone, which lives in the same Cloudflare account as the Worker. `wrangler deploy` creates its DNS record and certificate, so no DNS is managed by hand. The `workers.dev` URL stays on as a fallback, since it costs nothing and needs no zone.
- **Static SPA plus a Worker API, not `adapter-cloudflare`.** The client has no server rendering, so `adapter-cloudflare` would only add a SvelteKit server runtime in front of every page and move the API into SvelteKit routes. With `adapter-static`, `not_found_handling: "single-page-application"`, and `run_worker_first: ["/api/*"]`, pages and assets are served without invoking the Worker. Only API calls run code.
- **Free-tier fit.** Static asset requests are free and unlimited. Only `/api/*` counts against the 100,000 requests a day. The client calls it for sync and for push. One user, syncing on launch, on focus, after each edit, and once a minute while the app is open, stays far under 100,000 requests a day. Each delivered notification is one Durable Object alarm, against 100,000 Durable Object requests a day. The Worker bundle is about 735 KiB gzipped, about 110 KiB of it Sentry, against the free plan's 3 MiB, and its work is small against the 10 ms CPU limit. The daily backup is its heaviest run, at an estimated 5 to 8 ms today. The client build is 44 files and about 810 KB, self-hosted fonts and app icons included, with the largest file at 123 KB, against 20,000 files and 25 MiB per file.
- **Server storage.** Task data lives in Turso. Only an ephemeral run (see below) keeps it in the account Durable Object's SQLite instead. The Durable Object still holds the push alarm and the realtime and Ramble sockets. See [Sync](sync.md).
- **Daily Turso backups in R2.** Turso's free plan restores only the last 24 hours, so a Cron Trigger (`0 9 * * *`, UTC) on the same Worker dumps the production database every day into the `procrastimate-backups` R2 bucket as `turso/<YYYY-MM-DD>.sql`. `server/src/db/backup.ts` writes the dump the way `sqlite3 .dump` does: the schema plus an `INSERT` per row, read in one read batch so it is one snapshot. It reads raw SQL rather than Drizzle because it walks `sqlite_master` instead of the schema. The Worker already holds the Turso secrets, so no secret goes anywhere new. GitHub Actions was ruled out because the repo is public and its artifacts are readable by any signed-in user. After each successful upload the Worker deletes all but the newest 30 dumps. It prunes by count, not age, and not with an R2 lifecycle rule, so a stretch of failed runs never deletes the last good backups. The dump is not gzipped: gzip cost about a third of the free plan's 10 ms CPU budget, and 30 dumps of about 1 MB are nothing against R2's free 10 GB. A Sentry cron monitor, `turso-backup`, flags a run that fails or never reports, which is how a database that outgrows the 10 ms budget shows up. To restore, run `wrangler r2 object get procrastimate-backups/turso/<date>.sql --remote --file backup.sql`, then `sqlite3 restored.db < backup.sql`, `sqlite3 restored.db 'pragma journal_mode=wal'`, and `turso db import restored.db`. Then point the Turso secrets at the new database.
- **API paths are the same everywhere.** Routes are mounted at `/api/*` in the handler itself. The Vite proxy forwards `/api` unchanged, and native clients call `API_URL` plus `/api/...`.
- **Deploys run from GitHub Actions.** `.github/workflows/ci.yml` runs on every pull request and every push to `master`. A `checks` job typechecks, runs unit tests, builds, and validates the Worker bundle with `wrangler deploy --dry-run`. In parallel, one end-to-end job per Playwright project (`desktop` in Chromium, `mobile` in WebKit), with cached browsers, runs against `wrangler dev` serving the build. On a push to `master`, `wrangler deploy` runs only after all of them pass. Actions won over Workers Builds because the pipeline stays in the repo, one workflow covers the pull request check and the deploy, and it reuses the setup of Stefan's `email-save` Worker.
- **All secrets live in env-manager, online.** env-manager project `procrastinate` in AWS Secrets Manager is the source of truth. Two environments, and no `local` environment: `prod` for the Worker and deploys, `dev` for local development. The schema is not in local mode (`local: true` is gone), so `up` and `down` talk to AWS. Every Worker secret sits in the root `.env` schema's `server` scope as an optional field, so `env-manager gen --local` still builds from the schema defaults where there are no AWS credentials: CI, cloud agents, and the dev box. That flag is not an environment. `config.ts`, not the schema, decides what is required. The deploy, TestFlight, Turso platform, and agent credentials sit in the `scripts` target instead, so they never reach the server's reader. env-manager has no target without a reader, so `scripts/env.ts` exists and nothing imports it. `server/scripts/secrets.ts` is the only bridge out: `bun run secrets:push` uploads the set `prod` Worker secrets with `wrangler secret bulk`, `bun run secrets:github` mirrors the deploy credentials to GitHub, and `bun run secrets:check` reports drift by name. It never prints a value, and it never deletes a secret, since unset keys are skipped. Nobody runs `wrangler secret put` or `gh secret set` by hand. Only a machine with AWS access (Stefan's MacBook) can read the values.
- **Deploy credentials.** The workflow reads the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets, the same names `email-save` uses, mirrored from env-manager `prod` with `bun run secrets:github`. They are the only secrets in GitHub; CI gets no AWS access. Without them the deploy step is skipped with a warning, so `master` stays green.
- **Deploys never touch Worker secrets.** CI only runs `wrangler deploy`, which keeps existing secrets. No deploy step writes or deletes one, and `wrangler.jsonc` declares no `vars` with a secret's name, which would overwrite it; a unit test in `server/scripts/secrets.test.ts` guards that.
- **One version for every client: `<increment>.<yyyyMMdd>`.** `scripts/app-version.mts` reads it from `HEAD`: the commit count (`git rev-list --count`), then the commit's UTC date, such as `465.20261017`. A web deploy and a TestFlight build of the same commit show the same version without either committing a bump, and the count only grows on `master`. Vite defines it as `__APP_VERSION__`. On iOS every build writes it, whether from Xcode, `./sim`, or `scripts/archive`: Core's Generate phase writes `APP_VERSION` into a header, and the App and Widgets Info.plists are preprocessed with it as `CFBundleShortVersionString`. A `MARKETING_VERSION` setting cannot carry it, because Xcode reads build settings before any phase runs, so a generated xcconfig would show the previous commit's version. The Info.plist is processed after Core's phase, and a `MARKETING_VERSION` would override its value when `GENERATE_INFOPLIST_FILE` is on, so both targets write their whole Info.plist by hand with no `MARKETING_VERSION` at all. It fits that key's rule of at most three period-separated integers, and its first integer stays within four digits for years. `CFBundleVersion` stays the archive's UTC timestamp (see [iOS app](ios.md)), so a re-run of the same commit still uploads a higher build. A shallow clone would count only the commits it fetched, so the script fails there, and every CI checkout that builds the web client or the iOS app fetches full history. Settings shows it at the bottom. The Sentry release stays the commit SHA.
- **Hashed assets are cached forever.** `app-web/static/_headers` marks `/_app/immutable/*` as immutable, so repeat visits load from the browser cache.
- **Configuration is parsed once, at the boundary, and a missing production secret fails every request.** `server/src/config.ts` turns the raw bindings into a typed `Config` once per bindings object. `api.ts` parses it before routing, and the Bun dev server parses it before listening. Feature code reads `config(env)`, never `env.X`. `BETTER_AUTH_SECRET`, both Turso secrets, and both VAPID keys are required (`REQUIRED_WORKER_SECRETS`). A missing one makes every request fail with `500`, and the Worker log names the key, instead of running with sign-in off, push off, or an empty Durable Object store in place of the real Turso data. Optional providers are all or nothing: the Google web pair, Apple's services id with its stored JWT or its team id, key id, and `.p8`, and `RAMBLE_UPSTREAM`, which is `cassette` or unset. A partial set throws. ElevenLabs is the one optional feature that degrades on its own, and Ramble answers `503` without it.
- **Ephemeral runs.** `EPHEMERAL=1` relaxes the required secrets for unit tests, both end-to-end modes, and the Bun dev server when neither Turso secret is set. Data lives in memory or the Durable Object, Turso is never touched even when the shell has its secrets, and without `BETTER_AUTH_SECRET` a fixed public secret signs sessions that die with the in-memory user table. Production never sets it. The Bun dev server also generates a VAPID pair when none is set, since `dev` has none.
- **A deploy checks the Worker's secrets first.** Before `wrangler deploy`, CI runs `bun server/scripts/secrets.ts verify`, which lists the Worker's secret names with `wrangler secret list` and fails when a required one is missing. It needs only the Cloudflare credentials, so CI still has no AWS access. `secrets:check` also reports a required secret missing from env-manager.
- **Turso secrets.** The Turso org is `smirea` with one group, `default`, in `aws-us-east-2` (Ohio). `procrastimate-prod` and `procrastimate-dev` live there. `TURSO_DATABASE_URL` (`libsql://...`) and `TURSO_AUTH_TOKEN` (a non-expiring full-access database token) are kept per environment, prod in `prod` and dev in `dev`, and the prod pair is a Worker secret pushed with `bun run secrets:push`. `TURSO_API_TOKEN`, the org's platform API token for creating databases and minting tokens, is kept only in `prod` and never goes to the Worker.
- **`.dev.vars` always exists before `wrangler dev`.** Without it, wrangler falls back to the root `.env`, which is the env-manager schema. `bun run preview` and CI both write it first; CI passes `--generate-only` because it cannot reach AWS. A generate-only `.dev.vars` holds only a VAPID pair, so `wrangler dev` without AWS needs `--var EPHEMERAL:1`, as the end-to-end run passes.
- **ElevenLabs secret.** `ELEVENLABS_API_KEY` is a Worker secret on `procrastimate` for Ramble's transcription proxy (see [Ramble](ramble.md)), kept in env-manager `prod` and `dev` and pushed with `bun run secrets:push`, like the other Worker secrets: never in `vars`, CI, or client targets. It appears scoped to speech to text. `/api/ramble/socket` answers `503` without it. `RAMBLE_UPSTREAM` is a dev-only binding and is never a Worker secret.
