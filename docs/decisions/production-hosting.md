# Production hosting

- **One Cloudflare Worker on the free plan.** It serves the built client as static assets and runs `server/src/api.ts` for `/api/*`, so the browser talks to one origin in production too. `wrangler.jsonc` at the repo root configures it.
- **Production URL is `https://procrastimate.stf.lol`.** It is a Workers Custom Domain on Stefan's `stf.lol` zone, which lives in the same Cloudflare account as the Worker. `wrangler deploy` creates its DNS record and certificate, so no DNS is managed by hand. The `workers.dev` URL stays on as a fallback, since it costs nothing and needs no zone.
- **Static SPA plus a Worker API, not `adapter-cloudflare`.** The client has no server rendering, so `adapter-cloudflare` would only add a SvelteKit server runtime in front of every page and move the API into SvelteKit routes. With `adapter-static`, `not_found_handling: "single-page-application"`, and `run_worker_first: ["/api/*"]`, pages and assets are served without invoking the Worker. Only API calls run code.
- **Free-tier fit.** Static asset requests are free and unlimited. Only `/api/*` counts against the 100,000 requests a day. The client calls it only for push: one key fetch per launch and one schedule upload per change. Each delivered notification is one Durable Object alarm, against 100,000 Durable Object requests a day. The Worker bundle is 123 KiB gzipped, mostly zod, against the free plan's 3 MiB, and its work is small against the 10 ms CPU limit. The client build is 44 files and about 810 KB, self-hosted fonts and app icons included, with the largest file at 123 KB, against 20,000 files and 25 MiB per file.
- **Server storage is push only.** Tasks stay in `localStorage`. The only server state is each device's push schedule, in a Durable Object (see Push notifications). Sync adds one `Account` Durable Object with the synced state (see [Sync](sync.md)).
- **API paths are the same everywhere.** Routes are mounted at `/api/*` in the handler itself. The Vite proxy forwards `/api` unchanged, and native clients call `API_URL` plus `/api/...`.
- **Deploys run from GitHub Actions.** `.github/workflows/ci.yml` runs on every pull request and every push to `master`. A `checks` job typechecks, runs unit tests, builds, and validates the Worker bundle with `wrangler deploy --dry-run`. In parallel, one end-to-end job per Playwright project (`desktop` in Chromium, `mobile` in WebKit), with cached browsers, runs against `wrangler dev` serving the build. On a push to `master`, `wrangler deploy` runs only after all of them pass. Actions won over Workers Builds because the pipeline stays in the repo, one workflow covers the pull request check and the deploy, and it reuses the setup of Stefan's `email-save` Worker.
- **All secrets live in env-manager, online.** env-manager project `procrastinate` in AWS Secrets Manager is the source of truth. Two environments, and no `local` environment: `prod` for the Worker and deploys, `dev` for local development. The schema is not in local mode (`local: true` is gone), so `up` and `down` talk to AWS. Every secret sits in the root `.env` schema's `server` scope as an optional field, so `env-manager gen --local` still builds from the schema defaults where there are no AWS credentials: CI, cloud agents, and the dev box. That flag is not an environment. `server/scripts/secrets.ts` is the only bridge out: `bun run secrets:push` uploads the set `prod` Worker secrets with `wrangler secret bulk`, `bun run secrets:github` mirrors the deploy credentials to GitHub, and `bun run secrets:check` reports drift by name. It never prints a value, and it never deletes a secret, since unset keys are skipped. Nobody runs `wrangler secret put` or `gh secret set` by hand. Only a machine with AWS access (Stefan's MacBook) can read the values.
- **Deploy credentials.** The workflow reads the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repository secrets, the same names `email-save` uses, mirrored from env-manager `prod` with `bun run secrets:github`. They are the only secrets in GitHub; CI gets no AWS access. Without them the deploy step is skipped with a warning, so `master` stays green.
- **Deploys never touch Worker secrets.** CI only runs `wrangler deploy`, which keeps existing secrets. No deploy step writes or deletes one, and `wrangler.jsonc` declares no `vars` with a secret's name, which would overwrite it; a unit test in `server/scripts/secrets.test.ts` guards that.
- **Hashed assets are cached forever.** `app-web/static/_headers` marks `/_app/immutable/*` as immutable, so repeat visits load from the browser cache.
- **Sync setup secret.** `SYNC_SETUP_CODE` is a Worker secret on `procrastimate`, kept in env-manager `prod`. Without it the Worker still deploys and runs, and `POST /api/auth/setup` answers `503`, so sync is simply unavailable. To change it, edit it in env-manager `prod` and run `bun run secrets:push`. Locally, `wrangler dev` reads it from `.dev.vars`, which `bun server/scripts/secrets.ts dev-vars` writes from env-manager `dev`, and the Bun dev server from root `.env.local`. End to end tests use the hard-coded `e2e-setup-code`.
- **Turso secrets.** The Turso org is `smirea` with one group, `default`, in `aws-us-east-2` (Ohio). `procrastimate-prod` and `procrastimate-dev` live there. `TURSO_DATABASE_URL` (`libsql://...`) and `TURSO_AUTH_TOKEN` (a non-expiring full-access database token) are kept per environment, prod in `prod` and dev in `dev`, and the prod pair is a Worker secret pushed with `bun run secrets:push`. `TURSO_API_TOKEN`, the org's platform API token for creating databases and minting tokens, is kept only in `prod` and never goes to the Worker.
- **`.dev.vars` always exists before `wrangler dev`.** Without it, wrangler falls back to the root `.env`, which is the env-manager schema. `bun run preview` and CI both write it first; CI passes `--generate-only` because it cannot reach AWS.
- **ElevenLabs secret.** `ELEVENLABS_API_KEY` is a Worker secret on `procrastimate` for Ramble's transcription proxy (see [Ramble](ramble.md)), kept in env-manager `prod` and `dev` and pushed with `bun run secrets:push`, like `SYNC_SETUP_CODE`: never in `vars`, CI, or client targets. It appears scoped to speech to text. `/api/ramble/socket` answers `503` without it. `RAMBLE_UPSTREAM` is a dev-only binding and is never a Worker secret.
