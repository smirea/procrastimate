# API and database types

How the server's database, its HTTP endpoints, and every client share one set of types.

## Database

- **Drizzle is the source of truth.** `shared/db/schema.ts` defines every account table once, for Turso and for the `Account` Durable Object's SQLite, and `server/src/db/auth-schema.ts` defines Better Auth's. Every type that is a row, or part of one, comes from them: `Task`, `Project`, `Label`, and `Settings` are a live row's columns, a sync op's fields are those columns made optional, and a `Change` carries the `log` table's `seq` and `opId`.
- **A table per synced kind.** `tasks`, `projects`, `labels`, and `settings` have a column per field, `deleted`, and one clock per field in `clocks`. The clocks say which fields a row holds. A row the server only heard a partial edit or a delete for keeps its other columns at their schema defaults, which mean nothing until a clock is set for them. `server/src/db/entities.ts` turns a sync entity into its row and back, so the sync core still works on entities of any kind.
- **Zod only for what a column cannot say.** `shared/values.ts` holds the shapes stored inside JSON columns (`Due`, `Recurrence`, `Reminder`) and the narrower values of plain columns (`Priority`, `DateKey`). `shared/db/json.ts` maps each such column to its shape, and the tables take their TypeScript types from it, so each shape is stated once. Wire envelopes such as `SyncRequest`, and values no table stores, such as `AuthMethods`, are Zod.
- **Row schemas are generated.** `scripts/generate` reads the tables and writes `shared/db/generated/zod.ts`, one plain Zod object per table. drizzle-zod would derive the same at runtime, but it pulls all of Zod and part of Drizzle into the web bundle, about 70 KB gzipped. The generated file costs about 4 KB.
- **Every table is per user.** Each table but `ramble_budget` and Better Auth's has a `user_id` column, in Turso and in the Durable Object alike, so one store implementation serves both. A Durable Object still holds a single user's rows.
- **Queries go through Drizzle.** `server/src/account/sqlite-store.ts` runs on any synchronous Drizzle SQLite database: `drizzle-orm/durable-sqlite` on the Worker and `drizzle-orm/bun-sqlite` in tests. Turso uses `drizzle-orm/libsql/web`. The only raw SQL left is in the migrator and the migrations.
- **Better Auth runs on Drizzle.** With Turso it uses Better Auth's Drizzle adapter over the same database and migrations. Its tables keep the shape its Kysely migrations created: camelCase columns, and dates as ISO strings in `date` columns, read through a custom column type, so existing sessions stay valid. Without Turso it keeps the in-memory adapter, since the Worker has no other database to give it.
- **Migrations are drizzle-kit's.** `bun run db:generate` writes a migration to `server/drizzle/` and regenerates the bundle. CI fails when the schema has changed without a migration. The baseline uses `IF NOT EXISTS` because production Turso already had most tables. `0001_typed_entities` copies the old JSON `entities` rows into the typed tables with `json_extract` and leaves `entities` in place for a later migration to drop.
- **Migrations are bundled.** Neither the Worker nor a Durable Object can read files, so `scripts/generate` writes `server/src/db/generated/migrations.ts`. `server/src/db/migrate.ts` applies it with drizzle-kit's own bookkeeping table: once per Turso database and isolate, and when an `Account` object starts. Tables from before `user_id` are dropped first. Nothing locks a Turso migration, so two isolates starting at once can both apply it: write every migration to be safe to run twice, or accept that the losing isolate fails one request and retries.
- **Tests use real databases.** Store tests run on in-memory `bun:sqlite`, and Turso and Better Auth tests run on a local libSQL file, all through Drizzle.

## Endpoints

- **One oRPC v2 contract.** `shared/api/contract.ts` declares every HTTP endpoint with its method and path (oRPC's `openapi` meta), input, output, and typed errors. Inputs and outputs are built from the generated row schemas in `shared/sync/protocol.ts`, with Zod around them for envelopes.
- **Paths stay REST-like.** The contract keeps the `/api/...` paths, so the OpenAPI document reads like the API and iOS calls plain URLs.
- **Two implementers.** `server/src/router.ts` implements the procedures the Worker serves. `server/src/account/router.ts` implements the ones the user's `Account` object serves, plus an internal `wipe` that account deletion calls through a typed oRPC client. The Worker forwards account requests to the object without reading their bodies, and it decides which requests to forward from the contract's own routes. Validating twice would cost Worker CPU on a large first sync.
- **Validation is the contract's.** oRPC rejects an invalid input with a `400` and checks every output on the way out. Errors are oRPC's JSON body (`code`, `message`, `data`) with the same status codes as before. Clients branch on the code, which a non-oRPC `401` also decodes to. The push test reports oRPC's `GONE` and `BAD_GATEWAY`, so no status map is needed. Requests need a JSON content type.
- **iOS outboxes get one repair.** `POST /api/sync` bodies pass through `repairBooleanNumbers` before the contract validates them, for iOS builds that sent `0` and `1` as booleans.
- **Outside the contract.** Better Auth's `/api/auth/*` routes, except `/api/auth/methods`, and the two WebSockets (`/api/sync/socket` and `/api/ramble/socket`) stay as they are. A WebSocket upgrade is not something oRPC or OpenAPI can describe.

## Generated types

- **One generator.** `bun run generate` (`scripts/generate/index.ts`) writes the files below and rewrites a file only when its content changes. `bun run start` runs it in watch mode next to the server and client, `bun run build` and the iOS launcher run it first, Lefthook and CI run `generate:check`, and CI fails when a file is stale. Every output lives in a `generated` folder, which oxlint and oxfmt ignore.
- **OpenAPI.** `shared/api/generated/openapi.json` is the contract as OpenAPI 3.1, with the shared schemas named as components through Zod registry ids. The Swift generator folds an `<Name>Output` component into `<Name>` when they differ only by `additionalProperties`.
- **Web.** The web client calls the API through `api` in `app-web/src/lib/api.ts`, a `JsonifiedClient<RouterContractClient>` typed straight from the contract. At runtime it ships only `app-web/src/lib/generated/contract.json`, the contract's routes without their schemas, so the bundle carries no validators it does not use. The sync loop still validates responses with `syncResponseSchema`, because the server can be a different deploy than the open tab.
- **iOS.** `app-ios/Sources/Core/Generated/API.swift` holds a Codable type for every schema and one `API.Endpoints` descriptor per operation, generated by `scripts/generate/swift.ts` from the OpenAPI document. It needs no Swift package, so the app keeps zero dependencies, and it builds on Linux with `Core`. A field that is both optional and nullable becomes `Nullable<T>?`, because a sync patch tells a missing field from `null`. The app sends every contract call through `APIClient`, and `Core` builds the sync request from the outbox as `API.SyncRequest`, repairing the boolean numbers old builds stored first, since the typed request cannot hold them.
