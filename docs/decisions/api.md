# API and database types

How the server's database, its HTTP endpoints, and every client share one set of types.

## Database

- **Drizzle is the source of truth.** `shared/db/schema.ts` defines every account table once, for Turso and for the `Account` Durable Object's SQLite, and `server/src/db/auth-schema.ts` defines Better Auth's. Every type that is a row, or part of one, comes from them: `Task`, `Project`, `Label`, and `Settings` are a live row's columns, a sync op's fields are those columns made optional, and a `Change` carries the `log` table's `seq` and `opId`.
- **A table per synced kind.** `tasks`, `projects`, `labels`, and `settings` have a column per field, `deleted`, and one clock per field in `clocks`. The clocks say which fields a row holds. A row the server only heard a partial edit or a delete for keeps its other columns at their defaults or a filler, which mean nothing until a clock is set for them. `server/src/db/entities.ts` turns a sync entity into its row and back, so the sync core still works on entities of any kind.
- **Zod only for what a column cannot say.** `shared/values.ts` holds the shapes stored inside JSON columns (`Due`, `Recurrence`, `Reminder`) and the narrower values of plain columns (`Priority`, `DateKey`). `shared/db/json.ts` maps each such column to its shape, and the tables take their TypeScript types from it, so each shape is stated once. Wire envelopes such as `SyncRequest`, and values no table stores, such as `AuthMethods`, are Zod.
- **Row schemas are generated.** `scripts/generate` reads the tables and writes `shared/db/generated/zod.ts`, one plain Zod object per table. drizzle-zod would derive the same at runtime, but it pulls all of Zod and part of Drizzle into the web bundle, about 70 KB gzipped. The generated file costs about 4 KB.
- **Every table is per user.** Each table but `ramble_budget` and Better Auth's has a `user_id` column, in Turso and in the Durable Object alike, so one store implementation serves both. A Durable Object still holds a single user's rows.
- **Queries go through Drizzle.** `server/src/account/sqlite-store.ts` runs on any synchronous Drizzle SQLite database: `drizzle-orm/durable-sqlite` on the Worker and `drizzle-orm/bun-sqlite` in tests. Turso uses `drizzle-orm/libsql/web`. The only raw SQL left is in the migrator and the migrations.
- **Better Auth runs on Drizzle.** With Turso it uses Better Auth's Drizzle adapter over the same database and migrations, with its tables in `server/src/db/auth-schema.ts` and dates as epoch milliseconds. Without Turso it keeps the in-memory adapter, since the Worker has no other database to give it.
- **Migrations are drizzle-kit's, as it writes them.** `bun run db:generate` writes a migration to `server/drizzle/` and regenerates the bundle, and nobody edits the SQL. CI fails when the schema has changed without a migration.
- **No backwards compatibility while in development.** A database whose migration history is not a prefix of `server/drizzle` is wiped and rebuilt, accounts included: one from before Drizzle, or one migrated before the migrations were squashed. So squashing migrations during development is free. Revisit this before the data matters.
- **Migrations are bundled.** Neither the Worker nor a Durable Object can read files, so `scripts/generate` writes `server/src/db/generated/migrations.ts`. `server/src/db/migrate.ts` applies it with drizzle-kit's own bookkeeping table: once per Turso database and isolate, and when an `Account` object starts. Nothing locks a Turso migration, so two isolates starting at once can both apply it: write every migration to be safe to run twice, or accept that the losing isolate fails one request and retries.
- **Tests use real databases.** Store and migration tests run on in-memory `bun:sqlite`, and Turso and Better Auth tests run on a local libSQL file, all through Drizzle.

## Endpoints

- **One oRPC v2 contract.** `shared/api/contract.ts` declares every HTTP endpoint with its method and path (oRPC's `openapi` meta), input, output, and typed errors. Inputs and outputs are built from the generated row schemas in `shared/sync/protocol.ts`, with Zod around them for envelopes.
- **Paths stay REST-like.** The contract keeps the `/api/...` paths, so the OpenAPI document reads like the API and iOS calls plain URLs.
- **Two implementers.** `server/src/router.ts` implements the procedures the Worker serves. `server/src/account/router.ts` implements the ones the user's `Account` object serves, plus an internal `wipe` that account deletion calls through a typed oRPC client. The Worker forwards account requests to the object without reading their bodies, and it decides which requests to forward from the contract's own routes. Validating twice would cost Worker CPU on a large first sync.
- **Validation is the contract's.** oRPC rejects an invalid input with a `400` and checks every output on the way out. Errors are oRPC's JSON body (`code`, `message`, `data`) with the same status codes as before. Clients branch on the code, so every error the server answers outside an oRPC handler, such as the Worker's forward to the `Account` object, uses the same body through `server/src/errors.ts`. The push test reports oRPC's `GONE` and `BAD_GATEWAY`, so no status map is needed. Requests need a JSON content type.
- **iOS outboxes get one repair.** `POST /api/sync` bodies pass through `repairBooleanNumbers` before the contract validates them, for iOS builds that sent `0` and `1` as booleans.
- **Outside the contract.** Better Auth's `/api/auth/*` routes, except `/api/auth/methods`, and the two WebSockets (`/api/sync/socket` and `/api/ramble/socket`) stay as they are. A WebSocket upgrade is not something oRPC or OpenAPI can describe.

## Generated types

- **One generator.** `bun run generate` (`scripts/generate/index.ts`) writes the files below and rewrites a file only when its content changes. `bun run start` runs it in watch mode next to the server and client, `bun run build` and the iOS launcher run it first, Lefthook and CI run `generate:check`, and CI fails when a file is stale. Every output lives in a `generated` folder, which oxlint and oxfmt ignore.
- **One model for every client.** A type more than one client needs is defined once, as a table in `shared/db/schema.ts` or a Zod schema next to the code that makes it, with an `id` in Zod's registry (`.meta({ id })`). TypeScript types are `z.infer` of it, and Swift types are generated from it, so neither client restates a shape. Only what one client alone needs, such as the web's toasts or the iOS app's intents, stays in that client.
- **OpenAPI.** `shared/api/generated/openapi.json` is the contract as OpenAPI 3.1, with the named schemas as components.
- **Web.** The web client calls the API through `api` in `app-web/src/lib/api.ts`, a `JsonifiedClient<RouterContractClient>` typed straight from the contract. At runtime it ships only `app-web/src/lib/generated/contract.json`, the contract's routes without their schemas, so the bundle carries no validators it does not use. The sync loop still validates responses with `syncResponseSchema`, because the server can be a different deploy than the open tab.
- **iOS.** `scripts/generate/swift.ts` writes `app-ios/Sources/Core/Generated/API.swift` from every named schema, not only what crosses the network, plus one `API.Endpoints` descriptor per operation. It needs no Swift package, so the app keeps zero dependencies, and it builds on Linux with `Core`. Core's names (`TaskItem`, `Due`, `Snapshot`, `QuickAdd.Parsed`, `Search.Results`, and the rest) are typealiases of the generated types, and Core's behavior sits in extensions on them.
- **Swift that reads like Swift.** The generator shapes each type the way Core wrote it by hand:
  - Plain values become typealiases (`DateKey = String`). Integer enums get named cases from `x-enum-names`, and a schema `default` becomes `Priority.default`. String enums are `CaseIterable` and `Identifiable`.
  - `x-flatten` makes one struct of a union, as for `Recurrence`, whose `days` only a weekly repeat reads. `x-inline` gives a tagged union's cases their fields as associated values, as for `Reminder` (`.before(minutes:)`).
  - Every type is `Hashable`, and `Identifiable` when it has an `id`. Initializer defaults come from the Drizzle column defaults through `x-table`, from schema defaults, `nil` for optionals, and `[]` for arrays.
  - A field that is both optional and nullable is `T??`, as Core writes it: `nil` is missing and `.some(nil)` is `null`, which a sync patch depends on. `x-epoch-ms` keeps a `Date` in Swift for epoch milliseconds in JSON.
  - `x-swift-type` keeps Core's own type where it is deliberate: `SyncOp`, whose fields the diff handles as JSON values, `Range<Int>` for highlight spans, and the generic `NameHit` and `Suggestion`. `x-decode: custom` leaves the decoder to Core, as for the stored document, which drops a bad task on its own.
- **Validation at the boundaries.** `JSONDecoder.validating()` makes the generated types check every rule the Zod schemas check: bounds, patterns (translated to ASCII digits and an exact end, as in JavaScript), sizes, enum members, and named validators such as `isHlc` through `x-validate`. The API client, the sync request, and the stored document use it. Other decoders read only the shape, because shared functions accept values the wire rejects, such as a weekly repeat with one day.
- **The outbox repair.** `Core` builds the sync request from the outbox as `API.SyncRequest`, repairing the boolean numbers old builds stored first, since the typed request cannot hold them.
