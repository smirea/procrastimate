# API and database types

How the server's database, its HTTP endpoints, and every client share one set of types.

## Database

- **Drizzle owns the schema.** `shared/db/schema.ts` defines every account table once, for Turso and for the `Account` Durable Object's SQLite. Each row type the server handles (`Device`, `Entity`, `LogRow`, `PushTarget`, `RambleUsage`) is inferred from it. JSON columns take their types from the shared domain types, so a row's `data` is the sync core's `Fields` and a push target's `subscription` is `PushSubscriptionInfo`.
- **Every table is per user.** Each table but `ramble_budget` has a `user_id` column, in Turso and in the Durable Object alike, so one store implementation serves both. A Durable Object still holds a single user's rows.
- **Queries go through Drizzle.** `server/src/account/sqlite-store.ts` runs on any synchronous Drizzle SQLite database: `drizzle-orm/durable-sqlite` on the Worker and `drizzle-orm/bun-sqlite` in tests. Turso uses `drizzle-orm/libsql/web`. The only raw SQL left is in the migrator. Better Auth keeps its own Kysely adapter and migrations, because moving its tables would risk signing out every production session.
- **Migrations are drizzle-kit's.** `bun run db:generate` writes a migration to `server/drizzle/` and regenerates the bundle. CI fails when the schema has changed without a migration. The baseline migration uses `IF NOT EXISTS` because production Turso already had these tables before Drizzle.
- **Migrations are bundled.** Neither the Worker nor a Durable Object can read files, so `scripts/generate` writes `server/src/db/generated/migrations.ts`. `server/src/db/migrate.ts` applies it with drizzle-kit's own bookkeeping table: once per Turso database and isolate, and when an `Account` object starts. Tables from before `user_id` are dropped first.
- **Tests use real databases.** Store tests run on in-memory `bun:sqlite`, and Turso tests run on a local libSQL file, both through Drizzle.

## Endpoints

- **One oRPC contract.** `shared/api/contract.ts` declares every HTTP endpoint with its method, path, input, output, and typed errors. Inputs and outputs are the shared Zod schemas from `shared/sync/protocol.ts` and `shared/push.ts`, which describe wire and domain types, not database rows.
- **Paths stay REST-like.** The contract keeps the `/api/...` paths, so the OpenAPI document reads like the API and iOS calls plain URLs.
- **Two implementers.** `server/src/router.ts` implements the procedures the Worker serves. `server/src/account/router.ts` implements the ones the user's `Account` object serves, plus an internal `wipe` that account deletion calls through a typed oRPC client. The Worker forwards account requests to the object without reading their bodies, and it decides which requests to forward from the contract's own routes. Validating twice would cost Worker CPU on a large first sync.
- **Validation is the contract's.** oRPC rejects an invalid input with a `400` and checks every output on the way out. Errors are oRPC's JSON body (`code`, `status`, `message`, `data`) with the same status codes as before, so clients still branch on `401`.
- **iOS outboxes get one repair.** `POST /api/sync` bodies pass through `repairBooleanNumbers` before the contract validates them, for iOS builds that sent `0` and `1` as booleans.
- **Outside the contract.** Better Auth's `/api/auth/*` routes, except `/api/auth/methods`, and the two WebSockets (`/api/sync/socket` and `/api/ramble/socket`) stay as they are. A WebSocket upgrade is not something oRPC or OpenAPI can describe.

## Generated types

- **One generator.** `bun run generate` (`scripts/generate/index.ts`) writes the files below and rewrites a file only when its content changes. `bun run start` runs it in watch mode next to the server and client, `bun run build` and the iOS launcher run it first, Lefthook and CI run `generate:check`, and CI fails when a file is stale. Every output lives in a `generated` folder, which oxlint and oxfmt ignore.
- **OpenAPI.** `shared/api/generated/openapi.json` is the contract as OpenAPI 3.1, with the shared schemas named as components.
- **Web.** The web client calls the API through `api` in `app-web/src/lib/api.ts`, a `ContractRouterClient` typed straight from the contract. At runtime it ships only `app-web/src/lib/generated/contract.json`, the contract's routes without their schemas, so the bundle carries no validators it does not use. The sync loop still validates responses with `syncResponseSchema`, because the server can be a different deploy than the open tab.
- **iOS.** `app-ios/Sources/Core/Generated/API.swift` holds a Codable type for every schema and one `API.Endpoints` descriptor per operation, generated by `scripts/generate/swift.ts` from the OpenAPI document. It needs no Swift package, so the app keeps zero dependencies, and it builds on Linux with `Core`. A field that is both optional and nullable becomes `Nullable<T>?`, because a sync patch tells a missing field from `null`. The app sends every contract call through `APIClient`, and `Core` builds the sync request from the outbox as `API.SyncRequest`.
- **No database types on the wire.** Deriving the wire schemas from Drizzle with drizzle-zod would add about 70 KB gzipped to the web bundle, so wire types stay Zod and row types stay Drizzle. The sync handler's log rows are checked against `changeSchema` by the contract's output validation.
