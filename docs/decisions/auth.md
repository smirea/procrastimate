# Auth

Sign-in is Better Auth, inside the `App` object. It stayed through the moves to Postgres and to sync-engine because leaving it would mean moving scrypt password hashes and Google and Apple identities, which nothing here can test, and it runs in-process with nothing to host. The signed-in user owns the tasks. An install id only names the install.

- **Sessions, not device tokens.** Email and password sign-up and sign-in. No password reset, because the app does not send email. Google and Apple sign-in use the web redirect on the web and a native sheet on iOS. iOS posts the identity token to `POST /api/auth/sign-in/social`. Sessions last a year and extend after a day online, so days offline do not sign anyone out.
- **Registration is closed in production, for now.** A Better Auth `user.create.before` hook refuses any new user but `steven.mirea@gmail.com` with `403 REGISTRATION_CLOSED` and the message `Not public yet, you know who to talk to for access`, which both clients show as is. It covers email sign-up and both social flows; AI accounts skip it because they are created through the raw adapter. It keys on `SENTRY_ENVIRONMENT=production`, the only marker the deploy sets, so dev and tests stay open. It has no tests on purpose: it is a stopgap that will be reverted.
- **Where the session lives.** The web keeps the Better Auth cookie. It also caches the user id in `localStorage` under `procrastimate-user`, because the cookie is httpOnly and the app must open offline. iOS keeps the bearer token from `set-auth-token` in the Keychain under `procrastimate-session`, readable after the first unlock so a background relaunch on a locked phone still opens signed in. It keeps no cookies: every API request goes through `APIClient.session`, which neither stores nor sends them, because Better Auth refuses a request that carries its cookie without an `Origin` (`403 MISSING_OR_NULL_ORIGIN`), and native requests send no `Origin`. A cached session opens the app. The launch's session check is `GET /api/sync/token`, which names the user beside the token, so a launch asks one auth request instead of a session read and then a token, and the first connect uses that token instead of asking again. A network failure, a 5xx, or a page that is not the server's JSON keeps the session. A `401` clears it and shows sign-in.
- **Who a request is from.** `server/src/actor.ts` turns the session, or an AI account's `pm.<ownerId>.<secret>` bearer looked up by its SHA-256 in `api_tokens`, into the `Actor` (`{ id, name, kind, ownerId }`). `requireHuman` keeps AI accounts off the human-only routes. A session bearer, which iOS sends, is resolved once a minute per Worker isolate and cached in memory, the same trust the web's signed cookie cache gives, so a request costs no session read and a token revoked elsewhere works for at most a minute; sign-out drops it from that isolate's cache at once. There is no actor header and no forwarding any more: the Worker serves every route itself. See [Sharing](sharing.md).
- **Better Auth's tables are Drizzle's.** Better Auth runs on its Drizzle adapter with `provider: 'sqlite'` over the one SQLite database, without its transactions, since the database is synchronous, and the server's additive migration creates its tables (`server/src/db/auth-schema.ts`) with the rest. `bearer()` serves iOS and the sync engine on both clients, and `session.cookieCache` lets a request trust the signed cookie for five minutes before reading the session row, which saves a query on most requests. See [API and database types](api.md).
- **Rate limits live in the database.** Better Auth stores its rate limits in the database, so every request enforces the same ones. `AUTH_RATE_LIMIT=off` turns them off for the Bun dev server, unit tests, and the end-to-end runs, which sign up many users from one address. Production never sets it.
- **Sync tokens.** Sync carries the session's own token as a bearer; a signed-in human reads it from `GET /api/sync/token`; see [Sync tokens and access](sync-auth.md).
- **No JWT sessions.** Moving sessions to JWTs was weighed to cut auth requests and turned down. The server already skips most session reads (the cookie cache and the bearer cache above), a short-lived JWT needs a refresh call, and a refresh token that rotates would race between the app, its extensions, and a future Watch, which today share one long-lived session string. The token route doubles as the session check, and the sign-in methods load only on the sign-in screen.
- **The install id is not a secret.** A client-made id stored device-locally, sent as `x-procrastimate-device` on the push routes and Ramble, and on a browser WebSocket as the `device.<id>` subprotocol. There is no device table, no device list, and no revoke screen; the session is the credential.
- **Switching users does not upload the previous list.** The local database remembers who it belongs to, including after sign-out: on the web in its own local-only `procrastimate_owner` table, on iOS in `procrastimate-owner` in `UserDefaults`. The web's browser storage commits with relaxed durability, so a page closed right after a commit may lose it, though never out of order; a name kept in `localStorage` once outlived a clear lost that way and showed the previous account's rows. The web still writes `procrastimate-owner` to `localStorage` after the table, only so other tabs notice the switch. A different user stops sync and resets the engine's database (every synced table, its outbox, and its client id), so nothing of the previous user's uploads. The web records the new owner only once the reset worked and tries a failed one again, so the database never belongs to someone while it holds another account's rows. Every other open tab reloads when the owner changes, since its tab still reads as the previous account. Sign out keeps the database.
- **Sign-in is the first screen only without a session.** The screen is the glass card: email and password, and Sign in with Google or Apple when `GET /api/auth/methods` says those providers are configured. Only the sign-in screen asks, so a signed-in launch never does. Missing credentials hide the button, so CI boots without them.
- **Settings.** Delete all data deletes every own row locally, and the engine syncs the deletes. Sign out drops the session and keeps the local database. There is no account deletion, in the clients or on the server.
- **Secrets.** `BETTER_AUTH_SECRET`, the Google client ids and secret, and the Apple Services ID, client secret, and key material live in the root `.env` schema and go out through `secrets:push`. An empty value omits that provider. The Bun dev server and `.dev.vars` use a fixed insecure auth secret when env-manager leaves it empty.
- **iOS tests.** `PROCRASTIMATE_SIGNED_IN=1` is DEBUG-only. It shows the app without a Keychain token and does not call the server. Release ignores it. App Intents keep using the local store.
