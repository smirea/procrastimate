# Subtasks

- **Subtasks are tasks.** A subtask is a `Task` with a `parentId` and an `order` among its siblings, not a checklist item. It has its own date, repeat, priority, reminders, notes, and subtasks, so nesting has no depth limit. This matches Todoist, and it keeps one shape for reminders, search, and sync.
- **Where they show.** Project lists and `No date` show top-level tasks only, and a parent row shows a progress ring with `done/total` for its direct subtasks. A dated list (Inbox, Tomorrow, This week, and the widgets' Today) lists a dated subtask as its own row, marked with its parent's title, only while no task above it has a row in that same list, because a date is a commitment on its own but the parent's row already carries it. With a listed parent, grandparent, or any task higher up, the subtask shows only as that task's progress and preview, as in a project; when the nearest listed task is several levels up, its ring still counts only its direct subtasks, and the subtask is a tap away in details. The list's filter menu runs first and visibility is judged on the rows it keeps, so a filter that hides the parent lets its dated subtask show on its own row, as the parent is not visible. The filter menu counts that surfaced row too. A list is everything it covers: in Inbox a parent due next week hides its subtask due today, while the widgets' Today, which covers only overdue and today, lists that subtask. This lives in `dated` in `shared/views.ts` and its Swift port.
- **A completed parent sets its subtasks aside.** A task counts as open only while it and every task above it are open (`openTasks` in `shared/triggers.ts`, `Triggers.openTasks` in Swift). Completing a parent already completes its subtasks, but a write from another device, the agent API, or older data can leave an open task under a completed one, and that task is then treated as done everywhere: lists, counts, the Inbox badge, widgets, local and push notifications, Spotlight, and search, which lists it with the completed results. It reads as completed when its nearest completed ancestor was (`completedAtIn` in `shared/triggers.ts`, `Triggers.completedAt` in Swift): rows, search included, draw it checked with that date, the parent's progress ring counts it done and its preview drops it, and Siri's Complete never picks it while Uncomplete reopens it with its parents. Its own `completedAt` stays as stored, so reopening the parent brings it back. A parent missing from the tasks at hand does not count, so a share that holds a subtask without its parent still lists it.
- **Counts follow rows.** Every count and badge counts the rows its list shows, so a list with no visible rows never shows a number. The Inbox tab badge counts Inbox's own overdue and today rows (`dueDays(…, 'inbox')`), not a separate today query, so a subtask hidden under a parent due later is not counted.
- **Open subtasks preview on the parent row.** A row with open direct subtasks lists their titles on one line under the title and notes, in sibling order, each after a faint `〇` with a wide gap as the only separator, so the list reads as a checklist without commas. The line truncates with an ellipsis like the notes line, so a long checklist never grows the row. Completed subtasks drop out, and the line goes once none are open. The progress ring stays in the details line below, because it counts what is done and the preview only shows what is left. Every `TaskRow` shows it, so a subtask row in task details previews its own open subtasks too, and so does a public link's row on both clients. iOS's link rows leave out subtasks the link already lists as rows of their own, as a shared task does. It reads the store, so it updates in place the moment a subtask is checked, with no animation: a title leaving a single muted line needs none. Grandchildren are not listed on the top row, since a direct subtask's own row already previews them in details.
- **Adding in quick add.** Quick add takes subtask lines under the title and saves them with the new task. See [Quick add](quick-add.md).
- **Editing.** Task details lists the subtasks under the notes, with a field that adds one on Enter and keeps focus for the next. The field parses dates, repeats, priority, reminders, and `@` labels like quick add. It has no `#` project, and a `#Name` in a subtask's title stays text, because a subtask always shares its root task's project, and moving a parent moves every task under it. Tapping a subtask opens its details in the same sheet, sliding in like a navigation push, and a back chip with the parent's title replaces the project picker. Going back returns to where the parent was scrolled, on the web as on iOS. Opening a task afresh starts at the top.
- **Task details scroll.** The date, repeat, priority, and reminder chips sit under the title, outside the scrolling body, so their menus never clip. The notes and subtasks scroll on every screen size, so a long checklist never pushes `Add subtask` off a phone screen. `Complete` and `Delete` float over the bottom corners, and the body pads its end to clear them.
- **Subtask rows are task rows.** Task details lists subtasks with the same row component as every list (`TaskRow` on both clients), so a subtask shows its labels, notes, date, repeat, reminders, images, comment badge, and progress like any task. Placed as a subtask, the row differs where a parent's checklist needs it to: it stays when done, struck through, and checking toggles it in place; tapping it pushes its details; it drops the `Subtask of` marker, since the parent is right above; and it ends with the reorder handle. Postpone works the same as in a list: the hover button on the web, and on iOS a swipe, where swiping right completes or reopens and swiping left postpones. iOS 27 runs `swipeActions` outside a `List` too, so the details' scroll view needs no custom gesture, but there swipe actions keep the buttons and closures they were first built with. So `TaskRow` derives its swipe buttons from one hashable value (complete or reopen, and whether it can postpone) and keys the row on it, rebuilding the row whenever what the swipes offer changes. An edge with nothing to offer, such as a done subtask's trailing edge, is left off rather than attached empty: outside a `List` an empty edge still swipes open, to nothing, and the next swipe the other way only closes it. Any new row that swipes outside a `List` needs the same. The details' scroll view takes `swipeActionsContainer()` (iOS 27), which gives the rows a `List`'s coordination: an outside tap or a scroll closes an open row, and only one row is open at a time. The subtasks stay out of a real `List`, which would bring that for free, because a `List` can't sit inside the page's one scroll view without scrolling on its own, and the handle drag lifts a row over its neighbors, which a list's cells don't allow. A done subtask gets no trailing action, since a done task has nothing to postpone, and its context menu already deletes.
- **Titles wrap.** A subtask row shows its whole title over as many lines as it needs, because a subtask is often a note to self that loses its point when cut off.
- **Reorder.** Drag the handle on a subtask row, by mouse or touch, or focus it and press the up and down arrows. The rows it passes slide out of its way, and it settles into place on release. Near the top or bottom edge of the scrolling area the drag scrolls it, faster the closer it gets. On the web, subtasks and the sidebar's projects share one drag helper, `Reorder` in `app-web/src/lib/reorder.svelte.ts`: a subtask lifts at once from its handle, and a project row, which is itself a link, lifts after a few pixels of mouse movement or a long press. A lift measures each row's layout box, not its drawn one, so a row lifted while its neighbors still slide from the last move drops where the pointer puts it. Order persists. A move writes only the moved subtask's fractional `order`, so moves on two devices do not overwrite each other (see [Sync](sync.md#conflicts)).
- **Completing a parent completes everything under it.** Checking off a task completes every open subtask under it, at every depth. Undo puts back exactly the tasks the completion changed, and only their completion, date, and reminders, so subtasks that were already done stay done and edits made since survive. An open task never sits under a completed one, so reopening a subtask, or adding one, reopens its completed parents.
- **Checking a subtask in task details toggles it.** The checkbox is its own undo, so there is no toast. Completing a subtask with `Complete` in its own details returns to the parent.
- **Recurring parents reset their subtasks.** Completing a recurring task moves it to its next occurrence and reopens every subtask under it, so each occurrence starts with a fresh checklist. Subtask dates do not move with the parent. Undo restores the parent's date and every subtask's state.
- **Reminders stay per task.** A subtask notifies at its own due time and reminders, like any task, while it and every task above it are open. Completing a parent completes its subtasks, which silences theirs. Subtasks do not inherit the parent's reminders.
- **Search finds subtasks by their own text.** A subtask is a result like any task, matched on its own title and notes, never its parent's. Its row names its parent under the title, and opening it shows the back chip to the parent.
- **Labels are per task.** A new subtask starts with only the labels typed into it and never inherits or follows its parent's, unlike the project. A label marks the task it is on, so a label view lists only the tasks that carry it. This matches Todoist.
- **Turning subtasks into tasks.** The `…` menu on the Subtasks heading in task details turns a task's direct subtasks into tasks of their own, in one of three ways: keep their titles, start each with the parent's title (`Plan trip: Book flights`), or inherit the parent's labels, date, and priority wherever a subtask has none. Inheriting copies the date but not the repeat, because the repeat is the parent's routine, and it leaves a subtask on a calendar event alone. The project needs no copying, since a subtask already shares its root's. The parent stays, now without children, because it often still means something on its own, and deleting it is one tap away. Each subtask moves up one level and keeps its own subtasks: a top-level parent's become top-level tasks, and a nested parent's sit right after it among its siblings. Completed subtasks move too, so the parent is left with none. The toast's `Undo` writes back only the fields it changed (parent, order, title, labels, date, and priority). A subtask whose parent was deleted since stays where it is, so it never goes unreachable. The action shows only on tasks in the user's own space: moving a subtask up can carry it out of what a share grants (a shared task's subtasks, or a label share's unlabeled ones), the server would refuse the edit, and a guest's client cannot see the grant to tell. It is a store command in `shared/store.ts` (`explodeSubtasks`) with a Swift port, and it syncs as ordinary field edits. Ramble's parse-time promotion, which drops a parent with no title, works on a parse tree rather than stored tasks, so the two share no code.
- **Delete takes the subtree.** Deleting a task deletes every subtask under it, and undo restores all of them. Deleting a project deletes its tasks, subtasks included.
- **Stored data.** Tasks stored before subtasks existed load as top-level tasks. A subtask whose parent is missing, or whose parents loop, loads as a top-level task so it never goes unreachable.
