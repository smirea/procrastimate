# Quick add and natural language

- **Todoist quick add is the reference.** One input captures the title and its attributes. Recognized phrases are highlighted inline as you type and removed from the saved title. A typed phrase always parses unless the `Plain text` chip is on. To undo one, Stefan edits the text or clears the attribute from its chip's menu: `No date` for the date, `Priority 4` for priority, and `Inbox` for the project.
- **The same parser runs in quick add and in the task details title field.**
- **Plain text, per task.** The first chip in quick add's row is a `Plain text` toggle (`TextT` on the web, `textformat` on iOS). On, the parser reads no phrase (`literal` in `parseQuickAdd`'s options), so the whole text, whitespace collapsed, is the title: no highlights, no `#`/`@`/`/` suggestion lists, and no `Create` chips. Values picked with chips and menus still apply, and suggestion pills still show, since they come from history rather than from the text. It belongs to one task: every new draft, including the next one after a save in an open sheet, starts with it off, because a task that needs it is the exception and a sticky toggle would silently stop parsing the next one. It is not a pinnable button, so it always leads the row. Subtask lines and the task details title still parse.
- **Saving keeps quick add open for the next task.** After a save the title clears and keeps focus, so Stefan can type several tasks in a row; on iOS the keyboard stays up, and the web's `Add task` button never takes focus from the title. The next task starts from `reusedDefaults` (see Reuse below): the saved task's project, section, labels, place, and event, plus the date the sheet opened with, so a batch typed into a day group stays on that day. The draft's own date, priority, repeat, reminders, subtasks, images, and chips opened from the `+` menu clear. Nothing navigates while the sheet is open, because a list changing behind it would yank the context Stefan is capturing in. Feedback stays small: when the open list shows the task, its row scrolls into view behind the sheet and flashes; otherwise a toast names where it went (`Added to No date`, `Added to Inbox`, or the project's name) with a `Show` that closes quick add and opens that list with the row flashing. Each save replaces the previous save's toast, so a batch leaves one. iOS also plays a success haptic. Escape, `Cancel`, a scrim tap, and the phone sheet's swipe down close it and discard only the unsaved draft. `Open in task details` still saves, closes quick add, reveals the task in its list, and opens its details. Quick add used to close and show the task after every save; that made each extra task cost a reopen, and the `Show` toast keeps "see where it went" one tap away.
- **Quick add stays a capture surface, not a second details editor.** It holds what Stefan types in one motion: the title line, its chips, subtasks, and images (see [Images](images.md)). Notes, location and event edits beyond their chips, and reordering stay in task details, which is the full editor. A full form would slow the common case, a one-line task saved with Enter, to serve the rare one that task details already covers right after saving.
- **Expanding into task details.** Quick add stays the capture surface, and task details is its full mode. On the web the expand button (`Open in task details`) sits in the footer beside `Cancel`. On iOS a faint grabber tops the card, the standard affordance for a card that grows: dragging it up past about 60 pt, or flicking it up, expands, and a tap or the accessibility action does too. Expanding saves the draft exactly as `Add task` does, with every typed and picked attribute, the subtask list, a line still in the subtask field, and the images, then closes quick add, reveals the task in its list, and opens its details. Nothing is lost, because the same save path runs. It works without a title too, as the switch to the full editor before typing anything: it saves an untitled task with whatever metadata the draft holds (date, priority, project, labels), and details open with the title focused. Closed while still untitled, by any route (Close, Escape, the scrim, a swipe), that task is deleted outright with no undo toast, because it was never a task; the title being edited commits first, so a typed title always saves. On the web every sheet change blurs the focused field, since iOS Safari never blurs it for a tap on the scrim or a button. Widgets never list an untitled task, so the brief draft never reaches the home screen. The brief blank row in lists and sync is accepted for a one-user app. Task details edits a saved task in place, so a draft details editor would duplicate it; a task expanded by mistake is deleted from details. The button used to be disabled without a title, and Stefan read the dimmed button as broken.
- **Reuse on the same screen.** The next task in an open sheet, and the next quick add opened later on the same screen without a group of its own (`q`, the floating or tab bar `+`, the sidebar, or an empty list's bare `Add task` row), starts where the last task went: its project, section, labels, saved place or location, and event. Its date, priority, repeat, and reminders belong to one task and are not reused. The date comes from the sheet or screen instead: an open sheet keeps the date it opened with, and a later quick add takes the screen's own, so Tomorrow keeps adding to tomorrow. Leaving the screen forgets the last task, and so does `Open in task details` when it opens another list. A group's own heading `+`, such as a section's or an Inbox day's, always starts with that group's defaults. Reuse is one more source of `ListDefaults`, the same value a heading prefill passes, so `labelIds` holds every label rather than one. `reusedDefaults` in `shared/screens.ts`, ported to `Screens.reusedDefaults`, owns what carries over. The memory lives with navigation: `quickAddDefaults` and `reuseAdded` in `app-web/src/lib/screen.ts`, and `Navigator.listDefaults` and `reuseAdded` on iOS.
- **Suggestion pills from history, by word matching, with no AI.** While Stefan types, dashed pills under the title offer the project, labels, and place that similar past tasks were filed under, and a tap sets one. A section joins the project pill (`Home / Garden`) only when nearly all of that project's matching tasks sit in it (see the section eval below). The rule is `shared/task-suggestions.ts`, ported to `TaskSuggestions`. It finds the eight past top-level tasks, open or completed, that share the most rare words with the parsed title, and weights each by how closely it matches and how recently it was created, so a habit that changed wins over the old one. A value shows only when the tasks that hold it carry at least half the vote. A task without the field votes too, so a word that only sometimes means Home shows nothing, and a tie shows nothing. Places match by spot (`placeKey`), whatever each task named them, and a saved place's pill checks its label. No pill repeats what the draft already holds, or names a project, section, or label the draft cannot use.
  - **Where quick add opened is deliberate.** Quick add opened in a section, from its heading's `+` or its iOS menu, starts in that section, and a project screen in that project. Stefan put the task there on purpose, so a pill that would move it is a contradiction, not a convenience: a draft already in a project shows a pill for another project only when that project holds 90% of the vote (`sure`), and a pill for another section of its own project only when the section is sure too. A sure section is still offered inside its project, or over another of its sections, because a more specific place does not fight the one Stefan chose. Inbox is no placement, so a draft there gets the half-vote project pill as before. Stefan asked for this in October 2026. There are no time suggestions: a typed time already comes from the parser, and habitual times scored worst in the research.
  - **Why no model.** The October 2026 research (PR #210) compared this word matching with Apple's on-device model on made-up history. Word matching scored 93% precision and 87% recall on familiar wording in under a millisecond. The model alone scored 37 to 64% precision at 1.2 to 4 s per call, exists only on iOS, and mostly invented labels and places. A model fallback for new wording added a little recall for a second of latency, so it was dropped.
  - **Real history.** Rerun on a snapshot of Stefan's real data (278 top-level tasks over two weeks, each suggested from the tasks created before it): 82% precision and 67% recall overall, 83% and 71% on familiar wording, 81% and 65% on new wording, and 81% and 67% with only half the words typed. Always offering the most used project scores 92% and 66%. Projects are nearly always right (197 of 201 shown project pills, 98%). Labels and places are too rare in the history to show yet. A suggestion takes under 0.1 ms; the index over every task builds in about 2 ms per 300 tasks, once per quick add (on the first keystroke on the web, off the main actor when the card opens on iOS). Rerun with `bun scripts/suggestions-eval.ts <view.json>` on a `GET /view` snapshot; it prints aggregates only.
  - **Section pills only when sure.** On the same history, sections were the weak field: only one project uses sections, its tasks split about 60/40 between Features and Bugs, and both read alike (a bug and the feature it breaks share their words). The shipped half-vote was right on 59% of 135 shown section pills, barely above guessing the bigger section. None of the strategies tried reached a useful precision (shown pills that were right, then the share of sectioned tasks that got one): a stricter vote (two-thirds 60%/22%, 0.9 73%/5%), voting only among the project's tasks (0.9 81%/7%, on 16 pills), naive Bayes on the project's per-section words (posterior 0.9 63%/26%, 0.95 65%/18%), per-word log-odds signal words (about 40%), at least 20 or 40 past tasks in the section (55%, 52%), the last section used in the project (59%/54%), recency-weighted neighbors (64%/41%), requiring the vote to agree with the last section (72%/33%), and a gate that hides sections when the rule's own leave-one-out precision on the project's recent tasks is under 80% (58% on 12 pills). The only results near 80% rest on fewer than 20 pills, so section pills were first removed. They came back at the best of those strategies, 90% of the vote among the project's own matching tasks (81% precision), because a rare but right section pill is what makes the quiet rule above useful. Taking them out had left project accuracy as it was, and adding them back leaves it too. Re-measure when more projects have sections with real history.
- **Every space's names, on both clients.** Quick add parses, suggests, and lists in its project menu the projects, sections, and labels of every space a new task may land on: the user's own and every shared project or label shared to edit. One shared to view only is left out, because the server refuses a task there (`canAddTo`, `Screens.canAdd`). Picking a shared project, or typing it, moves the new task into that space, as `creationHome` routes it, so Stefan can file into a shared project from any screen. The labels picker lists, and creates in, the space the task will land in, and creating a project or label from `#` or `@` makes it in the user's own space. iOS used to offer only the screen's space; it now reads `Store.everySpace` under the `namesFromEverySpace` environment flag, which task details never sets, since a saved task never leaves its space.
- **The mic and the `+` share one corner.** The Ramble mic in the title's corner and the chip row's `+` are the same size (36 px on the web, 32 pt on iOS) and sit on the card's right padding edge, one above the other, so they read as one column.
- **Subtasks in quick add.** The checklist chip, or `Subtasks` in the `+` menu, opens a subtask field under the title. Return adds the line to a list under the title and keeps focus for the next. Each line parses like task details' `Add subtask`: dates, repeats, priority, reminders, and `@` labels, with no `#` project. Each line shows its parsed date, repeat, and labels, and an `×` removes it before saving. Saving creates the parent, then each subtask in order under it, including a line still in the field, and then clears the draft for the next task like any save, the parent's row showing `0/n`. Return in the title field still saves, and Return on an empty subtask field saves too, so a list ends with a double Return. The chip shows the count once lines exist. An empty field with no lines closes when it loses focus, and on the web Backspace in it returns to the title. Escape or `Cancel` discards the title and every subtask.
- **Repeated phrases.** Date, recurrence, priority, and project take the last matching phrase, because attributes usually trail the title. `Today task today` saves `Today task` due today. Reminders and labels keep every match.
- **The configuration row is the only timing readout.** Below the input, the date chip shows the parsed date and time, and chips show the repeat and each reminder, so Stefan can read what will be saved. In task details the chips show the title's parsed values while he edits, before Enter or blur saves them. A due time still notifies on its own, as the Reminder entry in [Domain](domain.md) describes. A glass timing preview above the input, such as `Tomorrow at 5:00 PM · Notifies at 5:00 PM · Repeats every Mon`, was removed from quick add and the task details title because it repeated that row. The add-subtask field dropped it too, so its highlighted phrases are the readout until the subtask is added.
- **One scrolling chip row with a `+` menu, as in Todoist.** The attribute chips sit on one line that scrolls sideways and never wraps, and the end that has more chips past it fades. A `+` pinned after the row opens a menu of every attribute action, including the ones not shown in the row. Picking one shows its chip for this draft, scrolls to it, and opens its picker. `Subtasks` opens the subtask field instead, and on iOS `Priority` is a submenu with the four levels. A wrapping row grew taller with every chip and pushed the input around above the keyboard, and the `+` keeps rare attributes one tap away without spending row space on them.
- **Pinned buttons are a synced setting.** Stefan picks which buttons the row shows, from the `+` menu (a pin beside each action on the web, a `Customize row` submenu of toggles on iOS) or from `Quick add buttons` in Settings. The choice is `quickAddButtons` on the synced settings record, so web and iOS show the same row. It defaults to Todoist's row: Date, Priority, and Reminders, plus the subtask checklist quick add already had. The list's order is the row's order: a newly pinned button goes last, and Settings reorders the list. A button that shows only because it holds a value follows the pinned ones in the default order. The `+` menu stays in the default order, so a pin toggled there never moves the row under the pointer. `moveButton` takes the neighbor to land before instead of an index, so the web reorders around `location` and `event`, which it hides, without moving them. `shared/quick-add-buttons.ts`, ported to `QuickAddButtons`, owns the order, the toggle, and the move rules.
- **A set attribute always shows.** An attribute that holds a value, whether typed, picked, or from a list default, shows its chip even when it is not pinned, so the row stays the readout of what will be saved.
- **Chip order.** Date, Priority, Reminders (with each typed reminder spelled out after it), Repeat, Labels, Subtasks, then on iOS Location and Event, then the `Create #name` or `Create @name` chips. The order is fixed, so a chip never moves when another appears. The web has no Location or Event chip, since only iOS picks them; a saved place shows in its Labels chip. A picked event hides Date and Repeat, as in task details. Labels is one chip with every label, typed or picked; unchecking a typed label in its picker removes the `@name`. A repeat picked with the Repeat chip replaces a typed one, and moves the date when the repeat starts on another day. A set priority fills the flag with its level's color (P1 red, P2 orange, P3 blue) on a capsule tinted with that color, and Priority 4 is a plain gray outline flag. Task details keeps its labeled `Priority` chip.
- **Pickers win over text.** Choosing a date, priority, or project with a picker removes the matching phrase from the input. Pickers close on selection, except the due picker's calendar, which stays open so a time can follow.
- **One due picker.** The date chip in quick add and task details opens one popover with four preset tiles (`Today`, `Tomorrow`, `Next week`, and `No date`), a month calendar, and a time row. Every pick commits at once. Tiles, not rows, keep it short enough to sit above the iPhone keyboard. The web draws its own Monday-first calendar, because the native date and time inputs were clumsy on desktop. iOS uses the native graphical `DatePicker`.
  - **Add time never commits a default.** `Add time` swaps the calendar for a time view: on the web a field that reads typed times such as `5:30pm` (the quick add time grammar) above a list of half hours, opened at the set time or the next half hour, and on iOS a wheel with a `Set <time>` button. Only a time Stefan picks, types, or scrolls to is saved. The old `Add time` saved 9am at once.
  - **A picked time never lands in the past.** It keeps a date still ahead. With no date, today's date, or an overdue date, it lands on the next time that clock time comes around, today or tomorrow once it has passed, the same rule as a typed time with no day. A calendar day picked after the time is a chosen day and wins. `dueAtTime` in `shared/task.ts`, ported to `Dates.dueAtTime`, owns the rule, and quick add's parser calls it for a time with no typed day.
  - **Removing the time** is the `x` beside the time row, which keeps the date.
- **Days.** `today`, `tomorrow`, and `tom`, `tmr`, `tmrw`. `tonight` is today at 8pm. `eod` is today at 5pm. `eow` is the coming Friday at 5pm, today on a Friday. A typed time replaces these default times, as in `tonight 9pm`.
- **Weekdays.** `mon` to `sun` and the full names mean the next one, counting today, so `wed` on a Wednesday is today. `next fri` and `nxt fri` mean the Friday of next week, which starts on Monday. `next week` is next Monday.
- **Offsets.** `2d`, `1w`, `2wk`, `3mo`, and `in 3 days`, `in 2 weeks`, `in 3 months`, `in 1 year` set a date with no time. `5m`, `5min`, `5 mins`, `2h`, `2hr`, `2hrs`, `2 hrs`, `in 2 hours`, and a bare `in 30` set the date and time that many minutes or hours from now. `mo` always means months and `m` always means minutes. Spelled-out units such as `2 hours` or `3 days` need `in`, because a bare length such as `study 2 hours` is not a due date. Months clamp to the end of a shorter month, so Jan 31 plus `1mo` is Feb 28.
- **Dates.** `oct 15`, `15 oct`, `15th october`, `the 15th`, and `10/15` or `10/15/2027`. A month name may be short or full, in any case, with a period after a short one (`Dec. 25`, `Sept. 30`), and the day may take an ordinal either way round, including `October the 20th`, `20th of October`, and `the 1st of December`. A weekday before it, as in `Monday, October 19` or `tue oct 20`, is part of the phrase and the date wins. A month and day can take a year, as in `jun 21 2027` or `may 23, 2027`, which is how Todoist writes dates beyond this year. A `20th of` needs its ordinal, so `chapter 3 of may` stays text. The day may be spelled out, from `first` to `thirty-first`, as in `October twentieth`, `Oct twenty-first`, `November the third`, or `the third of May`, because dictation sometimes writes ordinals as words. `the fifteenth` is the next 15th, like `the 15th`, but before an ordinary word a spelled-out day stays text, so `Pick the third option` keeps its words. `of the month` after a day is part of the date in either form, so `Meet the 1st of the month` and `Meet the first of the month` both save `Meet` due the next 1st, rather than one leaving `of the month` in the title and the other staying text. A day before a weekday is the nth weekday of a month, from the 1st to the 4th or the last: `the 1st Monday`, `the first Monday`, `the last Friday`, and `the first Monday of the month` are the next one, counting today, and `the first Monday of November` or `the last Friday of December` is the next one in that month. Before an ordinary word it stays text whole, so `Plan the first Monday meeting` sets no date. `the 5th Monday` stays text whole too, because most months lack one, the same rule as `every 5th Monday`. A spelled-out day before the month needs `of`, so `the first May draft` stays text, and a lowercase `may` or `march` before one is the verb, so `we may first need` and `they march second` stay text. A date without a year is the next one, counting today, so `feb 29` outside a leap year is the next leap day. A year below 1000 stays text. `the 15th` is the next 15th. Slash dates are month first, unless the first number cannot be a month, so `15/10` is October 15. When neither number can be a month, as in `15/14`, it stays text.
- **Times.** `5pm`, `5 pm`, `5p`, `11a`, `5:30p`, `17:30`, `1730`, `noon`, and `midnight`, optionally after `at`. `@` followed by a space means `at`, as in `Oct 2 @ 3pm` or `@ 3pm`, because people type it that way, while `@3pm` and `@name` stay a handle or a label. A time can sit before or after a day, as in `fri 5p` or `9am fri`, and a comma may separate them, as in `Oct 19, 10am` or `October 20th, 2027, 3pm`, because dictation writes dates that way. Without that, the day and the time were two phrases and the time alone won, so the date was lost.
- **A bare hour after `at`.** `at 10`, or `@ 10`, with no minutes or am/pm is a time, as in `Dentist November 3rd at 10`. 1 to 6 mean the afternoon (`at 3` is 3pm), 7 to 11 the morning (`at 10` is 10am), 12 is noon, and 13 to 23 read as 24-hour times. That follows when appointments usually fall, the way Todoist reads a bare hour as we remember it; we have not checked it against live Todoist. The hour needs `at`, so `Number 10` stays text, and it cannot be followed by an ordinary word, a decimal, or `%`, so `Look at 3 options`, `at 10.5`, and `at 10%` stay text. A word after it must start a whole phrase: a day, with or without `on`, or another phrase such as `p1`, `in 2 days`, or `every mon`, as in `at 10 tomorrow` or `at 3 on fri`. So `Look at 3 on the list` stays text. Punctuation may follow, as in `at 10, bring forms`. Speech reads it the same way, since dictation writes `at 10` for a spoken time.
- **Punctuation after a removed phrase stays on the title.** `Pay rent October 20th.` saves `Pay rent.`, and `Call mom tomorrow, then dad` saves `Call mom, then dad`. A comma or colon left at the very start, as in `Tomorrow, call mom`, is dropped.
- **A time with no day.** It lands on the next time that clock time comes around. That is today, or tomorrow once the time has passed, so `9am` typed at 10am is tomorrow at 9am and `midnight` is the coming midnight. A time equal to the current minute stays today. A typed day always wins, even if that leaves the time in the past, as with `wed 9am` typed on Wednesday at 10am. A time with no day uses the date set outside the text when there is one, such as the task's existing date in task details or the Today default in quick add, unless that would put it in the past. Then it takes the next time that clock time comes around, so `9am` typed at 10am from Today is tomorrow at 9am, and `9am` on an overdue task is the next 9am. A repeat with no typed date follows the same rule. This matches Todoist as far as we remember it. We have not checked it against live Todoist.
- **Recurrence.** `every day`, `daily`, `weekly`, `monthly`, `yearly`, `every week`, `every mon`, `every 2d`, `every 2 weeks`, `every 3mo`, `every other week`, `every weekday`, `every workday`, or `weekdays`, and a yearly repeat on a date, `every march 2nd` or `every 2nd march`, which starts on the next one, counting today. It takes the month and day forms a date does, so the day may be spelled out, as in `every March second` or `every third of May`, and a spelled-out day before the month needs `of`, so `every second March` stays text. After `every`, a lowercase `march` or `may` is the month, not the verb. A date that does not exist, such as `every feb 30` or `every February thirtieth`, stays text. A monthly repeat on a day is `every 3rd`, `every 15th of the month`, `every month on the 20th`, `every month on the twentieth`, `monthly on the 5th`, `every 2 months on the 31st`, or `every other month on the 1st`. It starts on the next such day, counting today, and on the last day of a month that lacks it, so `every 30th` typed in February starts on the 28th. A typed date moves to the next such day on or after it. A bare `every 3rd` needs digits and no ordinary word after it, so `every 3rd day` and `Every second counts` do not repeat, and a spelled-out day needs `on the` or `of the month`. A monthly repeat on a weekday is `every 3rd Monday`, `every last Friday`, `every first Monday of the month`, `every second Tuesday`, `every month on the 3rd Mon`, `monthly on the last Friday`, or `every 2 months on the 1st Monday`, from the 1st to the 4th or the last. `every second Tuesday` reads as the 2nd Tuesday of the month, like `every 2nd Tuesday`, not every other Tuesday. That is our call, not checked against live Todoist. It starts on the next such weekday, counting today, and a typed date moves to the next one on or after it. `every 5th Monday`, `every fifth Monday`, and `every month on the 5th Monday` stay text whole and set no date, because most months have no 5th Monday and `last` covers what people usually mean. Reading only `Monday` as the date would leave `every 5th` in the title, and guessing `last` or every fifth week would silently save something other than what was typed. `every other Tuesday` is a weekly repeat with interval 2, starting on the next Tuesday, counting today, and `every other mon and fri` repeats on that set every 2 weeks. A task stores it as an interval and a unit (day, weekday, week, month, or year), plus a weekday set for a weekly repeat on several days, or a day or weekday of the month for a monthly repeat. A repeat on a named day such as `every mon` is weekly and starts on that day. A weekday repeat typed on a weekend starts on Monday. Any other repeat with no typed date starts on the date set outside the text, such as a picked date, or else today. If its typed time has already passed today, it starts one interval later. A typed date such as `every fri oct 30` sets the first occurrence. Quick add and the task title store the repeat. See Recurring tasks for what completing one does.
- **Several weekdays.** A list of two or more weekdays joined by spaces, commas, slashes, `and`, or `&` is one repeat on that set, as in `every mon, wed`, `every mon and fri`, `gym mon wed fri 7am`, or `tue/thu`. It starts on the first listed day, counting today, and moves to the next listed day when its typed time has passed today. A typed date moves to the first listed day on or after it. A list that names one day, such as `every mon, monday`, is a plain `every mon`.
- **When a bare weekday list repeats.** Without `every`, a list repeats only next to a time, as in `mon wed fri 7am` or `7am mon wed fri`, or when it is slashed, as in `tue/thu`. A slash is compact schedule notation, so it needs nothing else. Anywhere else, as in `Discuss mon wed plan` or `Swap tue and thu shifts`, the whole list stays text and sets no date, because it names no single day and is most likely prose. A single weekday next to a time is still a due date, so `Lunch fri 12pm` does not repeat.
- **Priority.** `p1` to `p4`. `!!!` and `urgent` mean `p1`. `!!` and `important` mean `p2`. A single `!` is never parsed, because it is common in titles.
- **Reminders.** `remind me 30m before`, `remind 5m before`, `remind me 1 hour before`, `r5m`, `r1h`, `r2d`, `r1w`, `remind me at 4pm`, and `remind me tomorrow 9am`. A reminder at a time with no date lands on the due date. With no due date it lands today, or tomorrow once that time has passed. Todoist uses a leading `!` for reminders. ProcrastiMate does not, because `!!` is a priority shortcut.
- **Words stay words.** Phrases only match whole words, so `mon` in `lemon` or `5m` in `2.5m` never parse. Before matching, the parser masks text that only looks like a phrase:
  - `Tom` or `TOM` is a name. Only lowercase `tom` means tomorrow, and not after a word that takes a person, such as `call`, `email`, `with`, `to`, or `for`.
  - `tom`, `sun`, `sat`, `wed`, `daily`, `weekly`, `monthly`, and `yearly` stay text when an ordinary word follows them, as in `sun hat`, `sat on`, or `Daily standup`. At the end of the text, or before a time, `at`, another phrase, or `and` plus a weekday, they parse. So `I sat and waited` stays text while `every sat and sun` repeats.
  - A bare weekday list with no `every`, no time next to it, and no slash stays text, as in `Plan mon wed fri rota`.
  - A number after an address word (`apt`, `unit`, `suite`, `room`, `floor`, and similar) or before a street word (`st`, `ave`, `rd`, `blvd`, and similar) is part of an address, so `Apt 5p` and `5p Baker St` stay text.
  - A bare `19xx` or `20xx` is a year. Write `at 2030` for 8:30pm.
  - A number after `$`, `€`, or `£`, or after a decimal point, is not a time or an offset.
  - `1/2` always reads as January 2.
  - A date or reminder that lands after 9999-12-31, as in `3929284d` or `in 8000 years`, stays text. Such a date is not a valid date key, and the server would reject the write.
  - A repeat longer than 999 units, as in `every 1000 days` or `every 99999999mo`, stays text, and its words are claimed so no other rule reads them: `1000` is not a time, and `x every 99999999mo 9am` saves `x every 99999999mo` due at the next 9am. A repeat whose first occurrence would land after 9999-12-31 starts on the date it would otherwise align from, such as today.
  - A word right after `#` or `@` is a name or a handle, so `@5pm`, `@tomorrow`, `@p1`, and `@urgent` stay text.
  - A link is never a phrase, so `5m`, `p1`, `3pm`, `#anchor`, or `@user` inside a URL or a Markdown link stays part of it. The parser masks every link `linkify` finds (see Links in [Domain](domain.md)) before any rule runs.
- **Parsing order.** Reminders claim their text first, then recurrence, project, section, labels, priority, and the due date. A later rule never reads text an earlier rule recognized, so `every wed 9am` is one repeat and one time. That includes an earlier copy of a repeated phrase.
- **Projects.** `#Name` assigns an existing project, matched case-insensitively. It is highlighted only when the project exists.
- **Sections.** `/Name` puts the task in a section of the project typed with `#`, else of the project quick add opened with, matched case-insensitively, as in Todoist. With no project in effect it stays text. `/` opens that project's sections with a create row, like `#`. See [Sections](sections.md).
- **Labels.** `@name` adds an existing label, matched case-insensitively, anywhere in the text. Every `@label` counts, and a label typed twice is added once. Like `#`, the `@` must start the text or follow a space, and the name must end the word, so `bob@site.com`, `you@calls`, `@calls.com`, and `@callsign` stay text. An `@word` that names no label stays in the title. Typing labels in the task details title adds them to the task's labels and never removes any. An `@name` that names a saved place sets the task's place instead, arriving there, and is highlighted as a `place` token. Saved places are labels, so a label and a saved place never share a name and `@name` always resolves to one of them. A task has one place, so the last `@place` wins, like `#project`. A typed place wins over one picked with the Location chip or the labels picker, and picking one removes the typed `@place`. See [Places and events](places-and-events.md).
- **`#` autocomplete.** Typing `#` at the start of the text or after a space opens a project list above the input, filtered by the text after `#`. The filter may contain spaces only while it still starts a project name, so multi-word names stay searchable. Picking replaces the fragment with `#Name ` and keeps focus in the input.
  - **Order.** Best match first: exact name, then name prefix, then word prefix, then substring, all case-insensitive. Within a tier, the project that most recently received a new task comes first, then alphabetical. Recency is derived from task creation times, so it needs no stored field.
  - **Create.** When no project name equals the filter, the last row offers `Create project "<filter>"`, which creates the project and inserts it.
  - **Keys.** Up and down move the selection, Tab picks, and Enter picks unless the filter already names a project exactly and the selection was not moved, so `Fix sink #home` plus Enter still saves. Escape closes the list for that `#` without closing the sheet. Tapping a row picks it.
- **Unknown names offer to create, never silently.** Todoist creates labels on the fly and offers to create projects. ProcrastiMate does neither on its own, because a stray `#` or `@` word should never add a project or label Stefan did not mean. Every `#name` or `@name` that names nothing yet shows a `Create #name` or `Create @name` chip in the configuration row, and only a tap on the chip, or Enter or Tab on the suggestion list's create row while the caret is in the name, creates it. Saving with the name still unknown keeps it as title text. The chip hides for the name the suggestion list is open on, since the list already offers it. A name is a sigil at the start of the text or after a space, then letters, digits, `_`, or `-`, ending at a space or the end after any sentence punctuation, so `@calls,` offers `calls` and `@site.com` offers nothing. Text the parser claimed is skipped, so `#Side Project` never offers `#Side`, and each name is offered once. The rule is `unknownNames` in `shared/name-search.ts`, ported to `NameSearch.unknownNames`. Quick add only: the task details title keeps an unknown name as text, and its labels picker creates labels.
- **`@` autocomplete.** `@` opens a label list with the same rules as `#`: the same fragment rules, order, create row (`Create label "<filter>"`), keys, and taps. Recency is the newest task carrying the label. When the caret follows both a `#` and an `@`, the nearer one wins. One suggestion list serves both, driven by a table of the two kinds, so a fix to one applies to the other.
