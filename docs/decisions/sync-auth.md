# Sync tokens and access

How a device proves who it is to the sync routes, and how the server decides which rows a user may sync and write. The protocol and conflict rules are in [Sync](sync.md); shares and guests in [Sharing](sharing.md).

- **Sync carries the session token.** `POST /api/sync` and `GET /api/live` take the Better Auth session's own token as a bearer, which Better Auth's `bearer()` plugin reads like a cookie, so there is no second token, no signing key, and nothing to rotate. iOS already holds it in the Keychain. The web reads it from `GET /api/sync/token`, which requires a human's session (an AI account never syncs; it uses the agent API) and answers the raw session token and the user, because both clients use this route as their launch session check. A revoked session is refused at its next request; the bearer cache trusts a resolved token for at most a minute. A browser cannot set a header on a WebSocket, so the web sends the token as the `bearer.<token>` subprotocol, and the server copies it into `Authorization` before it reads the session (`withBearer`); the raw token is base62, which a subprotocol allows.
- **The `access` table says what a guest sees.** One row per entity a grantee, a person or an AI account, may see in another user's space: `id` is `<grantee>:<kind>:<entityId>`, with `grantee`, `owner`, `kind` (`task`, `project`, `section`, `label`), `entity_id`, and `role` (`view` or `edit`). A task's role is whether the grantee may edit it. A project's, section's, or label's is whether a new task of theirs may land there, which `guestRefusal` allows only through an edit share on it or on the whole space, so clients decide `canAddTo` from the row alone. `server/src/access.ts` recomputes the rows with `scopeOf` from the space's links and shares: one grantee's after a change to that grantee's share, and every grantee's after a write only when it moved what a guest may see in a space shared with anyone but managers (`touchesAccess`, `recomputeAccess`), inserting new rows, updating a changed role, and deleting the rest, all through the engine (`ServerWriter`) in the transaction of the change, so they sync to their grantee. The rows also admit a guest's writes: `admit` reads them, one indexed query per space and request, and a task the request adds counts as editable for its later writes. The sync view filters each pull through them, on the entity id and on `access.owner = user_id`, so a row only ever opens the owner's own rows and the scope logic stays in `shared/scope.ts`. Links have no grantee and get no rows, and neither does a manager of the whole space, which sees everything.
- **Admission on sync.** `POST /api/sync` is for signed-in humans. `admit` finds the space each write names: a `put` claims one in its `user_id`, and a `patch` or `delete` lands in the space of the stored row. A `put` of a row stored in another space is refused with `Belongs to another space`, whatever `user_id` it claimed. A write to another user's space is a guest's, checked with `guestRefusal` against the guest's `access` rows there; a guest with no rows there is refused with `Not shared with you`. An AI account acts through the agent API only. With a whole-space edit share it manages the space and `space.write` runs with the owner's rights (`manages` in its context); with a narrower share it is a guest like a person, its writes checked by `guestRefusal` against its own `access` rows.
- **The install id.** `x-procrastimate-device` names the install for the push routes and Ramble, and on a browser WebSocket travels as the `device.<id>` subprotocol. It is not a credential; the session is.
