# Sync tokens and access

How a device proves who it is to PowerSync, and how the server decides which rows a user may sync and write. The protocol and conflict rules are in [Sync](sync.md); shares and guests in [Sharing](sharing.md).

- **The Worker signs PowerSync tokens itself.** `GET /api/sync/token` requires a Better Auth session of a human (an AI account never syncs; it uses the agent API). `server/src/sync.ts` signs `{ sub: userId, aud: 'powersync', iat, exp }` as an EdDSA JWT with the Ed25519 key in `POWERSYNC_JWT_PRIVATE_KEY`, a JWK whose `kid` goes in the header, through WebCrypto, for five minutes. Clients ask for a new token when PowerSync reports the old one expiring. Better Auth's JWT plugin is not used: it would make PowerSync fetch a JWKS endpoint from the Worker, and a key that rotates with Better Auth's table would have to reach every PowerSync config.
- **The public key is in every PowerSync config.** `powersync/dev/service.yaml` and `powersync/prod/service.yaml` list their environment's public JWK inline with `additional_audiences: ['powersync']`; `powersync/local/service.template.yaml` lists the committed dev key. The private keys for dev and prod live in env-manager (`POWERSYNC_JWT_PRIVATE_KEY`), and the local one is `powersync/local/INSECURE-dev-jwt-key.json`, committed on purpose so every worktree and CI run signs the same way.
- **The proxy does not authenticate.** `/api/powersync/*` forwards every request; PowerSync checks the token. The cookie is removed before forwarding. The proxy only ever reaches the configured PowerSync origin: the request path is appended to `POWERSYNC_URL`'s path, never resolved as a URL against it, so a path such as `//evil.example/x` cannot turn the Worker into an open proxy or serve a foreign page on the app's origin.
- **The `access` table says what a guest sees.** One row per entity a human grantee may see in another user's space: `id` is `<grantee>:<kind>:<entityId>`, with `grantee`, `owner`, `kind` (`task`, `project`, `section`, `label`), `entity_id`, and `role` (`view` or `edit`). A task's role is whether the grantee may edit it. A project's, section's, or label's is whether a new task of theirs may land there, which `admit` allows only through an edit share on it or on the whole space, so clients decide `canAddTo` from the row alone. `server/src/access.ts` recomputes the owner's rows with `scopeOf` from the owner's snapshot and shares after every share change, and after an upload only when a write moved what a guest may see in a space with a human grantee (`touchesAccess`, `recomputeAccess`), under the space's advisory lock either way, inserting new rows, updating a changed role, and deleting the rest. The rows are also what admits a guest's writes: `guestRefusal` reads them, one indexed query per space, instead of loading the space. The `shared` Sync Stream joins through it on the entity id and on `access.owner = user_id`, so a row only ever opens the owner's own rows, the stream rules stay simple, and the scope logic stays in `shared/scope.ts`. Link shares and AI accounts get no rows.
- **Admission on upload.** `POST /api/upload` is for signed-in humans. `applyWrites` runs each write as one statement whose `WHERE` names the space (`user_id`), first in the actor's own space. A `put` that changed nothing names a row stored in another space, whatever `user_id` it claimed, and is refused with `Belongs to another space`. A `patch` or `delete` that changed nothing is looked up: a missing row is a delete that won, and a row in another space makes it a guest's write there, checked with `guestRefusal` against the guest's `access` rows in that space; a guest with no rows there is refused with `Not shared with you`. An AI account acts in its owner's space through a whole-space edit share, through the agent API only, where `applyAs` gives it the owner's rights.
- **The install id.** `x-procrastimate-device` names the install for the push routes and Ramble, and on a browser WebSocket travels as the `device.<id>` subprotocol. It is not a credential; the session is.
