# Integrations

Other apps on Stefan's iPhone create and read ProcrastiMate tasks, and tasks link out to GitHub. The first one is Notouroboros, his voice memo app (`~/code/ios-voice-memo`, bundle id `com.stefan.notetorus`), which extracts tasks from each memo with Apple's on-device model and sends them here.

- **ProcrastiMate is the source of truth for tasks.** Notouroboros keeps audio, transcripts, summaries, and the calendar event a memo is attached to. It no longer has reminders of its own. Once a task arrives here it is an ordinary task: editing, completing, or deleting it happens in ProcrastiMate, and the memo app only reads it back.
- **Through the server, not app to app.** iOS has no background channel between apps, and the memo app processes in the background. It calls the Worker with the same session ProcrastiMate uses, so the tasks reach every device through the usual sync nudge, whether or not ProcrastiMate is running.
- **No configuration.** Both apps are signed by team `FNYFHG5SV7` and share the keychain access group `FNYFHG5SV7.com.stefan.shared`. While signed in, ProcrastiMate keeps one generic password there, service `procrastimate-link`, account `default`, whose data is the JSON `{ "apiURL": "…", "token": "…" }`: its own API URL and its Better Auth bearer token. It writes the item at launch and after sign-in, and deletes it on sign-out or a `401`. The item is readable after first unlock, because the memo app processes with the screen locked. A Debug and a Release build share the bundle id, so only one is installed and the item always names the server that build talks to.
- **Feetback reads the same item.** Feetback, the shake-to-feedback package in ProcrastiMate and a-better-me ([iOS app](ios.md)), posts a feedback task with the session in `procrastimate-link`, through the agent routes (`GET /api/view`, `POST /api/tasks`, `PUT /api/images`). Any app of the team with the shared group in its `keychain-access-groups` can post there while ProcrastiMate is signed in on the device.
- **The entitlement lists the app's own group first.** `Config/App.entitlements` lists `$(AppIdentifierPrefix)com.stefan.procrastimate` before `$(AppIdentifierPrefix)com.stefan.shared`. Keychain writes without a group go to the first entry, so the session token itself stays private to ProcrastiMate.
- **Simulator builds are signed ad hoc.** A simulator honors keychain groups only from embedded entitlements, and a build with `CODE_SIGNING_ALLOWED=NO` gets `errSecMissingEntitlement` (`-34018`) on the shared item. `app-ios/scripts/run` builds for the simulator with `CODE_SIGN_IDENTITY=-`, and the memo app has to do the same for the two to share the item there.
- **The memo app is a device.** It sends `Authorization: Bearer <token>`, its own `x-procrastimate-device` id, and `x-procrastimate-device-name: Notouroboros`. It shows up beside the phone and the browser and can be revoked like them. Sharing the session rather than minting a narrower token is deliberate: one user, one phone, and both apps are Stefan's. ProcrastiMate signing out revokes the memo app with it. An agent that is not Stefan's own app uses an AI account and its `pm.` token with the command API instead; see [Sharing](sharing.md).

## The memo task contract

All three routes are account routes in `shared/api/contract.ts`, served by the `Account` object as the device the request names.

- **A memo task's `sourceKey` is `voicememo:<memoId>:<taskKey>`**, both lowercase UUIDs from the memo app. `shared/memo-tasks.ts` (ported to Core) builds and reads it. Nothing else marks the task: no label, no project. Every client derives the memo link from the key.
- **Keys are checked, not normalized.** `memoId` and every `key` must be lowercase UUIDs, or the request gets `400`. Swift's `uuidString` is uppercase, so the memo app lowercases it.
- **`PUT /api/memo-tasks`** takes `{ memoId, recordedAt, tasks: [{ key, title, notes, when, event }] }` and returns the memo's tasks. `recordedAt` is epoch milliseconds, like every other moment in the contract.
  - `title` is the task. `notes` holds why it matters, with the memo's own words quoted.
  - `when` is the spoken time phrase copied from the memo, such as `tomorrow at 3pm`, or null. The server parses it with the quick-add grammar (`spoken: true`) as of `recordedAt` in the account's synced time zone, or UTC before any device has synced one, and keeps only the due date and repeat it finds. A phrase it cannot read leaves the task undated.
  - `event` is a `TaskEvent` for the memo's attached calendar event, or null. The memo app sets it only when the memo ties the task to that event, such as "before next week's standup". Being recorded during an event does not make a task an event task. An event replaces the due date and repeat, as it does everywhere, so the server ignores `when` on a task that has one. The phone rewrites the event's occurrences from the calendar as for any event task.
  - The tasks land in the Inbox. A key the account has already seen is skipped, live or deleted, so a retry never duplicates a task and never brings back one Stefan deleted. The server finds the memo's live tasks by their key's prefix (`tasks_source_key`, with pattern ops) and the deleted ones' keys in the log's source key index, and reads nothing else unless a task is new. A memo task's id is a version 8 UUID of a SHA-256 of the owner, `memoId`, and `taskKey`, so two overlapping sends that both find a key fresh put the same row and converge on one task. The ops use `voicememo:<memoId>:<taskKey>` as their op id, so the log dedupes them too. Placing new tasks after the newest one reads `max(created_at)` off `tasks_user_created` in one probe.
- **`GET /api/memo-tasks?memoId=…`** returns `{ tasks: [{ key, id, title, completedAt, due, event }] }`, the memo's live tasks in the order they were sent, completed ones included. A deleted task is simply absent.
- **`GET` and `DELETE` read `memoId` from the query.** The contract keeps every path fixed, with no path parameters, and declares both with oRPC's detailed input structure because a compact `DELETE` would read a body.
- **`DELETE /api/memo-tasks?memoId=…`** deletes the memo's live tasks and their subtasks and returns `{ "ok": true }`. The memo app calls it only when Stefan chooses to delete the tasks along with the memo.

## Links

- **ProcrastiMate opens `procrastimate://task/<id>`** on iOS: it shows that task's details over the current screen. An id the device does not have yet waits up to a minute for sync to bring it, since a link can come straight after the task is created elsewhere, as Feetback's confirmation toast does. Past that, or for an id that never arrives, the link does nothing.
- **Notouroboros opens `notouroboros://entry?id=<memoId>`.** A memo task's row shows a small waveform icon, on iOS and the web. Its details show `Notouroboros`, which opens the memo on iOS. The web shows the same line without a link, because a browser cannot open the phone app.
- **The memo app assumes ProcrastiMate is installed.** It checks with `canOpenURL(procrastimate://)`. When ProcrastiMate is missing, the memo's extracted tasks stay on the memo with the note `Could save these todos if you also had ProcrastiMate.` When it is installed but signed out, the note asks to sign in. Either way the tasks go out on their own once the link appears.
- **Deleting a memo keeps its tasks.** When a memo has tasks in ProcrastiMate, deleting it asks whether to delete them too, and the default keeps them. A kept task keeps its link, which then opens a memo that no longer exists.

## Tinycast

Tinycast is the Mac launcher Stefan uses in place of Raycast. It runs Raycast extensions, so `app-tinycast/` is one, built with Raycast's `ray build`.

- **Two commands.** `Add Task` takes one argument, the quick add text, and posts it to `POST /api/tasks`, so the server's parser reads dates, repeats, priority, `#Project`, and `@label` exactly as the apps do; a HUD names the title and the date it got. `Tasks` lists Today, Inbox, Tomorrow, This week, No date, every project, and every label, picked from the search bar's dropdown. Typing searches every open task with the app's search and offers the text as a new task first, its title and date previewed by the shared quick add parser. A task typed into a project or label goes there unless the text names another project, and one typed into Today or Tomorrow without a date gets that day.
- **Row actions.** Return completes (with Undo, except a repeat that rolled to its next date), `⌘D` moves the date (the app's postpone options, a picked date and time, or none; a move keeps the time), `⌘P` sets the priority, `⌘O` opens the task in the web app at `/?task=<id>`, `⌘L` opens the first link in the title, and `⌃X` deletes after a confirmation. Every change shows at once and reloads the view when the server refuses it.
- **It uses a personal token.** The extension calls the agent API with a `pm.` token from Settings, stored as a Tinycast password preference, rather than Stefan's session. A desktop launcher cannot run Google or Apple sign-in, and a token is revocable on its own. A personal token makes the tasks it adds Stefan's own, since the launcher is Stefan typing, not an agent; an AI account's token also works, and credits that account. Requests send `User-Agent: Tinycast`, which the log records as the `api` client's device.
- **Shared code is bundled, not ported.** The views, formatting, search, quick add parser, and the oRPC agent contract come from `shared/`, so the lists match the apps. The last view is cached in Tinycast, so the list opens filled and refreshes behind it.
- **Clients.** Mac only, since Tinycast is a Mac launcher. iOS already has App Intents and Shortcuts for the same job, and the web app is the editor this opens.
- **Installing.** `bun run --cwd app-tinycast build` writes `app-tinycast/dist`, which Tinycast adds from Settings → Extensions → Add from folder. Rebuild and re-add it after a change.

## GitHub

A task can carry GitHub issues and pull requests as metadata, for the work Stefan tracks in ProcrastiMate while it happens on GitHub.

- **An explicit field, not links found in the text.** `tasks.github` holds a list of `{ repo, number, kind }` (`shared/github.ts`), set from details by pasting an issue or pull request link, or `owner/repo#123`. Detecting links in the title or notes was ruled out: a task often mentions a PR it is not about, and a pasted GitHub link in a title already becomes `[PR title](url)` (see [Link previews](link-previews.md)), which reads well on its own. Attaching is a deliberate act that puts the PR beside the date and priority.
- **Only which ones are stored; GitHub's state is read live.** A PR's state changes after it is attached, so its title and state (`open`, `draft`, `merged`, `closed`) come from `GET /api/github?url=` each time details open, cached on the client for a minute. A stored snapshot would sync stale state and churn writes. Rows show the GitHub mark and each `#number` without asking GitHub, since a list would ask once per row.
- **The server reads GitHub.** `server/src/github.ts` calls GitHub's issues API, which answers pull requests too and says one is a PR, so an issue link to a PR still reads as a PR. With `GITHUB_TOKEN`, a fine-grained read-only token for Stefan's repos and a Worker secret, private repos read too. Without it, public repos are read signed out, and past GitHub's rate limit the title comes from the page with no state. A private repo without the token shows only `repo#number`, still a link.
- **Opening.** The web opens GitHub in a new tab; iOS opens the URL, which the GitHub app takes when installed.
- **Clients.** Web and iOS. A public link blanks the list, like the other owner-only data (see [Sharing](sharing.md)), so a private repo's name never reaches a public page.

## Webhooks

An agent that works Stefan's tasks, such as the T3 Code task orchestrator, should hear when he adds a task or answers a question in a comment, instead of polling `GET /api/view` and every task's comments.

- **The log is the outbox.** A hook (`webhooks`, server only) keeps a cursor into `log`. The minute cron reads the hook's space after the cursor, sends one POST with what humans added, and moves the cursor only on a `2xx`. Nothing runs on the write path, so a dead receiver never slows a sync, and a failed POST resends the same delivery a minute later: `retry_through` freezes its range, so the retry carries the same events and `id` while newer changes wait for the next one. A day of failures, or a `404` or `410`, disables the hook until it is registered again, which resumes from that moment: an agent that was gone that long rereads the tasks anyway.
- **Up to a minute late, by choice.** Sending from the minute cron costs no request on the write path and needs no queue. An agent's wake does not need to be instant. A send right after the write would need its own in-flight guard against the cron.
- **Two events.** `task.added`, a task a human created, or moved into a watched project, and `comment.added`, a comment a human wrote. Each is judged by the task as it is now, so a task deleted before the cron runs, or moved out of the watched projects, is dropped. An AI account's writes never count, so an agent is not woken by its own work; a personal token's do, since that is Stefan typing. A moved task with subtasks is one addition, its root. Two known misreads, both rare and harmless to an agent that rereads the tasks: moving a task between two watched projects counts as adding it, and undoing the delete of a whole space reports every restored task, because the purge took their log rows.
- **The AI account owns its hooks.** Deleting the account deletes the hooks it registered.
- **Ids only.** A delivery carries ids, types, and a `summary` of counts, never titles or comment text. The receiver reads the rest through the agent API with its own token, so a leaked URL or delivery log shows nothing, and an agent never takes instructions from a webhook body.
- **Signed.** Each body carries `x-procrastimate-signature: sha256=<hex HMAC-SHA256>` with the hook's secret, which only registering returns. T3 Code checks it with a webhook task's `signature` set to that header, `hex`, and prefix `sha256=`.
- **The owner's or a manager's.** Registering, listing, and deleting are agent routes for the owner and an AI account holding the whole space (`requireManager`). Registering a URL again keeps its id and secret and updates its projects.
- **Clients show which projects a hook watches.** A project of the user's own that a live hook watches, by id or through a hook with no projects, reads `Watched by a webhook` under its title on the web and in the iOS navigation subtitle, so Stefan knows a task added there wakes an agent. A disabled hook shows nothing, since it wakes no one. Hooks are server only and never sync, so each client reads `GET /api/webhooks` when a project opens and again once that answer is a minute old (`webhooks.svelte.ts`, `WebhookWatch`); a shared project, whose hooks are its owner's, never asks. Registering, listing, and deleting stay agent routes; no app manages hooks.
