# UX principles

- **Simple, clean, sharp.** Few controls, generous whitespace, crisp type, and clear hierarchy. Every control earns its place. Sync and notification setup are not controls: sync is always on, and permission is asked once with no prompt copy of our own.
- **Mobile first.** The web UI must always work great on an iPhone-sized screen, since Stefan uses it from his phone. Design for a 393 px wide viewport first and widen from there.
  - **Layout.** Below 768 px the sidebar becomes a drawer behind a menu button, a floating add button opens quick add, and quick add and task details open as bottom sheets. From 768 px up the sidebar is always visible and sheets float as a centered dialog and a side panel.
  - **Touch.** Every tap target is at least 44 px on phones and touch screens, using an invisible hit area where the visible control is smaller. Fields use at least 16 px text so iOS does not zoom on focus.
  - **No hover-only interactions.** Hover only adds polish. Every action is reachable by tap, and hover styles apply only on devices that can hover.
  - **Safe areas.** The layout respects `env(safe-area-inset-*)` for the notch, the Dynamic Island, and the home indicator.
  - **Nothing ends under floating chrome.** Every scrolling screen, sheet, and dialog lets its last content scroll fully clear of the floating add button, the iOS tab bar, the floating Complete and Delete buttons, and the on-screen keyboard. Chrome that hides while typing gives its room back, so no screen leaves a dead gap above the keyboard. `app-web/e2e/layout.e2e.ts` checks every web screen at 1280 px and 393 px, with the phone keyboard emulated.
  - **On-screen keyboard.** Quick add stays usable while the keyboard is open. Sheets dock above the keyboard by tracking the visual viewport, and the return key submits. Below 768 px a toast shown while a sheet is open moves to the top of the screen, because the sheet covers the bottom where toasts normally sit, and a toast keeps its action on one line, truncating only its message.
  - **Text fields grow with their text.** The title and `Add subtask` fields in task details wrap and grow up to eight lines, then scroll inside, so a long subtask is never cut off. Quick add's title grows to ten lines on iOS and twelve on the web, because a long dictated title cut to four lines hid what Stefan just said. While its subtask list is open, the sheet has to fit that list above the keyboard as well, so the title goes back to four lines and the subtask field stays at three. On a phone web screen the title also stops where it would push the sheet's buttons above the keyboard off screen, never below three lines. Every one stays one line of text: Return submits and a pasted line break becomes a space. Notes grow without a cap, because the details body already scrolls, and comments grow to about twelve lines. After every edit, including a paste or dictation, the caret's line stays in view: inside a field at its cap, and in the sheet around a field that grew under the keyboard. WebKit skips both after a paste, so `followCaret` in `app-web/src/lib/caret.ts` scrolls them on the web, and `EditorCaret` does it on iOS. Web fields size themselves with CSS `field-sizing: content`, which Chrome and Safari both support, instead of script.
  - **Same shapes as iOS.** The drawer and inset bottom sheets map directly to the Liquid Glass port. The floating add button maps to the `+` in the trailing circle of the iOS tab bar.
- **Screens act alike.** Every list screen (Inbox, No date, Completed, a project and its sections, a label, a place, an event) behaves the same way on every client, through one map per concern instead of per-screen code.
  - **Quick add inherits the screen's context.** Quick add opened on a screen starts with that screen's project, section, label, place, event, or day, so the new task lands on the screen it was added from, and saving keeps that screen open. `screenDefaults` and `screenHolds` in `shared/screens.ts`, ported to Core's `Screens`, map a screen to both, and every entry point (the web's `q`, floating button, sidebar, and add rows, and the iOS tab bar `+` on any tab, pinned ones included) reads them, as does Ramble. A heading narrows it: a project section's add row or menu adds to that section, an Inbox day heading to that day, and a No date place heading on iOS to that place. Inbox itself, No date, and Completed add an undated task with no list, because capture from Inbox has always been undated and No date holds such tasks. So does a shared project or label the user may only view: `canAddTo` in the same module decides it once, the way the server admits a new task: a shared project or label takes one only through an edit share on it or on the whole space, read from the roles sync sends with a space's `targets`. Both the defaults and each screen's add row read it, so `q`, the floating button, and the iOS tab bar `+` never offer a list the screen itself hides its add row for.
  - **Every task row offers the same actions.** A task row, a completed row, and a search result take the same actions wherever they show: Complete or Reopen, Postpone while open and not on an event, Delete with an Undo toast, and Copy as Markdown. A task the user may only view, and a repeating task's past completion in Completed (the task itself is still open), offer only Copy. `rowActions` in `shared/row-actions.ts`, ported to Core's `RowActions` and checked by its vectors, decides the list once. iOS builds each row's context menu and swipes from it. The web opens one shared row menu, mounted once at the root, on a right click, a long press on touch (iOS Safari fires no `contextmenu`, so touch keeps its own timer), and Shift+F10 or the context menu key, with arrow-key focus and Escape giving focus back. Its postpone options sit flat in a `Postpone` group, since the web avoids nested dropdowns. Every delete goes through one `deleteTask` in `app-web/src/lib/completion.ts`, and the web keeps its hover Postpone and completed-row trash buttons beside the menu.
  - **Every screen copies as Markdown.** Each list screen has a whole-screen copy, and each heading a copy of its section.
- **Motion on every interaction.** Opening, closing, adding, completing, and switching views all animate. Motion is short (about 150 to 250 ms), eased like a spring, and never gates input.
- **Optimistic by default.** A tap never waits on the network to show its result. Task edits are local first through sync. Requests outside sync (AI accounts, shares, people search, sign out) change the UI at once and roll back with an error toast when the server refuses. A row the server is still creating takes actions anyway, and they wait for it. Both clients use one `OptimisticList` shape for this: `app-web/src/lib/optimistic.svelte.ts` and `app-ios/Sources/App/Sync/OptimisticList.swift`.
  - **Pending only for what the server makes.** A soft pulsing placeholder (`.pending-value` on the web, `PendingValue` on iOS) holds the place of a value only the server can make, such as a new token's secret or a new link's URL. Nothing else gets a spinner or a dimmed row.
  - **Irreversible or unknowable flows give immediate feedback instead.** Sign-in buttons read `Signing in…`, `Creating account…`, or `Opening Google…`, because only the server knows whether the password is right. A Todoist import reads `Importing…` while the zip is read.
  - **Errors from an action are toasts, not inline text.** Inline error text is only for a screen that could not load at all, such as `Sharing needs a connection`. The iOS Settings and Share sheets carry their own `ToastStack`, like task details, because a sheet covers the root one.
- **Reduced motion.** Under `prefers-reduced-motion`, CSS transitions and animations collapse to instant, and Svelte transitions pass their params through `motion()` in `ui.svelte.ts`, which zeroes the duration. CSS cannot reach Svelte transitions because they animate from script.
- **A leaving row is gone for assistive tech.** A row moving between lists or day sections exists twice while it animates. Every task, completed, and subtask row, and every Inbox day or project section that animates out, carries `{@attach leaving}` from `ui.svelte.ts`, which mirrors the `inert` Svelte puts on an outroing element into `aria-hidden`, so screen readers and role queries meet the row once. The animation itself is unchanged.
- **Liquid Glass parity.** The web UI ports to iOS with Liquid Glass. See [Visual language](visual-language.md) for layering, materials, shapes, motion, spacing, and controls.
