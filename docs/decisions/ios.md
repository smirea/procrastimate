# iOS app

- **A native SwiftUI app at feature parity with the web app.** It does everything the web client does, as listed row by row in [iOS parity](../ios-parity.md), and looks like the web app per [Visual language](visual-language.md), with native iOS 26 Liquid Glass chrome, sheets, lists, swipe actions, menus, date pickers, search, and haptics instead of web lookalikes. Apple Watch and distribution come later.

## Project and architecture

- **Build on the existing `app-ios/` scaffold.** It already has `Package.swift`, `App.xcodeproj` with a file-system-synchronized `Sources/App` group and the shared `App` scheme, the bundle id `com.stefan.procrastimate`, the env-manager `Config/` bridge, and the `scripts/run` launcher behind `bun run start:ios`. Nothing gets a second project or launcher.
- **iOS 26 is the minimum, iPhone first.** Liquid Glass (`glassEffect`, `GlassEffectContainer`, `.buttonStyle(.glass)` and `.glassProminent`), the bottom search tab (`Tab(role: .search)`), and `TextEditor` bound to an `AttributedString` all need iOS 26. Stefan is the only user and runs current iOS, so there is no reason to support older versions. The macOS 14 app target is dropped. iPad runs the same app with `.sidebarAdaptable` tabs and no extra design work.
- **Two targets: `Core` and `App`.**
  - `Sources/Core` is a SwiftPM library with Foundation only, no SwiftUI or UIKit. It holds the model, the store and its commands, and the Swift port of the shared logic. `swift test` runs `Tests/CoreTests` on macOS and on Linux, so cloud agents without Xcode can build and test the logic.
  - `Sources/App` is the SwiftUI app, which depends on `Core`. `Tests/AppUITests` holds the XCUITests. Both are synchronized folders in `App.xcodeproj`, so later work adds files without editing `project.pbxproj`.
  - In `App.xcodeproj`, `Core` is a static library target over the same synchronized `Sources/Core` folder, linked into `App`. A local package reference was not used, because `Package.swift` sits in the project's own folder. `Package.swift` declares only `Core` and `CoreTests`, since the SwiftUI app cannot build on Linux, so `swift run` no longer launches anything.
  - `CoreTests` use Swift Testing (`import Testing`), which runs the same way on macOS and Linux.
- **One folder per owner.** `Sources/App` has `Navigation/` (`RootView`, `Route`, `Sheet`, `Navigator`), `Launch/`, `Data/`, `Theme/`, and `Screens/<Area>/` with one file per screen: `Lists/` and `QuickAdd/` (S5), `Details/` (S6), `Browse/` and `Search/` (S7), and `Settings/` and `Notifications/` (S8). A slice replaces its own placeholders and adds files under its own folders. Route and sheet ids are plain `String`s until S2 adds the model.
- **Logic stays out of views.** Every rule that decides what a task is, where it shows, or what a chip says lives in `Core` and is covered by the test vectors. Views only render `Core` values and send store commands.
- **Inject the clock and time zone.** `Core` never reads `Date()`, `TimeZone.current`, or `Calendar.current` itself. The app passes a clock and calendar in, so tests and vectors pin them. A DEBUG-only launch environment (`PROCRASTIMATE_NOW`, `PROCRASTIMATE_TZ`, `PROCRASTIMATE_RESET`) lets XCUITests start from an empty store at the web suite's pinned moment, Wednesday, October 14 2026, 10:00 UTC.
  - `Core.LaunchOptions` parses the three keys and rejects malformed values, and the app crashes on launch rather than run with a half-applied harness. `PROCRASTIMATE_NOW` takes an ISO 8601 moment and freezes the clock there, like Playwright's `clock.setFixedTime`. `PROCRASTIMATE_RESET=1` deletes `Application Support/procrastimate` and the app's `UserDefaults` domain before the first frame, the equivalent of a fresh browser profile. The scaffold fixes only that folder (`StoreLocation`); the store's format and shape come with the sync design.
  - The app reads the device clock in one place, `AppClock.system`, and hands the clock to views through `@Environment(\.clock)`. Release builds ignore the launch environment.
- **Dependencies stay at zero.** Unzipping uses a small in-house zip reader on top of Apple's `Compression` framework (raw DEFLATE), mirroring the web's 30-line CSV reader. ZIPFoundation is the fallback if Todoist zips use features the reader does not handle. `Compression` does not exist on Linux, so the zip reader lives in `App`. `Core` takes the extracted files, like the TS `readTodoistBackup(files)` after the web unzips with `fflate`, which keeps `Core` building and testing on Linux.

## UI mapping

- **Navigation.** A `TabView` with Inbox, Today, Upcoming, Browse, and a search tab (`role: .search`), opening on Inbox like the web. Browse lists projects and labels with their open counts, then Notifications and Settings, like the web sidebar. Inbox and Today show their open counts as tab badges. The tab bar minimizes on scroll. This maps to the web drawer's contents with native chrome.
- **Add button.** A floating `.glassProminent` plus button above the tab bar on every task list, like the web's floating `Quick add`. On iPad with a hardware keyboard, `q` opens quick add, and Cmd-K opens search.
- **Lists.** Plain `List`s on the solid base layer with a leading priority-tinted checkbox, the date, repeat icon, reminders, and label chips. Each row has a leading swipe that completes it, a trailing swipe that deletes it with undo, and a context menu. Rows animate in and out with list animations, and the checkbox fills on the first frame.
- **Sheets.** Quick add is a short sheet docked above the keyboard. Task details is a sheet with a `NavigationStack`, so opening a subtask pushes it with a back button named after the parent. Search and settings never stack with another sheet, as on the web.
- **Pickers.** The date, priority, reminder, and project chips open `Menu`s, and the date chip offers presets plus a graphical `DatePicker`. Pickers that must stay open across taps (the repeat menu's weekday toggles and the labels picker) are popovers with `presentationCompactAdaptation(.popover)`, because a `Menu` closes on every tap.
- **Smart input.** Quick add, the details title, and the add-subtask field share one input: a `TextEditor` on an `AttributedString` that tints parsed phrases with the same token colors as the web, the chip row below it with `Keep as text`, and the `#` and `@` suggestion list above it, driven by one table of the two kinds like the web.
- **Quick add rules live in `Core`.** `QuickAddDraft` holds the text, the phrases kept as text, and the chip picks, with the web `QuickAdd.svelte` rules: the text wins over a pick, a pick removes the phrase that set it, and saving resets to the sheet's defaults. These come from a web component rather than `shared/`, so they have unit tests in `CoreTests` instead of vectors. The `#` and `@` suggestions call `NameSearch`.
- **The smart input re-tints, never rebuilds.** Each change re-applies the token backgrounds in place with `AttributedString.transform(updating:)`, so the caret stays put, and a typed Return is stripped and submits instead of adding a line.
- **Undo.** A glass toast at the bottom with `Undo`, five seconds, matching the web's text such as `Completed "Standup", next due Friday 9am`.
- **Haptics.** `.sensoryFeedback`: success on complete, selection on picker changes and weekday toggles, and a light impact when a subtask drag picks up and drops. Nothing buzzes on typing.
- **Colors.** A script generates `Sources/App/Theme/Tokens.swift` from the semantic tokens in `app-web/src/index.css`, with light and dark values for `ink`, `muted`, `accent`, priorities, date tones, and parser highlights, and CI fails when the generated file is stale. The generator is `app-ios/scripts/tokens.ts` (`--check` for CI). It also writes the `AccentColor` asset from `--color-accent`, the app's global accent, because system chrome such as a sheet's toolbar buttons ignores SwiftUI's `tint`. It emits every color token, named in camelCase without the `--color-` prefix, as `Palette.<name>` with a light and a dark sRGB value that follow the trait collection, plus a `ShapeStyle` shorthand so views write `.foregroundStyle(.muted)`. Materials are the system's: glass for floating chrome and solid backgrounds for content.
- **Accessibility.** System glass and materials already turn solid under Reduce Transparency and Increase Contrast. Custom motion reads `accessibilityReduceMotion` and becomes instant, like the web's `motion()`. Every control has an accessibility label that matches the web's accessible name, so XCUITests and Playwright find the same handles.
- **Browse.** An inset grouped `List` on the canvas: Projects in creation order, then Labels alphabetically in `en-US` collation (`Browse.labelsByName`, shown once a label exists), then Notifications and Settings. Each row carries its open count (the same `Views.projectTasks` and `Views.labelTasks` lists the screens show) as its accessibility value. Projects and labels have no user-picked colors on either client, so "colors" are the tokens: the label tag in `toneLabel`, the project `number` icon in `muted`. `Add project` in the Projects header inserts a focused `Project name` row in place, like the web sidebar's inline field: Return or losing focus creates it and pushes it, and an empty name cancels.
- **Project and label screens.** They reuse the task list screen, so rows, swipes, the empty state, and the add button behave like Inbox, and the add button opens quick add with the project or label as its default. Renaming and deleting sit in the `Project actions` or `Label actions` toolbar menu, the native stand-in for the web header's popover. `Rename` opens an alert prefilled with the name, which suits a one-field edit better than editing the large title in place. Delete confirms with a `confirmationDialog` using the web's wording (`Delete House and its 3 tasks?`, `Delete phone?` with `Its tasks stay, without the label.`), then pops back to the screen it came from rather than jumping to Inbox, and the record goes once the pop has played, so its Browse row leaves in view.
- **Search is the search tab.** `SearchScreen` puts `.searchable` on the search tab's stack and focuses the field when it appears. Results come from `Core`'s `Search`, grouped and limited by `SearchSections` (5 projects, 5 labels, 30 open, 15 completed, the full count in each header), with matched spans on the `tokenMatch` highlight through `AttributedString`. A task result opens task details as a sheet over the tab. A project or label result pushes its screen onto the search tab's own stack, so Back returns to the results, which is how iOS apps open search results instead of switching tabs. Scrolling dismisses the keyboard.
- **Search actions and keys.** Return opens the selected result, which is the first one until a hardware keyboard's Up or Down moves it (`onKeyPress`, not reachable from simulator XCUITests). Escape is the search field's own cancel. Cmd-K opens the search tab at its field, closing any sheet and popping a result left open on the tab, and Cmd-K again returns to the previous tab, registered by `searchShortcuts()` on `RootView`. The web's bare `/` stays web only: a key command without a modifier would take the character from whichever text field is focused (quick add, `Project name`, a rename alert), and SwiftUI has no app-wide text focus to gate it on. A completed result reopens from its leading swipe or context menu and an open one completes the same way, matching list rows. Task details add `Reopen` with S6.
- **Search results in XCUITests.** Each result's identifier is `result-<title>`, `result-project-<name>`, or `result-label-<name>`, and its accessibility value reads its matched spans (`Matches call`), which tells VoiceOver why a result is listed and gives the tests what Playwright reads from `mark`.
- **Theme.** `System`, `Light`, and `Dark` live in Settings, stored in `UserDefaults` under `procrastimate-theme`. `System` stores nothing. The app sets the window's `overrideUserInterfaceStyle` when the root appears, before its first frame, and on every choice, with `.unspecified` for `System`. Sheets and UIKit chrome such as the document picker inherit it. `preferredColorScheme` is not used: going back to `nil` keeps the last forced style, and a sheet that is already open, like Settings itself, does not restyle. Reduced motion is one root `.transaction` that drops animations while Reduce Motion is on, so no view repeats the check. XCUITests read the applied theme from a background pixel. `XCUIDevice.shared.appearance` reports a change on the CI simulator without restyling it, so the native test checks `System` in light only and the web half covers the live switch. Glass fallback and Reduce Motion have no paired test, because a UI test cannot change those settings.

## Shared logic and test vectors

- **Swift ports of `shared/`.** `Core` ports the quick add parser, dates and recurrence (`nextOccurrence`, `alignToRecurrence`, `stepRecurrence`, month clamping), `notificationTimes` and `reminderFiresAt`, subtasks (complete, reopen, move, orphans, progress), name search for `#` and `@`, search with ranking and highlights, the CSV reader, and the Todoist reader and merge.
- **Pure logic lives in `shared/`, not in the web app.** Everything that decides what both clients show is in `shared/`: list membership and order (`views.ts`), chip, row, heading, and toast strings (`format.ts`), notification times and text (`notifications.ts`), the stored document and its loading rules (`snapshot.ts`), and the store's commands (`store.ts`). The commands are pure functions over `{ tasks, projects, labels }` that return new arrays and objects for what they change, and take the new record's id and time from the caller, so the Svelte store (raw state, one `#apply` per command) and the Swift store call the same rules. Todoist import goes through `mergeBackup` in `todoist.ts`, which S4 ports.
- **One JSON corpus, recorded from the TS unit tests.** `shared/vectors/<module>.json` holds `{ fn, test, input, output }` cases. The TS tests wrap each ported function with `recorded('<module>', fn)` from `shared/vectors/record.ts`, and import `describe` and `test` from it too, since Bun exposes no current test name; those wrappers name each case after its test. With `VECTORS=record`, every call during `bun test shared` writes its input and the real TS output, and each test file's `afterAll` writes its modules, because `bun test` runs no exit hooks. Outside record mode `recorded` returns the function itself. The test assertions prove the TS output is the intended behavior, and the corpus carries it to Swift, so there is one source of cases and no hand-written expectations to drift.
- **Generating it.** `bun run vectors` runs the shared tests in record mode with `TZ=America/New_York`, which has a DST change inside the corpus window (November 1, 2026), so time zone bugs show up instead of hiding behind UTC. Files are pretty-printed with sorted keys and cases in test order, so a diff reads as a behavior change. Dates are recorded as epoch milliseconds plus the zone in each file's header, and `DateKey` and `TimeOfDay` stay strings.
- **Checking both sides.** The web `checks` job runs `bun run vectors`, then fails if `git status --porcelain shared/vectors` prints anything. That catches both a changed file and a new, uncommitted vector file, which `git diff` alone would miss, so TS behavior cannot change without the corpus being regenerated. The iOS workflow's `core` job runs `swift test`, where `VectorTests` decodes every file and asserts that the Swift port returns the recorded output for each case. A TS change that alters behavior therefore turns iOS CI red until the Swift port matches.
- **The Swift port mirrors the TS modules.** `Core` has one namespace per module: `Dates` (`task.ts` dates and recurrence), `Notifications`, `Subtasks`, `Views`, `Format`, `StoreRules`, and `Snapshot`, with the same function names, so a vector's `fn` maps to one Swift call. The task type is `TaskItem`, because `Task` would shadow Swift concurrency's `Task` in the app. `DateKey` and `TimeOfDay` are strings, calendar math is civil (day counts, no zone), and only turning a date and time into a moment takes a `TimeZone`. That conversion follows JavaScript's `new Date(y, m, d, h, min)`: a repeated hour at a DST change takes its first occurrence and a skipped hour moves forward by the gap, so Swift and the web pick the same instant. Timestamps are `Int` epoch milliseconds, as in the document.
- **The quick add parser keeps the TS patterns.** `QuickAdd.parse(input, options, in: zone)` ports `parseQuickAdd` with the same rules, guards, and order, and its regular expressions are the TS sources character for character. `QuickAdd.Pattern` translates each one for ICU (`NSRegularExpression`, which runs on Linux) so it matches like JavaScript without the `u` flag: `\w`, `\d`, and `\b` stay ASCII, `\s` is JavaScript's whitespace set, `$` is the end of the input, and set syntax inside a class is escaped. ICU rejects unbounded lookbehind, so a `+` or `*` inside one is capped at 64 characters, which a title never reaches. Token `start` and `end` are UTF-16 offsets, like JavaScript string indices, so the app converts them with `String.Index(utf16Offset:in:)` before tinting the `AttributedString`. Swift's own `Regex` was not used, because its word boundaries and character classes are Unicode by default, so matching like JavaScript would mean rewriting the patterns rather than translating them.
- **One data shape.** `Core`'s Codable snapshot is the same JSON document as the web's `procrastimate` localStorage value, including the optional `sync` section. A sync op's `fields` stay opaque `JSONValue`s until S9 ports the protocol. A vector holds a web-written snapshot, which Swift must decode and re-encode unchanged. Loading follows the web's rules: an invalid task is dropped on its own, new optional fields default, and an invalid document is discarded, with no migrations.
- **Search and import namespaces.** `CSV` (`csv.ts`), `Search` (`search.ts`), `NameSearch` (`name-search.ts`), and `Todoist` (`todoist.ts`). Their text code follows JavaScript strings, through `UTF16Text`: highlight ranges, the caret, and fragment offsets count UTF-16 code units, whitespace is JavaScript's `\s`, and names compare by code unit, so a highlight or a `#` fragment lands on the same characters on both clients. Views convert offsets to `String.Index` with `String.Index(utf16Offset:in:)`.
- **Functions in vector inputs.** A vector cannot hold a function. `lastUsed(tasks, idsOf)` records through test wrappers named `lastUsedProjects` and `lastUsedLabels`, which map to `NameSearch.lastUsed` with `projectIdsOf` or `labelIdsOf`. Every `mergeBackup` call in the tests takes ids from a fresh `id-1`, `id-2`, … counter, which `VectorTests` replays.
- **Todoist dates go through the parser.** `Todoist.readTodoistDate` reads ISO dates itself and passes anything else to `QuickAdd.parse`, which must account for the whole text, as on the web.

## Data

- **Standalone local store.** The store is one JSON snapshot in Application Support, held in an `@Observable` store on the main actor. Every command applies in memory at once and writes atomically off the main actor, coalesced so a burst of edits is one write. Several thousand tasks encode in a few milliseconds, which fits the snappy bar without an index.
- **The store lives in `Core`.** `Store` is a main-actor `@Observable` class over the `Snapshot`, with one method per `StoreRules` command, each ending in `commit(next)`, which keeps tasks sorted by `createdAt` then `id`. `SnapshotFile`, an actor, writes `Application Support/procrastimate/procrastimate.json` atomically, coalescing a burst of commits into one write of the newest snapshot. `Core` only needs Foundation and Observation for this, so `swift test` covers loading, saving, and undo on Linux.
- **The `sync` section stays absent until pairing.** Like the web's document, an unpaired device writes no `sync` key, which [Sync](sync.md) reads as unpaired, and the store carries a loaded section through every commit untouched.
- **Not SwiftData.** The ported logic works on value arrays of tasks, exactly like the TS. SwiftData would force a mapping between `@Model` objects and those values on every command, add migrations the product does not want, and move the document away from the web's shape, which a future sync or a manual transfer can use as is.
- **Todoist import on iOS.** `Import from Todoist` in Settings opens `.fileImporter` for a `.zip`, and the app also accepts a zip shared or opened into it. The same reader and merge as the web run on the device, nothing uploads, and the summary and warnings read the same. The XCUITest uses the same synthetic backup as the web suite: CI zips `shared/fixtures/todoist-backup.mts` with DEFLATE through `app-ios/scripts/todoist-fixtures.ts`, which also writes a `.zip` that is not a zip and a text file the picker must not offer, and copies the zip into the app's Documents folder on the simulator, and the test picks it under On My iPhone in the document picker, so it goes through the real file picker.
- **Built on the sync model from the start.** The JSON file holds the same document as the web: the snapshot plus a `sync` section (device id, cursor, outbox), which stays empty until the device pairs. Tasks stay sorted by `createdAt` then `id`, and every command goes through one `commit(next)` so the sync client can diff it into the outbox later without touching the commands. S5 builds the store this way. S9 adds the client half of [Sync](sync.md): the HLC, `diff`, and `applyChanges` ported against `shared/vectors/sync.json`, the Keychain token, pairing in Settings, and syncing on launch, foreground, background refresh, and after a commit. The server-side merge and `fixups` are never ported.

## Notifications

- **Local notifications, no server push.** The app schedules `UNNotificationRequest`s with a `UNTimeIntervalNotificationTrigger` for each future moment from `notificationTimes`. Moments are instants, so an interval from the app clock is exact and keeps working under the pinned test clock, where a calendar trigger would read the real one. A due time is a reminder, a date with no time never notifies, and a moment notifies once, exactly as [Domain](domain.md) says. Titles and bodies come from the shared notification text, such as `Due now` or `Due at 6:00 PM`. Notifications need no APNs and no push entitlement. After sync pulls changes from another device, the schedule is recomputed like after any local change.
- **Replace the whole schedule after every change.** Like the server does for Web Push, the app computes the full schedule after each command, debounced, and diffs it against the pending requests. Each identifier is the shared `pushTag` (`<taskId>:<epoch ms>`), so a re-add replaces the request instead of duplicating it, and completing, editing, deleting, and restoring need no cancel path. A repeating task schedules its next occurrence once completing moves its date.
- **iOS keeps at most 64 pending requests.** The app schedules the soonest 60 and refills when it opens, comes to the foreground, after each change, and from a `BGAppRefreshTask`. Moments past the window still fire if Stefan opens the app within the gap. Each delivered notification is a reminder to open the app, which then refills the window.
- **In the foreground, toast only.** The notification center delegate's `willPresent` returns no banner and the app shows the `Reminder: <title>` toast with `Open`, matching the web rule that the open app shows the toast and leaves the system notification to the background.
- **The app has its own on switch.** iOS cannot hand a permission back, so `Turn off` clears an in-app `procrastimate-notifications` preference and removes the pending requests, and `Turn on notifications` sets it again without a second system prompt. Status reads `Off`, `Blocked`, or `On` in the Browse row.
- **Asking for permission.** The app never prompts on its own. The Notifications screen in Browse explains what will notify and asks only from `Turn on notifications`. The first timed task saved while notifications are off shows a once-per-launch `Get notified when it's due?` toast that opens that screen. The app detects that task by observing the store's tasks, and imported tasks (those with a Todoist `sourceKey`) never nudge. A denied permission links to the app's page in Settings. Web-only states (Add to Home Screen, server unavailable, unsupported) do not exist on iOS.
- **Tapping a notification opens its task** in task details from the `taskId` in its payload. `Send a test notification` schedules one five seconds out, and it is the one notification that shows as a banner while the app is open, since the toast is only for task moments. Until S6 lands task details, `Navigator.openTask` is the single seam a tap goes through.
- **Testing notifications.** The XCUITests allow the real springboard prompt, and a DEBUG-only `PROCRASTIMATE_NOTIFICATIONS_DENIED=1` launch key answers `Don't Allow` without one. In DEBUG, the `N scheduled on this device` text carries the pending requests in its accessibility identifier as `pending: <title>@<ISO moment>: <body>; …`, where Playwright reads the server's push schedule for the same synced account. The web halves block the service worker and stand in for `PushManager` and the permission, because WebKit in Playwright has no Web Push.

## Siri, Shortcuts, and Spotlight

- **The iOS app works with Siri, Shortcuts, and Spotlight.** Every feature someone can do in the app, and that makes sense from outside it, ships with App Intents in the same change: the intent, an App Shortcut phrase when it is something Stefan would say, and an `AppEntity` when Shortcuts or Siri should pick a task, project, or label. This is the default for a new feature, not a follow-up.
- **App Intents are iOS-only.** The web client is excluded because Siri, the Shortcuts app, Spotlight, and App Intents are system features of iOS. There is no web counterpart to build.
- **Intents live in the App target.** `Sources/App/Intents` uses AppIntents and CoreSpotlight. `Core` stays Foundation-only, so `swift test` still runs on Linux. The decisions the intents share live in `Core` as `IntentRules`: quick-add resolution, which task a title names, and which tasks are indexed.
- **Add Task uses the quick-add grammar.** The title is parsed with `QuickAdd`, so a date, priority, project, label, and reminder in the words work as they do in the sheet. A phrase in the title wins over a Shortcuts field for that same thing. A field fills only what the title left unset. `#Project` and `@label` still name records that already exist.
- **Complete and uncomplete.** Complete marks the open task done, with the same undo toast as the checkbox. Uncomplete reopens a completed one. A spoken title resolves through the task entity query: exact title, ignoring case and accents, open tasks first and newest first, then a prefix, then search. When the resolved task is in the wrong state, the intent uses the matching task that is in the right state, so "complete Buy milk" still completes the open one.
- **Open.** Open List switches to Inbox, Today, or Upcoming. Open Project pushes that project. Open Task presents its details. Search opens the search tab on the query and returns the task hits. List Today and List Overdue speak those tasks without requiring the app on screen.
- **Entities.** Tasks, projects, and labels are `AppEntity` values with `EntityQuery` and `EntityStringQuery`, so Shortcuts and Siri can pick them.
- **Spotlight indexes open tasks.** After each change the app reindexes them with `CSSearchableIndex` and `IndexedEntity`, including the title, the due line, and the project and label names. The task query adopts `IndexedEntityQuery`, so Spotlight can ask the app to rebuild that index. Completing or deleting a task removes it. Tapping a result opens the task.
- **Phrases.** `ProcrastimateShortcuts` registers the shortcuts, each phrase naming the app, and the app calls `updateAppShortcutParameters()` at launch.
- **Tests.** `IntentRulesTests` covers resolution and matching on Linux. `AppIntentsParityTests` runs each intent's `perform()` on the simulator through the DEBUG launch key `PROCRASTIMATE_INTENTS`, because the simulator's Siri service is not available in CI. Release builds ignore that key.

## Build and verification

- **Cloud agents have no Xcode.** They write Swift on Linux, run `swift test` for `Core` locally with a Swift toolchain, and rely on macOS CI for the app, simulator, and screenshots.
- **A separate iOS workflow.** `.github/workflows/ios.yml` runs on every pull request and push to `master`, apart from `ci.yml`, so it never slows the web checks or blocks the Worker deploy. It has no path filter, because a required check behind a path filter stays pending forever, and macOS runners are free for public repositories. It is not a required check, so a red iOS run warns without blocking a merge until the port catches up with the web. Its jobs run in parallel:
  - `core` (`macos-26`): `swift test` for `Core`, including `VectorTests`.
  - `core-linux` (`ubuntu-latest`, `swift:6.2` container, the Swift that ships with Xcode 26): the same `swift test`, so what agents run locally matches CI. Agents install a Linux toolchain with `swiftly`.
  - `app` (`macos-26`, Xcode 26): checks `Tokens.swift` is fresh, builds the app, then runs `xcodebuild test` with the XCUITests on an iPhone 16 simulator (393 points wide, the same width as Playwright's iPhone 15 Pro profile) on the iOS 26 runtime with `TZ=UTC`. Screenshots are `XCTAttachment`s named after their parity id, exported with `xcrun xcresulttool export attachments` and uploaded as the `ios-parity` artifact with the `.xcresult` bundle. The job creates a fresh iPhone 16 simulator on the newest iOS 26 runtime each run, so the device never depends on what the runner image preinstalls.
  - `web-parity` (`ubuntu-latest`): runs the Playwright `parity` project and uploads `app-web/test-results/parity/` as the `web-parity` artifact.
  - `parity-report`: after `app` and `web-parity`, it downloads both artifacts and uploads `parity-report`, a static HTML page that shows each parity id's web and iOS screenshots side by side. It runs even when one side failed, and shows a missing screenshot as missing, so a native-only screenshot such as `shell-today` appears with an empty web column.
- **Paired parity tests.** Each row of the parity checklist has one XCUITest and one Playwright test that run the same scenario: the same seed through quick add, the same pinned clock, the same taps, and equivalent assertions on the same accessible names and visible strings.
  - XCUITests live in `app-ios/Tests/AppUITests/<Area>ParityTests.swift` as `test_<parity_id>`.
  - Playwright tests live in `app-web/e2e/parity/<area>.e2e.ts`, titled `<parity-id>: <scenario>`, in a `parity` project that runs WebKit with the iPhone 15 Pro profile. The existing `desktop` and `mobile` projects and their tests stay unchanged.
  - Both sides save `<parity-id>.png`: web under `app-web/test-results/parity/`, iOS in the `ios-parity` artifact.
  - Rules that do not need UI, such as every parser phrase and guard, are proven by the vectors. The UI test covers one representative scenario.
- **Reading highlights in XCUITests.** XCUITest cannot read text attributes, so the smart input carries its tokens in the editor's accessibility identifier, such as `due: tomorrow 5pm; priority: p1`, and the tests assert that where Playwright asserts `[data-token]`. A checkbox's accessibility value is its priority (`Priority 1`), where Playwright checks the tint variable. The iOS 26 tab bar keeps badges out of the accessibility tree, so the counts test checks the rows each badge is computed from and the screenshot shows the badges. Simulator XCUITests cannot reach `onKeyPress` with synthesized hardware keys, so the smart input's arrow, Tab, Return, and Escape handling for `#` and `@` mirrors the web's `handleKeydown` without a paired test.
- **Feature map.** Each slice replaces the `iOS: Planned` entries of the features it ships in `.cursor/skills/verify-procrastimate/features/` with the XCUITest command and names, and updates its rows in [iOS parity](../ios-parity.md).
