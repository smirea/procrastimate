# iOS app

- **A native SwiftUI app at feature parity with the web app.** It does everything the web client does, as listed row by row in [iOS parity](../ios-parity.md), and looks like the web app per [Visual language](visual-language.md), with native Liquid Glass chrome, sheets, lists, swipe actions, menus, date pickers, search, and haptics instead of web lookalikes. Apple Watch comes later; distribution is TestFlight first, per [Distribution](#distribution).

## Project and architecture

- **Build on the existing `app-ios/` scaffold.** It already has `Package.swift`, `App.xcodeproj` with a file-system-synchronized `Sources/App` group and the shared `App` scheme, the bundle id `com.stefan.procrastimate`, the env-manager `Config/` bridge, and the `scripts/run` launcher behind `bun run start:ios`. Nothing gets a second project or launcher.
- **Debug uses `dev`, Release uses `prod`.** `bun run env:ios` writes `Config/Env.xcconfig` from the two env-manager environments: `API_URL[config=Debug]` from `dev`, `API_URL[config=Release]` from `prod`. `Config/Base.xcconfig` includes it and then pins Release to `https://procrastimate.stf.lol`, so a TestFlight or App Store archive calls production even when the generated file is missing or `dev` points at a machine on the LAN. CI writes the file with `--generate-only`, which uses the schema default for Debug (`http://127.0.0.1:6121`) and the same prod URL. There is no `local` environment.
- **Only the latest major iOS, iPhone first.** The deployment target is iOS 27, and the app uses the newest API wherever one exists, with no `#available` checks or fallback paths. Each new major iOS raises the target in the same change that adopts its APIs. Stefan is the only user and runs current iOS, so there is no reason to support older versions. The build has no deprecation warnings: `SpeechAnalyzer` for dictation, `installAudioTap`, `submitTaskRequest`, SwiftUI's `webAuthenticationSession`, typed `NotificationCenter` messages through `onMessage`, `NWPathMonitor` as an async sequence, and `Mutex` instead of locks. The macOS 14 app target is dropped. iPad runs the same app with the same bottom bar and no extra design work.
- **Two targets: `Core` and `App`.**
  - `Sources/Core` is a SwiftPM library with Foundation only, no SwiftUI or UIKit. It holds the model, the store and its commands, and the Swift port of the shared logic. `swift test` runs `Tests/CoreTests` on macOS and on Linux, so cloud agents without Xcode can build and test the logic.
  - `Sources/App` is the SwiftUI app, which depends on `Core`. It is a synchronized folder in `App.xcodeproj`, so later work adds files without editing `project.pbxproj`. There is no UI-test target.
  - In `App.xcodeproj`, `Core` is a static library target over the same synchronized `Sources/Core` folder, linked into `App`. A local package reference was not used, because `Package.swift` sits in the project's own folder. `Package.swift` declares only `Core` and `CoreTests`, since the SwiftUI app cannot build on Linux, so `swift run` no longer launches anything.
  - `CoreTests` use Swift Testing (`import Testing`), which runs the same way on macOS and Linux.
- **One folder per owner.** `Sources/App` has `Navigation/` (`RootView`, `Route`, `Sheet`, `Navigator`), `Launch/`, `Data/`, `Theme/`, and `Screens/<Area>/` with one file per screen: `Lists/` and `QuickAdd/` (S5), `Details/` (S6), `Browse/` and `Search/` (S7), and `Settings/` and `Notifications/` (S8). A slice replaces its own placeholders and adds files under its own folders. Route and sheet ids are plain `String`s until S2 adds the model.
- **Logic stays out of views.** Every rule that decides what a task is, where it shows, or what a chip says lives in `Core` and is covered by the test vectors. Views only render `Core` values and send store commands.
- **Inject the clock and time zone.** `Core` never reads `Date()`, `TimeZone.current`, or `Calendar.current` itself. The app passes a clock and calendar in, so tests and vectors pin them. A DEBUG-only launch environment (`PROCRASTIMATE_NOW`, `PROCRASTIMATE_TZ`, `PROCRASTIMATE_RESET`, `PROCRASTIMATE_SIGNED_IN`) can start the app from an empty store at the web suite's pinned moment, Wednesday, October 14 2026, 10:00 UTC.
  - `Core.LaunchOptions` parses the keys and rejects malformed values, and the app crashes on launch rather than run with a half-applied harness. `PROCRASTIMATE_NOW` takes an ISO 8601 moment and freezes the clock there, like Playwright's `clock.setFixedTime`. `PROCRASTIMATE_RESET=1` deletes `Application Support/procrastimate` and the app's `UserDefaults` domain before the first frame, the equivalent of a fresh browser profile. That folder (`StoreLocation`) holds the PowerSync database and the image upload queue, so a reset starts from an empty database. The Keychain session stays. `PROCRASTIMATE_OFFLINE=1` keeps sync disconnected, so a UI test can edit offline and see the edit upload on the next launch.
  - The app reads the device clock in one place, `AppClock.system`, and hands the clock to views through `@Environment(\.clock)`. Release builds ignore the launch environment, except `PROCRASTIMATE_SENTRY_SMOKE=1`, which proves Sentry reporting in production ([Observability](observability.md)). `PROCRASTIMATE_SIGNED_IN` is DEBUG-only and opens the app without a Keychain session.
- **API types are generated, not imported.** `Sources/Core/Generated/API.swift` comes from the server's contract through `bun run generate`, so the HTTP calls are typed without Apple's OpenAPI generator and its runtime packages. See [API and database types](api.md).
- **Dependencies stay at zero, except Sentry, PowerSync, and GRDB.** `powersync-swift`, pinned exactly at 1.16.4, links its `PowerSync` and `PowerSyncGRDB` products into `App` only, and brings GRDB 7.11.1, CSQLite, and the PowerSync SQLite extension with it. They are the sync product and the ORM the [Postgres and PowerSync](../postgres-powersync.md) move chose: PowerSync replaces the app's own sync engine, and GRDB records are how every app read and write reaches the local database. `PowerSyncGRDB` is marked alpha upstream; the proof of concept and the app use only `configurePowerSync`, `openPowerSyncWithGRDB`, records, and `ValueObservation`. sentry-cocoa, pinned exactly, links only into `App` as its `Sentry-Dynamic` product, and only `Sources/App/Support/Telemetry.swift` imports it ([Observability](observability.md)). The static `Sentry` product made Xcode embed an unlinked stub `Sentry.framework` holding only Sentry's privacy manifest, ad hoc signed, which export did not re-sign and App Store Connect rejected; the dynamic framework is embedded and signed like any other, and its dSYM lands in the archive. The App target sets `LD_RUNPATH_SEARCH_PATHS` to `@executable_path/Frameworks`; without it the embedded framework is never found and the app dies at launch. Its first package resolve downloads every binary xcframework in its manifest, about 346 MB, which the shared SwiftPM cache keeps after that. Unzipping uses a small in-house zip reader on top of Apple's `Compression` framework (raw DEFLATE), mirroring the web's 30-line CSV reader. ZIPFoundation is the fallback if Todoist zips use features the reader does not handle. `Compression` does not exist on Linux, so the zip reader lives in `App`. `Core` takes the extracted files, like the TS `readTodoistBackup(files)` after the web unzips with `fflate`, which keeps `Core` building and testing on Linux.

- **Errors the user sees are `ErrorReport`s.** An `ErrorReport` holds the short `message` the UI shows and a `detail` (request, status, response body, or the underlying error). Creating one logs it to the unified log under the bundle id with category `errors`, so Xcode's console and Console.app show it (`log stream --predicate 'category == "errors"'` on a simulator). `ErrorText` shows the message, and DEBUG builds also show the detail, selectable, under it. Release logs the detail as private.

## UI mapping

- **Navigation.** A `TabView` with the pinned screens (Inbox and No date until changed) and Browse, opening on the first pin, switched by the app's own bottom bar (below). Browse has the search field at the top, then Inbox and No date while they are not pinned, projects, shared items, places, events, and labels with their open counts, then Settings, and Completed at the very bottom. This maps to the web drawer's contents with native chrome.
- **Tab bar and add button.** The app draws its own bottom bar instead of the system tab bar: a Liquid Glass capsule with the pinned screens (Inbox badged with the overdue plus today count) and Browse, and beside it one accent glass `Quick add` circle (62 pt), 21 pt from the bottom edge like the system bar. The system bar cannot tint a tab, and the role that gets the separate trailing circle changed from `.search` on iOS 26 to `.prominent` on iOS 27, which left a hidden placeholder tab showing as a fourth tab under an overlaid button. Tapping the selected tab pops it to its root. The bar hides while the keyboard or quick add is up, and does not minimize on scroll. The bar floats over the tabs instead of insetting them, because `TabView` hands each tab a fresh safe area. Every screen in a tab, root or pushed, gets the room through one `tabBarClearance()` modifier, sized from `TabBarMetrics` so the last row and the bottom of each list scroll 12 pt clear of the bar and the `+`. The room shrinks by the safe area already under the content and goes to zero while the keyboard is up, since the bar hides then. Toasts use the same modifier, so they sit just above the bar, or just above the keyboard. Quick add starts with the project or label on screen as its default and never switches tabs. It stands in for the web's floating `Quick add` and is always in thumb reach. With a hardware keyboard, Cmd-K opens search.
- **Pinned tabs.** The tabs before Browse are pins: an ordered list of `Pin` values (Inbox, No date, a project, a label, a place, or an event; never Completed, which is history, not a list to work through). Browse is always the last tab. `Settings > Tabs` adds, removes, and reorders pins, and lists every screen Browse lists that is not already pinned. A pin stays per device in `UserDefaults` rather than syncing, because how many tabs fit depends on the screen, the bar exists only on iOS, and a per-device value needs no server schema. A pin keeps a place's or event's name, since those exist only while open tasks point at them. Tapping the open pin at its root, or long pressing any pin, opens a menu of the screens not already pinned; picking one swaps that tab to it for good. Every tab is at least 70 pt wide, so `Settings > Tabs` allows as many pins as fit beside Browse across the screen's portrait width (4 on a 402 pt iPhone). When the tabs do not fit beside the `+` at the current width, the `+` moves above the trailing end of a full-width bar and `tabBarClearance()` adds its height. The layout counts every pin, shown or not, so a pin hiding or coming back only resizes the tabs and never moves the `+`. A pin with no open tasks hides, except Inbox, and except while it is open, so finishing its last task keeps the tab until you leave it, as No date always did. A project or label that is gone keeps its pin stored but hidden, including one deleted on its own screen, whose tab moves to the first other pin; the pin comes back when the project or label does, from an undo on the web or a restored share. Only a sync merge moves a pin for good: to the survivor, or out of the list when the survivor is already pinned (`[Pin].following` in `Core`). A pin whose project or label never returns is never pruned. Nothing on the device can tell a deletion that stays from one that will be undone, the pins are a few bytes in `UserDefaults`, and a hidden pin takes no room in the bar or in `Settings > Tabs`. Editing `Settings > Tabs` leaves a hidden pin in its slot, so its tab comes back where it was. Opening a project, label, Inbox, or No date from an intent, a share link, or after quick add goes to its tab when pinned, else on top of Browse.
- **No inline `Add task` row.** The tab bar's `+` replaces the web's inline `+ Add task` row at the end of each list. It is always in thumb reach without scrolling to the end of a long list, it is how Todoist's iOS app adds tasks, and a second `Add task` control would duplicate it and share the accessible name of quick add's `Add task`.
- **Lists.** Plain `List`s on the web's tinted canvas (`CanvasBackground`: `canvas` with the warm glow at the top left and the cool one at the top right, fixed to the screen), with clear row backgrounds so the canvas shows through, like the web's rows, and a leading priority-tinted checkbox, the date, repeat icon, reminders, and label chips. Rows have no separators and 6 pt of vertical padding. Each row has a leading swipe that completes it, a trailing swipe that postpones it, and a context menu with a `Postpone` submenu and `Delete`. The postpone swipe opens a confirmation dialog with the shared `postponeOptions` and `Pick a date…`, which opens task details. Event tasks have no postpone. Swipe action buttons stay the system's: SwiftUI's `swipeActions` draws its own capsules and honors only a button's label and `tint`, so they cannot take a glass style. Every task list and Browse pull to refresh, which reconnects PowerSync if its stream dropped, reloads the people cache, and ends once the stream is idle, at most five seconds later; sync is otherwise live, so this is for when Stefan doubts it. The Inbox root hides its navigation bar and fades a small title in once the list scrolls. A pushed list uses an inline bar with the same small title on scroll. Rows animate in and out with list animations, and the checkbox fills on the first frame.
- **Sheets.** Quick add is a glass card attached to the top edge of the keyboard over a scrim, shown as an overlay on `RootView` rather than a sheet, because a sheet floats above the keyboard with a gap. Tapping the scrim or `Cancel` discards the draft. While it is open, toasts move to the top of the screen, as on the web. Task details is a sheet with a `NavigationStack`, so opening a subtask pushes it with a back button named after the parent. Settings never stacks with another sheet, as on the web.
  - The back button is the web's back chip, `Back to <parent>`, in place of the system one. A subtask opened straight from the Inbox or search opens with its ancestors already on the stack underneath it, so the chip and the edge swipe both pop to the parent. Every pushed screen keeps the edge swipe back, including screens that hide the system back button, because Stefan expects to slide back anywhere. SwiftUI turns the swipe off when it hides the back button, so `SwipeBack.swift` turns it back on for every `UINavigationController`.
  - The toolbar holds the project menu with its icon and name, truncated, or the back chip on a subtask, plus `Close`. `Complete` (or `Reopen`) floats at the bottom left and `Delete` at the bottom right, as on the web. They are clear Liquid Glass capsules with a tone-colored label (green, accent, red), like the toolbar's glass buttons; a tone-tinted glass fill read as a solid button. The page pads its end so they never cover content. Below the toolbar, the title, chips, labels, notes, and subtasks scroll as one page, because iOS popovers and menus float above the sheet and never clip, which is why the web keeps its chips outside the scroll area.
  - Toasts show inside the sheet too, since the list's toasts sit under it, so deleting or completing a subtask still offers `Undo`.
- **Pickers.** The date, priority, and project chips open `Menu`s, and the date chip offers presets, a graphical `DatePicker`, and a time wheel. Pickers that must stay open across taps or hold fields (the repeat menu's weekday toggles and custom interval, the reminders list with its custom date and time, and the labels picker) are popovers with `presentationCompactAdaptation(.popover)`, because a `Menu` closes on every tap and holds no fields.
- **Task details rules live in `Core`.** `TaskDetails` (the title's draft and commit, and a date change dropping the repeat), `RepeatMenu` (presets, weekday toggles, custom intervals, and the start date), and `ReminderMenu` port the rules of `TaskDetails.svelte`, `RecurrencePicker.svelte`, and `ReminderPicker.svelte`. Like `QuickAddDraft`, they come from web components rather than `shared/`, so `CoreTests` covers them with unit tests instead of vectors.
- **Subtask reorder.** Each subtask row has a handle with its own `DragGesture`, like the web's pointer drag: the row follows the finger, the rows it passes slide one step, and release calls `moveSubtask`, which writes only that subtask's fractional `order`. `List` with `onMove` was not used, because the subtasks sit in a scrolling page with the notes and fields rather than a list, and its drag starts on a long press anywhere in the row. VoiceOver gets `Move up` and `Move down` actions on the handle in place of the web's arrow keys.
- **Project reorder.** Browse's Projects section is a `List`, so it takes `onMove`: a long press on a row lifts it, the system animates the rows it passes, and release calls `moveProject`. That is the standard iOS list reorder and needs no edit mode, so it is used here even though subtasks need their own gesture. Browse's project rows have no context menu: with one, holding still opened the menu and the drag only started if the finger moved within about half a second. `Copy as Markdown` for a project lives in its screen's `Project actions` menu.
- **Smart input.** Quick add, the details title, and the add-subtask field share one input: a `TextEditor` on an `AttributedString` that tints parsed phrases with the same token colors as the web, the chip row below it, and the `#` and `@` suggestion list above it, driven by one table of the two kinds like the web.
- **Quick add rules live in `Core`.** `QuickAddDraft` holds the text and the chip picks, with the web `QuickAdd.svelte` rules: the text wins over a pick, a pick removes the phrase that set it, and saving resets to the sheet's defaults. These come from a web component rather than `shared/`, so they have unit tests in `CoreTests` instead of vectors. The `#` and `@` suggestions call `NameSearch`.
- **The smart input re-tints, never rebuilds.** While the editor has focus, `EditorTints` writes the token backgrounds straight into the focused `UITextView`'s text storage, right after each change and again once typing pauses. Writing them back through the `AttributedString` binding while UIKit was still applying a keystroke made SwiftUI push a stale copy of the text: the newest phrase sometimes stayed untinted (`p1` at the end of the text), and a keystroke typed during the push, such as Return, was dropped, so the field did not clear after saving. Background attributes on the storage change neither the characters nor the selection, so the caret stays put. Without focus, the binding is styled with `AttributedString.transform(updating:)`. A typed Return is stripped and submits instead of adding a line. DEBUG builds expose what the storage renders tinted as `Rendered highlights`.
- **Undo.** A glass toast at the bottom with `Undo`, five seconds, matching the web's text such as `Completed "Standup", next due Friday 9am`.
- **Haptics.** `.sensoryFeedback`: success on complete, selection on picker changes and weekday toggles, and a light impact when a subtask drag picks up and drops. Nothing buzzes on typing.
- **Colors.** `bun run generate` writes the git-ignored `Sources/App/Generated/Tokens.swift` from the semantic tokens in `app-web/src/index.css`, with light and dark values for `ink`, `muted`, `accent`, priorities, date tones, and parser highlights. The generator is `scripts/generate/tokens.ts`, so every build writes the colors and nothing can drift. It also writes the `AccentColor` asset from `--color-accent`, the app's global accent, because system chrome such as a sheet's toolbar buttons ignores SwiftUI's `tint`. It emits every color token, named in camelCase without the `--color-` prefix, as `Palette.<name>` with a light and a dark sRGB value that follow the trait collection, plus a `ShapeStyle` shorthand so views write `.foregroundStyle(.muted)`. Materials are the system's: glass for floating chrome and solid backgrounds for content.
- **Accessibility.** System glass and materials already turn solid under Reduce Transparency and Increase Contrast. Custom motion reads `accessibilityReduceMotion` and becomes instant, like the web's `motion()`. Every control has an accessibility label that matches the web's accessible name.
- **Browse.** An inset grouped `List` on the canvas: Projects in their order, then Labels alphabetically in `en-US` collation (`Browse.labelsByName`, shown once a label exists), then Notifications and Settings. Each row carries its open count (the same `Views.projectTasks` and `Views.labelTasks` lists the screens show) as its accessibility value. Projects have no user-picked colors, so the project `number` icon is `muted`. Each label's tag takes its own color, as on the web (see Labels UI). `Add project` in the Projects header inserts a focused `Project name` row in place, like the web sidebar's inline field: Return or losing focus creates it and pushes it, and an empty name cancels. With a long project list the list scrolls the new field into view, so it can take focus.
- **Project and label screens.** They reuse the task list screen, so rows, swipes, and the empty state behave like Inbox, and the tab bar's `+` opens quick add with the project or label as its default. A pushed list always shows its name centered in the bar; a tab's root list fades its name in once scrolled. Tapping the selected pinned tab, or long pressing it, opens the swap menu (see Pinned tabs). Renaming and deleting sit in the `Project actions` or `Label actions` toolbar menu, the native stand-in for the web header's popover. The label menu also holds the `Color` submenu. `Rename` opens an alert prefilled with the name, which suits a one-field edit better than editing the title in place. Delete confirms with a `confirmationDialog` using the web's wording (`Delete House and its 3 tasks?`, `Delete phone?` with `Its tasks stay, without the label.`), then pops back to the screen it came from rather than jumping to Inbox, and the record goes once the pop has played, so its Browse row leaves in view.
- **Search lives in Browse.** Browse puts an always-visible `.searchable` field at its top. Typing replaces the Browse list with `SearchResults`. Results come from `Core`'s `Search`, grouped and limited by `SearchSections` (5 projects, 5 labels, 30 open, 15 completed, the full count in each header), with matched spans on the `tokenMatch` highlight through `AttributedString`. A task result opens task details as a sheet. A project or label result pushes its screen onto Browse's stack, so Back returns to the results. The query lives on `Navigator`, which empties it whenever Browse is entered from another tab and sets it in `showSearch(query:)`, so Cmd-K starts empty and the Search App Intent passes its words. Scrolling dismisses the keyboard.
- **Search actions and keys.** Return opens the selected result, which is the first one until a hardware keyboard's Up or Down moves it (`onKeyPress`). Escape is the search field's own cancel. Cmd-K opens Browse and focuses its search field, closing any sheet and popping Browse's stack, registered by `searchShortcuts()` on `RootView`. Pressing it again keeps the field focused. The web's bare `/` stays web only: a key command without a modifier would take the character from whichever text field is focused (quick add, `Project name`, a rename alert), and SwiftUI has no app-wide text focus to gate it on. A completed result reopens from its leading swipe or context menu and an open one completes the same way, matching list rows, and task details reopen it with `Reopen` in the toolbar.
- **Search result names.** Each result's identifier is `result-<title>`, `result-project-<name>`, or `result-label-<name>`, and its accessibility value reads its matched spans (`Matches call`), which tells VoiceOver why a result is listed.
- **Theme.** `System`, `Light`, and `Dark` live in Settings, stored in `UserDefaults` under `procrastimate-theme`. `System` stores nothing. The app sets the window's `overrideUserInterfaceStyle` when the root appears, before its first frame, and on every choice, with `.unspecified` for `System`. Sheets and UIKit chrome such as the document picker inherit it. `preferredColorScheme` is not used: going back to `nil` keeps the last forced style, and a sheet that is already open, like Settings itself, does not restyle. Reduced motion is one root `.transaction` that drops animations while Reduce Motion is on, so no view repeats the check. Glass fallback and Reduce Motion follow the system settings.

## Shared logic and test vectors

- **Swift ports of `shared/`.** `Core` ports the quick add parser, dates and recurrence (`nextOccurrence`, `alignToRecurrence`, `stepRecurrence`, month clamping), `notificationTimes` and `reminderFiresAt`, subtasks (complete, reopen, move, orphans, progress), name search for `#` and `@`, search with ranking and highlights, the CSV reader, and the Todoist reader and merge.
- **Pure logic lives in `shared/`, not in the web app.** Everything that decides what both clients show is in `shared/`: list membership and order (`views.ts`), chip, row, heading, and toast strings (`format.ts`), notification times and text (`notifications.ts`), the row writes a command turns into (`rows.ts`), and the store's commands (`store.ts`). The commands are pure functions over `{ tasks, projects, labels }` that return new arrays and objects for what they change, and take the new record's id and time from the caller, so the Svelte store (raw state, one `#apply` per command) and the Swift store call the same rules. Todoist import goes through `mergeBackup` in `todoist.ts`, which S4 ports.
- **One JSON corpus, recorded from the TS unit tests.** `shared/vectors/<module>.json` holds `{ fn, test, input, output }` cases. The TS tests wrap each ported function with `recorded('<module>', fn)` from `shared/vectors/record.ts`, and import `describe` and `test` from it too, since Bun exposes no current test name; those wrappers name each case after its test. With `VECTORS=record`, every call during `bun test shared` writes its input and the real TS output, and each test file's `afterAll` writes its modules, because `bun test` runs no exit hooks. Outside record mode `recorded` returns the function itself. The test assertions prove the TS output is the intended behavior, and the corpus carries it to Swift, so there is one source of cases and no hand-written expectations to drift.
- **Generating it.** `bun run vectors` runs the shared tests in record mode with `TZ=America/New_York`, which has a DST change inside the corpus window (November 1, 2026), so time zone bugs show up instead of hiding behind UTC. Files are pretty-printed with sorted keys and cases in test order, so a diff reads as a behavior change. Dates are recorded as epoch milliseconds plus the zone in each file's header, and `DateKey` and `TimeOfDay` stay strings.
- **Checking both sides.** The web `checks` job runs `bun run vectors`, then fails if `git status --porcelain shared/vectors` prints anything. That catches both a changed file and a new, uncommitted vector file, which `git diff` alone would miss, so TS behavior cannot change without the corpus being regenerated. The iOS workflow's `core` job runs `swift test`, where `VectorTests` decodes every file and asserts that the Swift port returns the recorded output for each case. A TS change that alters behavior therefore turns iOS CI red until the Swift port matches.
- **The Swift port mirrors the TS modules.** `Core` has one namespace per module: `Dates` (`task.ts` dates and recurrence), `Notifications`, `Subtasks`, `Views`, `Format`, `StoreRules`, and `Rows`, with the same function names, so a vector's `fn` maps to one Swift call. The task type is `TaskItem`, because `Task` would shadow Swift concurrency's `Task` in the app. `DateKey` and `TimeOfDay` are strings, calendar math is civil (day counts, no zone), and only turning a date and time into a moment takes a `TimeZone`. That conversion follows JavaScript's `new Date(y, m, d, h, min)`: a repeated hour at a DST change takes its first occurrence and a skipped hour moves forward by the gap, so Swift and the web pick the same instant. Timestamps are `Int` epoch milliseconds, as in the document.
- **The quick add parser keeps the TS patterns.** `QuickAdd.parse(input, options, in: zone)` ports `parseQuickAdd` with the same rules, guards, and order, and its regular expressions are the TS sources character for character. `QuickAdd.Pattern` translates each one for ICU (`NSRegularExpression`, which runs on Linux) so it matches like JavaScript without the `u` flag: `\w`, `\d`, and `\b` stay ASCII, `\s` is JavaScript's whitespace set, `$` is the end of the input, and set syntax inside a class is escaped. ICU rejects unbounded lookbehind, so a `+` or `*` inside one is capped at 64 characters, which a title never reaches. Token `start` and `end` are UTF-16 offsets, like JavaScript string indices, so the app converts them with `String.Index(utf16Offset:in:)` before tinting the `AttributedString`. Swift's own `Regex` was not used, because its word boundaries and character classes are Unicode by default, so matching like JavaScript would mean rewriting the patterns rather than translating them.
- **One data shape.** `Core`'s model is generated from the shared schemas (see [API and database types](api.md)): `Snapshot` is one space's data plus its settings, as `shared/model.ts` defines it, and `Access` is an `access` row. A row write's `values` stay `JSONValue`s, which `Rows.rowWrites` builds generically like the web's `Fields`, comparing entities as values first so only the ones a command touched are encoded.
- **Search and import namespaces.** `CSV` (`csv.ts`), `Search` (`search.ts`), `NameSearch` (`name-search.ts`), and `Todoist` (`todoist.ts`). Their text code follows JavaScript strings, through `UTF16Text`: highlight ranges, the caret, and fragment offsets count UTF-16 code units, whitespace is JavaScript's `\s`, and names compare by code unit, so a highlight or a `#` fragment lands on the same characters on both clients. Views convert offsets to `String.Index` with `String.Index(utf16Offset:in:)`.
- **Functions in vector inputs.** A vector cannot hold a function. `lastUsed(tasks, idsOf)` records through test wrappers named `lastUsedProjects` and `lastUsedLabels`, which map to `NameSearch.lastUsed` with `projectIdsOf` or `labelIdsOf`. Every `mergeBackup` call in the tests takes ids from a fresh `id-1`, `id-2`, … counter, which `VectorTests` replays.
- **Todoist dates go through the parser.** `Todoist.readTodoistDate` reads ISO dates itself and passes anything else to `QuickAdd.parse`, which must account for the whole text, as on the web.

## Data

- **The store lives in `Core`, over rows.** `Store` is a main-actor `@Observable` class holding the signed-in user's own `Snapshot`, one `Snapshot` per owner who shares with them, the `access` rows, and the people cache. It keeps every `StoreRules` command synchronous: a command replaces memory at once, and `commit` turns the before and after of the space it ran in into `RowWrite`s with `Rows.rowWrites`, then hands them as one `RowBatch` (a version, the space's owner as `user_id`, the writes) to an injected `writer`. `Core` stays Foundation-only and knows nothing of PowerSync or GRDB, so `swift test` covers commands, row writes, and grouping on Linux.
- **One serial writer.** The app's `SyncClient` feeds each batch to an `AsyncStream` that one task drains, so batches reach the database in commit order, each in one GRDB transaction (`LocalDatabase.write`). GRDB's `upsert` fails on PowerSync's views and `save` of a new record writes nothing, so a put is `insert` (or `updateChanges` when the row is already there), a patch is `updateChanges` on the stored row with the changed fields merged in, and a delete is `deleteOne`. `updateChanges` compares GRDB's own encoding before and after, so only changed columns are written and queued, never a JSON column Postgres spelled with spaces. A patch of a row that is gone changes nothing, as on the server. `Store.saved()` returns once the writer finished every commit made before the call; App Intents await it before they return, since the system may suspend the process right after, and `flush()` awaits it before it looks at PowerSync's queue.
- **Settings are only ever patched, and only once the row exists.** The server creates every user's settings row and never lets a client's put overwrite it, so the client never builds one. A settings change before the first sync brought the row shows at once and waits in the store (`unsavedSettings`); the reload that brings the row writes it as one patch of the changed fields over the server's values. A change still waiting when the app quits is lost, which is the price of never guessing the rest of the row.
- **Reloads never undo a command.** A `ValueObservation` over every synced table reads the rows, groups them by `user_id` into `Spaces` (own, shared by owner, and `access`), and calls `store.reload`. A reload that arrives while a batch is still on its way to the database is held back, and the writer reads again once it catches up (`Store.written`), so a stale read never rolls the screen back. A row that does not decode is left out and logged.
- **Generated row types.** `bun run generate` writes `Sources/App/Generated/SyncedTables.swift` from the `pg-core` schema (`scripts/generate/tables.ts`): the PowerSync `Schema` (every synced table with `ignoreEmptyUpdates`, JSON columns as text) and a `RowLayout` on each Core type a table holds, found by its schema's `x-table`. `SyncedRow<Value>` is the one GRDB record over them: it reads each column into the Core type through JSON, so a row decodes with the API's rules, and writes JSON columns as compact sorted JSON text. A synced table without a Core type fails the generator.
- **The database file.** `Application Support/procrastimate/procrastimate.sqlite`, opened with `configurePowerSync` and `openPowerSyncWithGRDB`. PowerSync creates its views on its first call, so the app awaits `getPowerSyncVersion()` before the first write and the observation; launch reads the rows synchronously first, which works from the second launch on because the views persist in the file, so the first frame shows the data.
- **Device-local state is `UserDefaults`.** The people cache (`procrastimate-people`), when reminders were last shown (`procrastimate-reminders-checked-at`), the install id Ramble sends as `x-procrastimate-device` (`procrastimate-install-id`), the owner (`procrastimate-owner`), pins, and the theme. Nothing else is sent with a device header.
- **Not SwiftData.** The ported logic works on value arrays of tasks, exactly like the TS. SwiftData would force a mapping between `@Model` objects and those values on every command and add migrations the product does not want. GRDB records over PowerSync's views keep the values as they are.
- **Todoist import on iOS.** `Import from Todoist` in Settings opens `.fileImporter` for a `.zip`, and the app also accepts a zip shared or opened into it. The same reader and merge as the web run on the device, as one command and one batch of row writes. The reader and merge are covered by the Todoist vectors.

## Sync

- **The connector.** `SyncConnector.fetchCredentials` calls `GET /api/sync/token` with the Keychain bearer; a `401` signs out. `uploadData` first uploads every queued image (`TaskImages.uploadQueued`), then reads a batch of PowerSync's queue with `opDataTyped` (`opData` turns numbers into strings), folds it to one write per row with `Rows.coalesce`, fills a put's missing columns with null (PowerSync leaves null columns out, and the server reads a put as the whole row), posts `{ writes }` to `POST /api/upload`, shows `Rows.rejectionNotice` as a toast for what came back `rejected`, and completes the batch. A network failure throws, so PowerSync retries.
- **The connector never uploads `access`.** Only the server writes `access`; a queued entry for it, or for any table the client does not write, is dropped and logged rather than thrown, because a throw would stall every upload behind it. The DEBUG sharing demo keeps its `access` rows in memory (`demoAccess`) for the same reason. `uploadData` reads up to 1000 queued entries, so one command's writes almost never split across requests.
- **Connected while signed in.** `SyncClient.start()` connects once a session token exists and its owner is known, with a 200 ms upload throttle and a 2 s retry; coming back to the foreground reconnects a dropped stream. A second `start()` while the first is still connecting joins it. After the first sync the app writes the device's time zone into the settings row when it differs, and loads the people cache from `GET /api/people`, also whenever a shared space's owner has no name yet. There is no timer, no socket, and no outbox of the app's own.
- **Switching users clears the database.** `Session.adopt` runs `disconnectAndClear()`, empties the store, and clears the local images when the session's user is not `procrastimate-owner`. Signing out disconnects and keeps the database.
- **The Keychain names the token's owner.** A reinstall keeps the Keychain but loses `UserDefaults` and the database, so the session check stores the user id beside the token (`procrastimate-session-user`), and a launch with an empty `procrastimate-owner` opens the empty database as that user's, offline included. Filing rows under a guessed owner showed the user's own data as a space shared by "Someone" and uploaded new tasks as `local`, which the server refused. Only a token stored before the id was kept has no known owner: then the store's `me` is nil, it reads nothing from the database, keeps every commit in memory, and sync does not connect, while `Session.start` repeats the session check, backing off from 1 to 30 seconds. Adopting the owner keeps the database, writes the held commits in order as the owner's, and connects. Without a token the owner is `local`, which never syncs, and adopting a user from it clears the database as for any other user.
- **App Intents and Spotlight read the same store.** `SyncClient.shared(clock:)` is the one instance, created at launch or by whichever intent runs first.
- **Measured.** A throwaway `./sim test` against a worktree's server signs in, adds a task from quick add and finds it in `GET /api/view`, sees a task created through `POST /api/tasks` on screen about 0.1 s later (XCUITest's own polling included), and sees a task added under `PROCRASTIMATE_OFFLINE=1` survive the restart and reach the server once the next launch connects.

## Notifications

- **Local notifications, no server push.** The app schedules `UNNotificationRequest`s with a `UNTimeIntervalNotificationTrigger` for each future moment from `notificationTimes`. Moments are instants, so an interval from the app clock is exact and keeps working under the pinned test clock, where a calendar trigger would read the real one. A due time is a reminder, a date with no time never notifies, and a moment notifies once, exactly as [Domain](domain.md) says. Titles and bodies come from the shared notification text, such as `Due now` or `Due at 6:00 PM`. Notifications need no APNs and no push entitlement. When sync brings changes from another device, the store reloads and the schedule is recomputed like after any local change.
- **Replace the whole schedule after every change.** Like the server does for Web Push, the app computes the full schedule after each command, debounced, and diffs it against the pending requests. Each identifier is the shared `pushTag` (`<taskId>:<epoch ms>`), so a re-add replaces the request instead of duplicating it, and completing, editing, deleting, and restoring need no cancel path. A repeating task schedules its next occurrence once completing moves its date.
- **iOS keeps at most 64 pending requests.** The app schedules the soonest 60 and refills when it opens, comes to the foreground, after each change, and from a `BGAppRefreshTask`. Moments past the window still fire if Stefan opens the app within the gap. Each delivered notification is a reminder to open the app, which then refills the window.
- **In the foreground, toast only.** The notification center delegate's `willPresent` returns no banner and the app shows the `Reminder: <title>` toast with `Open`, matching the web rule that the open app shows the toast and leaves the system notification to the background.
- **Permission is the switch.** The app asks on first launch. When the system allows notifications, they are on, and there is no in-app off switch. Settings shows one line: `Notifications: On`, `Notifications: Off`, or `Notifications need permission`. The last one opens the app's page in Settings. There is no Notifications row in Browse and no `Turn on` toast.
- **Tapping a notification opens its task** in task details from the `taskId` in its payload. `Navigator.openTask` is the seam a tap goes through. A reminder toast while the app is open stays; it is the open app's own reminder, not a prompt to turn notifications on.
- **Testing notifications.** The schedule is covered by `NotificationScheduleTests`. A DEBUG-only `PROCRASTIMATE_NOTIFICATIONS_DENIED=1` launch key answers the denial without a prompt. Release builds ignore it.

## Places and calendar events

- **Set on the iPhone only.** The `Location` chip after the reminder chip opens an Apple Maps search (`MKLocalSearchCompleter` suggestions biased to where Stefan is, resolved with `MKLocalSearch`) with an `Arrive`, `Leave`, or `During` menu beside the field, and saves a 150 m `TaskLocation`. The `Event` chip opens upcoming EventKit events for 60 days, the moment (`Before`, `Start`, `During`, `After`) with minutes, and `Only this one` for a repeating event. Quick add shows the same two chips after the reminders. Neither has a quick add phrase, Ramble, or App Intent support: a place or an event is picked from a list, not typed or spoken.
- **An event stands in for the date.** Linking one clears the due date and the repeat in the same patch, and the event chip takes the date chip's place while the repeat chip hides. The reminder chip then offers only the presets, counted back from the event's moment, since a custom date would not follow a moved event.
- **Permissions on first use.** Location access is requested when a place is first set, asking for Always, which iOS shows as When In Use first and offers to upgrade later. Full calendar access is requested when the event sheet opens. Nothing asks at launch, and background sync never asks.
- **`CLMonitor` region conditions, never GPS.** Each armed place is one `CLMonitor.CircularGeographicCondition` keyed by spot and radius, shared by every task there, so many tasks at one place take one slot. A crossing goes to each of that place's tasks that is armed, by its own trigger. iOS evaluates regions from cell and Wi-Fi changes and relaunches the app for a crossing, which costs far less battery than continuous or significant-change updates. The monitor is opened when the app is created, so a relaunch for a crossing finds its listener. With Always granted, the app also holds a `CLServiceSession` requiring Always from that same moment, because since iOS 18 `CLMonitor` delivers no events to an app that is not in use unless such a session is held, and it must be retaken at every launch, background relaunches included. Without it, crossings arrived only once the app was opened.
- **At most 20 places, armed when they matter.** iOS monitors 20 regions per app. A place with a due date or reminders is armed only from the start of its due day (`Triggers.scheduledDue`) or its first reminder, whichever comes first; one with neither is always armed. A place arms with its first armed task, and the 20 soonest-armed places win. The conditions re-sync on launch, foreground, after every store change (so sync pulls too), and from background refresh, and a second `BGAppRefreshTask` (`com.stefan.procrastimate.places`) is asked for at the next arming moment.
- **A crossing is an edge.** The last state of each condition is stored across launches, and `Arrive` notifies only on unsatisfied to satisfied, `Leave` on the reverse. The first report after a condition is added has no prior state, so setting a place while standing in it never notifies. The open app shows a crossing as a toast with `Open`, like a reminder; tapping the notification opens the task through `Navigator.openTask`.
- **`During` is a Live Activity per place.** A `Widgets` app extension (`com.stefan.procrastimate.widgets`) draws `PlaceActivityAttributes` on the lock screen and in the Dynamic Island, listing the place's open `During` tasks. The attributes live in `Sources/Activity`, a synchronized folder both targets build. Every sync brings activities in line with the stored states: one per place that is inside, updated as tasks complete, ended on leaving. ActivityKit only starts an activity from the foreground, so a crossing in the background posts a notification instead, and the next foreground sync starts the activity if Stefan is still there.
- **The calendar is the source of an event's times.** `CalendarSync` rewrites each open event task's title, all-day flag, and occurrences from EventKit on launch, foreground, `EKEventStoreChanged`, and background refresh, writing only when something changed, so reminders and the push server follow a moved event on every client. A series lists up to 10 occurrences in 60 days from the start of today, resuming at the stored current occurrence by its original start, so completing a series task (which drops its occurrence) is not undone. A pinned occurrence is found by its original start, and a plain event by its id. A moved occurrence is detached and its identifiers gain `/RID=<date>`, so the series is named by the part before it. When nothing is found, the task keeps what it had.
- **Testing.** The simulator cannot be tapped from an agent, so the DEBUG launch key `PROCRASTIMATE_DEMO` seeds place and event tasks, adds calendar events, opens sheets and Browse search, types into the focused field, and moves an event. See the `places-and-events` feature file.

## Siri, Shortcuts, and Spotlight

- **The iOS app works with Siri, Shortcuts, and Spotlight.** Every feature someone can do in the app, and that makes sense from outside it, ships with App Intents in the same change: the intent, an App Shortcut phrase when it is something Stefan would say, and an `AppEntity` when Shortcuts or Siri should pick a task, project, or label. This is the default for a new feature, not a follow-up. A preference such as dictation or the theme does not: it is not an action on a task, and it is not something Stefan asks Siri to change.
- **App Intents are iOS-only.** The web client is excluded because Siri, the Shortcuts app, Spotlight, and App Intents are system features of iOS. There is no web counterpart to build.
- **Intents live in the App target.** `Sources/App/Intents` uses AppIntents and CoreSpotlight. `Core` stays Foundation-only, so `swift test` still runs on Linux. The decisions the intents share live in `Core` as `IntentRules`: quick-add resolution, which task a title names, and which tasks are indexed.
- **Add Task uses the quick-add grammar.** The title is parsed with `QuickAdd`, so a date, priority, project, label, and reminder in the words work as they do in the sheet. A phrase in the title wins over a Shortcuts field for that same thing. A field fills only what the title left unset. A reminder in the title replaces the Reminder field, rather than scheduling both. `#Project` and `@label` still name records that already exist.
- **Complete and uncomplete.** Complete marks the open task done, with the same undo toast as the checkbox. Uncomplete reopens a completed one. A spoken title resolves through the task entity query: exact title, ignoring case and accents, open tasks first and newest first, then a prefix, then search. When the resolved task is in the wrong state, the intent uses the matching task that is in the right state, so "complete Buy milk" still completes the open one.
- **Open.** Open List switches to Inbox, No date, or Browse. Open Project opens that project, in its own tab when pinned. Open Task presents its details. Search opens Browse with the query in its search field and returns the task hits. List Today and List Overdue speak those tasks without requiring the app on screen.
- **Entities.** Tasks, projects, and labels are `AppEntity` values with `EntityQuery` and `EntityStringQuery`, so Shortcuts and Siri can pick them.
- **Spotlight indexes open tasks.** After each change the app reindexes them with `CSSearchableIndex` and `IndexedEntity`, including the title, the due line, and the project and label names. Renaming a project or label reindexes too, because those names are part of the entry. The task query adopts `IndexedEntityQuery`. The reindex methods that take `CSSearchableIndexDescription` are iOS 27; on the deployment target the app donates the index itself after each change. Completing or deleting a task removes it. Tapping a result opens the task. An intent that runs before the screen is up, or while the app is not showing, still updates Spotlight and the notification schedule after it writes the snapshot.
- **Phrases.** `ProcrastimateShortcuts` registers the shortcuts, each phrase naming the app, and the app calls `updateAppShortcutParameters()` at launch. A phrase can fill an `AppEntity` or an `AppEnum` only, so the task title and the search words are the follow-up question rather than part of the phrase. The system keeps ten shortcuts. Start Ramble takes the suggested slot Delete All Data had; Delete All Data stays an intent, without a suggested phrase.
- **Tests.** `IntentRulesTests` covers resolution and matching on Linux. Release builds ignore the DEBUG launch key `PROCRASTIMATE_INTENTS`.

## Build and verification

- **Cloud agents have no Xcode.** They write Swift on Linux, run `swift test` for `Core` locally with a Swift toolchain, and rely on a manual iOS workflow run for the app, simulator, and screenshots.
- **A separate iOS workflow.** `.github/workflows/ios.yml` runs on every pull request and push to `master`, apart from `ci.yml`, so it never slows the web checks or blocks the Worker deploy. The macOS `core` and `app` jobs run on a pull request that touches `app-ios/`, `shared/`, `scripts/generate/`, `app-web/src/index.css`, `package.json`, `bun.lock`, or the workflow, and on a manual `workflow_dispatch`, so an iOS change never merges with only the Linux tests. A `changes` job decides. Other pull requests and pushes to `master` skip them with `if`, which reports success, so a required check of that name does not stay pending; TestFlight already archives every app change on `master`. `core-linux` runs on every pull request and push. Its jobs:
  - `core` (`xcode-27`, iOS pull requests and `workflow_dispatch`): `swift test` for `Core`, including `VectorTests`.
  - `core-linux` (`ubuntu-latest`, `swift:6.4.1` container, the Swift that ships with Xcode 27): the same tests through `swift test --build-system native`, since the default backend crashes intermittently on Linux. See [Testing](testing.md). Agents install a Linux toolchain with `swiftly`.
  - `app` (`xcode-27`, Xcode 27, iOS pull requests and `workflow_dispatch`): checks that Debug calls dev and Release calls production, and builds the app so the privacy manifest is in the bundle. It runs nothing generated before `xcodebuild`, so it also proves a fresh clone builds in one pass. It does not drive the UI.
- **No paired UI tests.** Parser phrases, guards, and the other shared rules are proven by the vectors. The web smoke is auth and sync. See [Testing](testing.md).
- **Feature map.** Each slice updates the features it ships in `.cursor/skills/verify-procrastimate/features/` and its rows in [iOS parity](../ios-parity.md).

## Distribution

- **TestFlight first, built in CI.** The app ships as `ProcrastiMate` (display name) under bundle id `com.stefan.procrastimate` and team `FNYFHG5SV7`, which the app target sets with automatic signing. Internal TestFlight testers need no App Review; the App Store does.
- **App Store metadata lives in the project.** Category `public.app-category.productivity`. iPhone allows portrait and both landscapes; iPad allows all four orientations, which iPad multitasking requires. `Config/Info.plist` sets `ITSAppUsesNonExemptEncryption` to `false`, since the app only uses HTTPS, so uploads skip the export compliance question. The launch screen stays the generated one.
- **One icon source.** The 1024-pixel `AppIcon` is a single universal image rendered from `app-web/scripts/app-icon.svg` with the tile color filling the corners, because iOS applies its own mask and rejects icons with transparency. `app-web/scripts/icons.ts` renders it with the web icons, so editing the SVG and rerunning that script updates both clients. The browser favicon is a separate, simpler head-only drawing, `app-web/static/icons/favicon.svg`, that stays legible at 16 pixels.
- **Release builds call production.** `Config/Base.xcconfig` sets `API_URL[config=Release]` to `https://procrastimate.stf.lol` after including `LocalSecrets.xcconfig` and `Env.xcconfig`, so an archive never ships a dev URL and needs no command-line override. Debug comes from env-manager `dev`, `http://127.0.0.1:6121` by default. The iOS workflow's `app` job checks both.
- **Archive and upload with an API key.** `app-ios/scripts/archive` archives Release unsigned (`CODE_SIGNING_ALLOWED=NO`), then exports with `method = app-store-connect` and uploads with `destination = upload`. Export is the only signing step: `-allowProvisioningUpdates` and an App Store Connect API key make Xcode use the existing cloud-managed Apple Distribution identity and its App Store profile. The archive does not sign, so it does not create an Apple Development certificate. A fresh runner that archived with automatic signing was minting a new "Apple Development: Created via API" certificate on every upload, and the account is at that cap. Setting `CODE_SIGN_IDENTITY` to Apple Distribution on that automatic archive is rejected: Xcode treats automatic signing as development and reports a conflicting identity. The key id, issuer id, and `.p8` path come from `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_KEY_PATH`, and the script refuses a key inside the repo. `--export-only` writes the `.ipa` instead. The build number is the UTC time as `year.MMdd.HHmmss` (three integers, the first at most four digits, as `CFBundleVersion` requires) unless `BUILD_NUMBER` overrides it, so uploads always increase without committing a bump. The version comes from the build itself (see [Production hosting](production-hosting.md)), so the archive passes none.
- **TestFlight builds come from GitHub Actions, not a Mac.** `.github/workflows/testflight.yml` runs the archive script on an `xcode-27` runner (the app needs the iOS 27 SDK, which the `macos-26` images lack) on every push to `master` that touches `app-ios/`, and on a manual `workflow_dispatch`. It never runs on pull requests. Pushes share the `testflight` concurrency group with cancel-in-progress, so a newer push cancels the run already in progress. A debounce job waits ten minutes on a Linux runner, then skips the archive only when a newer commit on `master` since this run touched `app-ios/` or `.github/workflows/testflight.yml`, because that commit starts its own run. A later web or server commit does not, since the path filter would not start one, and this run still archives. The macOS runner is claimed only for a build that uploads. A manual `workflow_dispatch` skips the wait and builds the selected commit. The key lives in env-manager `prod` as `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY_B64` (the `.p8` base64 on one line) and reaches the repository secrets through `bun run secrets:github`; the job decodes it into the runner's temp directory and deletes it at the end. The internal group `me` has access to all builds, so each upload reaches it with no assignment step. `.github/workflows/testflight-processed.yml` polls the App Store Connect API with the same key until that build's processing state is VALID, and it does not archive. Pushing the file checks the build it names; a manual run checks the build number you pass. Xcode Cloud was the first choice, but the App Store Connect API cannot create an Xcode Cloud product: the first workflow has to be made in Xcode on a Mac, and the Xcode Cloud GitHub app has to be granted this repository. If it is set up later, turn this workflow's push trigger off so master is not uploaded twice, and set Xcode Cloud's next build number above 2026 because its integer build numbers would otherwise sort below the timestamp builds already in version 1.0.
- **Privacy manifest.** `Sources/App/PrivacyInfo.xcprivacy` declares no tracking, and the user id, email address, and crash, performance, and other diagnostic data collected for app functionality and linked to the user, since Sentry events carry the user's id and email, plus the one required-reason API the app calls, `UserDefaults` with reason `CA92.1` (the theme, the pins, the people cache, the install id, when reminders were last shown, and the launch reset). App Store Connect rejects uploads, TestFlight included, that use such an API undeclared, so a new required-reason API (file timestamps, disk space, system boot time) needs its entry in the same change.
- **Still needed before the App Store:** an App Store Connect app record for the bundle id, the privacy label (user id, email address, crash, performance, and diagnostic data, linked to the user, not used for tracking), screenshots, and a description.
