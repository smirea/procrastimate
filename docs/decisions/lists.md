# Lists

- **Top-level lists.** A top-level list is a screen of tasks a user can open, pin, and pick from a menu. The lists are Inbox, Tomorrow, This week, and No date, then every project, every project and label shared with the user, every place open tasks hang off, every calendar event open tasks hang off, and every label. Completed is not one. It is a log of finished work, so the web sidebar adds it after the fixed lists, iOS puts it at the bottom of Browse, and nothing pins it. A shared task that no shared project or label leads to is not a list either, so it is listed after the shared lists.
- **One catalog.** `listCatalog` in `shared/lists.ts`, ported to Core's `Lists.catalog`, is the only place that decides which lists exist, what each is called, how they group, and their order. It returns every group in a fixed order: `Lists`, `Projects`, `Shared with me`, `Places`, `Events`, `Labels`. Projects follow `projectsInOrder`, shared lists follow `sharedEntries`, places and events follow `placeGroups` and `eventGroups`, and labels sort by name. A saved place is a label, so it lists with the labels and not with the places. The web sidebar, iOS Browse, the iOS tab swap menu, and `Settings > Tabs` all read it. Each surface only filters it: the tab menu and `Settings > Tabs` leave out what is already pinned, Browse leaves out pinned fixed lists, and a surface hides a group with no entries except Projects, which keeps its add button. A new list kind goes into the catalog, and every surface gets it.
- **Empty lists stay.** A list keeps its sidebar entry, Browse row, and tab while it has no tasks, because a menu that changes when you don't expect it is more annoying than an empty list. Places and events are the exception. They exist only while open tasks point at them, so they leave with their last open task.
- **Counts.** Each entry carries the number of open rows its screen lists. Inbox is the exception. It counts overdue and today's tasks, the same number as its badge. A shared list counts 0, since its row shows who shared it instead.
- **Tomorrow and This week.** Two dated views next to Inbox, built on `dueDays` in `shared/views.ts`, so they group and sort exactly like Inbox. Tomorrow lists only tomorrow's tasks, in one list with no heading, since its title already names the day. This week lists what is overdue, today, and each later day through Sunday. Weeks start on Monday, as `Next week` in postpone does, so on a Sunday This week is only today and what is overdue. Quick add on Tomorrow starts tomorrow, and quick add on This week starts today, or on the day of the heading it opened from, so the new task lands on the screen it was added on. The web serves them at `/tomorrow` and `/this-week`. On iOS they are pins and Browse rows, and App Intents can open them.
- **Pickers and parsing.** The project picker and quick add's `#`, `@`, and `/` choose where a task lives, not which screen to open. So they offer projects, sections, and labels, the things a task can belong to, and no fixed list, place, or event. That is a different job from the catalog's, so they do not read it.
