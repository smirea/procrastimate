# Performance audit, November 2026

This audit times every screen, input, and action of the web app, times the iOS app's main paths, reads production's traces and Cloudflare's analytics, and follows each path down to the Worker and the `App` Durable Object. For each one it asks what would have to change for the action to be seamless. It records what was measured, what this audit changed, and what is left, with the evidence for each.

## How it was measured

- **Data.** Production on November 5, 2026 held 399 tasks (69 open, 330 completed), 6 projects, 4 sections, 1 label, 31 tasks with attachments, and 73 KB of notes. `app-web/perf/audit.perf.ts` seeds an account of that shape, and `PERF_SCALE=10` seeds ten times the tasks.
- **Harness.** The spec drives the production build served by `wrangler dev` (`E2E_WORKER=1`), so the `App` object runs on its own SQLite as it does in production. Chromium runs at 4x CPU throttling, about a phone. Each action reports its longest input-to-paint (INP as Event Timing measures it, in 8 ms steps), main-thread time beyond 50 ms in long animation frames ("blocked"), the rows the store read back, and the API calls it made. [Testing](decisions/testing.md) says how to run it.
- **Comparison.** Before and after builds ran interleaved, two rounds each, because other agents' builds swing this Mac's load average between 10 and 110 within minutes. One run made while an iOS build compiled beside it tripled every number, including untouched paths, and was discarded. Counts (API calls, rows) do not depend on load; timings within about 20 ms are noise.
- **iOS.** The `PerfDemo` harness in [iOS app](decisions/ios.md), built with `SWIFT_OPTIMIZATION_LEVEL=-O` and run on the worktree's iPhone 18 Pro simulator through throwaway XCUITests: `bulk:400 script visitall` for details, completing, and tabs, and a test typing 34 characters into Notes. Each logs every main run loop pass over 8 ms.
- **Production.** Sentry's spans for the `procrastimate-worker` project over 7 days, and Cloudflare's GraphQL analytics (`workersInvocationsAdaptive`, `durableObjectsInvocationsAdaptiveGroups`, `durableObjectsPeriodicGroups`) from October 29 to November 6, read with the deploy account's Wrangler login.

## What this audit changed

- **Notes save when typing pauses, on web and iOS.** Every keystroke in Notes ran a whole store command. On the web that is a local write and read back, a copy into `sessionStorage`, and a `POST /api/sync` within 100 ms. On the server it is a write, an `_log` row, a `log` row with five indexes, and a head published to every socket, so every other open device pulled. On iOS it was a store commit with an O(N) diff and index rebuild on the main thread, a widget timeline reload, and the same sync. Both clients now keep typed notes in the field and save 400 ms after the last key, and at once on blur, on close, and when the page or app goes to the background. Measured on the web: 20 characters made 14 syncs and 20 reads before, and 0 syncs while typing after. At 10x data the store reads went from 20 taking 207 ms to 1 taking 15 ms. An end-to-end step proves a reload right after typing keeps the text, and fails with the page-hide save removed. Two throwaway XCUITests prove the iOS note survives a relaunch after a pause and after going to the Home Screen. On iOS, typing 34 characters into Notes stalled the main thread for 706 ms in all before, in passes up to 236 ms; after, each keystroke is an 8 to 14 ms pass and the save after the pause one of 74 ms.
- **A blank field no longer runs the quick add parser.** Opening any task's details parsed its empty `Add subtask` field, and in Chromium that parse spent about 55 ms of a 4x-throttled frame in the parser's rule loop. The parser now skips its rules and masks for blank text, whose result was the same. Opening details went from 120 to 136 ms to 56 ms, and from 57 to 69 ms blocked to 0. The reason a blank parse cost that much in the page, when Node parses it in 0.1 ms once warm, was not found.
- **The parser warms up in idle time.** Its `reminder`, `due`, and weekday-list patterns are 12 KB, 12 KB, and 7 KB. V8 compiles each on its first run and again, to native code, on its second: under Node the first two parses took 65 ms and 34 ms on this Mac, and later ones 0.1 ms. JavaScriptCore compiles once (8.5 ms). The layout runs two parses in separate idle callbacks once the store has loaded. Without them the first quick add keystrokes hit a 27 to 73 ms long frame in the input handler. With them there was none, in two runs each.
- **Rows render only the first line of notes.** A row shows one truncated line, but rendered the whole note through `LinkedText`, each link with its icon and favicon request. A 2,600-character note made a row of 130 accessibility nodes. Rows now pass the first non-blank line, cut at 280 characters.
- **The desktop sidebar is not mounted on a phone.** CSS hid it below 768 px, but it stayed mounted and rebuilt the list catalog, with its counts over every task, on every command.
- **An index covers the agent API's view.** `clientsOf` groups the space's task log by id, and no index matched, so it walked every space's task log through `log_entity`. `log_user_task(user_id, kind, id, seq)` covers it: 31 ms against 7.8 ms over 60,000 log rows in `bun:sqlite`.

## Checked and left alone

- **Migrations on every object start.** This audit first measured `openStore` at a median 0.26 ms on a warm `bun:sqlite` database and left it alone. That measured the wrong thing. A production `wrangler tail` later showed the minute cron at 63 to 113 ms and every minute pull at 98 to 155 ms of object CPU, and a workerd profile of a pull after a minute idle found the object rebuilding itself: 68 ms of JavaScript, of which the constructor's two migrations were 12.7 ms and the first sync after them 18 ms. They now run only when a fingerprint of their statements changes, and the same pull takes 4.4 ms, the constructor 0.3 ms. In production, a tail after the deploy (version `682091f6`, November 6) measured the object's CPU on the minute cron at 6 to 13 ms (median 10), against 63 to 113 ms (median 79) before; on the web tab's minute pulls at 7 to 19 ms (median 16), against 46 to 155 ms (median 104); and on the agent's `GET /api/view` at 67 to 81 ms, against 189 to 207 ms. The object still keeps each sync's wall time near 2,000 ms after its response, about what `@sentry/cloudflare` waits to flush its envelopes, and costs duration, not the user's wait. A local probe that timed every `ctx.waitUntil` in the object, with Sentry on and pointed at a local sink, saw each finish in 2 to 10 ms for syncs and status checks alike, so neither the sync route's own work nor Sentry's local behavior makes it; only the flush to the real ingest, or the runtime, can, and that needs a probe deployed to production. The bearer session cache also went from one minute to five, the web cookie cache's, since at one minute it expired as each minute pull arrived.
- **Search animations.** Each keystroke animates the results with `flip` and a fade, and `flip` measures every row twice, about 30 ms of a throttled key. The motion is a design choice, and the key still paints in about 100 ms.
- **Sentry at full sampling.** [Observability](decisions/observability.md) measured it at about 10 ms a sync and chose to keep every trace. Production's CPU numbers below say it is most of each request's CPU; that decision is Stefan's to revisit.
- **The e2e helper's cursor.** `syncWrites` in `e2e/fixtures.ts` sends a cursor past the head so it pulls nothing, but the engine answers a cursor past the head with a full snapshot. It only costs the tests a snapshot per seed.

## What is still open, by layer

Each item names what limits the action today and what would make it seamless. None of these is visible at today's scale unless it says so.

### Web client

- **Long lists render every row.** At 10x data, opening a project or the Inbox blocks 145 to 205 ms after the paint, and a theme switch blocks 143 ms recomputing styles. Both grow with rows on screen, not with interaction. Rendering the first screenful and the rest in idle frames, or windowing the list, would remove it. At today's 69 open tasks no list blocks.
- **Every command rebuilds whole lists.** A command replaces `store.own`, so the sidebar's catalog, the open list's day grouping, and the filter options rerun over every task, and `animate:flip` measures every row of a list whose array changed. A completed or edited task costs O(tasks) work per command. Memoizing the lists on the fields they read and keeping an unchanged list's array would make an edit cost O(changed rows).
- **The store reads back its own writes.** After each command the worker writes, logs the change, and the store reads the changed rows back and rebuilds the space with `resolveDangling` and a sort. At today's scale this is 10 to 15 ms of worker time and nothing on screen. Skipping the read when the log names only rows this tab just wrote with the same values would remove it.
- **Launch makes 7 API calls.** `/api/me` duplicates the user `/api/sync/token` already returns, `/api/people` could ride along, and `/api/push/key` could be cached with the subscription. Each is a request to the one object, off the first frame.
- **Bundles.** The main chunk is 529 KB (150 KB gzipped) and the layout 353 KB (105 KB gzipped), because the layout imports quick add, Ramble, search, settings, sharing, details, and the image viewer up front. `sqlite3.wasm` is 879 KB (408 KB gzipped). The service worker caches them, so only the first visit after a deploy pays for them.

### iOS

Measured at 400 tasks: the first details open in a launch takes 758 ms, later ones 209 to 265 ms, and closing 92 to 107 ms; completing a task 24 to 76 ms; switching tabs 10 to 48 ms. [iOS app](decisions/ios.md) traced the details cost to SwiftUI building a `NavigationStack` sheet of about a hundred views, not the app's code, and these numbers match it. After launch, the main thread has 91 to 173 ms of passes over 8 ms before it idles, in three launches; the monitor starts after the first frame. XCTest's launch metric (`XCTApplicationLaunchMetric`, to the first responsive frame, 5 launches each) measured what precedes it: 2.36 to 2.49 s with no tasks, 2.74 to 2.88 s at 400, and 3.03 to 3.09 s at 4,000, against 2.07 to 2.39 s for the UI test host, an app of one `Text`, on the same simulator. So the app's own launch costs about 0.1 s empty and 0.45 s at production's size, most of it the synchronous first read `ios.md` chose so the first frame shows data; reading it off the main actor behind a launch screen that matches the first frame is the lever. Typing 16 characters into search, through `PlacesDemo`'s `type:`, which types the way the keyboard does, costs passes of 21 to 94 ms a keystroke; typing into quick add 8 to 12 ms a keystroke, after one 281 ms pass as the sheet opens. The same 34-character Notes test proves the save on leaving the foreground on its own: with the pause raised to 10 s it passes, and with the `scenePhase` save also removed it fails. Through XCUITest taps, which add the framework's accessibility snapshots to the main thread, so these read high: opening Settings from Browse takes passes totalling 432 ms (the longest 285 ms); a task with two images opens its details in a 189 ms pass and the full-screen viewer in 207 ms over four passes (84 ms the longest); a project opens in 484 ms over six passes (288 ms), its `…` menu in 257 ms (141 ms), and the Share sheet in 377 ms (293 ms); a place view in 356 ms (182 ms); and signed out, the sign-in screen draws in 55 ms. The machine's load average was 40 to 130 throughout, from other agents. A second run at a load average of 24 to 28 matched it within the noise: Settings 555 ms (295 ms the longest pass), details with images 175 ms, the viewer 202 ms (75 ms), a project 488 ms (276 ms), its menu 263 ms (148 ms), the Share sheet 343 ms (256 ms), and a place 338 ms (129 ms). Numbers that hold across that range of load are the screens' own cost, most of it SwiftUI and UIKit building the presented views, plus XCUITest's accessibility snapshots, which `ios.md` measured at about a third of the main thread. The rest of this section is read from the code and not measured.

- **Store observation is too coarse.** One `snapshot` and one `index` back every view, so any commit or sync redraws every visible row in every tab, hidden tabs included. Per-task observation, or rows built from plain values and made `Equatable`, would limit a change to the rows it touched.
- **Commits rebuild everything on the main thread.** Each commit sorts all tasks, diffs every task and comment into row writes, rebuilds the index, and, once the database reports back, rebuilds the space in `LocalRows` and compares the whole snapshot again.
- **Launch and activation.** The first read and decode, the engine's `migrate`, and a 60-day EventKit query run on the main actor, and `SessionToken.read()` goes to the Keychain on every call.
- **Search typing.** Each keystroke stalls the main thread 21 to 94 ms at 400 tasks. A release-build microbenchmark puts the search itself at 0.7 to 0.9 ms over 400 tasks, and finding each row's place with `firstIndex(of:)` at 0.04 ms. Main-thread CPU over typing 16 characters (`PROCRASTIMATE_TYPE_CPU`, three runs each) was 941 to 1,196 ms when the query matched, 249 to 499 ms for a query that matches nothing but runs the same search, and 465 to 650 ms typing the same text into quick add. So the cost is building and drawing the result rows, about 40 to 50 ms a keystroke for up to 45 rows, each rebuilding its swipe actions, context menu, link detection, title layout, and accessibility strings, since every keystroke changes every row's highlights. Removing the list's `.animation` made no difference to it (four interleaved rounds each). Removing one part at a time, interleaved three rounds each at a load average of 90 to 260, did not single one out: the shipped row measured 607 to 973 ms, without swipes and the context menu 505 to 837 ms, without the accessibility strings 588 to 1,171 ms, and with plain text in place of the linked title and notes 479 to 968 ms. The cost is spread across the row's parts, or the differences are smaller than this machine resolved. A Time Profiler trace (`xctrace record --template 'Time Profiler' --device <udid> --attach <pid>`, 14 s over search typing at 400 tasks, 2,723 main-thread samples) names it, as shares of samples, which load does not skew the way it skews durations: SwiftUI's view graph update holds 51% of the main thread and Core Animation layout 47% (layout runs inside the update, so they overlap), while all of the app's own code is about 10%: `SearchResults.body` 4.1%, `Search.scoreTask` 2.4%, `Store.postponeOptions` for each row's swipe actions 1.8%, `Triggers.openTasks` 1.9%, `SearchResultRow.body` 1.3%, `Links.text` 1.0%. So a keystroke's cost is SwiftUI re-diffing and laying out every visible result row, whose views all change because their highlights do. A seamless search needs rows that change less per keystroke: a row view that is `Equatable` on what it shows, highlights kept out of the row's identity-heavy modifiers, or results updated once per frame instead of per keystroke. Quick add rebuilds every space's projects and labels three times per body pass, yet typing in it measured 8 to 12 ms a keystroke, so that costs nothing visible.
- **Images.** Attachments read and decode on the main actor into an unbounded dictionary of full-size images, and one image arriving redraws every thumbnail.

### Server and infrastructure

What production measured, before the open items:

- **Load.** The Worker served 2,450 to 3,960 requests a day from October 30 to November 5, 2 to 4% of the free plan's 100,000, with no errors. Over 7 days Sentry saw 18,735 `POST /api/sync`, 10,071 minute-cron ticks, 606 agent `GET /api/view`, and 262 launch session checks.
- **Latency.** `POST /api/sync` takes a median 9.8 ms inside the Worker and a p95 of 290 ms; the agent's `GET /api/view` 19 ms and 158 ms; `GET /api/favicon` 273 ms and 1.25 s, since it fetches the site. The slowest syncs, 739 ms and 1,038 ms, spent 574 ms and 863 ms before the object's span began, which is an object starting.
- **Worker to object.** In 50 syncs on November 5 the object's span began a median 38 ms after the Worker's (p90 53 ms), in 50 from November 3 and 4 a median 72 ms (p90 269 ms). That gap holds the Worker's own start, the hop, and the wait in the object's one-request-at-a-time queue.
- **Where the object runs.** There is one `App` object. Cloudflare's analytics place its invocations in DFW through November 4 and in SEA from November 5. The hop was larger while it sat in DFW, beside this client's DFW edge, than in SEA, so the colo is not what the gap is made of, and pinning it with a `locationHint` would buy little. The object moved on its own, which Cloudflare does.
- **CPU.** The Worker uses a median 16 to 24 ms of CPU a request (p99 49 to 69 ms), over the free plan's nominal 10 ms, though no request has failed for it. The `App` object uses 56 to 132 s of CPU a day, about 20 to 35 ms a request. The app's own work is a fraction of that: a notes sync on a 400-task space takes 0.13 ms in `bun:sqlite`, and 2.4 ms of JavaScript in local `wrangler dev`, of which about 1.5 ms is `@sentry/cloudflare`'s request wrapper running even with Sentry off. In production that wrapper also starts a span per query, at full sampling. The rest was measured locally against a Sentry sink: with `SENTRY_ENVIRONMENT=production` and the DSN pointed at a local server, the same sync took 3.9 to 4.4 ms of JavaScript against 2.1 to 2.3 ms with Sentry off, in two of three interleaved rounds (the third was even), and each request sent about 33 KB of envelopes, its whole body and a span per query. The Worker's median CPU, 16 ms, is above a sync's median wall time inside it, 9.8 ms, so much of it runs after the response, where `@sentry/cloudflare` builds and sends its envelopes; the rest is isolate starts, each evaluating the 3.9 MB Worker bundle (724 KB gzipped). Production's CPUs and isolate counts cannot be profiled, so the split between the two is an inference. Sampling server traces at a fraction, dropping the per-query spans, or capturing bodies only on errors are the levers, against [Observability](decisions/observability.md)'s choice to keep every trace for one user.

- **Per request, from `wrangler tail`.** Thirty production requests to `GET /api/status` on November 6 split the CPU directly. A warm Worker uses a median 6 ms (3 to 13 ms) and 83 ms of wall time, and the object 3 ms and 19 ms. The first request into a fresh Worker isolate used 28 ms, and into the object 15 ms, which is what a start costs. Three real syncs from the browser used 30 to 62 ms in the Worker and 14 ms in the object, though their bodies were 97 bytes. The Worker forwards a sync the way it forwards a status check and reads neither, so the extra CPU is the Sentry work around a traced, body-capturing request, as the local profile found; 3 samples cannot split it further. A minute-cron tick used 39 ms in the Worker and 17 ms in the object. So Cloudflare's daily median of 16 ms is a mix of warm forwards at about 6 ms, isolate starts near 28 ms, and syncs at 30 ms and more.
- **Writes hold the object's responses.** The sync above spent 115 ms of wall time in the object for 14 ms of CPU, and status checks that arrived meanwhile waited 383 to 558 ms for 2 to 9 ms of CPU. That matches a Durable Object's output gate, which holds every response until the storage writes before it are confirmed; this is inferred from the timing, not traced. It is what the 290 ms p95 of `POST /api/sync` is made of, and it grows with writes per second, which the notes fix cut from one per keystroke to one per pause.

Open items:

- **The minute cron wakes the object 1,440 times a day.** Each tick runs `deliverDue` and the webhook scan, with a Sentry transaction and check-ins, even when nothing is due; Sentry times a tick at a median 155 ms in the Worker and 441 ms at p95. An object alarm set to the next push time, and re-armed by `replan` and by a write to a space with a webhook, would wake it only when there is work. A tick also queues behind, or ahead of, a user's sync on the single-threaded object.
- **Writes do more storage work than the edit.** One counted write updates the row, `_changes`, `_log`, `_meta`, and a `log` row with five indexes, two of them JSON expressions. When it moves a push field, `replan` reads every open task. On the free plan's 100,000 rows written a day, the notes fix above removed the largest source: a log row per keystroke.
- **Every socket hears every head.** A write publishes the new head to every user's devices, and each pulls, finding nothing new when the write was someone else's. With one user this is correct. With many, publishing to the sockets of the spaces that changed would keep it O(readers).
- **Sync bodies are parsed four times.** `api.ts` parses and re-serializes the body to set the client, the engine parses it again, and the response is cloned and parsed to read `rejected`. Calling the space directly would parse once.
- **Link titles, favicons, and GitHub states fetch from the object.** Each device asks again, since responses are private. Caching them in the Worker with `caches.default`, keyed by URL, would answer most of them at the edge.
- **Image bytes live in the object's SQLite and in every backup.** Each image request goes through the Worker to the object, and the daily backup holds every image as base64 in one string in the object's memory. Moving the bytes to R2 behind signed URLs would let the Worker serve them from cache, and keep the dump small.
